    架构¶

    本页是关于如何构建代码库的实用总结。权威的、 规范版本为docs/design/system-architecture.md； 该文档就是合同——该页面是面向开发人员的概述。

    模块化整体架构（不是单一存储库）¶

    该应用程序是 作为一个单元部署的一个 Symfony 应用程序，其中包含 几个独立的业务模块。它故意“不是”多服务 monorepo：模块共享一个内核、一个 Doctrine EntityManager、一个缓存和 一辆 Messenger 总线，但它们的行为必须像独立服务一样。

    • 模块仅通过 服务接口 进行通信（请参阅 Cross-Module Dependency Rules）。
    • 每个模块都拥有其实体、存储库、控制器和服务。
    • Core 是基础性的，绝不能依赖于业务模块。
    ┌────────────────────────────────────────────────────────────┐
│                     Single application                     │
│   Kernel · config/ · public/ ·  migrations/ ·  tests/      │
│  ┌────────┐ ┌─────────┐ ┌────────┐ ┌────────┐ ┌─────────┐  │
│  │  Core  │ │ Common  │ │Identity│ │ Trade  │ │  ...    │  │

    src/下的模块¶

    模块 责任
    Core 框架抽象：RestController、BaseService、视图混合、表达式查询引擎、序列化
    Common CMS 原语：类别、标签、内容、评论、页面、媒体、图片、设置
    Identity 身份验证和帐户：用户、个人资料、RefreshToken、JWT/OTP 流程
    Trade 电子商务核心：产品、规格、订单、订单项目、定价管道
    Store 多店铺运营：店铺、会员、StoreOrder分发
    Inventory 库存、材料、食谱、预订、分类账
    Payment 发票生命周期、网关抽象、webhooks、事件
    Wallet 余额、原子转账、存款/取款、凭证、扣除
    Promotion 带有小型嵌入式DSL的促销规则、策略、计算
    Settlement 规则驱动的资金分配和结算最终性
    Storage 媒体存储抽象（本地/七牛）
    Wechat 微信登录（小程序/公众号）和微信支付V3网关
    Authorization 作用域 RBAC (global/store)、DqlExpression 行作用域、存储范围授予、严格字段授予、审核日志、AuthorizationVoter（请参阅 docs/design/bundles/authorization.md 和 manual/authorization.md）

    层架构¶

    请求流经严格的单向链：

    HTTP (Controllers / View mixins)  →  Service  →  Repository  →  Entity  →  Infrastructure
    • HTTP 层 — 仅控制器。唯一涉及请求/响应的层。 Thin：它读取输入，调用一项服务，并通过 View mixin 进行渲染。 单独的 App（只读用户）、Manage（管理员 CRUD）和 Webhook 命名空间。
    • 服务层 — 所有业务逻辑、事务和验证都位于此处。 服务暴露接口；其他模块和控制器取决于接口， 从来没有具体的类。
    • 存储库层 — 仅 Doctrine 数据访问查询。
    • 实体层 — 纯领域对象（Doctrine 实体），没有业务逻辑。
    • 基础设施 — 框架提供的 ORM、缓存、序列化器、信使。

    层依赖规则¶

    规则 来自 至 允许吗？
    R1 控制器 服务 是的
    R2 控制器 实体 是（仅输入提示/返回）
    R3 控制器 存储库 否 — 通过服务
    R4 控制器 实体管理器 否 — 通过服务
    R5 服务 存储库 是的
    R6 服务 实体 是的
    R7 服务 实体管理器 是的
    R8 服务 其他服务 是（通过 DI，接口优先）
    R9 实体 存储库 不
    R10 实体 服务 不
    R11 实体 实体管理器 不

    关键设计模式¶

    RestController + View Mixins¶

    每个业务控制器都扩展App\Core\Controller\RestController (src/Core/Controller/RestController.php)，提供success()/warning() JSON 信封、分页和 @display/@expands 响应整形。

    CRUD 端点由 src/Core/View/ 下的可重用 mixin 组装而成：

    • ListApiViewMixin / ScopedListApiViewMixin — 列表+分页
    • DetailApiViewMixin / ScopedDetailApiViewMixin — 单个记录
    • CreateApiViewMixin、UpdateApiViewMixin、DeleteApiViewMixin — 突变端点
    • SingleCreateAndUpdateApiViewMixin、SingleDetailApiViewMixin — 单例资源
    • WorkflowApiViewMixin — 由控制器驱动的工作流程转换

    基础服务 + 特征¶

    服务扩展App\Core\Service\BaseService并实现模块接口。 BaseService 包含三个特征：

    • BaseServiceInfrastructureTrait — 容器/EntityManager/存储库连接
    • BaseServiceReadListTrait — 通用列表/过滤器实现
    • BaseServiceMutationTrait — 通用创建/更新/删除行为

    结果是每个实体都有一个通用的 CRUD 服务，具体服务会覆盖该服务 域规则需要它的地方。每个模块服务还声明一个接口 （例如OrderServiceInterface extends BaseServiceInterface）。

    表达式动态查询引擎 & DqlExpression¶

    列表端点接受解析为 DQL 的表达式查询参数：

    参数 意义
    @filter 声明式过滤条件（客户端提供，仅限 GET）
    @sort / @order 订购条款
    @dql 原始 DQL 片段/嵌入表达式
    @select 选定字段的投影

    共享语法在src/Core/Parser/中实现（ExpressionDqlParser， ExpressionQueryBuilderAssembler）并通过执行 App\Core\Service\ExpressionService 与 QueryBuilderFactory。相同的语法 为服务器拥有的 DqlExpression (src/Core/Query/DqlExpression.php) 提供支持 行级授权：commonFilter()可能会返回 new DqlExpression('entity.getUser() == this.getUser()') 或 new DqlExpression('entity.getStoreUuid() in storeUuids', ['storeUuids' => $allowed]), 通过 ExpressionDqlParser + ExpressionQueryBuilderAssembler 编译并且 自动使用 id/uuid 标准进行 AND 编辑。与@filter不同，它是 失败关闭（错误时为 500）并支持带有空集合的 in/not in 安全。

    定价管道¶

    订单定价是一个按优先顺序排列的计算器链，全部标记为 trade.price_calculator 并按 getPriority() 升序排序：

    订单 计算器 优先
    1 BasePriceCalculator (src/Trade/Service/Pricing/) -100
    2 QuantityCalculator 50
    3 TotalAggregator 55
    4 PromotionCalculator (src/Promotion/Service/) 60

    OrderService 使用 #[AutowireIterator('trade.price_calculator')] 收集它们 并按优先顺序应用它们。添加新的定价步骤 = 实施 PriceCalculatorInterface，标记它，完成。

    支付网关注册¶

    PaymentGatewayInterface 实现（模拟、钱包、微信等）已注册 针对 payment.gateway 标签 src/Payment/Resources/config/services_payment.yaml 并在运行时通过 PaymentGatewayRegistry — 支持根据发票切换提供商并发送至 具有与提供商无关的发票事件的 webhooks (PaymentNotifyController)。

    发件箱/收件箱模式¶

    跨模块写入永远不会同步调用目标模块：

    • 发件箱 — 每个发布模块都将其自己的 *OutboxMessage 实体保存在 与变更相同的交易。 scheduler 服务轮询 app:{module}:outbox:publish 命令（贸易、商店、库存、结算） 将消息刷新到 Messenger。
    • 收件箱/处理程序 — 消费模块中的消息处理程序 (MessageHandler/) 是这些事件的唯一读者，并维护自己的诚信和 幂等性（例如 inventory ReservationRequestedHandler、store TradeOrderCreatedHandler，结算SettlementFundingConfirmedHandler）。

    其他值得注意的模式¶

    图案 哪里
    聚合上的 UUID 身份 跨模块引用是 UUID (Core\Utils\UUID)；持久密钥永远不会像普通整数 ID 那样跨越边界
    钱包乐观锁定 Wallet携带整数version列；并发余额更新检测冲突而不是覆盖
    软删除 Product / Specification 使用 isDeleted 标志 (Trade\Entity)，以便定价和历史记录仍然可以引用已删除的记录
    代币轮换 刷新令牌以散列方式存储 (HMAC-SHA256)，并在每次使用时轮换并进行重用检测 (Identity\Security\TokenManager)
    精确资金结算 QuantumAmount (Settlement\Service\Money) 是固定比例的以 10 为基数的整数量程（默认 18，brick/math），避免浮点错误； AllocationRoundingService 处理余数分布（最大余数）
    注册表模式 PaymentGatewayRegistry、PaymentAdjustmentRegistry、DepositProviderRegistry、WithdrawProviderRegistry、MediaStorageRegistry、SettlementContextResolverRegistry

    跨模块依赖规则¶

    关注 规则
    教义协会 没有跨模块的 Doctrine 关联/关系。 实体永远不会通过外键引用另一个模块的实体
    耐用的参考资料 在模块之间，引用通过 UUID （或明确记录的业务密钥）聚合，而不是本地自动增量 id
    合同 跨模块服务调用交换 仅标量值/快照/DTO — 没有跨边界的实体、存储库或 EntityManager
    写 使用发件箱模式：在一个事务中持久保存更改和发件箱消息；目标模块使用它自己的收件箱消息
    阅读 使用收件箱/消息处理程序作为消耗另一个模块状态的入口点；禁止跨模块直接存储库读取
    依赖方向 业务模块可以自动装配 Core 和（接口优先）彼此； Core 绝不能导入业务模块；禁止循环模块依赖
    共享状态 事件有效负载仅携带标量快照和外部身份；接收模块仍然强制执行自己的授权

    这在实践中表现出来¶

    • Trade发布TradeOrderCreatedMessage/TradeOrderCancelledMessage； Store 消耗它们将订单分发到商店 (StoreOrder)。
    • Store发布StoreOrderAcceptedMessage/StoreOrderRejectedMessage； Trade 消耗它们来移动订单状态。
    • Trade通过ReservationRequestedMessage请求库存预订； Inventory 通过ReservationConfirmed/RejectedMessage确认/拒绝。
    • Payment 发出 InvoicePaidEvent、InvoiceRefundedEvent 等； Wallet 网关和Settlement资金流通过它们自己的处理程序做出反应。
