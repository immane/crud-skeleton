    集成事件（发件箱/收件箱模式）¶

    本项目中的模块（交易、店铺、库存、结算、钱包、支付）共用一个 内核、一个 Doctrine EntityManager 和一个 Messenger 总线，但它们不得触及 彼此的实体或存储库。跨模块通信是事件驱动的 持久：模块通过发件箱发出它拥有的事实，并消耗*来自其他模块的事实 通过 收件箱** 模块，通过 Symfony Messenger 连接。

    该模式可防止两种故障模式：

    • 丢失事件 — 事件被写入与业务相同的数据库事务中 更改（事务发件箱），因此即使进程在运行中终止，它也永远不会丢失。
    • 重复交付 — 消费者在同一事务中记录消费事件行 作为业务效果，以 eventId （幂等收件箱）为键。
    flowchart LR
    subgraph Producer["Producer (module A)"]
        A[Business operation]
        O[Outbox table<br/>*_outbox_message]
        P[Publish command<br/>app:*:outbox:publish]
    end

    subgraph Consumer["Consumer (module B)"]
        H[Worker / handlers]
        I[Inbox table<br/>*_consumed_event]

    end

    A -- "same DB transaction" --> O
    O -- "poll + claim" --> P
    P -- "Messenger 'async'<br/>(Doctrine transport)" --> H
    H -- "same DB transaction" --> I
    H -- "apply" --> B
    • 生产者端（发件箱）： *OutboxService::record(topic, aggregateType, aggregateId, payload) 将一行插入模块的 *_outbox_message 表中。发布命令 （app:<module>:outbox:publish，每个模块一个）轮询表、声明行、构建 一个信封，并将 Messenger 消息分派到 async 传输上。
    • 消费者端（收件箱）： #[AsMessageHandler] 验证信封，检查 模块的 *_consumed_event 表用于 eventId，并且在一个数据库事务内 应用效果并记录消耗事件行。

    1. 传输配置¶

    config/packages/messenger.yaml：

    framework:
    messenger:
        failure_transport: failed          # dead-letter queue (doctrine://default?queue_name=failed)

        transports:
            async:
                dsn: '%env(MESSENGER_TRANSPORT_DSN)%'   # default: doctrine://default?auto_setup=0
                options:
                    use_notify: true
                    check_delayed_interval: 60000
                retry_strategy:
                    max_retries: 3
                    multiplier: 2
            failed: 'doctrine://default?queue_name=failed'

        routing:
            App\Trade\Message\TradeOrderCreatedMessage: async
            App\Trade\Message\TradeOrderCancelledMessage: async
            App\Trade\Message\StoreOrderAcceptedMessage: async
            App\Trade\Message\StoreOrderRejectedMessage: async
            App\Inventory\Message\ReservationRequestedMessage: async
            App\Inventory\Message\ReservationReleaseRequestedMessage: async
            App\Inventory\Message\ReservationConfirmedMessage: async
            App\Inventory\Message\ReservationRejectedMessage: async
            App\Inventory\Message\ReservationReleasedMessage: async
            App\Settlement\Message\SettlementFundingConfirmedMessage: async
            App\Settlement\Message\SettlementAllocationPostingMessage: async
    • 所有集成消息路由到单个 async 传输（一个 Doctrine 表 messenger_messages)，由 worker Compose 服务使用： messenger:consume async --time-limit=3600 --memory-limit=256M。
    • Messenger 应用自己的传输中重试（3 次重试，指数乘数 2）； 耗尽的消息将转到 failed 传输。
    • 发件箱在顶部添加了自己的声明/延迟层（请参阅 Publishing flow) 所以同一个信封永远不会被交给 Messenger 两次，即使两个调度程序发生争用。

    2. 消息和信封¶

    2.1 消息类¶

    大多数模块消息都是单个 array $envelope 的瘦 final readonly 载体：

    final readonly class TradeOrderCreatedMessage
{
    /** @param array<string, mixed> $envelope */
    public function __construct(public array $envelope) {}
}
    留言 制作者 消耗于 信封型
    App\Trade\Message\TradeOrderCreatedMessage 贸易发件箱 商店 ✅ envelope
    App\Trade\Message\TradeOrderCancelledMessage 贸易发件箱 商店 ✅ envelope
    App\Store\Message… → StoreOrderAcceptedMessage、StoreOrderRejectedMessage 商店发件箱 贸易 ✅ envelope
    App\Inventory\Message\ReservationRequestedMessage 商店发件箱 库存 ✅ envelope
    App\Inventory\Message\ReservationReleaseRequestedMessage 商店发件箱 库存 ✅ envelope
    App\Inventory\Message\ReservationConfirmedMessage 库存发件箱 商店 ✅ envelope
    App\Inventory\Message\ReservationRejectedMessage 库存发件箱 商店 ✅ envelope
    App\Inventory\Message\ReservationReleasedMessage 库存发件箱 商店 ✅ envelope
    App\Settlement\Message\SettlementAllocationPostingMessage 结算发件箱 结算 ❌ 显式字段（allocationUuid、planUuid）
    App\Settlement\Message\SettlementFundingConfirmedMessage 外部生产者（异步） 结算 ❌ 显式字段

    位于 Target 模块命名空间中的 Store 消息类被导入到 生产者命令；例如StoreOrderAcceptedMessage/StoreOrderRejectedMessage 是 App\Trade\Message\* 类被 App\Trade\MessageHandler\* 使用，而 ReservationRequestedMessage/ReservationReleaseRequestedMessage 是 App\Inventory\Message\*被App\Inventory\MessageHandler\*消耗。

    2.2 信封结构¶

    发布命令从发件箱行组装版本化信封。贸易 出版商展示了最完整的形状：

    $envelope = [
    'eventId'       => $message->getEventId(),                       // UUID v4, unique
    'type'          => str_replace('.v1', '', $message->getTopic()), // 'trade.order.created'
    'version'       => 1,
    'occurredAt'    => $message->getOccurredAt()->format(DATE_ATOM), // ISO-8601
    'aggregateType' => 'trade_order',
    'aggregateId'   => $message->getAggregateId(),                   // source aggregate uuid
    'correlationId' => $message->getAggregateId(),                   // trace scope
    'causationId'   => null,                                         // parent event (none at source)
    'payload'       => $message->getPayload(),
];
    信封键 贸易 商店 库存 目的
    eventId ✅ ✅ ✅ UUID v4；收件箱的幂等键
    type ✅ ✅ ✅ 不带 .v1 后缀的主题
    version ✅ ✅ ✅ 1
    occurredAt ✅ — — 源事实何时发生 (ISO-8601 ATOM)
    aggregateType ✅ — — 来源聚合种类
    aggregateId ✅ ✅ ✅ 源聚合 uuid
    correlationId ✅ — — 追踪范围（按 Trade 设置为订单 uuid）
    causationId ✅ — — 父事件 ID（源事件为空）
    payload ✅ ✅ ✅ 业务数据（数组）

    aggregate_type、aggregate_id、payload、occurred_at、available_at、published_at、 attempts 和 last_error 也保留在发件箱表本身中。

    和解 AllocationPostingMessage 和 SettlementFundingConfirmedMessage 代替 携带 显式标量字段 而不是信封（请参阅 Settlement flow）。

    3. 发布流程¶

    每个带有发件箱的模块都有一个 Command/PublishOutboxCommand.php 注册为 app:<module>:outbox:publish。 compose.yaml 中的调度程序每隔 OUTBOX_PUBLISH_INTERVAL（默认5）。

    scheduler:
  extends:
    service: app
  command:
    - /bin/sh
    - -ec
    - |
      while :; do
        php bin/console app:trade:outbox:publish --no-interaction
        php bin/console app:store:outbox:publish --no-interaction
        php bin/console app:inventory:outbox:publish --no-interaction
        php bin/console app:inventory:reservations:release-expired --no-interaction
        php bin/console app:settlement:allocations:requeue-due --no-interaction
        php bin/console app:settlement:outbox:publish --no-interaction
        sleep "${OUTBOX_PUBLISH_INTERVAL:-5}"
      done

    三个标准步骤（与贸易、商店、库存、结算相同）：

    1. 选择早于其 available_at 的未发布行 （findUnpublished() — published_at IS NULL AND available_at <= now ORDER BY id ASC LIMIT 100）。
    2. Claim — claim($id, now + 1 minute) 运行一个原子 UPDATE … SET available_at = :until WHERE id = :id AND published_at IS NULL AND available_at <= now 仅当更新一行时才返回 true。这是并发防护： 第二个刻度（或重新启动的调度程序）将跳过其他工作人员已声明的行。
    3. 调度匹配的总线消息。成功markPublished()邮票 published_at。关于任何\Throwable（或不受支持的主题）defer($id, $error, now + 5 min) 递增 attempts，存储 last_error，并将 available_at 推出，以便该行 可以稍后重试。最后 EntityManager 被刷新一次。

    Trade 的发布者还将主题列入白名单，并将其他任何内容视为不受支持的主题：

    if (!in_array($message->getTopic(), ['trade.order.created.v1', 'trade.order.cancelled.v1'], true)) {
    $this->repository->defer($id, 'Unsupported Trade outbox topic: ' . $message->getTopic(), new \DateTimeImmutable('+5 minutes'));
    continue;
}

    Inventory 发布者是异常值：它选择 数组投影 (findUnpublishedForPublishing()) 并标记通过直接发布/记录的尝试 存储库更新而不是通过工作单元，因此它不会刷新实体状态。

    交付保证与订购。 交付至少一次并在 1 分钟内重试 索取租约和 5 分钟退让。尽最大努力在id之前按发件箱订购；消费者 必须是顺序容忍的（它们保护工作流/状态 can()），这正是 处理程序会这样做。

    4.消费流量和幂等性¶

    4.1 收件箱（消费事件）表¶

    表 编号 事件 ID 有效负载跟踪列
    store_consumed_event 大智 VARCHAR(36) 独特 aggregate_id、payload_hash(64)
    inventory_consumed_event 大智 VARCHAR(36) 独特 aggregate_id、payload_hash(64)
    settlement_consumed_event INT VARCHAR(64) 独特 source_aggregate_type、source_aggregate_id、payload_hash(64)

    所有三个共享 topic、processed_at 和 payload_hash（JSON 编码的 SHA-256） 信封）。 Trade 没有收件箱表：它的处理程序由工作流程的保护 can(transition) 检查加上事务内的 store-uuid 快照匹配，因此 重复的 store.order.accepted.v1 / store.order.rejected.v1 是无操作。

    4.2 eventId 的幂等性¶

    规范的消费者形状 - 读取检查，然后在交易内重新检查，以及 以原子方式写入消耗的行，效果如下：

    public function __invoke(TradeOrderCreatedMessage $message): void
{
    $eventId = $message->envelope['eventId'] ?? null;
    $payload = $message->envelope['payload'] ?? null;
    // ...validate...

    if ($this->consumedEventRepository->findOneBy(['eventId' => $eventId]) !== null) {
        return; // already processed
    }

    $this->entityManager->wrapInTransaction(function () use ($eventId, ...): void {
        if ($this->consumedEventRepository->findOneBy(['eventId' => $eventId]) !== null) {
            return; // re-check under the transaction (closes the race window)
        }
        $this->entityManager->persist(new StoreConsumedEvent(
            $eventId,
            'trade.order.created.v1',
            (string) ($payload['orderUuid'] ?? ''),
            hash('sha256', json_encode($message->envelope, JSON_THROW_ON_ERROR)),
        ));
        // ...apply the business effect...
    });
}

    库存进一步收紧。它的isAlreadyConsumed()比较存储的 payload_hash 以及使用 hash_equals 到达的信封的哈希值；一个重复使用的 eventId 具有 不同 有效负载会引发 InventoryMessageIntegrityException （“事件 ID 已与不同的有效负载一起重复使用”）。结算的exists($eventId)支票是 更简单：重复使用的 id 会被默默地跳过。

    4.3 验证¶

    处理程序在接触数据库之前会防御性地验证其信封：

    • type / version 完全匹配（例如 'inventory.reservation.released' / 1）。
    • 必需的键存在于正确的标量类型中（eventId 是 商店管理员；库存处理程序还要求它是格式正确的 UUID）。
    • 库存另外验证：aggregateId === payload['reservationId']， 每个 id 的 UUID 格式 ^[0-9a-f]{8}-…-[1-8]…-[89ab]…$，ISO-8601 时间戳 （允许使用小数秒）、唯一的线路 ID 和数量字符串匹配 ^[0-9]+(?:\.[0-9]{1,6})?$。
    • 相关性交叉检查（例如ReservationReleaseRequestedHandler验证 信封中的 storeUuid / tradeOrderUuid / storeOrderUuid 与存储的匹配 保留，否则会抛出InventoryMessageIntegrityException）。
    • 使重试无害的业务防护：仅限ReservationConfirmedHandler 接受仍为 awaiting_inventory 且其 reservationId == payload['reservationId']； SettlementService::postAllocation() 对于已经 posted / cancelled / reversed 分配提前返回。

    5. 相关性/因果关系追踪¶

    • 交易 分配 correlationId = aggregateId （交易订单 uuid）和 causationId = null 在每个出站信封上 — 整个订单传奇（订单创建 → 店铺受理→库存预约→取消）共享该关联范围。
    • 结算 是唯一将跟踪保存到其域模型中的模块： SettlementFundingConfirmedMessage 带有 correlationId/causationId，并且 settlement_plan 存储 correlation_id 和 causation_id 列。的 SettlementFundingConfirmedHandler 将它们复制到 SettlementFunding 合约中。
    • 商店/库存信封不带有相关性/因果关系标头；血统是 根据有效负载相关键重建 - orderUuid、storeUuid、 tradeOrderUuid、storeOrderUuid、reservationId — 以及来自消费事件 aggregate_id 列。

    6.4 Settlement allocation posting¶

    Settlement is an inbox-first module: funding confirmations arrive from outside as explicit-field messages.

    7. Operational notes¶

    • Dead letters accumulate on the failed transport (messenger_messages with queue_name = 'failed'); the outbox row is left unpublished so it can be manually re-queued or repaired.
    • Stuck rows show up as published_at IS NULL with a non-null last_error; they are re-attempted automatically after their available_at passes.
    • Race safety relies on the claim UPDATE being conditional (published_at IS NULL AND available_at <= now), plus the index (published_at, available_at) on each outbox table (Inventory appends id).
    • The INVENTORY_ENABLED environment toggle decides whether Store skips inventory altogether and accepts orders immediately, or waits for an inventory.reservation.confirmed.v1.
