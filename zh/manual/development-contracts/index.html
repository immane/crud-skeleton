    开发合同¶

    保持模块化整体连贯的规则：层边界、跨模块 通信、服务边界、命名、代码风格、性能和安全性。 这些是面向开发人员的规范设计文档的配套文件 (docs/design/system-architecture.md、docs/design/system-contracts.md、 docs/design/module-design.md、docs/design/naming-convention.md)。

    1. 图层规则¶

    请求通过严格的单向链移动：

    HTTP (Controllers / View mixins)  →  Service  →  Repository  →  Entity  →  Infrastructure
    规则 来自 至 允许吗？ 为什么
    R1 控制器 服务 是 正常流量
    R2 控制器 实体 是 仅输入提示/返回
    R3 控制器 存储库 不 浏览服务
    R4 控制器 实体管理器 不 浏览服务
    R5 服务 存储库 是 数据访问
    R6 服务 实体 是 域名运营
    R7 服务 实体管理器 是 交易
    R8 服务 其他服务 是 DI，接口优先
    R9 实体 存储库 不 实体是纯粹的
    R10 实体 服务 不 没有业务逻辑部门
    R11 实体 实体管理器 不 持久是外在的

    交易合约¶

    • 事务仅存在于 服务层 - 控制器从不调用 beginTransaction() / commit() / rollback() (T4)。
    • 相关实体的多个突变包含在 wrapInTransaction() (T1) 中。
    • 钱包转账使用实体的显式 beginTransaction/commit/rollback 锁定 (PESSIMISTIC_WRITE) (T2)，并且 EntityManager 在经过一段时间后恢复 使用 $em->isOpen() 防护 (T3) 进行回滚。
    • Mixin 驱动的突变（createAction、batchUpdateAction）自动换行 除非@partial=true。 @partial=true 独立处理每一项；否则 所有项目一起提交或回滚。

    抛出和捕获异常的地方¶

    层 可能会抛出 必须抓住
    实体 不 —
    存储库 仅原则例外 —
    服务 业务异常（InsufficientFundsException、OrderInvalidTransitionException、...） —
    控制器 否 — 转换为 warning() 域例外 → warning() 为 400/404/500

    /api/* 上未处理的异常通过以下方式转换为 JSON {code, message, class} ExceptionInterceptor（在开发中绕过）。

    2. 跨模块通信¶

    模块共享一个内核、一个 EntityManager、一个缓存和一个 Messenger 总线 — 但是 必须表现得就像它们是独立的服务一样。

    关注 合同
    教义协会 没有跨模块关联。 实体永远不会将另一个模块的实体作为关系/FK
    耐用的参考资料 引用通过 UUID (App\Core\Utils\UUID) 或明确记录的业务密钥跨模块进行聚合 - 绝不是本地自动增量 ID
    合同输入，标量数据输出 跨模块服务调用交换 仅标量/快照/DTO — 绝不是实体、存储库或 EntityManager
    写 发件箱：发布模块将 *OutboxMessage 实体持久保存在同一事务中作为更改； app:{module}:outbox:publish 命令将其刷新到 Messenger
    阅读 收件箱/消息处理程序：使用模块通过自己的 MessageHandler/ 处理程序读取另一个模块的状态，这些处理程序强制执行完整性和幂等性
    直接存储库跨模块读取 禁止
    依赖方向 业务模块可以自动装配 Core 和（接口优先）彼此； Core 绝不能导入业务模块；禁止循环模块依赖

    信使路由（异步传输）¶

    注册消息包括：交易订单创建/取消/商店接受/拒绝， 库存预留请求/确认/拒绝/释放，结算资金确认和 分配过帐。处理程序位于消费模块的 MessageHandler/ 中 目录（例如src/Store/MessageHandler/TradeOrderCreatedHandler.php， src/Inventory/MessageHandler）。失败传输是 failed 并重试 3 次， 加倍退避。

    注册表用于横切扩展而不是直接连线¶

    可热插拔的协作者通过标记的迭代器进行收集并通过 注册表 — 非硬连线：PaymentGatewayRegistry (payment.gateway)， PaymentAdjustmentRegistry、DepositProviderRegistry、WithdrawProviderRegistry、 MediaStorageRegistry、SettlementContextResolverRegistry 和 trade.price_calculator 定价链（优先排序，促销60）。

    3. 服务边界¶

    服务形态¶

    • 每个服务都实现一个模块接口：{Entity}ServiceInterface extends App\Core\Service\BaseServiceInterface。
    • 实现扩展App\Core\Service\BaseService，它组成 BaseServiceInfrastructureTrait（容器/EM/存储库/记录器/序列化器， 交易包装器、验证器）、BaseServiceReadListTrait（get/list、 QueryBuilder 列表、DQL 编译）和 BaseServiceMutationTrait （new/update/remove、关系/日期映射、序列化器 + 验证器集成）。
    • 服务不得返回原始 HTTP 响应（控制器的工作）并且不得触及 直接使用 Request — 使用 getCurrentRequest()。

    存储库形状¶

    • 存储库扩展ServiceEntityRepository，将ManagerRegistry放入 构造函数，并返回实体/数组/标量。
    • 存储库不得**将原始 QueryBuilder 返回给消费者 - 即 服务层的关注点——并且在被使用时可能会暴露 *RepositoryInterface 其他模块。
    • Doctrine 3.6+ 存储库带有 @extends ServiceEntityRepository<...> PHPDoc （由 Rector 的 AddAnnotationToRepositoryRector 强制执行）。

    控制器形状¶

    • App 控制器（公共读取）用 ApiView 扩展 RestController， DetailApiViewMixin、ListApiViewMixin；他们设置 $serviceClass 并可能覆盖 commonFilter() 用于行级范围。没有创建/更新/删除。
    • Manage 控制器（管理 CRUD）添加 Create/Update/DeleteApiViewMixin 并且是 在类级别保护#[IsGranted('ROLE_ADMIN')]。
    • 控制器仅声明特定于模块的构造函数依赖项 - RequestStack， SerializerInterface、TranslatorInterface，集装箱经#[Required]到达 RestController 上的 setter 注入。

    4. 命名约定¶

    命名空间承载着模块；类名带有域概念。 docs/design/naming-convention.md具有权威性；这四项规则是：

    ＃ 规则
    N1 类名=领域概念（裸首选）；所有权存在于名称空间中
    氮气 仅在 (a) 跨模块冲突/歧义或 (b) 模块内基础设施（发件箱/注册表/网关/提供商）时添加模块前缀
    N3 Service / Controller / Repository / Event / Exception 严格镜像实体名称：{Entity}Service、{Entity}Controller、{Entity}Repository
    N4 前缀策略在模块内是一致的——绝不混合使用前缀和裸

    受保护的跨模块冲突组（永远不要删除前缀）¶

    概念 保留类名
    订单 Trade\Order、Store\StoreOrder
    用户 Identity\User、Wechat\WechatUser
    发件箱留言 Trade\TradeOutboxMessage、Store\StoreOutboxMessage、Inventory\InventoryOutboxMessage
    消费事件 Store\StoreConsumedEvent、Inventory\InventoryConsumedEvent

    （2026-08-15 前缀重构删除了 Wallet*/Inventory*/Store* 前缀 独特的概念 - WalletTransaction→Transaction，InventoryStock→Stock， StoreMembership→Membership — 零迁移或 API 损坏；表名、URL 并且路线名称未更改。）

    禁止：发明服务后缀（实体 Category 的 CategoryService 是 很好，但是为非服务类添加任意 XxxService 名称则不行）， 模块内的前缀不一致、非镜像控制器/服务名称。

    5. 代码风格¶

    面积 规则
    PHP 新代码中的 >= 8.4、declare(strict_types=1)
    属性/回报 显式类型，绝不仅限文档块；可以为 null 作为 ?Type
    命名空间 src/ 下的 PSR-4 App\
    使用语句 按字母顺序排列
    文件 每个文件一个类/特征/接口，文件名=类名
    课程 帕斯卡案例；方法/属性驼峰命名法；常量 UPPER_SNAKE
    接口 *Interface后缀；摘要Abstract* / Base*；特征 *Trait 或描述性 (ListApiViewMixin)
    测试 *Test 后缀，命名空间 App\Tests\...
    评论 关于接口/抽象方法的 PHPDoc；对自记录代码没有评论； @deprecated + 删除的迁移说明

    6. 性能¶

    实践 它出现在哪里
    对每个列表进行分页 RestController::pagination() — 默认限制 100，QueryBuilder 的 Doctrine Paginator
    项目列而不是获取所有内容 @select、@display（例如 reduce = 仅 id + __toString）
    将过滤推送到数据库 表达式 DSL 编译为 DQL (ExpressionDqlParser)；内存中的后备只是一个后备
    避免隐式关系加载 关系加载缓慢；通过 @expands
    并发写入受到保护 Wallet 使用乐观锁定（version 列）和悲观写入进行传输；令牌轮换使用重用检测
    成本高昂的查找被索引/简短 关于聚合的 UUID/IAM 参考；存储库公开有针对性的查询
    批量管理员写入保持事务性 @partial=true 用于每项模式，否则单事务
    长时间运行的工作变为异步 Messenger 异步传输 + 发件箱发布命令

    7. 安全¶

    身份验证¶

    • JwtAuthenticator 提取并验证 Authorization: Bearer JWT 并构建 护照； TokenManager 颁发/撤销令牌并管理刷新令牌生命周期。
    ＃ 规则
    S1 访问令牌：RS256 签名、7200s TTL
    S2 刷新令牌：不透明，在数据库中进行 HMAC-SHA256 哈希处理，1 年 TTL
    S3 刷新令牌在每次使用时轮换
    S4 重复使用已撤销/替换的刷新令牌会撤销所有用户的令牌
    S5 已撤销的访问令牌 JTI 将被列入黑名单，直至自然到期
    S6 私钥永远不会被提交
    S7 生产中的 HTTPS

    授权¶

    • 访问控制集中在config/packages/security.yaml：/api/v1/manage → ROLE_ADMIN; /api→IS_AUTHENTICATED_FULLY；公共列表（授权流程， 注册、微信登录、付款通知、文档、GET /api/v1/public）是 PUBLIC_ACCESS。
    • 行级范围是通过 commonFilter()/listFilter() 覆盖的每个控制器 （例如，用户只能看到自己的记录；应用程序端过滤器强制执行）。
    • 管理控制器还带有类级别#[IsGranted('ROLE_ADMIN')]。
    • 角色层次结构：ROLE_ADMIN: [ROLE_USER]。

    验证顺序¶

    Controller field whitelist ($requiredCreateProperties / $acceptedCreateProperties)
  → controller hook validation (processCreateContent / processUpdateContent)
    → @transform expression
      → Service::update() → Symfony Validator → entity #[Assert\*] constraints

    速率限制¶

    资源 限制
    OTP 请求（每部电话） 每 60 秒冷却时间 1 次
    OTP 验证（每部手机） 最多尝试 5 次

    由 Redis (OTP_REDIS_DSN) 或本地缓存后备 (LocalCacheOtpStorage) 支持。

    记录卫生¶

    • PUT/POST 上的请求正文记录在 INFO 中，用户 ID、URI、正文被截断为 1 KB。
    • 切勿在生产中记录明文密码、令牌、OTP 代码或 PII。
    • 频道：app、doctrine（开发）、security。

    金钱和身份¶

    • 货币是整数美分或固定规模的量子（QuantumAmount，18 位十进制， brick/math) — 永远不会浮动。
    • 跨模块的聚合引用是 UUID——绝不是原始 FK 或自动增量 id。

    8. 重大变更政策¶

    改变 允许吗？
    具有默认实现的新 mixin 特征/钩子 是的，已记录
    更改钩子签名/删除 mixin 方法/更改响应信封 否 — 主要版本
    添加查询参数 是（向后兼容）
    删除支持的查询参数 否 — 弃用 + 主要版本
    更改 BaseServiceInterface 否 — 跨模块影响评估
    添加模块 是的，遵循模块清单 (docs/design/module-design.md)
