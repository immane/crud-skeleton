    开发工作流程¶

    如何在 CI 中对该存储库进行分支、审查、分析和验证。按照这个 处理每一项更改，从单行修复到新模块。

    1. 分支模型¶

    该存储库使用基于主干的流程和长期集成分支：

    main  ──────────────────────────────────────────────►  stable / release (PR target)
   \                                                /
    └── dev ───────────────────────────────►  integration (PR target for features)
           \
            ├── feat/xxx         feature branch (merged into dev)
            ├── fix/yyy          bug-fix branch (merged into main or dev)
            └── chore/zzz        tooling / docs / refactor branches
    分公司 目的 CI 运行于
    main 稳定的树干；只有经过审查、测试、迁移验证的代码才会出现在此处 推 + 拉请求
    dev 发布前功能积累的集成分支 仅 pull_request (ci/migrations)，推送文档部署
    feat/*、fix/*、chore/* 短期工作分支，每个 PR 一个 pull_request（定位 main/dev）

    规则：

    • 切勿直接推送到 main 或 dev。 所有更改均通过拉取请求到达。
    • 针对 main（版本、修补程序）或 dev（功能、较大更改）打开 PR。
    • 经常变基或合并，使分支保持接近目标。
    • 较新的推送取代了对同一 PR 或分支的正在进行的检查（CI 已配置） 与 concurrency: cancel-in-progress: true）。

    2. 编码标准¶

    所有工具都需要 PHP 8.4+。

    要求 标准
    PHP版本 >= 8.4 (composer.json require.php)
    命名空间 PSR-4 App\ 位于 src/ 下，App\Tests\ 位于 tests/ 下
    标量/返回类型 尽可能明确；新代码中需要严格类型 (declare(strict_types=1))
    物业类型 显式（绝不仅限文档块）
    可空 ?Type 语法
    使用语句 按字母顺序排列
    每个文件一个类 文件名等于类/特征/接口名称
    评论 PHPDoc 仅针对接口和抽象方法；对自文档化代码没有评论
    命名 参见naming convention——模块命名空间携带所有权，服务/控制器/存储库镜像实体名称

    3.静态分析¶

    静态分析的运行方式与 CI 的运行方式完全相同——在本地，它们必须在 PR 之前是绿色的。

    3.1 PHPStan（8 级）¶

    composer phpstan

    在phpstan.neon中配置：

    设置 价值
    水平 8
    路径 src/
    排除 src/*/Exception/*、src/Identity/Sms/AliyunSmsProvider.php
    引导程序 vendor/autoload.php
    Symfony 集成 vendor/phpstan/phpstan-symfony/extension.neon（读作var/cache/dev/App_KernelDevDebugContainer.xml）
    学说整合 vendor/phpstan/phpstan-doctrine/extension.neon 与 objectManagerLoader: phpstan-bootstrap.php
    PHPDoc 确定性 treatPhpDocTypesAsCertain: false（控制器使用特征混合中的$this->service/$this->get()）
    通用物品箱 易微信AccessToken / Server合约

    phpstan-bootstrap.php 启动一个最小的 App\Kernel 并返回 Doctrine EntityManager 因此 PHPStan 可以解析存储库/Doctrine 元数据。在 CI 中它运行 具有独立的 SQLite URL (var/phpstan.db)，因此它永远不会接触真正的数据库。

    生成或刷新基线（仅当严格性要求强制时）：

    composer phpstan-baseline

    3.2 Rector（仅在 CI 中键入规则）¶

    composer rector:types:check      # dry-run — the CI gate
composer rector:types            # actually apply the type rules

    rector-types.php 在 src/ 上仅启用两个规则：

    规则 它强制执行什么
    AddAnnotationToRepositoryRector Doctrine 3.6+ 存储库必须携带 @extends ServiceEntityRepository<...>
    CompleteReturnDocblockFromToManyRector ->mappedBy/->inversedBy OneToMany/ManyToMany 返回 PHPDoc 集合

    composer rector（更广泛的选择加入重构）不是 CI 的一部分 — 查看其差异 申请前请仔细：

    composer rector      # dry-run of the broad rule set
composer rector:fix  # apply it

    3.3 添加修复/基线条目¶

    不要让 PHPStan 批发沉默。如果无法输入真正的边界情况，请添加 phpstan.neon 中的范围 ignoreErrors 条目 带有解释原因的注释 — 现有条目均带有解释（可选 SDK、特征混合、生命周期 回调）。

    4. 提交约定¶

    • 常规提交，仅英文。
    • 格式：type(scope): subject — 例如feat(settlement): add rule version diffing, fix(inventory): recover EM after rollback、test(wallet): cover concurrent transfers。
    类型 用于
    feat 新能力
    fix 错误修正
    refactor 行为保留重组
    test 仅测试
    docs 文档/评论
    chore 工具、CI、依赖项、内务处理
    ci 工作流程文件更改
    perf 表演工作
    • 主语：祈使语气，无句号，小写（名词/专有名称除外）。
    • 正文（可选）：内容和原因，而不是如何。 Closes #123 的参考问题。
    • 保持每次提交的重点；每次提交一个逻辑更改。
    • 提交消息仅以英文书写——这是一条硬性规定。

    5. 拉取请求清单¶

    每个 PR 必须满足存储库模板 (.github/pull_request_template.md)：

    • [ ] 分支已与 main 保持同步
    • [ ] 摘要描述了更改；相关问题已链接
    • [ ] 标记的更改类型（错误/功能/文档/测试/重构/CI/i18n）
    • [ ] ./vendor/bin/phpunit — 所有测试均通过
    • [ ] 覆盖率不低于 90%
    • [ ] composer phpstan — 8 级检查通过
    • [ ] composer rector:types:check — 无需更改 PHPDoc 类型
    • [ ] 执行手动烟雾测试（PR 中描述）
    • [ ] 提交遵循常规提交
    • [ ] 新功能包括测试
    • [ ] API 更改用 #[OA\*] 属性记录
    • [ ] 行为变化反映在 docs/ai/context.md 中（如果适用）
    • [ ] 为新的面向用户的消息添加了 i18n 翻译键（en、zh、zh_Hant、ja）

    6. CI 管道¶

    .github/workflows/ 中存在三个工作流程。全部都是路径触发的 — 不相关 更改不会重新运行整个管道。

    6.1 ci.yml — PHPStan + PHPUnit（带覆盖）+ Rector¶

    触发器 — 推送到 main/master 并针对 main、master 或拉取请求 dev，仅限于这些路径：

    src/**            tests/**          config/**         migrations/**
bin/**            composer.json     composer.lock     symfony.lock
phpunit.dist.xml  phpstan.neon      phpstan-bootstrap.php
rector*.php       .env.test         .github/workflows/ci.yml

    工作（ubuntu-latest 上的 PHP 8.4）：

    工作 它运行什么 笔记
    phpstan composer phpstan DATABASE_URL=sqlite:///.../var/phpstan.db
    tests composer install → 启动 Postgres 16 服务 → 创建 app_test_1..4 → 运行 ParaTest，有 4 个工作人员 + PCOV 覆盖范围 → 强制执行 90% 的线路阈值 矩阵： php: ['8.4']
    rector composer rector:types:check（试运行） DATABASE_URL=sqlite:///.../var/rector.db

    并行测试作业详细信息：

    1. shivammathur/setup-php 与 coverage: pcov、ini-values: pcov.directory=src — 因此 PCOV 仅测量 src/ 下的应用程序代码。
    2. postgres:16 服务容器使用 app/app_secret 凭据启动，并且 健康检查。
    3. app_test_1 … app_test_4 数据库是通过psql 创建的。
    4. 测试运行：
    PCOV_ENABLED=1 PARATEST=1 php vendor/bin/paratest \
  --processes=4 --coverage-text=/tmp/coverage.txt --display-deprecations

    每个 ParaTest 工作线程（标记 1-4）通过以下方式获取自己的 Postgres 数据库 PARATEST_DATABASE_URL_TEMPLATE=postgresql://.../app_test_{token}?... — 并发 模式删除/创建永远不会竞争。 5. 90% 门从覆盖文本中解析 Lines: <pct> 并通过以下方式失败 bc 如果低于 90.0 则进行比较。

    tests 作业的完整环境镜像 .env.test （JWT 键位于 tests/Identity/Security/、APP_ENV=test、MESSENGER_TRANSPORT_DSN=doctrine://default?auto_setup=0、 MAILER_DSN=null://null、OTP_REDIS_DSN，空运行时的阿里云短信测试值）。

    6.2 migrations.yml — MySQL 迁移链¶

    触发器 — 推送到 main/master 并针对 main/master/dev 推送 PR， migrations/**、config/**、bin/**、composer.json、composer.lock、 symfony.lock，以及工作流程文件本身。

    作业mysql-migration-chain：

    1. 启动mysql:8.4服务（crud_skeleton_test数据库，用户app/app）。
    2. composer install 与 DATABASE_URL=mysql://app:app@127.0.0.1:3306/crud_skeleton_test?serverVersion=8.4&charset=utf8mb4。 3.php bin/console doctrine:migrations:migrate --no-interaction --env=dev
    3. php bin/console doctrine:migrations:status --env=dev

    这证明完整的迁移链适用于真实的 MySQL 8.4 实例 （基于模式工具的测试模式的下游）。

    6.3 docs.yml — 文档构建和 GitHub Pages 部署¶

    触发器 — 推送到 main/dev 并针对 main/master/dev 推送 PR， docs/**、README*.md、scripts/build-docs.sh、scripts/translate-docs.py、 mkdocs.yml，以及工作流程文件本身。

    工作 运行于 行动
    build 仅限 pull_request pip install mkdocs-material deep-translator → bash scripts/build-docs.sh（双语网站建设）
    deploy 只推 相同的构建，然后 peaceiris/actions-gh-pages 将 ./site 发布到 gh-pages 分支

    scripts/translate-docs.py + build-docs.sh 产生双语 （英文/中文）mkdocs 站点 — 不要通过提交生成的文件来绕过它。

    7. 本地数据库与 CI 数据库¶

    背景 数据库 如何隔离
    tests 工作 (CI) PostgreSQL 16 (app_test_1..4) 每个 ParaTest 代币一个数据库
    本地并行运行 每个工作线程的 SQLite (var/test_paratest_{pid}.db) 每个进程一个文件
    本地串行运行 SQLite (var/test.db) 单个文件

    tests/bootstrap.php 决定：如果 PARATEST=1 并且没有明确的 DATABASE_URL 模板 提供后，它将每个工作线程切换到自己的 var/test_paratest_{pid}.db 并急切地 创建架构。当 CI 提供 PARATEST_DATABASE_URL_TEMPLATE 时，它会替换 而是使用工人令牌。来自真实环境的显式 DATABASE_URL 永远不会 受到 sqlite 后备的打击。

    覆盖范围始终使用 PCOV (PCOV_ENABLED=1 / coverage: pcov) 进行测量。 基于 Xdebug 的覆盖 (XDEBUG_MODE=coverage) 在本地工作，但不在 CI 中使用。

    8. 完成的定义¶

    在 PR 清单之上，当出现以下情况时，变更就完成了：

    1. composer phpstan — 8 级干净（没有理由没有新的基线条目）。
    2. composer rector:types:check — 无需更改类型规则。
    3. ./vendor/bin/phpunit（或PARATEST=1 ./vendor/bin/paratest --processes 8 --runner WrapperRunner）—绿色，覆盖率≥90%的线路。
    4. 针对 MySQL 验证迁移链（CI migrations.yml 作业）。
    5. 针对任何端点更改更新 OpenAPI #[OA\*] 属性。
    6. 面向用户的字符串具有翻译键（en、zh、zh_Hant、ja）。
