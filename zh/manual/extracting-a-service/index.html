    从整体中提取服务¶

    CRUD Skeleton 是一个 单一模块化整体 — 一个 Symfony 应用程序，一个作曲家 项目，一棵带有命名空间模块的 src/ 树（App\Trade、App\Wallet、 App\Settlement，...）。它不是一个多应用程序单一存储库。本指南解释了 如何使用一个模块并将其变成一个独立的服务/应用程序 以现有模块边界为蓝图。

    好消息：代码库的设计使这成为可能。的 结算 ↔ 钱包关系是服务的一个工作示例 边界看起来像。本指南正式化了该过程。

    1.预提取规则¶

    在移动任何代码之前，模块必须已经是边界干净的。以下 三个规则使得拔牙变得机械化而不是手术化。

    1.1 无跨模块学说关联¶

    实体决不与另一个实体中的实体保持 ORM 关联 模块。没有 ManyToOne/OneToMany 属性指向外部 模块，并且不同模块拥有的表之间没有外键。

    检查是否有违规行为：

    # In the module you intend to extract, grep for cross-module entity imports
rg "use App\\\\(Trade|Payment|Store|Inventory|Identity)\\\\Entity" src/Settlement

    目标模块中的每个表都必须是独立的。跨模块查找 是通过 UUID 或标量引用 手动完成的，而不是通过连接键。

    1.2 UUID 引用而不是对象/ID 链接¶

    实体内部的外部身份是一个包含远程信息的纯字符串列 聚合的 UUID，不是数据库级外键，也不是对象引用。

    src/Settlement/Entity/SettlementAllocation.php 是典型的例子：

    #[ORM\Column(name: 'uuid', type: 'string', length: 36)]
private string $uuid;

#[ORM\Column(name: 'plan_uuid', type: 'string', length: 36)]
private string $planUuid;

#[ORM\Column(name: 'rule_version_uuid', type: 'string', length: 36, nullable: true)]
private ?string $ruleVersionUuid;
    • 本地行保留整数代理键 (id) 和 UUID。
    • 远程身份存储为 string(36) UUID 列，并建立索引以供查找。
    • 永远不要假设引用的行存在；服务层重新验证。

    使用类型/id 对来表示事物是所使用的模式 结算合约 — SettlementSubject 是 type : id 作为字符串：

    final readonly class SettlementSubject
{
    public function __construct(
        public string $type,
        public string $id,
        public string $version,
    ) { }
}

    1.3 跨边界的标量合约¶

    模块通过接口和不可变的 DTO 进行交互——绝不是通过 实例化另一个模块的实体或调用另一个模块的服务 直接。跨模块合约位于 Contract/ 中（只读值对象） 和 Port/ （消费者实现或注入的接口）。

    结算定义了它需要的边界：

    • src/Settlement/Contract/* - ConfirmedAllocation，PostedAllocation， ReversalRequest、VoucherPostingReceipt、SettlementSubject、...全部 final readonly class 仅包含标量的 DTO。
    • src/Settlement/Port/SettlementVoucherPort.php — 拥有的接口 结算，由托管方（钱包）执行：
    interface SettlementVoucherPort
{
    public function post(ConfirmedAllocation $allocation): VoucherPostingReceipt;
    public function reverse(PostedAllocation $allocation, ReversalRequest $request): VoucherPostingReceipt;
}

    该实现位于消费者自己的命名空间中： src/Wallet/Integration/Settlement/WalletSettlementVoucherPort.php。主持人 模块拥有实现；消费模块拥有该接口。

    规则 1.3 的结果： 一个只涉及 Contract/* 的模块 来自其他模块的 Port/* 可以被取出并指向不同的主机 实现（一个 HTTP 客户端、另一个服务、测试中的假冒），无需 改变自己的代码。

    2. 选择模块并映射其边界¶

    src/Settlement 是第一次提取的最佳候选者，因为它是 最独立的。它的布局是模板：

    src/Settlement/
├── Command/          # app:settlement:* console commands (scheduler loop)
├── Context/          # SettlementContextResolver registry pattern
├── Contract/         # immutable cross-module DTOs (scalar-only)
├── Controller/       # API controllers (Manage/ namespace)
├── Entity/           # Doctrine entities — self-contained tables
├── Exception/        # module exception hierarchy
├── Integration/      # Fake/ and Fixture/ test doubles
├── Message/          # Messenger message classes (async)
├── MessageHandler/   # MessageHandler::__invoke consumers
├── Port/             # interfaces the module depends on (implemented elsewhere)
├── Repository/       # Doctrine repositories
├── Resources/config/ # services_settlement.yaml (service wiring)
└── Service/          # domain services + *ServiceInterface aliases

    其他模块遵循相同的形状（钱包、贸易、库存、商店……）， 每个都有相同的子命名空间。唯一的区别是细节——例如 钱包将 Service/ 拆分为 Deposit/、Withdraw/、Transfer/、 Payment/功能文件夹并具有应用程序Controller/和管理Controller/。

    映射依赖关系¶

    对于每个模块，有两个列表：

    1. 它依赖于其他什么 — 合约、端口和消息 进口。对于结算，这些是无；只取决于它自己 Contract//Port/。 （钱包则相反：它实现 SettlementVoucherPort并消耗App\Settlement\Contract\*。）
    2. 其他人依赖它 - 谁实现它的端口 (App\Wallet\Integration\Settlement\WalletSettlementVoucherPort)，谁 使用它的合约，以及它的哪些消息被路由到 config/packages/messenger.yaml。

    “依赖于其他”列表为空（或仅合同）的模块是 可按原样提取。端口指向的模块（结算←钱包）保留 它的域并在接线时交换端口实现。

    每个模块的提取清单¶

    • [ ] 模块内没有 use App\...\Entity 跨模块导入
    • [ ] 所有跨模块引用都是Contract/*和Port/*
    • [ ] 每个出站事件都是一个 OutboxMessage 行 + Messenger 消息
    • [ ] 每个入站事件均从收件箱/已消耗事件表中消耗
    • [ ] 命令名称遵循 app:{module}:{...} 并列在 compose.yaml 中
    • [ ] Resources/config/services_{module}.yaml 保存所有模块接线
    • [ ] config/services.yaml App\|: 自动装配仅排除基础类

    3. 创建应用程序骨架¶

    创建一个新的独立 Symfony 应用程序（或在 monorepo 中创建一个新的 Composer 包） 顶级）将托管该模块：

    composer create-project symfony/skeleton settlement-service
cd settlement-service
composer require symfony/orm-pack symfony/messenger symfony/translation

    您正在复制的内容（按顺序）：

    1. src/Kernel.php — MicroKernel 引导程序。
    2. composer.json — 自动加载 PSR-4 地图："App\\": "src/"。
    3. config/services.yaml — 导入模块配置+全局自动装配。
    4. 模块配置接线（参见Wiring）。

    框架故意被最小化：没有 templates/，没有 webpack，什么都没有 API 框架超出了模块实际使用的部分。

    4.移动代码¶

    将模块的目录物理移动到新应用程序中：

    # Inside the new app
mkdir -p src
mv ../crud-skeleton/src/Settlement src/Settlement

    因为模块是命名空间隔离的 (App\Settlement\...)，所以命名空间 零重命名后保持有效。保留它 App\Settlement 除非你愿意 重命名新服务的根命名空间；如果这样做，命名空间重命名是 机械查找/替换。

    移动必须跟随的部分¶

    随模块一起发货 示例（结算）
    实体+存储库 Entity/*、Repository/*
    领域服务 Service/*、Service/Money/*
    服务接口+别名 *ServiceInterface + services_settlement.yaml
    控制器 Controller/Manage/*
    控制台命令 Command/PublishOutboxCommand.php、RequeueDuePostingCommand.php
    消息+处理程序 Message/*、MessageHandler/*
    合同和港口 Contract/*、Port/*
    测试双打 Integration/Fake/*、Integration/Fixture/*
    模块迁移文件 migrations/Version2026...*.php（结算表）

    留下¶

    • 其他模块拥有的端口实现。 钱包的 WalletSettlementVoucherPort 留在整体中（或者变成一个小的 萃取上游的适配器）。结算从不直接进口； 这取决于接口App\Settlement\Port\SettlementVoucherPort。
    • 任何非特定于模块的全局自动装配 (config/services.yaml App\: 块，_instanceof 标记规则）。这些仅以新的形式移动 应用程序需要自己的模块。

    5. 基线迁移¶

    该模块的表当前位于单体的单一迁移中 历史。在提取之前，生成一个基线，以便新服务可以 仅从其自己的模式开始。

    1. **将创建/修改模块表的所有迁移压缩为一个 新应用程序内的新 Version{time}BaselineSettlement.php：
    final class Version20260820000000BaselineSettlement extends AbstractMigration
{
    public function up(Schema $schema): void
    {
        // CREATE TABLE settlement_plan (...)
        // CREATE TABLE settlement_rule (...)
        // CREATE TABLE settlement_allocation (...)
        // ... module tables only
    }
}

    1. 从整体迁移中删除模块的表语句 导出数据的直接迁移之后的历史记录。保留 Monolith 的历史线性：提取版本带来了一次迁移 将数据迁移出去后，新服务会进行一次基线迁移。

    2. 从第一次部署新服务时将 version_control 设置为开启： doctrine:migrations:version --add --all 应用基线后，或 latest_as_of 在迁移配置中，因此独立历史记录匹配 内置架构。

    3. 使用与 .github/workflows/migrations.yml 相同的作业模式进行验证： 将链从头开始应用于新的 MySQL 8.4 并断言 doctrine:migrations:status 报告最新的基线。

    6. 接线¶

    在新应用程序中重现模块的服务接线。每个模块都拥有一个 已包含其依赖关系图的配置文件：

    • src/Core/Resources/config/services.yaml
    • src/Identity/Resources/config/services_identity.yaml
    • src/Settlement/Resources/config/services_settlement.yaml
    • ...每个模块一个

    src/Settlement/Resources/config/services_settlement.yaml 显示模式：

    services:
    _defaults:
        autowire: true
        autoconfigure: true

    App\Settlement\Service\SettlementServiceInterface:
        alias: App\Settlement\Service\SettlementService

    # ...

    App\Settlement\Port\ClockInterface:
        alias: App\Settlement\Service\SystemClock

    App\Settlement\Port\SettlementVoucherPort:
        alias: App\Wallet\Integration\Settlement\WalletSettlementVoucherPort   # <-- host impl

    when@test:
        services:
            App\Settlement\Integration\Fake\InMemorySettlementVoucherPort:
                public: true
            App\Settlement\Port\SettlementVoucherPort:
                alias: App\Settlement\Integration\Fake\InMemorySettlementVoucherPort

    从 config/services.yaml 导入：

    imports:
    - { resource: '../src/Settlement/Resources/config/services_settlement.yaml', ignore_errors: true }

    重新指向端口¶

    在整体中，SettlementVoucherPort 的别名是 App\Wallet\Integration\Settlement\WalletSettlementVoucherPort。在新的 服务，端口必须解析为随服务一起提供的实现：

    • 迁移过程中：如果您也移动了电子钱包适配器，请保留它 进入新应用程序（它拉入钱包实体/服务 - 事实上是一个钱包 提取也）。
    • 独立服务：针对新服务自己实现端口 存储或对钱包服务的出站 HTTP 调用：
    final class HttpSettlementVoucherPort implements SettlementVoucherPort
{
    public function post(ConfirmedAllocation $allocation): VoucherPostingReceipt { /* POST to wallet.svc /api/... */ }
    public function reverse(PostedAllocation $allocation, ReversalRequest $request): VoucherPostingReceipt { /* ... */ }
}

    并更改 services_settlement.yaml 中的别名。无结算代码 变化——这就是端口间接的全部意义。

    消息传递¶

    将 config/packages/messenger.yaml 中的模块条目移动到新应用程序 （例如routing: App\Settlement\Message\SettlementFundingConfirmedMessage: async）。 在整体中，删除这些路由，如果模块的消息现在是 流程外交付，通过集成替换剩余的消费者 点（webhook/HTTP 调度或共享传输）。

    调度程序和控制台命令¶

    已导出的命令 (app:settlement:...) 由 scheduler服务于compose.yaml。在新的部署中：

    • 从整体的scheduler循环中移除沉降线。
    • 在运行的新服务中添加scheduler（或主机cron） app:settlement:outbox:publish 和 app:settlement:allocations:requeue-due 在相同的循环模式上：
    while :; do
  php bin/console app:settlement:outbox:publish --no-interaction
  php bin/console app:settlement:allocations:requeue-due --no-interaction
  sleep "${OUTBOX_PUBLISH_INTERVAL:-5}"
done

    7. 测试¶

    该模块已经发布了自己的测试替身，因此新服务可以测试 完全隔离的模块：

    • App\Settlement\Integration\Fake\InMemorySettlementVoucherPort — 实现 没有数据库的主机端口。
    • App\Settlement\Integration\Fixture\FundingSnapshotContextResolver — 一个 用于集成测试的标记为 settlement.context_resolver 的固定装置。

    重用单体的测试约定（参见docs/design/system-contracts.md §7 和 docs/testing/crud-skeleton-production/):

    合同 要求
    覆盖范围 ≥ 90% 线路覆盖率，在 CI 中强制执行
    测试数据库 每个测试的干净模式，由模式工具构建
    单元测试 PHPUnit\Framework\TestCase — 无内核
    内核测试 IntegrationKernelTestCase — 启动内核
    网络测试 IntegrationWebTestCase — 完整的 HTTP 周期
    when@test 接线 模块配置中的 Ports/fakes + when@test 部分

    从 tests/UnitTest/Settlement 复制相关测试文件并 tests/Integration 执行该模块，然后将它们从 整体。静态分析保持相同：

    composer phpstan            # Level 8, isolated SQLite DATABASE_URL
composer rector:types:check # Rector type rules dry-run

    8. CI¶

    单体应用的 CI 是 .github/workflows/* 中的三个作业。重新生产它们 新的回购协议：

    工作 源工作流程 命令
    静态分析 ci.yml → phpstan composer phpstan（PHP 8.4，SQLite 数据库 URL）
    校长 ci.yml → rector composer rector:types:check（SQLite 数据库 URL）
    测试 ci.yml → tests Paratest 覆盖率 ≥ 90%，PostgreSQL 16
    移民 migrations.yml 新鲜MySQL 8.4链申请+状态

    参考 CI 使用的 DATABASE_URL 值：

    # phpstan / rector (no DB server needed)
DATABASE_URL="sqlite:///%kernel.project_dir%/var/phpstan.db"

# tests matrix
DATABASE_URL="postgresql://app:app_secret@127.0.0.1:5432/app_test?serverVersion=16&charset=utf8"
PARATEST_DATABASE_URL_TEMPLATE="postgresql://app:app_secret@127.0.0.1:5432/app_test_{token}?serverVersion=16&charset=utf8"

# migrations
DATABASE_URL="mysql://app:app@127.0.0.1:3306/...?serverVersion=8.4&charset=utf8mb4"

    9. 码头工人¶

    重新使用现有的 Dockerfile 并编写布局作为新的模板 服务。提取后的制作图：

    # monolith compose.yaml — Settlement lines removed from scheduler's loop,
# Settlement messages removed from messenger routing
scheduler:
  command:
    - /bin/sh
    - -ec
    - |
      while :; do
        php bin/console app:trade:outbox:publish --no-interaction
        php bin/console app:store:outbox:publish --no-interaction
        php bin/console app:inventory:outbox:publish --no-interaction
        php bin/console app:inventory:reservations:release-expired --no-interaction
        sleep "${OUTBOX_PUBLISH_INTERVAL:-5}"
      done

    # settlement-service compose.yaml — same shapes, own database volume
services:
  app:
    build: .                     # same Dockerfile style
    environment: &app-env
      APP_ENV: prod
      APP_SECRET: ${APP_SECRET:?required}
      DATABASE_URL: "mysql://...@settlement-db:3306/..."
      MESSENGER_TRANSPORT_DSN: ${MESSENGER_TRANSPORT_DSN:?required}   # shared/broker
    volumes:
      - ./var:/var/www/html/var   # JWT keys + cache, persisted

  worker:
    extends: { service: app }
    command: ["php", "bin/console", "messenger:consume", "async", "--time-limit=3600", "--memory-limit=256M", "--no-interaction"]

  scheduler:
    extends: { service: app }
    command:
      - /bin/sh
      - -ec
      - |
        while :; do
          php bin/console app:settlement:outbox:publish --no-interaction
          php bin/console app:settlement:allocations:requeue-due --no-interaction
          sleep "${OUTBOX_PUBLISH_INTERVAL:-5}"
        done

  nginx:
    image: nginx:alpine
    ports: ["${APP_PORT:-8081}:80"]      # separate port from the monolith
    volumes:
      - ./public:/var/www/html/public:ro
      - ./docker/nginx/default.conf:/etc/nginx/conf.d/default.conf:ro
    healthcheck:
      test: ["CMD", "wget", "-q", "-O", "/dev/null", "http://localhost/health/ready"]

  settlement-db:
    image: mysql:${MYSQL_VERSION:-8.4}
    environment:
      MYSQL_DATABASE: ${MYSQL_DATABASE:-settlement}
      MYSQL_USER: ${MYSQL_USER:-app}
      MYSQL_PASSWORD: ${MYSQL_PASSWORD:?required}
      MYSQL_ROOT_PASSWORD: ${MYSQL_ROOT_PASSWORD:?required}
    volumes: [settlement_db_data:/var/lib/mysql]

  redis:
    image: redis:7-alpine

  mailer:
    image: axllent/mailpit

networks:
  internal:

volumes:
  settlement_db_data:

    要点保持不变：

    • 入口点（JWT 密钥引导 + 产品验证）和健康检查 端点（/health/live、/health/ready）随应用程序移动 - 它们位于 src/Core，因此复制 src/Core （或至少模块使用的部分） 提取。
    • nginx 在其自己的主机端口上发布并通过以下方式进行健康检查 /health/ready。
    • 跨服务消息传递是唯一真正的新部分：这两项服务 共享传输（相同 MESSENGER_TRANSPORT_DSN 代理）或 消费服务通过 HTTP 调用端口实现。
    • 生产部署是附加的：部署新服务、迁移数据 （单体上的一次转换迁移，新服务上的一个基线）， 然后删除模块的调度程序行、信使路由和表。

    练习：结算与钱包¶

    关注 结算（先提取） 钱包（当前主机）
    拥有合同 Contract/*、Port/SettlementVoucherPort 消耗 App\Settlement\Contract\*
    实现端口 — Integration/Settlement/WalletSettlementVoucherPort
    数据库表 仅settlement_*，没有FKs wallet_*、voucher_*、transaction_*、...
    跨模块参考 UUID 列（plan_uuid、rule_version_uuid） deposit('settlement', ...) + 凭证字段
    异步边缘 发件箱发布 + SettlementFundingConfirmedMessage、SettlementAllocationPostingMessage 通过端口同步消耗结算过帐
    测试接缝 InMemorySettlementVoucherPort、FundingSnapshotContextResolver —（它提供了它们）

    提取结算=获取域名、合约、命令和测试 双倍，将 SettlementVoucherPort 实现为 HTTP/队列适配器，以及 交付其基线迁移 + CI + compose。因为钱包只会接触 通过Contract/*和Port/SettlementVoucherPort进行结算，单体 side 不需要更改业务逻辑 - 只需要别名 services_settlement.yaml （离开整体）和信使路由 条目（离开整体）。

    然后提取钱包（稍后的步骤）使用相同的配方，以及额外的 托管其端口（结算）的模块现在必须调用它 远程。
