    API 合约¶

    HTTP API 的线路级合约：JSON 信封、身份验证、URL 约定、分页、错误处理、OpenAPI 文档和 webhooks。每个端点 必须遵守这些约定。

    1.JSON 信封¶

    /api/v1/*下的所有业务端点返回一个统一的信封，由 App\Core\Controller\RestController (success() / warning())。

    1.1 成功 (success())¶

    {
  "data": {},
  "code": 0,
  "message": "SUCCESS",
  "paginator": {
    "page": 1,
    "limit": 20,
    "pages": 5,
    "total": 100,
    "has_previous": false,
    "has_next": true
  }
}
    领域 类型 出现时间 描述
    data 任何 总是 有效负载：对象、数组、null 或标量
    code 整数 总是 应用程序级代码。当前的实现会发出 0 表示成功（请参阅下面的注释）
    message 字符串 总是 状态文本； "SUCCESS" 默认
    paginator 对象 仅当响应分页时 分页元数据

    关于 code 的注释： 设计合同 (docs/design/api-design.md §1.1) 指定 code 镜像 HTTP 状态（例如 200），自述文件显示了该示例。 当前的RestController::success()实现编写"code": 0并携带 响应行中的真实 HTTP 状态 (200/201/204)。将 HTTP 状态视为 权威性，code作为错误码使用的应用通道。

    成功时的 HTTP 状态映射：GET 200、POST 201、PUT 200、DELETE 204 （空主体），204 响应呈现为空。

    1.2 错误 (warning())¶

    {
  "code": 400,
  "message": "Validation failed: email is required",
  "raw_data": ""
}

    warning() 将 code 设置为传递的错误代码，通过 转换器，并携带可选的raw_data有效负载。状态码遵循 HTTP 语义：400验证，401认证，403授权，404未找到， 500 服务器错误。

    1.3 请求和响应示例¶

    curl -X POST "http://127.0.0.1:8000/api/v1/manage/contents" \
  -H "Content-Type: application/json" \
  -H "Authorization: Bearer {token}" \
  -d '{"title":"Hello","body":"World"}'

    {
  "data": {
    "id": 42,
    "title": "Hello",
    "body": "World",
    "createdAt": "2026-08-20T09:00:00+00:00"
  },
  "code": 0,
  "message": "SUCCESS"
}

    1.4 认证/微信令牌端点¶

    返回凭证的端点不使用信封。他们返回一个平原 令牌有效负载（参见§2）。

    2. 身份验证¶

    2.1 方案¶

    Authorization: Bearer {access_token}
    • 访问令牌：RS256 JWT，默认 TTL 7200s (ACCESS_TOKEN_TTL)。
    • 刷新令牌：不透明，存储在数据库中散列（HMAC-SHA256）， 默认 TTL 1 年 (REFRESH_TOKEN_TTL)，每次使用时轮换并重复使用 检测（S4：重用的撤销令牌撤销所有用户的令牌）。

    防火墙（config/packages/security.yaml）适用于^/api； manage 前缀 需要 ROLE_ADMIN，其他一切都需要 IS_AUTHENTICATED_FULLY，并且 列出的公共路线除外。

    2.2 端点¶

    以下所有端点都是 PUBLIC_ACCESS （不需要令牌）：

    端点 方法 身体（必填） 回应
    /api/auth/login 发布 {"identifier","password"} 200 个代币； 400 个缺失字段； 401 不良凭证； 403电话-未经验证
    /api/auth/register 发布 {"email","username","password","phone"?} 201 个代币； 400 弱/失踪； 409 个重复项
    /api/auth/otp/request 发布 {"phone","purpose":"login\|verify_phone"} 204 已发送； 400 无效； 429 限时
    /api/auth/otp/verify 发布 {"phone","otp","purpose"} 200 个令牌（目的=登录）或 {"phone_verified":true}； 400/401
    /api/auth/token/refresh 发布 {"refresh_token"} 200 个新代币对； 401 无效/重复使用
    /api/auth/logout 发布 {"access_token"?, "refresh_token"?} 204、撤销提供的令牌

    登录接受 电子邮件、用户名或电话 作为 identifier（电话检测： ^\+?[0-9]{7,20}$）。 OTP 用途为 login 和 verify_phone； OTP TTL 为 300 秒 默认（OTP_TTL），通过Redis存储（OTP_REDIS_DSN）。

    成功令牌负载（登录/注册/otp验证/令牌刷新/微信登录）：

    {
  "access_token": "eyJhbGc...",
  "expires_in": 7200,
  "refresh_token": "eyJhbGc..."
}

    3. URL 约定¶

    3.1 前缀¶

    范围 前缀 访问
    认证 /api/auth/* 公共访问
    公共读取API /api/v1/app/* 已验证（读取）
    管理 CRUD API /api/v1/manage/* ROLE_ADMIN
    公共只读（选择加入） /api/v1/public GET + PUBLIC_ACCESS
    微信整合 /api/wechat/* 公共和认证的混合
    支付网络钩子 /api/payment/notify/* (+ /api/payment/refund-notify) PUBLIC_ACCESS — 网关验证
    API 文档 /api/doc、/api/doc.json 公共访问

    路由在 config/routes.yaml 中按模块注册，前缀为 /api/v1 App 和 Manage 控制器树（属性路由）。

    3.2 资源样式¶

    大会 示例
    小写、连字符、复数 /api/v1/manage/order-items
    详细信息通过路径 ID /categories/{id}
    没有尾部斜线； URL 中没有的动词 POST /categories 创建
    子资源 /orders/{id}/items
    通过整数 id 或 UUID 进行记录查找 由 ApiView::mixIdToCommonFilter 处理（uuid 与 id）

    3.3 非CRUD路线¶

    运营 图案
    批量更新插入 POST /{resource}/batch-update
    创建单件/批量 POST /（对象或数组体）
    单例更新插入 PUT /
    工作流程待办事项 GET /{resource}/todo
    工作流程转换 GET /{resource}/{id}/transitions
    工作流程执行 POST /{resource}/{id}/do/{transition}
    工作流程重置 PUT /{resource}/{id}/status-reset

    3.4 微信端点¶

    端点 方法 访问 目的
    /api/wechat/miniapp/login 发布 公共 js_code → 智威汤逊
    /api/wechat/miniapp/phone 发布 已验证 绑定微信手机
    /api/wechat/oauth/url 获取 公共 官方帐号 OAuth URL
    /api/wechat/oauth/callback 发布 公共 OAuth code → JWT

    4. 分页¶

    列表端点通过 RestController::pagination() 进行分页：

    查询参数 默认 意义
    page 1 从 1 开始的页码
    limit 100 每页项目

    分页器对象：{ total, page, limit, pages, has_previous, has_next }。 pages是 max(1, ceil(total / limit))。分页仅适用于GET并支持 Doctrine\ORM\QueryBuilder 集合（通过 Doctrine Paginator 计数）和普通集合 数组/ArrayCollection。

    4.1 动态查询系统（列表过滤）¶

    当同时使用过滤器参数和分页时，服务将组装查询；的 控制器对结果进行分页。

    参数 示例
    @filter entity.status == "active"
    @dql (entity.price > 100)
    @order createdAt\|DESC
    @select entity.id, entity.name
    @groupBy entity.category
    @hints 教义查询提示
    @sort 内存中排序后备表达式
    @expands category,tags
    @display complex / reduce / 表达式映射
    @showDQL 调试：返回编译后的 DQL

    突变参数：@partial（每项非事务模式），@transform（表达式 字段转换）、@mode（mixed 更新插入/strict 更新）、@basis（更新插入匹配 字段）。

    过滤表达式运算符：==、!=、>、<、>=、<=、&&、||、!、 in / not in（集合成员资格，例如entity.getStoreUuid() in storeUuids； 空 in [] → 1 = 0、空 not in [] → 1 = 1)、matches（文字子字符串或 /regex/flags/）和链接属性访问（entity.getCategory().getName()）。 相同的运算符集为服务器拥有的 DqlExpression 行范围提供支持 commonFilter()（例如new DqlExpression('entity.getUser() == this.getUser()')）， 它们是失败关闭的，而不是回退到内存中评估。

    5. 错误处理¶

    频道 哪里
    控制器级 mixins/controllers 捕获域异常并转换为 warning() with 400/404/500
    全球 ExceptionInterceptor（/api/*上的kernel.exception）将未处理的异常转换为JSON{code, message, class}；在 dev 中被绕过（标准 Symfony 错误页面）
    无效的 JSON 请求正文必须是有效的 JSON；格式错误的 JSON 被拒绝

    状态语义：400 验证、401 身份验证、403 授权、404 未授权 发现，429 速率限制（例如 OTP 请求），500 服务器错误。消息很短， 面向用户并进行翻译。

    除了 webhook 回调之外，每个 /api/* 路由上的响应都是 application/json （见§7）。

    6.OpenAPI / NelmioApiDoc¶

    • Swagger UI：/api/doc
    • OpenAPI JSON：/api/doc.json

    该捆绑包是 nelmio/api-doc-bundle 和 zircote/swagger-php (zircote/swagger-php) 属性。每个端点都声明 #[OA\*] 属性 - 请求正文、查询 参数和响应代码。 OpenAPI集成测试构建了完整的 规范正在进行中，并且 OpenApiEnricherListener 增强了响应。

    每个操作所需的属性：列表（#[OA\Get] + 查询参数）、详细信息 (#[OA\Get] + @expands)，创建(#[OA\Post] + @partial/@transform + 请求 body)、更新 (#[OA\Put] + body)、删除 (#[OA\Delete])、批量 (#[OA\Post] + @mode/@basis/@partial），工作流程（#[OA\Get]/#[OA\Post]/#[OA\Put]）。

    7. Webhook¶

    支付提供商通过 webhook 命名空间通知平台（无 /api/v1 前缀）：

    路线 方法 访问
    /api/payment/notify/{payment} 发布 公共访问
    /api/payment/refund-notify 发布 公共访问

    流程（src/Payment/Controller/Webhook/PaymentNotifyController.php）：

    1. 控制器从PaymentGatewayRegistry解析出{payment}的网关。
    2. $gateway->notify($request) 验证提供商签名（每个网关拥有 其验证）。
    3. InvoiceService::handleNotifyResult()更新发票和发货 与提供商无关的发票事件。
    4. $gateway->getNotifySuccessResponse() 返回特定于提供者的成功正文。

    验证失败时，响应为 400 text/plain (FAIL: <reason>)；任何其他 错误是 400 text/plain FAIL。 Webhook 响应不是 JSON 信封 - 它们 是每个提供商所需的特定于网关的纯文本/接受的字节。

    微信支付 V3 回调流经相同的网关抽象 (/api/payment/notify/wechat)。
