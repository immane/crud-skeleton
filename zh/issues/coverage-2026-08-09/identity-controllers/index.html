    Bugs found¶

    Bug A — unguarded json_decode(..., JSON_THROW_ON_ERROR) → HTTP 500 on empty/malformed bodies¶

    • Files/lines: AuthController.php 73 (login), 134 (register), 331 (refresh), 385 (logout); OtpController.php 33 (requestOtp), 59 (verifyOtp).
    • Description: every JSON endpoint decodes the raw body with JSON_THROW_ON_ERROR and no guard for a missing/empty/malformed body. json_decode('', …) throws JsonException (verified: JsonException: Syntax error). Only logout() guards the empty body ($content === '' ? [] : …, line 385), but a non-empty malformed body still throws.
    • Impact: a client that sends no body or malformed JSON gets an uncaught JsonException (HTTP 500 / error page) instead of a controlled 400; potentially leaks exception details in non-prod. All six OTP/login/register/refresh/logout entry points are affected.
    • Reproduction: POST /api/auth/otp/request with empty body, or POST /api/auth/logout with body {oops → JsonException bubbles out of the controller.
    • Proposed fix: wrap the decode in a try/catch (\JsonException) (or validate json_last_error() after a non-throwing decode) and return $this->error(..., 400); for logout() extend the guard to non-empty malformed bodies as well.
    • Tests: OtpControllerCoverageTest::testRequestOtpWithMalformedBodyShouldReturnBadRequest and AuthControllerCoverageTest::testLogoutWithMalformedJsonShouldNotThrow are skipped (they assert the fixed 400/204 behavior; the current src throws). Kept in the suite to guard the future fix.

    Bug B — verify_phone reports phone_verified=true for phone numbers with no user account¶

    • 文件/行： AuthController.php 294–300； OtpController.php 93–99。
    • 描述：成功进行带有 verify_phone 目的的 OTP 验证后，控制器会查找用户，并且仅在用户存在时保留该标志，但始终返回 ['phone_verified' => true] — 即使 findByPhone() 返回 null 时也是如此。 login 的目的不一致：它为缺失/未经验证的用户返回 401。
    • 影响： 客户端被告知手机已验证，但没有任何结果；此后，用户仍将在 OTP 登录（或任何电话验证门）时被阻止。谎言只能被客户端察觉（重复请求会重新发出 OTP）。次要但不正确的成功合同。
    • 复制： (1) 为任何没有帐户的手机请求 verify_phone OTP（requestOtp 不检查是否存在），(2) 验证它→ HTTP 200 {"phone_verified": true}，即使没有更新任何行。
    • 建议的修复： 当 findByPhone() 没有为 verify_phone 生成用户时，返回 404/401，或者记录响应故意不透明（反用户枚举），并为未知电话返回中性消息，同时仅针对已知电话保留。请注意，当前行为是可观察的（它永远不会透露用户是否存在），因此如果这是意图，它至少应该与 login 目的一致。
    • 测试： OtpControllerCoverageTest::testVerifyOtpVerifyPhoneReportsSuccessForUnknownUser 和 AuthControllerCoverageTest::testVerifyOtpVerifyPhoneReportsSuccessForUnknownUser 描述当前行为（它们通过）并在报告中将其固定下来。

    Bug C — OtpService::maskPhone() 在日志中泄露短电话号码¶

    • 文件/行： OtpService.php 109–116 (maskPhone)。
    • 描述： 对于任何长度超过 4 个字符的电话，maskPhone() 返回 mb_substr($phone, 0, 3) . '****' . mb_substr($phone, -4)。对于长度为 5-7 的电话，两个子字符串覆盖每个数字（例如 '12345' → '123****2345'），因此“屏蔽”值是插入星号的完整数字。
    • 影响： 对于短电话号码（5-7 位数字 — 例如传统/短国家/地区号码），OTP 日志行 [OTP] Sent … phone=… 会将完整号码公开给具有日志访问权限的任何人。对于典型的 E.164 11-14 位数字，当前掩码很好 (+86****5678)。
    • 复制： 使用记录器调用generateAndSend('12345', …)；日志上下文 phone 是 '123****2345'（所有五个数字都存在）。
    • 建议的修复： 通过前 N 个和最后 N 个带有尺寸保护的掩模，例如当 strlen < 8 时隐藏除第一个/最后两个字符之外的所有字符，或者重复使用像 substr($phone,0,2).'****'.substr($phone,-2) 这样的常量掩码，并另外确保至少一个掩码中间字符。
    • 测试： 没有跳过 — 当前输出由 OtpServiceCoverageTest 记录（+86****5678 对于 14 位数字，*** 对于 4 位数字）。

    Bug D — 具有纯数字用户名的用户永远无法使用其用户名登录¶

    • 文件/行： AuthController.php 82–89（登录）；与UserRepository::findByIdentifier() (40–51) 交互，它确实处理电话标识符。
    • 描述： login() 通过 findByPhone() 路由与 /^\+?[0-9]{7,20}$/ 匹配的每个标识符，并且永远不会回退到 findByIdentifier()。因此，用户名仅包含数字（注册允许任何非空用户名字符串，例如 13800138000）的用户永远无法使用该用户名进行身份验证 - findByPhone() 返回 null 并且代码返回 401 Invalid credentials 而无需查阅用户名索引。
    • 影响： 具有数字用户名的帐户无法通过用户名登录；唯一的工作标识符是电子邮件（或他们的电话，如果设置+验证）。合法凭证的静默身份验证失败。
    • 复制：注册num@example.com / 用户名13800138000； POST /api/auth/login 与 identifier: '13800138000'，正确的密码 → 401（已验证：单元测试断言 200 因实际 401 而失败）。
    • 建议的修复： 当 findByPhone() 返回 null 时，转到 findByIdentifier($identifier) （或者始终调用 findByIdentifier() 并将未经验证的手机壳单独映射到 403）。 findByIdentifier() 已经对电话标识符应用了 phoneVerified 保护，因此保留了电话语义。
    • 测试： AuthControllerCoverageTest::testLoginWithNumericUsernameShouldSucceed 被 跳过（断言固定的 200；当前 src 返回 401）。

    Bug E — CreateUserCommand 接受空电子邮件/用户名并创建损坏的帐户¶

    • 文件/行： CreateUserCommand.php 70–86（仅验证密码）。
    • 说明： 该命令验证密码是否非空 (70–74)，但从不验证电子邮件/用户名参数。对于 email: ''，命令继续：findByEmail('') → null，然后将 User 与 email = '' 保持在一起并返回 SUCCESS（已验证：persist() 被调用并且命令退出 0）。 getUserIdentifier() 然后回退到 'anonymous'。
    • 影响： 电子邮件/用户名为空的垃圾帐户；使用相同的空电子邮件进行第二次运行会遇到数据库唯一约束并崩溃，并显示未捕获的 UniqueConstraintViolationException 而不是友好的失败消息。
    • 复制： php bin/console app:identity:user:create '' emptymail 'Password123!' → 使用 email="" 创建帐户并退出 0。
    • 建议的修复： 添加镜像密码检查的守卫，例如if ($email === '') { $io->error('Email cannot be empty.'); return Command::FAILURE; } （与用户名相同）在存储库查找之前。
    • 测试： CreateUserCommandCoverageTest::testExecuteWithEmptyEmailShouldFail 被 跳过（断言 Command::FAILURE 且无 persist；当前 src 保留并返回 SUCCESS）。

    Bug F（次要/稳健性）- CreateUserCommand 删除非数组 --role 值¶

    • 文件/行： CreateUserCommand.php 94–96 ($roleInputs = is_array($rolesOption) ? $rolesOption : [])。
    • 描述： 当 getOption('role') 不是数组时，角色将被默默丢弃。真正的 CLI (ArgvInput) 总是将单个 --role=X 规范化为 VALUE_IS_ARRAY 选项的 ['X']（已验证），因此正常使用没问题 — 但 CommandTester/ArrayInput 以及任何传递普通字符串的编程调用会默默地失去所有角色。
    • 影响：低；对于传递字符串的调用者，角色将被默默忽略。编写测试或嵌入命令时会造成混乱。
    • 复制： new CommandTester($cmd)->execute([... '--role' => 'ROLE_EDITOR']) → 创建的用户只有ROLE_USER。
    • 建议的修复： 防御性正常化，例如$roleInputs = is_array($rolesOption) ? $rolesOption : [$rolesOption]; 并过滤非字符串（第 136 行已经跳过它们）。
    • 测试： CreateUserCommandCoverageTest::testExecuteSkipsNonStringAndEmptyRoleOptionValues 覆盖跳过；此处记录了差异，没有测试断言固定行为。
