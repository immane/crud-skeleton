    发现错误¶

    Bug 1 — BaseServiceMutationTrait.php:137 — 可变的 DateTime 分配给不可变类型的 setter¶

    • 描述： 当更新类似日期的字段时，该特征总是构建一个可变的 new \DateTime((string) $val) 并将其传递给 setter，无论属性/setter 类型如何。
    • 影响： 对于具有 \DateTimeImmutable 类型属性/设置器（例如 #[ORM\Column(type: 'datetime_immutable')]）的实体， update() 抛出 TypeError: must be of type DateTimeImmutable, DateTime given。不可变的日期时间字段 无法通过通用服务进行更新。
    • 复制： 具有 private ?\DateTimeImmutable $created; + setCreated(\DateTimeImmutable) 的实体；打电话 $service->update($entity, ['created' => '2026-02-02 08:00:00']) → TypeError （写入时确认 BaseServiceMutationTraitCoverageTest）。跳过测试：testUpdateWithImmutableDateTimeTypedPropertyIsBroken。
    • 建议的修复： 检查 setter/property 类型（特征已经知道 isDateLikeMapping）并构造 \DateTimeImmutable 当目标类型不可变时，或者通过\DateTime::createFromInterface()进行规范化 / 适当的班级。

    Bug 2 — BaseServiceReadListTrait.php:254 — 排序器比较器永远不会返回 0¶

    • 描述： return $this->getLegacyEvaluator()->evaluateBool($sorter, ...) ? 1 : -1; 没有 0 案例，所以 比较器报告 x < y 是否有相等的键（(x,y) 和 (y,x) 都返回 -1）。
    • 影响： 违反 usort 比较器契约（必须是反对称的）。关系产生不稳定/未定义 订购；畸形的分拣机会默默地降级而不是保持秩序。
    • 复制： @sort 比较两个相等 id 实体的 id — 比较器针对两个参数顺序返回 -1。
    • 建议的修复： 计算可比较的标量（例如 $a = evaluateBool(...) / $b = ...）并返回 $a === $b ? 0 : ($a ? 1 : -1)，或者当布尔值相同时返回0。

    Bug 3 — BaseServiceReadListTrait.php:242-243, 255-256 — 遗留评估器已失效 catch (\Exception)¶

    • 描述： LegacyEvaluator::evaluate()已经在内部捕获了每个\Exception并返回false， 所以 catch (\Exception $e) { return false; } / return 0; 块永远不会触发。仅\Error（例如未定义 表达式内实体上的方法）转义 - 并且这些不会被 catch (\Exception) 捕获。
    • 影响： 防守接球给人虚假的信心；在内存中来自实体 getter 的 \Error 过滤/排序作为未处理的 500 传播，而不是被抑制。死代码。
    • 复制： 注入一个遗留的求值器，该求值器会抛出evaluateBool()； catch 永远不会到达 因为 evaluate() 已经吞掉了异常。 （覆盖率测试通过注入 evaluateBool() 直接抛出的子类。）
    • 建议的修复： 捕获 \Throwable （如果内存中评估必须永远不会失败）或删除死捕获。

    Bug 4 — BaseServiceReadListTrait.php:132-134 — $joiner 中无法访问 !is_string 守卫¶

    • 描述： $joiner = function(?string &$expression, ...) 通过引用绑定。在严格模式下，传递一个 非字符串（例如数组@groupBy[] / @order[]）在调用站点之前守卫抛出TypeError if (!is_string($expression)) return; 运行。守卫无法到达（在沙箱中验证）。
    • 影响： 格式错误的查询参数会导致 500 TypeError 而不是正常的验证错误；警卫是 误导性的死代码。
    • 复制： 以 @groupBy 作为数组的请求 → $joiner($groupBy, ...) 上的 TypeError。
    • 建议的修复： 在调用 $joiner 之前验证 @select/@groupBy/@order 是字符串，或者扩大 参数mixed &$expression。

    Bug 5 — BaseServiceMutationTrait.php:58-59, 157-158, 178-179 — 无法访问的 !is_object($object) 检查¶

    • 描述： 三个 if (!is_object($object)) throw new RuntimeException('Object became invalid during update') 块无法访问：当 $object 不是对象时，update() 已经抛出 ValidatorException （行 40-48），之后没有任何内容将 $object 重新分配给非对象（作者甚至添加了 @phpstan-ignore function.alreadyNarrowedType）。
    • 影响： 死代码；误导性信号表明该对象可以在更新过程中更改类型。这3行就是原因 BaseServiceMutationTrait无法达到100%线路覆盖。
    • 复制： 无（无法访问）。
    • 建议的修复： 删除冗余检查（第 58-59、157-159、178-180 行）。

    次要/设计说明¶

    • ExpressionService::buildFilter() 在缓存命中时返回 Doctrine\ORM\Query，但在缓存命中时返回 QueryBuilder 错过（记录在Query|QueryBuilder）。调用者仅使用 getDQL()/parameters，因此今天它是无害的，但是 返回类型不一致是一个潜在的合同问题。缓存命中路径也信任 parameters 是可迭代的 （具有非数组 parameters 的无效缓存条目将在 array_map 中出现 TypeError）。
    • RestController::expandObjectToMetadata()深度防护0 === $level（第192行）默认情况下永远不会触发 $level = -1（递减-1, -2, …永远不等于0）；递归仅受链长度的限制。
    • BaseServiceMutationTrait::update()关系处理调用$object->$getter() ?? new ArrayCollection() （第 103 行）；返回普通数组的 getter 在 ->map() 上会失败。教义收藏不受影响。
    • BaseServiceInfrastructureTrait::getLogger()/getEntityManager() 容器后备分支仅 当自定义 ServiceLocatorInterface 为访问器返回 null 时可达；与DefaultServiceLocator 构造函数始终直接填充 $this->logger/$this->em。
