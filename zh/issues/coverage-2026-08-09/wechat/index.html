    发现错误¶

    Bug 1 (HIGH) - 微信支付 v3 通知永远不会成功¶

    • 文件/行： src/Wechat/Service/Payment/WechatPayGateway.php — notify() （服务器在第 102 行获取，PSR 请求在第 105 行构建，serve() 在第 126 行调用）。
    • 描述： notify() 根据传入的 Symfony 请求构建 PSR 请求 仅用于签名验证器，但从不将其提供给 EasyWeChat 服务器。 $app->getServer() 是通过 RequestUtil::createDefaultServerRequest() → ServerRequestCreator::fromGlobals() 内部构造的。在 Symfony 请求周期中，php://input 已被 HttpFoundation 消耗，并且在 CLI/队列上下文中它是空的，因此 $server->serve() 始终解析空主体。
    • 影响： 每个真实的微信支付 v3 支付回调都会失败并显示 PaymentVerificationException: WeChat notify verification failed: Invalid request body.（PaymentNotifyController::notifyAction 返回 HTTP 400 FAIL: ...）。发票永远不会通过 webhook 标记 paid。
    • 复制： tests/Wechat/Service/Gateway/WechatPayGatewayNotifyBugTest.php 构建一个真正的 EasyWeChat\Pay\Application （真正的 Merchant），使用格式良好的 TRANSACTION.SUCCESS JSON 主体调用 WechatPayGateway::notify()，并观察 PaymentVerificationException: ... Invalid request body. - 服务器从未见过该主体。 （删除 markTestSkipped() 会使测试失败，即不满足断言“失败不得为‘无效的请求正文’”。）
    • 建议的修复： 在 $response = $server->serve(); 之前，传播传入请求，例如$app->setRequestFromSymfonyRequest($request); （或 $server->setRequest($psrRequest);），并使用相同的验证请求而不是新构建的请求。

    Bug 2（低）- code2Session 使用访问令牌客户端¶

    • 文件/行： src/Wechat/Service/WechatService.php — code2Session() 第 127 行：$app->getClient()->get('/sns/jscode2session', ...)。
    • 描述： MiniApp::getClient() 返回一个 EasyWeChat\Kernel\HttpClient\AccessTokenAwareClient，它将 access_token 附加到每个请求（并在未缓存时通过 GET /cgi-bin/token 获取一个请求）。 /sns/jscode2session 是一个 appid+secret 端点，不需要访问令牌。 EasyWeChat 的规范助手 MiniApp\Utils::codeToSession() 使用普通的 getHttpClient()。
    • 影响： 每个小程序登录都会进行一次额外的 /cgi-bin/token 往返（第一次缓存未命中），如果令牌端点失败，即使 code2Session 会成功，登录也会失败。有效，但浪费/额外的故障表面。
    • 复制：如果没有实时凭证，则无法直接复制；可通过检查 MiniApp::createClient() / AccessTokenAwareClient::request() 来证明。
    • 建议修复： return $this->getMiniApp()->getUtils()->codeToSession($jsCode); 或致电 $this->getMiniApp()->getHttpClient()->request('GET', '/sns/jscode2session', ['query' => [...]])->toArray(false)。

    Bug 3（中）——自动生成的微信用户身份可能会发生冲突¶

    • 文件/行： src/Wechat/Service/WechatAuthService.php — findOrCreateUser() 第 116-119 行。
    • 描述：使用从 openid 的 最后 8 个字符派生的 username/email 创建新用户：wx_<suffix> / wx_<suffix>@wechat.local（均由 User::setUsername/setEmail 小写）。共享相同 8 字符尾部的不同 openids 会生成相同的用户名/电子邮件。 User 实体对两者（uniq_users_username、uniq_users_email）都有唯一的约束。
    • 影响：大规模（8 个字符的生日悖论，约 6 万用户），使用冲突后缀的第二个新用户登录在 flush() → HTTP 500 期间抛出 UniqueConstraintViolationException，用户无法登录。 WechatUser/User 记录也在强制执行约束之前创建，因此留下了部分写入。
    • 复制： 单元级 - 对 findOrCreateUser() 的两次调用，其 openid 仅在最后 8 个字符之外有所不同（例如 aaa...o12345678 与 bbb...o12345678）均派生 wx_o12345678。需要真正的数据库与表面齐平；未添加作为保持套件绿色的测试。
    • 建议的修复： 使用完整的 openid （或其哈希值）作为后缀，例如mb_substr($openid, 0, 40) + 清理，或 substr(hash('sha256', $openid), 0, 12)，和/或捕获 UniqueConstraintViolationException 并回退到现有用户。
