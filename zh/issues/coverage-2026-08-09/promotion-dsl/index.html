    发现错误（仅报告 - 未更改来源）¶

    Bug 1（中）- type: tiered 永远无法解析¶

    • 文件/行： src/Promotion/Service/Dsl/Lexer.php:20（关键字表）与src/Promotion/Service/Dsl/Parser.php:66-67交互（parseType()需要IDENTIFIER）。
    • 描述： 'tiered' 被词法为 TokenType::KEYWORD_TIERED，但 parseType() 只接受 IDENTIFIER 作为类型标头。因此，PromotionTemplate::TYPE_TIERED = 'tiered' (src/Promotion/Entity/PromotionTemplate.php:24) 是唯一不能用 DSL 编写的促销类型。
    • 影响： 分层促销模板永远无法使用自己的类型标头在 PromotionTemplateService::parseDsl()/update() 之间往返（type: tiered 抛出 Expected promotion type identifier）。即使存在 TieredStrategy，类型 'tiered' 也无法使用。
    • 复制： (new Parser())->parse((new Lexer())->tokenize("type: tiered\ndo:\n tiered:\n - threshold: 100 discount: 10")) 抛出 [1:7] Expected promotion type identifier。
    • 建议的修复：在parseType()中，接受KEYWORD_TIERED标记作为有效的类型标识符（其值已经是'tiered'），或者删除tiered的关键字状态并仅在parseAction()中对其进行关键字检查。

    Bug 2 (MEDIUM) — and:/or: 块被吞噬后的同级条件¶

    • 文件/行： src/Promotion/Service/Dsl/Parser.php — parseLogicBlock() 循环，第 148-171 行（块持续消耗直到 section 关键字）。
    • 说明： 一旦进入逻辑块，后面的所有条件行都会被吸收到其中，因此混合表达式 (a OR b) AND c 会解析为 a OR b OR c。该语法无法表达逻辑块后面的条件。
    • 影响： 误报匹配。旨在要求 (cart >= 1000 OR cart <= 10) AND cart == 500 在单独 cart == 500 时匹配的促销，因为 == 500 条件会泄漏到 OR 中。
    • 复制： DSL when:\n or:\n cart.subtotal >= 1000\n cart.subtotal <= 10\n cart.subtotal == 500 与 cart.subtotal = 500 评估 true （预期：false）。由 ParserBugReproTest::testOrBlockAbsorbsSiblingCondition* 守护。
    • 建议的修复： 在第一个非缩进（顶级）条件上终止逻辑块，或需要显式块分隔符；例如跟踪标记中的缩进，因此当同级条件从父级缩进开始时 parseLogicBlock() 会停止。

    Bug 3 (LOW) — 带有尾随点的路径的误导性错误¶

    • 文件/行： src/Promotion/Service/Dsl/Parser.php:254-258 (parseDottedPath())。
    • 描述： cart. >= 200 将 >= 运算符消耗到路径 (cart.>=) 中，然后在 parseOperator() 中失败并显示 Expected operator — 该消息指出了错误的问题。
    • 影响： 格式错误的 DSL 被拒绝（没有无提示的错误评估），但诊断指向操作员而不是格式错误的路径。
    • 复制： ParserBugReproTest::testTrailingDotPathRejectedWithConfusingMessage。
    • 建议的修复：在parseDottedPath()中，使用.后，验证以下标记是IDENTIFIER（或者点不是路径上的最后一个标记）并抛出Expected property name after '.'。

    Bug 4（低）- priority: X desc 标志已解析但从未使用¶

    • 文件/行： src/Promotion/Service/Dsl/Parser.php:586-589 写入 data['desc']； src/Promotion/Service/PromotionService.php:201-226 (getPriority()) 只读value； getAvailable() 始终按降序排序（usort($sorted, fn($a,$b) => getPriority($b) <=> getPriority($a))，第 75-77 行）。
    • 描述： desc 修饰符存储在 AST 中，但在 src/Promotion 中没有消费者（grep 确认）。因为排序已经总是降序，所以该标志是无声的无操作 - 用户编写 priority: 100 desc 不会发生方向变化，也不会出现错误。
    • 影响： 失效功能/误导性 DSL；未来的“asc”方向也将被忽略。
    • 复制： ParserBugReproTest::testPriorityDescFlagIsParsedButUnused。
    • 建议的修复： 要么在比较器中尊重 desc，要么拒绝 desc （或任何方向词）并出现明显错误。

    Bug 5（低）- simulate() 与没有 when: 的模板的真实管道不一致¶

    • 文件/行： src/Promotion/Service/PromotionTemplateService.php:76-100（当不存在 when 子节点时，$matched 保持 false）与 src/Promotion/Service/PromotionService.php:126-134（当不存在 when 节点时，evaluateDslConditions() 返回 true）。
    • 描述： 始终有效的促销（没有 when: 的 do: 块）由定价管道应用，但 simulate() 报告 matched = false。
    • 影响： 模拟/预览 UI 报告不足，与始终在线的营销活动相匹配；用户可能认为该活动不活跃。
    • 复制： 现有套件中的 testSimulateReturnsStructure 已经编码了 matched=false；预期行为记录在 ParserBugReproTest::testSimulateNoWhenNodeAlwaysMatches 中（已跳过）。
    • 建议的修复： 当 AST 包含 do: 块但没有 when: 节点（镜像 evaluateDslConditions()）时，将 $matched 初始化为 true。

    Bug 6 (LOW) — 多个 when: 部分的处理不一致¶

    • 文件/行： src/Promotion/Service/Dsl/Parser.php:37-39 允许重复 when: 部分； src/Promotion/Service/PromotionService.php:150-158 (findWhenNode()) 仅返回第一个； src/Promotion/Service/PromotionTemplateService.php:81-92 (simulate()) 仅报告最后。
    • 描述： 有两个 when: 块，实际评估仅强制执行第一个，而 simulate() 仅显示最后一个。没有错误，也没有两者的结合。
    • 影响：第一个 when: 之后写入的条件在生产中会被默默忽略，从而改变促销实际匹配的内容。
    • 复制： ParserBugReproTest::testParserAllowsMultipleWhenSections 显示两个在解析中幸存下来的 when 节点。
    • 建议的修复： 在解析时拒绝第二个 when: 部分，或者使两个 findWhenNode()/simulate() 遵循所有 when: 节点（并将它们放在一起）。

    Bug 7（低，稳健性） - 解析器 EOL-skip 分支无法从词法分析器输出访问¶

    • 文件/行： src/Promotion/Service/Dsl/Lexer.php:39-41 （跳过空白/注释行，因此每个物理行最多存在一个 EOL）与解析器的“消耗杂散 EOL 并继续”分支（Parser.php 152–153、185、293–294、521–522、607–608）。
    • 描述： 词法分析器无法生成连续的 EOL 标记，因此这些防御分支对于任何 DSL 字符串都是无效的。它们只能通过将手工构建的令牌数组提供给 Parser::parse() 来访问（就像 ParserCoverageTest 那样）。
    • 影响：潜在的脆弱性而不是可观察到的缺陷；如果词法分析器发生变化（例如保留空行），解析器行为将悄然发生变化。
    • 复制： ParserBugReproTest::testLexerNeverEmitsConsecutiveEolTokens。
    • 建议的修复： 不需要；文档，或决定是否应保留空白行并发出真正的 EOL。
