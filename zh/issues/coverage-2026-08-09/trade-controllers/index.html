    交易订单控制器 — 覆盖范围和错误报告¶

    • 日期：2026-08-09
    • 范围：src/Trade/Controller/App/OrderController.php、src/Trade/Controller/Manage/OrderController.php
    • 任务：将两个控制器的线路覆盖率提高到约 100% 并查找错误。
    • 遵守约束：src/ 下的任何内容均未修改。仅添加了 tests/ 下的新测试文件和此报告。

    为什么需要虚假服务¶

    OrderServiceInterface 声明 wrapInTransaction() 仅通过 @method PHPDoc 标记，并且 PHPUnit 12 不再为 PHPDoc 声明的方法生成模拟方法（createMock() 生成未经 wrapInTransaction 验证的模拟）。控制器在 payAction/fulfillAction/refundAction/cancelAction/doTransitionAction 中调用 $this->service->wrapInTransaction(...)，因此无法使用普通模拟来执行这些路径。

    OrderControllerServiceFake 实现 OrderServiceInterface 并将每个真正的接口方法委托给支持 PHPUnit 模拟（因此 $service->method('get')->with(...)->willReturn(...) 保持与现有测试中完全相同的工作），同时添加一个真正的 wrapInTransaction() ，它要么调用回调（invokeTransaction = true），要么表现得像无操作。现有的 Manage OrderControllerTest::setUp() 现在使用 new OrderController(new OrderControllerServiceFake($this->service), ...) 构建控制器；所有 15 项预先存在的测试仍然未改变地通过。

    安全容器如何连接以进行单元测试¶

    AbstractController::getUser() 需要一个暴露 security.token_storage 的容器。应用程序测试注入一个模拟的 ContainerInterface，其 has()/get() 服务于模拟的 TokenStorageInterface + TokenInterface，因此 getCurrentUser() 返回一个具有可配置 id 的 User 模拟（对于匿名情况则返回 null）。现有的 Manage 测试从不调用 getUser()，因此它们不受影响。

    发现错误¶

    Bug 1 - 应用程序 submitAction/confirmAction 让工作流/数据库故障以 HTTP 500（高）的形式出现¶

    • 文件/行： src/Trade/Controller/App/OrderController.php:158-166 (applyUserOrderTransition())，由 submitAction (123-132) 和 confirmAction (134-143) 使用。
    • 描述： 与 cancelAction (194-202) 和 paymentAction (226-230) 不同，它们将 wrapInTransaction(...)/workflow->apply(...) 包裹在 try/catch 中并返回 400 警告，applyUserOrderTransition() 在 wrapInTransaction() 内执行转换，没有 try/catch。任何异常（工作流 NotEnabledTransitionException、数据库故障、侦听器错误）都会从操作中传播出去。
    • 影响： 失败的提交/确认返回未处理的异常→ HTTP 500（Symfony 异常处理），而不是同一控制器上的所有其他突变返回一致的 400 {"code":400,"message":...} JSON。 API 客户端看到不一致的合同；在开发中，原始异常可能会暴露。
    • 复制：（通过探测测试验证）- 所有者匹配，workflow->can($order,'submit') === true，然后 workflow->apply($order,'submit') 抛出。结果：submitAction() 抛出 RuntimeException('submit boom');同一文件中的 cancelAction()/paymentAction() 对于等效失败返回 400 警告。
    • 正确行为测试： App\Tests\Trade\Controller\App\OrderControllerTest::testSubmitActionReturnsWarningWhenTransitionFails 断言 400 响应；它针对当前代码失败，因此被跳过（请参阅跳过的项目）。
    • 建议的修复： 
      try {
    $this->service->wrapInTransaction(function () use ($order, $transition) {
        $this->workflow->apply($order, $transition);
    });
} catch (\Throwable $e) {
    return $this->warning($e->getMessage(), 400, '', 400);
}
return $this->success($order, $successMessage);

    Bug 2 — 管理 doTransitionAction 将任意请求字段转发到 update()，允许订单数据篡改（中）¶

    • 文件/行： src/Trade/Controller/Manage/OrderController.php:322-332 （特别是 :329 $this->service->update($entity, $content);）。
    • 描述： /do/{transition}端点将整个解码后的请求正文传递给OrderService::update()。 BaseServiceMutationTrait::update() (src/Core/Service/Concern/BaseServiceMutationTrait.php:38+) 通过序列化程序 (object_to_populate) 应用实体的任何可设置属性，而不仅仅是白名单。相比之下，updateAction() (105-112) 明确限制对 notes 和 metadata 的突变。
    • 影响： ROLE_ADMIN 调用者可以改变受保护的订单数据 - 例如totalAmount、currency、paidAt、trackingNumber — 只需将其包含在转换主体中即可：POST /manage/orders/{id}/do/complete {..., "totalAmount": 1} 永久重写订单总数（后面的 workflow->apply() 仅重写 status）。这绕过了普通更新端点强制执行的字段白名单，并允许转换调用更改定价数据。
    • 复制： Order 暴露 totalAmount + setTotalAmount()；在update()中的反射循环之后，剩余的键被反序列化到实体上，因此totalAmount被设置。控制器的 can() 防护在更新之前运行，并且仅检查转换，而不检查有效负载字段。
    • 正确行为测试： App\Tests\Trade\Controller\Manage\OrderControllerTest::testDoTransitionDoesNotForwardArbitraryFieldsToUpdate 断言更新负载不包括 totalAmount；它针对当前代码失败，因此被跳过。
    • 建议的修复： 在调用 update()、镜像 updateAction() 之前，将 doTransitionAction 接受的字段（例如 notes、reason、trackingNumber、shippingAddress）列入白名单。此外，首先运行 workflow->apply()，然后仅保留安全字段，因此状态/总计永远不会通过转换主体被篡改。

    Bug 3 — 返回到 API 客户端的原始异常消息（低/与代码库一致）¶

    • 文件/行： 两个控制器中的每个 catch (\Throwable $e) 块都会逐字返回 $e->getMessage()：App createAction:81、quoteAction:102、cancelAction:201、paymentAction:229；管理createAction:67、quoteAction:88、payAction:180、paymentAction:205、fulfillAction:231、refundAction:274、doTransitionAction:335。
    • 描述： 内部异常消息（数据库约束、钱包/网关内部、序列化器错误）在 message 字段中向 API 客户端公开。
    • 影响： 信息泄露/令人困惑的客户端错误。请注意，这是代码库范围内的约定（src/Core/View/* 中存在相同的模式），因此此处仅将其记录为注释，而不将其视为回归。
    • 建议的修复： 记录真正的异常并返回稳定的、用户安全的消息（例如 ApiViewMessages::UNKNOWN_ERROR / 现有的 RestController::UNKNOWN_ERROR）。

    跳过的项目¶

    • App\Tests\Trade\Controller\App\OrderControllerTest::testSubmitActionReturnsWarningWhenTransitionFails — 跳过，因为它断言正确的行为（提交/确认失败必须返回 400 JSON 警告，如取消/付款），并且根据当前代码（错误 1）将 失败。
    • App\Tests\Trade\Controller\Manage\OrderControllerTest::testDoTransitionDoesNotForwardArbitraryFieldsToUpdate — 跳过，因为它断言正确的行为（转换体不得改变任意顺序字段），并且根据当前代码（错误 2）将失败。

    已验证的非错误（已调查并清除）¶

    • 管理 refundAction 发票分支 (259-260) — 它在 refundPayment() 之后返回，而不在控制器中应用 refund 工作流转换。这不是一个错误：InvoiceService::refund() 调度 InvoiceRefundedEvent，Trade\EventListener\OrderInvoiceListener::onInvoiceRefunded() 应用 refund 转换并设置 refundedAt。由现有集成测试TradePaymentIntegrationTest::testOrderPaymentAndRefundThroughInvoiceEvents确认（订单以STATUS_REFUNDED结尾）。
    • 应用 createAction store-context 202 路径 — 订单状态不会保留为普通草稿：OrderService::createOrder() 应用 store_submit 转换并在同一事务 (src/Trade/Service/OrderService.php:111-140) 中记录 trade.order.created.v1 发件箱消息。
    • paymentAction 上的无效支付方法 — 控制器转发任何字符串，但验证发生在服务端：InvoiceService::pay() 通过网关注册表解析方法并抛出未知方法（捕获 → 400）。由应用程序单元测试覆盖，断言 mock/wallet/wechat 已转发。
    • doTransitionAction “can() 失败”路径返回 HTTP 200 — 这是由现有集成测试断言的（testOrderCannotCancelAfterPaid 期望 200 + 非零代码），因此这是有意为之。
    • wrapInTransaction 在 OrderServiceInterface 上的可用性 — 它是一个仅 @method 的声明，因此 createMock() 无法在 PHPUnit 12 下生成它；由于这个原因引入了虚假服务（这是测试基础设施说明，而不是产品错误）。
