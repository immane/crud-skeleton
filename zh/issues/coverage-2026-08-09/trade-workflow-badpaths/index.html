    交易订单工作流程 — 状态机和不良路径覆盖率报告¶

    • 日期：2026-08-09
    • 范围：config/packages/workflow.yaml（订单状态机）、src/Trade/Entity/Order.php、src/Trade/Service/OrderService.php、src/Trade/EventListener/OrderWorkflowListener.php、src/Trade/Controller/App/OrderController.php、src/Trade/Controller/Manage/OrderController.php以及它们公开的 HTTP 端点。
    • 任务：详尽地练习每个订单工作流程转换（所有状态、防护、不良路径），查找错误。
    • 遵守约束：src/ 下的任何内容均未修改。仅添加了 tests/ 下的新测试文件和此报告。

    每组涵盖的内容¶

    工作流状态机单元测试（无数据库）：

    1. 来自每个状态的每个启用的转换 (enabledTransitionsProvider、validTransitionProvider) — 来自 config/packages/workflow.yaml 的确切弧线：
    2. draft → submit/store_submit/cancel
    3. pending → confirm/cancel
    4. awaiting_store_acceptance → store_accept/store_reject/cancel
    5. store_accepted→confirm/cancel； store_rejected → cancel
    6. confirmed→pay/cancel； paid → fulfill; fulfilled→complete； completed → refund
    7. cancelled/refunded 是终端（没有启用的转换）
    8. 错误路径（invalidTransitionProvider，约 39 例）- 应用未启用的转换会抛出 NotEnabledTransitionException 并使状态保持不变；未知的转换名称抛出UndefinedTransitionException； can() 对他们来说是错误的；重复的 submit/pay 被拒绝。
    9. OrderWorkflowListener的时间戳副作用 - cancel→cancelledAt、pay→paidAt（仅当为空时设置）、fulfill→fulfilledAt（仅当为空时）、complete→completedAt、refund→refundedAt（仅当为空时）； submit/confirm/store_* 不设置。
    10. Guard 探针 — 证明 config/packages/workflow.yaml 声明无 Guard 规则：工作流程单独允许在没有金额/用户/钱包的订单上使用 pay，没有 fulfilledAt 的 complete 以及没有原因的 refund。

    HTTP 集成测试（真实 SQLite 模式）：

    1. 带有时间戳断言的愉快路径 draft→pending→confirmed→paid→fulfilled→completed→refunded 到 /do/{transition}。
    2. 商店分支：通过/do的store_submit→store_accept→confirm→pay和store_submit→store_reject→cancel；草稿中的 store_accept 被拒绝。
    3. 从所有六种可取消状态取消； cancel 在 paid 之后被拒绝。
    4. 重复的submit/refund被拒绝，状态不变；未知的转换被拒绝； /do 缺少订单 → 404。
    5. /transitions端点列出了每个状态的确切启用集（跨所有状态的数据驱动）； 404 缺少订单。
    6. /todo 返回已启用转换的订单，不包括终端（cancelled、refunded）订单。
    7. /pay — 防护拒绝（汇票 → 400、缺少 systemWalletId → 400、缺少订单 → 404、无用户/钱包的订单 → 400）、钱包转账成功（余额移动 3000 用户→系统、paidAt+paymentMethod 设置、状态 paid）、第二次付款被拒绝。
    8. /fulfill — 错误状态 → 400，未找到 → 404，成功存储 trackingNumber/shippingAddress + fulfilledAt，状态 fulfilled。
    9. /refund — 状态错误 → 400，缺少 reason → 400，未找到 → 404，钱包退款成功（余额已恢复，refundedAt+refundReason 设置，状态 refunded）。
    10. 应用端点——创建/提交/确认/取消快乐路径，重复提交→400，付费后取消→400，跨用户→404，未找到→404。
    11. 状态重置：PUT /manage/orders/{id}/status-reset 返回 404 — 重置路由是订单的死代码（参见发现 5）。

    发现错误¶

    发现 1 — 订单工作流程没有保护规则； /do/{transition} 让管理员无需付费即可运行整个付费生命周期（中-高）¶

    • 文件/行： config/packages/workflow.yaml（订单部分）-任何转换上都没有guard:； src/Trade/Controller/Manage/OrderController.php:308-339 (doTransitionAction)。
    • 描述： 工作流程仅定义圆弧。安装的 Symfony Workflow Transition 值对象不再具有防护 API (vendor/symfony/workflow/Transition.php)，因此防护表达式是不可能的。唯一的强制执行是 OrderService 状态检查（pay 需要 confirmed、refund 需要 completed、fulfill 需要 paid）以及控制器 can() 调用。通用POST /manage/orders/{id}/do/{transition}端点仅调用can() - 因此ROLE_ADMIN可以移动任何订单draft→paid（do/submit，do/confirm，do/pay），→fulfilled，→completed，→refunded，没有钱包，没有发票，也没有资金移动。
    • 影响： 订单可以标记为已付款/履行/已完成/退款，而无需任何实际付款；财务状态完整性完全取决于每个调用者记得使用钱包端点，而不是 /do。这是演示脚本自己的快乐路径（scripts/tests/demo-trade-workflow.php 步骤 1 使用 do/pay），因此它旨在用于演示 - 但对于生产而言，它是一个真正的数据完整性漏洞。
    • 复制： OrderWorkflowApiTest::testHappyPathDraftToRefundedViaDoTransitions（按设计通过）和OrderWorkflowStateMachineTest::testWorkflowLayerAllowsPayWithoutAmountWalletOrUser（通过-证明没有守卫）。
    • 建议的修复： 不要通过 /do/{transition} 公开货币转换 (pay/refund) - 将 /do 限制为非货币转换（submit、store_*、confirm、fulfill、complete）或要求 pay/refund 提供付款参考。或者重新添加守卫表达式作为工作流事件侦听器/阻止程序（守卫作为 API 在此 Symfony 版本中不再存在）。

    发现 2 — OrderService::pay/refund/fulfill 不应用工作流程转换（低/设计拆分）¶

    • 文件/行： src/Trade/Service/OrderService.php:146-265（pay、refund、fulfill）。
    • 描述：这些方法验证当前状态，执行钱包转账/设置业务字段（paidAt、refundedAt、fulfilledAt、trackingNumber、paymentMethod、refundReason），但从不调用$this->workflow->apply(...)。状态更改仅发生在控制器中（Manage/OrderController::payAction/fulfillAction/refundAction 在 wrapInTransaction 内调用 workflow->apply()）。 OrderWorkflowListener特意保留了预设的paidAt/fulfilledAt/refundedAt（仅在为空时设置），这确认了拆分设计。
    • 影响： 任何直接使用 OrderService::pay() 的调用者（未来的命令/worker/saga）都将设置 paidAt，而订单保持 confirmed — 不一致的状态。方法中的状态检查是唯一的保护措施，它们不能防止直接调用者跳过转换。
    • 复制： 单位级 — 已确认订单上的 OrderService::pay() 设置 paidAt 并留下 status === 'confirmed'（由现有 OrderServiceTest 覆盖）。
    • 建议的修复：要么让 OrderService::pay/refund/fulfill 自己应用匹配的工作流转换，要么大声记录调用者必须将每个服务调用与工作流转换配对。

    发现 3 — doTransitionAction 将任意请求主体字段转发到 update()，从而实现订单数据篡改（中 — 先前记录）¶

    • 文件/行： src/Trade/Controller/Manage/OrderController.php:329。
    • 描述： /do/{transition} 将整个解码后的正文传递给 OrderService::update()，它通过序列化程序应用任何可设置的属性（没有白名单，不像 updateAction() 限制为 notes/metadata）。
    • 影响： POST /manage/orders/{id}/do/submit {"totalAmount": 1}重写订单总数；对于 currency、paidAt 等也是如此。绕过普通更新白名单。
    • 复制： OrderWorkflowApiTest::testDoTransitionMustNotForwardArbitraryBodyFieldsToUpdate — 跳过，因为它断言正确的行为（篡改的 totalAmount 不得持续）并且当前失败。 docs/issues/coverage-2026-08-09/trade-controllers.md 中的完整详细信息（Bug 2）。

    发现 4 — 应用程序 submit/confirm 将工作流/数据库故障传播为 HTTP 500（中 — 先前记录）¶

    • 文件/行： src/Trade/Controller/App/OrderController.php:158-166 (applyUserOrderTransition)，由 submitAction/confirmAction 使用。
    • 描述： 与cancelAction/paymentAction（try/catch并返回400）不同，applyUserOrderTransition()在wrapInTransaction内执行workflow->apply()，没有catch；失败会作为未处理的 500 转义，而不是 API 的 400 {code,message} 合约。
    • 复制： 在概念上由 OrderWorkflowApiTest::testAppSubmitOnAlreadySubmittedOrderIsRejected 覆盖（保护路径干净地返回 400） - 500 路径需要中间事务抛出并固定在 tests/Trade/Controller/App/OrderControllerTest.php 中（跳过正确行为测试）。 trade-controllers.md 中的完整详细信息（Bug 1）。

    发现 5 — status-reset 端点是死代码，无法处理订单（低）¶

    • File/line: src/Core/View/WorkflowApiViewMixin.php:104-109 (resetMarkingAction).
    • Description: No controller uses WorkflowApiViewMixin (verified by grep — only the mixin file itself and its unit test reference it), so PUT /manage/orders/{id}/status-reset is not a route on the order controllers and returns 404 (OrderWorkflowApiTest::testStatusResetRouteIsNotRegisteredOnOrderControllers). Even if wired up, resetMarkingAction() calls $entity->setStatus([]) — an array into Order::setStatus(string) → TypeError — and the route placeholder {id} does not match the $entity argument name. (The placeholder mismatch is already flagged in docs/issues/coverage-2026-08-09/core-view.md.)
    • Impact: The documented "reset" workflow flow does not exist for orders; the mixin is latent broken code.
    • Proposed fix: either delete the mixin or fix it ($entity->setStatus(Order::STATUS_DRAFT) + argument named $id), and add the route to the order controllers if reset is actually wanted.

    Finding 6 — Order entity has no STATUS_ constants for the store states (INFO)¶

    • File/line: src/Trade/Entity/Order.php:19-26.
    • Description: Order::STATUS_* covers only draft/pending/confirmed/paid/fulfilled/completed/cancelled/refunded. The store states awaiting_store_acceptance, store_accepted, store_rejected are bare string literals across OrderService, controllers and message handlers.
    • Impact: typos/renames are not caught by static analysis; inconsistent with the constant-based statuses.
    • Proposed fix: add STATUS_AWAITING_STORE_ACCEPTANCE, STATUS_STORE_ACCEPTED, STATUS_STORE_REJECTED and use them.

    Finding 7 — Raw exception messages returned to API clients (LOW — codebase-wide convention)¶

    • File/line: every catch (\Throwable $e) in both order controllers returns $e->getMessage() verbatim (e.g. Manage/OrderController.php:180,205,231,274,335).
    • Impact: internal wallet/gateway/DB messages leak to clients. Noted only — this is the established convention across the codebase (see trade-controllers.md Finding 3).

Fails against current code (Finding 3). (Mirrors the already-skipped unit test in tests/Trade/Controller/Manage/OrderControllerTest.php.)
    • (Reference only) App\Tests\Trade\Controller\App\OrderControllerTest::testSubmitActionReturnsWarningWhenTransitionFails and ...Manage\OrderControllerTest::testDoTransitionDoesNotForwardArbitraryFieldsToUpdate — previously skipped in trade-controllers.md; not duplicated here.

    Verified non-bugs (investigated and cleared)¶

    • Workflow allows pay from store_accepted? No — confirm must come first (confirm: from: [pending, store_accepted]); pay is only from confirmed. Covered by invalidTransitionProvider + integration happy path.
    • pending → awaiting_store_acceptance? Not a transition — store_submit is from draft only (the docs context.md §7.1 diagram is a simplification). Tested per the actual workflow.yaml.
    • Refund from paid/fulfilled (task phrasing "paid/…→refunded")? The config only allows refund: from: completed. refundAction correctly guards on can('refund'); direct do/refund from paid is rejected. Confirmed by testRefundEndpointRejectsNonCompletedOrder + invalidTransitionProvider.
    • Manage refundAction invoice branch skipping the workflow transition — not a bug: InvoiceService::refund() dispatches InvoiceRefundedEvent and OrderInvoiceListener::onInvoiceRefunded() applies the refund transition (covered by existing TradePaymentIntegrationTest).
    • /todo pagination/query params — list(null, null, false) intentionally evaluates the request; no filter params are sent, and assertPrivilegedQueryParameters allows plain admin GETs. Only a scalability TODO in the mixin, not a correctness bug.
