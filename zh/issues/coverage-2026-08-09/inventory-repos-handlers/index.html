    Bugs found¶

    Bug #1 — Release handler accepts impossible calendar dates; its new \DateTimeImmutable() check is a no-op¶

    • 文件/行： src/Inventory/MessageHandler/InventoryReservationReleaseRequestedHandler.php:97-100。
    • 描述： requestedAt 仅由第 97-98 行的正则表达式验证，然后由第 100 行的 new \DateTimeImmutable($requestedAt) 验证。PHP 的 DateTimeImmutable 构造函数默默地 * 规范化 * 超出范围的日期而不是抛出 — 2026-02-30T00:00:00+00:00 毫无例外地变成 2026-03-02 — 因此第 100 行永远不会失败，并且不会添加任何超出正则表达式的内容。 101-102 处的 catch 只能由第 98 行的正则表达式 throw 触发。同时，预订请求处理程序的 parseDate() (InventoryReservationRequestedHandler.php:153-179) 通过 DateTimeImmutable::getLastErrors() 拒绝相同的不可能日期。两个处理程序对同一类型时间戳的验证不一致。
    • 影响： 今天较低（requestedAt 被记录但从未进行比较），但发布方默默地接受请求方拒绝的损坏时间戳，第 100 行是死防御代码。
    • 复制（集成探针）： 成功处理带有 requestedAt = '2026-02-30T00:00:00+00:00' 的有效释放消息（释放预留，消耗事件）。预订请求消息中的相同日期将被 InvalidArgumentException 拒绝。
    • 建议的修复： 使用与请求处理程序相同的严格帮助程序解析 requestedAt （检查 getLastErrors()，例如共享 InventoryReservationRequestedHandler::parseDate() 或提取公共验证器），并删除多余的 new \DateTimeImmutable() 行。

    Bug #2 - parseDate() 分数分割中无法到达的防御分支¶

    • 文件/行： src/Inventory/MessageHandler/InventoryReservationRequestedHandler.php:161-163。
    • 描述： $parts = preg_split('/(?=[+-]\d{2}:\d{2}$)/', $normalized); if ($parts === false || count($parts) !== 2)。该模式是锚定在字符串末尾的零宽度先行，因此对于任何包含点的 ISO 字符串，它仅匹配一次（紧接在尾随时区偏移之前）； preg_split 始终恰好生成两个部分，并且从不返回这些输入的 false （调用者的正则表达式已将时间戳形状和分数限制为 \d{1,6}）。 163 路无法接通。
    • 影响： 功能上无影响；这是将请求的处理程序保持在 99.11% 的单个语句，并表明该检查是针对正则表达式已排除的格式错误的输入类进行防御性编写的。
    • 复制： 覆盖范围 — 第 163 行仍然是所有 109 个库存测试中唯一未覆盖的语句；无法进入该分支进行任何输入。
    • 建议的修复：删除 count($parts) !== 2 替代方案（仅保留 $parts === false 防护），或用时间戳正则表达式中的两个捕获组替换 preg_split/explode 舞蹈。

    Bug #3（操作，中等）- 任何处理程序失败都会关闭共享的 EntityManager¶

    • 文件/行： InventoryReservationRequestedHandler.php:34 和 InventoryReservationReleaseRequestedHandler.php:35 调用 $this->entityManager->wrapInTransaction(...)； Doctrine\ORM\EntityManager::wrapInTransaction() (vendor/doctrine/orm/src/EntityManager.php:180) 在发生任何异常时在回滚之前调用其 finally 块中的 $this->close()。
    • 描述： 这些处理程序中的每个故障路径 - 未找到预留（版本：41）、相关性不匹配（版本：48）、事件 ID/有效负载冲突（请求：188、版本：128-129）或服务异常（例如数量过大）（请参阅 Bug #4） - 都会使容器的 EntityManager 关闭 并清除其身份映射以用于流程的其余部分。经验验证：在 InventoryReservationConflictException 之后，$em->isOpen() 返回 false，下一个 persist()+flush() 抛出 Doctrine\ORM\Exception\EntityManagerClosed: The EntityManager is closed.（只读存储库查询仍然有效，因为 find() 不断言 isOpen()）。
    • 影响： 在每个进程处理多条消息的 Messenger 工作线程中（同步传输或没有按消息 EM 重置的异步工作线程），单个失败的 Inventory 消息会毒害每个后续消息的共享 EM — 它们的写入崩溃并出现 EntityManagerClosed。每个失败模式也是一个永久的重试循环：因为消费事件行是在失败的同一个事务中写入的，所以消息永远不会被确认，并且项目没有死信（与之前记录的无最大尝试发件箱发现一致）。
    • 复制（集成探针）：通过请求的处理程序触发预留冲突，然后在同一容器上 persist() + flush() EntityManager → EntityManagerClosed。
    • 建议的修复： 在新的/可设置的 EM（信使 DoctrineClearEntityManagerWorkerSubscriber 或失败时重置中间件）上运行每个处理程序，或者让处理程序在容易失败的服务调用之前确认所消耗的事件，以便有害消息不会干扰工作人员；至少记录这些处理程序需要一个新的 EM-per-message 工作人员。

    Bug #4（验证差距，低）- 超大数量通过处理程序验证，然后在服务内崩溃¶

    • 文件/行： src/Inventory/MessageHandler/InventoryReservationRequestedHandler.php:122（项目数量正则表达式/^[0-9]+(?:\.[0-9]{1,6})?$/）与src/Inventory/Service/Quantity.php:20-22（14位整数上限，decimal(20,6)）。
    • 描述： 处理程序的数量正则表达式允许任意长的整数部分。 Quantity::normalize() 将整数部分限制为 14 位并抛出 InvalidArgumentException: Quantity exceeds decimal(20, 6).。发送 quantity: '123456789012345' 的生产者传递 validateEnvelope()，然后服务在处理程序的事务中抛出异常，导致消息失败（并且根据 Bug #3，关闭 EM）。
    • 影响： 低；语法上有效但超出范围的数量会成为永远重试的有害消息，而不是被信封验证器拒绝。
    • 复制（集成探针）：带有 quantity = '123456789012345' 的请求消息通过 validateEnvelope()，然后处理程序失败并返回 InvalidArgumentException: Quantity exceeds decimal(20, 6).。
    • 建议的修复： 绑定处理程序正则表达式中的数字，例如/^[0-9]{1,14}(?:\.[0-9]{1,6})?$/，或对 validateEnvelope() 内的每个项目调用 Quantity::normalize()，以便预先拒绝超出范围的数量。
