    3. 验证正确的行为（积极测试）¶

    • @filter 编译为 DQL 并正确过滤（entity.getSortOrder() > 0 → 子集；==；matches "slug-1" → LIKE；单属性 trueentity.getName() → IS NOT NULL）。 200 + 正确paginator.total。
    • @order=entity.sortOrder|DESC → 正确的排序。
    • @select=entity.id,entity.name → 仅投影（无slug/description）。
    • @groupBy + @select → 分组行。
    • @display=reduce 和 @display=["entity.name"] 场投影。
    • 创建时的 @transform (Math.ceil(3.7) → "4")。
    • limit=abc / page=abc → 400（BadRequestHttpException，异常拦截器 JSON 信封）——正确 4xxs 的一种格式错误的参数情况。
    • /system/entities 列表、/system/entities/{name} 元数据（types/columnName/nullable + ManyToOne targetEntity）、/system/router 路由转储 — 所有 200 个都带有 {data,code:0,message:"SUCCESS"}。
    • 通过?_locale=zh|zh_Hant|ja和Accept-Language: en-US进行字段名称翻译。
    • 每个语言环境的消息翻译：Entity is not found → zh 实体未找到。、zh_Hant 實體未找到。、ja エンティティが見つかりません。、en Entity is not found。
    • /api/doc.json：存在模块标签（Auth,System,Wechat,Products,Orders,Categories,…,Payment,Wallet），tags中或任何操作中都没有留下List/Detail/Create/Update/Delete/Workflow；关键端点映射到正确的模块。
    • AccessLogListener 写入真实行 (@testauth#1 POST /api/v1/manage/categories | 201 | REQ: … | RES: …) 并且不记录 GET。
    • 分页：页面超出范围→空项+正确的has_next=false；负页→强制为1； limit=0 → 强制为 1；完整的{total,page,limit,pages,has_previous,has_next}形状。
    • 信封形状：成功列表{data,code,message,paginator}；成功详细信息{data,code,message}（无分页器）；警告{code,message,raw_data}（无data）；异常{code,message,class}。

    4. 发现错误¶

    BUG-1 — 对于 JWT 身份验证的 HTTP 请求，BaseService::$user 始终为 null → 所有管理员控制的查询参数 403 — 高¶

    • 位置： src/Core/Service/BaseService.php:77 ($this->user = $token ? $token->getUser() : null;)，由 src/Core/Service/Concern/BaseServiceReadListTrait.php:119-120（过滤器后备管理门）、:270-271 (assertPrivilegedQueryParameters)、:291-295 (hasAdminRole) 使用。
    • 描述： BaseService::$user 在构建时从 security.token_storage 得到解决。服务类是容器单例，并且在每个请求令牌上下文之外实例化，因此对于 HTTP 请求，$user 永久为 null。经验证明的根本原因是：在请求期间，令牌存储确实包含经过身份验证的用户（角色ROLE_ADMIN,ROLE_USER），但容器缓存的服务实例具有user=null，而同时构建的new CategoryService($container)具有user=ROLE_ADMIN,ROLE_USER。
    • 影响： @dql、@sort、@hints 始终抛出 AccessDeniedHttpException (403)，即使对于 ROLE_ADMIN 用户也是如此；无法编译为 DQL 的 @filter 表达式（需要内存中 LegacyEvaluator 回退）也始终为 403，而不是回退。记录的动态查询权限系统无法通过 HTTP 使用。次要影响：对于价格管道上下文，src/Trade/Service/OrderService.php:55 读取相同的 $this->user。
    • 复制： 使用 ROLE_ADMIN JWT，GET /api/v1/manage/categories?@dql=SELECT c.id FROM App\Common\Entity\Category c → 403 {code:403, message:"@dql is restricted to administrators.", class:"…AccessDeniedHttpException"}。
    • 建议的修复： 在请求时从令牌存储解析用户（例如注入 TokenStorageInterface 并读取 list()/hasAdminRole() 内的用户），或标记 BaseService 子类请求范围；不要将主体缓存在长期存在的单例中。
    • 测试： testDqlRestrictedForEveryoneCurrently、testSortRestrictedForEveryoneCurrently、testHintsRestrictedForEveryoneCurrently、testInvalidFilterFallsToAdminGateCurrently（回归、通过）； testDqlAllowedForAdminReturnsFilteredResults、testSortAllowedForAdminSortsInMemory（正确行为，跳过）。

    BUG-2 — @expands 创建动态 __metadata 属性 → PHP 8.5 弃用 → 破坏 failOnDeprecation — 高¶

    • 位置： src/Core/Controller/RestController.php:198 ($node->__metadata = $node;)。
    • 描述： 扩展将动态属性附加到实体。在 PHP 8.2+ 上，这已被弃用 (Creation of dynamic property …::__metadata is deprecated)。存储库的 phpunit.dist.xml 设置 failOnDeprecation="true"，因此使用 @expands 的任何请求都会将套件变为红色。
    • 影响： @expands 在 CI 中实际上是不可测试/不安全的，应被视为已损坏。 （另外观察到：在此设置中，序列化的扩展关系返回了 null，因此扩展没有可见的有效负载效果。）
    • 复制： GET /api/v1/manage/categories?@expands=["parent"] → 从 RestController.php:198 弃用。
    • 建议的修复： 在可以扩展的实体上声明类型化 public mixed $__metadata = null; （或使用 #[AllowDynamicProperties]/外部映射），并使 expandObjects/expandObjectToMetadata 仅附加序列化器所需的元数据。
    • 测试： testExpandsReturnsMetadataWithoutDeprecation （跳过，引用此错误）。

    BUG-3 — 格式错误的 @select（数组）返回 HTTP 500 而不是 400 — 中¶

    • 位置： src/Core/Service/Concern/BaseServiceReadListTrait.php (if (!is_string($select)) throw new ValidatorException('@select must be a string.');)，通过 src/Core/View/ListApiViewMixin.php:listAction() 未捕获（无 try/catch）进入 ExceptionInterceptor。
    • 描述： @select[]=a&@select[]=b 使 $select 成为一个数组； ValidatorException 不是 HttpException，代码为 0，因此 ExceptionInterceptor 将其映射到 500，而不是 400。
    • 影响： 对于格式错误的请求，客户端会收到 500（服务器错误）。
    • 复制： GET /api/v1/manage/categories?@select[]=entity.id&@select[]=entity.name → 500 {"message":"@select must be a string.","class":"…ValidatorException"}。
    • 建议的修复： 在 ListApiViewMixin::listAction() 中捕获 ValidatorException 并返回 warning(…, 400, …, 400)，或者使读取列表特征抛出 BadRequestHttpException。
    • 测试： testArraySelectReturns500Currently（回归，通过）； testArraySelectReturns400（正确行为，跳过）。

    BUG-4 — matches 带有正则表达式文字在 SQLite 上崩溃（无 REGEXP 函数） — 中等（环境）¶

    • 位置： src/Core/Parser/ExpressionDqlParser.php (matches → REGEXP(%s, %s) = TRUE)。
    • 描述： /pattern/flags 编译为 REGEXP() 调用； SQLite 没有 REGEXP 函数，因此查询在执行时失败并带有 no such function: REGEXP。普通的 LIKE 风格 matches "slug-1" 效果很好。
    • 影响： 正则表达式过滤适用于 MySQL，但在 SQLite 测试环境（以及任何 SQLite 部署）中需要 500 秒。
    • 复制： GET /api/v1/manage/categories?@filter=entity.getSlug() matches "/^slug-1$/i" → 500 {"message":"…no such function: REGEXP","class":"…DriverException"}。
    • 建议的修复： 通过数据库平台保护 REGEXP（例如，在测试中注册 SQLite REGEXP 用户函数/使用 LIKE 后备），或记录正则表达式匹配仅限 MySQL。
    • 测试： testRegexMatchesWorksOnCurrentDb（跳过）。

    BUG-5 — 系统端点为未知实体返回 500 HTML（不是 404 JSON） — 中¶

    • 位置： src/Core/EventListener/ExceptionInterceptor.php:21 (EFFECTIVE_PATTERN = '/^\/(api)\/.*$/'); src/Core/Controller/System/EntityController.php:66-67（getClassMetadata 对于未知的 FQCN 抛出异常）。
    • 描述：拦截器仅处理 /api/* 路径，因此 /system/entities/{name} 上的 MappingException （未知实体）会绕过 JSON 错误信封并呈现 Symfony 的 HTML 错误页面 (500)。 docs/ai/context.md §12 中的文档暗示这些是 API 风格的系统端点；消费者获得 HTML。
    • 影响： 系统端点没有 JSON 错误契约；错误的实体名称是 500（服务器错误）而不是 404。
    • 复制： GET /system/entities/App/Does/Not/Exist → 500 text/html 与 Doctrine\Persistence\Mapping\MappingException: Class 'App\Does\Not\Exist' does not exist。
    • 建议的修复： 将拦截器模式扩展到 /system （或在 EntityController::retrieveAction() 和 warning(…, 404, …, 404) 中捕获 MappingException）。
    • 测试： testMissingEntityReturns500HtmlCurrently（回归，通过）； testMissingEntityShouldReturn404Json（正确行为，跳过）。

    BUG-6 — default_locale: zh 不会成为活动区域设置 — 有效默认值为英语 — 低¶

    • 位置： config/packages/translation.yaml:2 (default_locale: zh);框架 Symfony\Component\HttpKernel\EventListener\LocaleListener 仅将默认语言环境设置为优先级 100，并且在没有显式 _locale 的情况下绝不会激活它；应用程序的自定义 App\Core\EventListener\LocaleListener （优先级 20）仅覆盖匹配的 ?_locale/Accept-Language。
    • 描述：没有区域设置提示，活动请求区域设置保持 en （PHP Request 默认） - 在 reqDefaultLocale=zh 时验证 reqLocale=en/translatorLocale=en。因此，default_locale: zh 只为翻译器提供缺失键的后备（这可能会产生奇怪的 en-with-zh-fallback 混合）。 LocaleListener 文档块和 docs/ai/context.md 都声明回退 en，它与有效行为匹配，但与配置相矛盾。
    • 影响：配置错误 - 即使 default_locale 说中文，应用程序默认为英文响应；文档/配置不匹配。
    • 复制： GET /api/v1/manage/categories/999999（无提示）→ message: "Entity is not found"（en）； fr-FR 标头 → 也 en。
    • 建议的修复： 设置 default_locale: en 以匹配实际情况，或者使自定义 LocaleListener 在没有提示匹配时应用配置的默认值。
    • 测试： testNoLocaleHintUsesEffectiveEnglishDefault、testUnsupportedLocaleLeavesEffectiveEnglishFallback（断言实际行为，通过）。

    BUG-7 — OpenApiEnricherListener::detectTag() 前缀检查永远不会匹配方法前缀的操作Ids — 存储未标记的端点 — 中¶

    • 位置： src/Core/EventListener/OpenApiEnricherListener.php:259-262（str_starts_with($opId, 'system-')、'wechat-'、'store-'）。
    • 描述： Nelmio 使用 HTTP 方法（get_store-orders-list、post_store-orders-accept）为操作 ID 添加前缀，因此锚定的 str_starts_with 检查永远不会触发。未锚定的 manage|app|public 正则表达式和 str_contains(…, 'sys-auth') 检查仍然有效，这就是具有显式 OA tags 的 system-*/wechat-* 端点能够生存的原因。存储端点（没有显式的 OA 标签，没有 META 条目）最终根本没有标签。
    • 影响： /api/v1/store/stores/{scopeId}/orders… (list/detail/accept/reject/fulfill) 在丰富的规范中具有空的 tags → 文档 UI 中缺少模块标记。
    • 复制： GET /api/doc.json → paths['/api/v1/store/stores/{scopeId}/orders/{orderUuid}/accept']['post']['tags'] === []。
    • 建议的修复： 在检测之前去除方法前缀（例如 preg_replace('/^(get|post|put|delete|patch)_/', '', $opId)），或使用 str_contains 进行前缀检查。
    • 测试： testStoreOrderEndpointsAreLeftUntaggedCurrently（回归，通过）； testStoreOrderEndpointsShouldBeTaggedStore（正确行为，跳过）。

    附加观察结果（不阻塞）¶

    • @order=entity.sortOrder|UP（无效方向）和@order=entity.nope|ASC（未知字段）表面为 500 QueryException 而不是 400 — 不验证 @order 标记。
    • TransformContent (src/Core/View/TransformContent.php:156-157) 默默地吞下 @transform 计算失败 — 格式错误的转换表达式无操作而不是出错。
    • 文档（docs/ai/context.md §5）显示Math.mul(value, 100)，但src/Core/Utils/Math.php没有mul方法。
    • translations/messages.ja.yaml:293 将 "SUCCESS" 映射到中文字符串 操作成功。 （应该是日语字符串）。

    6. 建议的后续行动¶

    1. 修复 BUG-1（请求时用户解析）——解锁 @dql/@sort/@hints + @filter 内存回退，这是价值最高的动态查询功能。
    2. 修复 BUG-2（键入 __metadata/无动态属性），使 @expands 不再失败 failOnDeprecation。
    3. 制作ListApiViewMixin映射ValidatorException→400（BUG-3）并验证@order。
    4. 将 /system 前缀添加到 ExceptionInterceptor (BUG-5) 并捕获 404 JSON 的 MappingException。
    5. 在标签检测之前规范化操作Id (BUG-7) 并将 default_locale 配置与实际行为对齐 (BUG-6)。
