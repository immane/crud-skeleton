    3. Bugs found (no source changes made)¶

    BUG-1 — amount is silently coerced with (int) — fractional/string amounts truncated (Medium)¶

    • Location: src/Wallet/Controller/Manage/TransferController.php:36 (createAction) and :83 (depositAction)
    • Description: $amount = (int) ($content['amount']);. The only guard is empty() (presence) and $amount <= 0 (positivity); there is no integer-ness validation. A JSON amount: 12.99 becomes 12, amount: "12abc" becomes 12, and amount: "1e3" becomes 1 (1000 silently reduced to 1). Fractional values are truncated, not rejected.
    • Impact: financial correctness — a client sending a decimal amount (e.g. 1.99) has 0.99 silently dropped (99% under-credited/under-debited); the error is invisible to the caller. The pre-existing fuzz test tests/Wallet/Integration/WalletApiRegressionTest.php:427 even codifies the truncation ('float amount' => [['...', 50.5], 201] // casts to int 50, passes), so the risk is known and accepted but still dangerous for real payment amounts.
    • Reproduction: POST /api/v1/manage/transfers with {"fromWalletId":1,"toWalletId":2,"amount":1.99} → the service is called with amount = 1 and the wallet is debited 1 cent, not 1.99.
    • Proposed fix: validate the raw value is a non-negative integer before casting — reject unless is_int($content['amount']) or a string matching /^\d+$/ (400 on floats/fractional/exponential strings), then cast.

    BUG-2 — HTTP status derived from exception message text (str_ends_with(..., 'not found')) (Medium/Low)¶

    • Location: src/Wallet/Controller/Manage/TransferController.php:69 (createAction) and :110 (depositAction)
    • Description: $status = str_ends_with($e->getMessage(), 'not found') ? 404 : 500; — the 404-vs-500 decision is made by sniffing the exception message. Any RuntimeException whose message happens to end in not found is reported as a 404 client error, even a genuine server fault (e.g. a DBAL/SQL message ending in ... not found, or a message built from untrusted input).
    • Impact: server-side failures are masked as 404s (misleading to clients, logs, and monitoring; 4xx responses are generally not retried), and the mapping cannot distinguish a real "wallet not found" from any other runtime failure.
    • Reproduction: service throws new \RuntimeException('Connection refused: schema not found') → the endpoint returns 404 instead of 500.
    • Proposed fix: introduce a dedicated domain exception (e.g. WalletNotFoundException) for the not-found cases in TransferService, and map 404 from the exception type; let all other RuntimeExceptions fall through to 500.

    BUG-3 — empty() treats amount = 0 as "missing", returning the wrong validation message (Low)¶

    • 位置：src/Wallet/Controller/Manage/TransferController.php:32 和 :79
    • 描述：存在检查 empty($content['amount']) 对于 0、"0" 和 false 评估为 true，因此带有 amount: 0 的请求会被 'fromWalletId, toWalletId, and amount are required'（存款：'toWalletId and amount are required'）而不是 'Amount must be positive' 拒绝。 HTTP 代码仍然是 400，但该消息具有误导性。
    • 影响：令人困惑的验证错误；对于文字值 0 来说，数量正分支（将给出准确的消息）是无法到达的。
    • 复制：POST /api/v1/manage/transfers 和 amount: 0（有效 ID）→ 正文消息表示这些字段是必填字段。
    • 建议的修复：拆分检查 - 要求存在 array_key_exists/isset（或独立检查每个 fromWalletId/toWalletId/amount）并对解析的整数应用正性检查，因此 0 到达“金额必须为正”分支。
    • 测试：testCreateActionZeroAmountShouldReportAmountNotPositive / testDepositActionZeroAmountShouldReportAmountNotPositive（跳过，断言正确的行为）。

    BUG-4 — 幂等重放返回内部不一致的 201 主体（中）¶

    • 位置：src/Wallet/Controller/Manage/TransferController.php:53-54（createAction）和:98-99（depositAction）；根本原因在 src/Wallet/Service/TransferService.php:53-57 / :169-174
    • 描述：在幂等重放时（请求携带已存在的 referenceId）TransferService 返回存储的交易，同时忽略新请求的金额。控制器从整数 amount 字段 ('amount' => $amount) 的 请求 构建响应，但从 amountFloat 和 transactionId 的 存储事务 构建响应。不同数量的重播会产生例如"amount": 99999 与 "amountFloat": 500.0 一起位于同一 201 正文中。
    • 影响：无双花（即幂等点），但任何读取响应 amount 字段的客户端/审计都会得到与返回的交易和 amountFloat 不一致的值；监督和簿记可能会被误导。
    • 复制：通过referenceId = REF-1转账，金额50000（201）；使用 amount = 99999 重播相同的 referenceId → 201 使用 data.amount = 99999 但使用 data.amountFloat = 500.0 和原始 transactionId。 （现有集成测试 testTransferApiIdempotency 重新发送相同数量，因此不会暴露差异。）
    • 建议的修复：从返回的交易（$result->transaction->getAmount() 和 $result->transaction 的钱包 ID）构建成功负载，而不是回显请求值，或者让 TransferService 显示实际应用的金额/ID。
    • 测试：testCreateActionIdempotentReplayEchoesStoredAmount（跳过，断言响应金额等于存储的交易金额）。

    BUG-5 — WalletService::reconcile() 不是原子的（低）¶

    • 地点：src/Wallet/Service/WalletService.php:124-125
    • 描述：$this->em->persist($tx); $this->em->flush(); 在每个钱包循环内运行，没有包装交易。如果钱包 n 的协调抛出（例如数据库错误、getExpectedBalance 失败），则已刷新的钱包 1..n-1 的调整仍然保留 - 仅部分应用协调。
    • 影响：协调运行失败会留下部分调整存款（由于协调是幂等的，因此可以在重新运行时恢复，但对于操作工具来说令人惊讶，它会增加 totalDeposited/预期余额，直到重新运行完成为止）。
    • 复制：两个钱包，其中第二个在 getExpectedBalance()/flush() 期间失败 → 尽管命令失败，第一个钱包的调整交易仍被提交。
    • 建议的修复：将循环包装在单个事务中（beginTransaction/commit、rollback 在 catch 中），以便协调是全有或全无，或者至少记录/发出部分状态。

    • database is locked /瞬态数据库错误是已记录的共享var/test.db问题；重试时，完整的 tests/Wallet 运行是干净的。这两个新的测试文件是纯单元测试（无数据库）。
    • 新的单元测试使用 new \ReflectionProperty(...)->setValue(...)，而不使用已弃用的 ReflectionProperty::setAccessible()（PHP 8.5 要求）；他们在 phpunit.dist.xml 下产生零弃用/通知/警告。
    • 没有更改 src/ 文件。跳过的3个测试记录了BUG-3（创建+存款）和BUG-4；套房保持绿色。
