    发现错误¶

    Bug 1 — Quantity::multiply() 包含无法访问的填充代码（低/死代码）¶

    • 文件/行： src/Inventory/Service/Quantity.php:74-75
    • 描述： if (strlen($result) <= 12) { $result = str_pad($result, 13, '0', STR_PAD_LEFT); } 永远不可能是真的。 Quantity::parts() 始终返回规范化值的数字，该值至少是 '0.000000' → 7 个字符的数字字符串。长乘累加器由 (string)$carry . $partial . str_repeat('0', $position) 构建，其中 $partial 恰好是 len(strrev(leftDigits)) = 7 字符；因此，运行结果的最终数字位置绝不会少于 14 个字符。经验验证：每个操作数对（包括全零操作数）都会产生长度 ≥ 14 的原始累加器。
    • 影响： 功能上无影响 — 死代码。它是 Quantity 中唯一未覆盖的语句（98.72%），并且无法通过公共 API 覆盖它，因为没有任何输入使防护为 true。
    • 复制： multiply() 的检测副本 - 对于 0.000000×0.000000、1×0.000001、2×3、0.5×0.25、10×0.000001 等，strlen($result) 始终 ≥ 14。
    • 建议的修复：删除第 74-75 行（第 77-81 行的分割逻辑已经正确处理最小宽度情况，正如 0.5 × 0.25 = 0.125000 测试所证明的那样）。

    Bug 2 — InventoryService::reserve() 幂等性哈希对时区敏感（中）¶

    • 文件/行： src/Inventory/Service/InventoryService.php:186-193（特别是'expiresAt' => $expiresAt?->format(DATE_ATOM)）
    • 描述：幂等性哈希嵌入了用DATE_ATOM序列化的expiresAt，它保留了原始时区偏移量。以不同偏移量表示的同一时刻（例如 2026-07-27T00:00:00+00:00 与 2026-07-27T08:00:00+08:00 — 相同的时间戳）会产生不同的哈希（已验证：032530aa… 与 47da849e…）。
    • 影响： 使用以不同偏移量编写的 expiresAt 重试相同的预留请求（超时后至少一次传递）的生产者会遇到第 205 行的 hash_equals 防护，并得到一个虚假的 InventoryReservationConflictException （“预留 ID 已与不同的请求重用”）而不是原始预留，从而破坏了语义相同重试的幂等性。同一模块中的保留/释放消息处理程序通过 ISO 字符串往返 expiresAt，因此可以从消息传递路径访问它。
    • 复制： reserve(reservationId, store, trade, order, items, new DateTimeImmutable('2026-07-27T00:00:00+00:00')) 然后使用 new DateTimeImmutable('2026-07-27T08:00:00+08:00') 重试 - 相同的瞬间，不同的哈希值。
    • 建议的修复： 在散列之前将 expiresAt 标准化为 UTC，例如$expiresAt?->setTimezone(new \DateTimeZone('UTC'))->format(DATE_ATOM)，因此哈希值与偏移量无关。

    Bug 3 — StockController 注入一个它从不使用的服务（低/死依赖）¶

    • 文件/行： src/Inventory/Controller/Manage/StockController.php:24 (protected readonly InventoryStockServiceInterface $service)
    • 说明： 构造函数属性 $service 从未被引用；每个操作都委托给 $inventory (InventoryServiceInterface) 依赖项。未使用的 InventoryStockService/InventoryStockServiceInterface 保留在 DI 中。
    • 影响： 死依赖 — 没有功能影响，但 DI 接线和接口具有误导性：读者期望 service 属性支持列表/详细信息端点，而实际上这些端点由 InventoryService::getStockView() 提供服务。
    • 建议的修复： 删除未使用的构造函数参数（及其服务连接），使 StockController 具有单个 InventoryServiceInterface 依赖项。

    Bug 4 — InventoryService::release() 在失败之前部分改变内存中的预留（低/稳健性）¶

    • 文件/行： src/Inventory/Service/InventoryService.php:277-290
    • 描述： $reservation->release()（第277行）将内存状态翻转为RELEASED并在循环抛出Reservation material was not found.（284）或Reservation stock was not found.（289）之前设置releasedAt。 wrapInTransaction回滚数据库，但受管实体保持其RELEASED内存中状态； Doctrine 不会在回滚时刷新/恢复托管实体。
    • 影响： 在故障路径中，实体将报告 released，而 DB 仍保留 confirmed，并且保留数量仍保持分配状态。如果在同一个请求/工作线程中捕获异常，并且实体管理器随后被刷新，则将提交一半应用的释放而不释放库存 - 保留数量泄漏。仅当预订/材料/库存数据已经不一致时才可访问（例如，在确认预订时删除了材料行），这就是现有绿色测试从未执行过它的原因。
    • 复制： 保留一个已确认的预订，其行引用了不存在的材料，然后调用 release() — 它在第 284 行抛出 after $reservation->release() 已经返回 true； $reservation->getStatus() 报告 released，尽管没有任何内容被保留。
    • 建议的修复： 在调用 $reservation->release() 之前预先验证所有行（材料 + 库存查找），或将失败包装在 $this->entityManager->refresh($reservation) / 重新获取中，以便实体无法保留半应用状态。
