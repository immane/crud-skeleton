    支付 ↔ 交易 + 钱包集成 — 覆盖范围和错误报告¶

    日期： 2026-08-09 工程师： PHP测试工程师（自动化） 范围： 跨模块端到端测试（支付+交易+钱包）+错误发现 约束： src/ 下没有变化 — 仅测试 + 报告。

    1. 总结¶

    添加了新的端到端集成测试文件，涵盖支付↔交易+钱包 集成（发票生命周期、网关、钱包余额调整提供商、公共 通知 webhook）。该套件通过 HTTP 堆栈针对真实的 SQLite 模式运行 （WebTestCase + DatabaseBootstrapTrait）。

    结果： 14 tests, 266 assertions — green （在多次运行中验证；仅 环境共享-var/test.db 片状，参见§5)。

    复制了四项编排结果并记录在第 4 节中（一项高影响力 bug：网关通知失败后无法重试付款）。

    4. 错误/发现¶

    4.1 BUG-001（高）— 网关通知失败后无法重试付款；订单被永久卡住¶

    • 位置： src/Trade/Service/OrderService.php:280-302 （createPayment 重用 无条件链接发票）+ src/Payment/Service/InvoiceService.php:67-70 （pay() 需要 start_pay 转换，该转换只能从 pending 启用， 参见config/packages/workflow.yaml:20-21）。
    • 描述： createPayment() 每当订单时都会重用 $order->getInvoiceId() 已经有链接的发票。如果该发票达到最终未付款状态 （failed 通过 status=failed webhook 或 cancelled），重试调用 InvoiceService::pay() 抛出 InvoiceInvalidTransitionException （“无法应用 从状态failed转换start_pay”）。不创建新发票且不重置 路径存在。
    • 影响： 网关通过notify webhook报告失败后，用户可以 不再通过正常支付端点支付订单。订单保持不变 confirmed 无限期；仅手动/数据库干预（或取消+创建新的 顺序）恢复。这也使得failed支付状态成为了交易的死胡同 整合。
    • 复制： PaymentTradeIntegrationTest::testPaymentCannotBeRetriedAfterFailedNotify — 确认订单 → 模拟支付 → 通知 status=failed → 发票 failed → 重试 付款 → 400，发票计数保持 1，订单卡住 confirmed。
    • 建议的修复： 在 OrderService::createPayment 中，当链接的发票位于 终端未付款状态 (failed/cancelled)，创建新发票（并释放/取消 旧的），或在重新尝试之前添加工作流程重置（例如 failed → pending）。 或者，显示明确的“发票需要重置”错误，而不是通用错误 无效转换。

    4.2 BUG-002（中）- paid 订单的直接发票退款退回资金但保留订单 paid¶

    • 位置： src/Trade/EventListener/OrderInvoiceListener.php:73-77 (onInvoiceRefunded 仅在 $this->workflow->can($order, 'refund') 时应用顺序 refund 转换， 仅从 completed、config/packages/workflow.yaml:87-89 启用）。
    • 描述： 直接退还已支付的发票（例如，POST /api/v1/manage/invoices/{id}/refund， 没有订单状态保护 - src/Payment/Controller/Manage/InvoiceController.php:103-124) 将资金移回，但链接订单仍保留在 paid 和 paymentStatus=refunded 中。
    • 影响： 财务/状态不一致 - 资金被退回，但订单仍在 显示为已付费。 Order::STATUS_PAID 上的按键可以执行退款/履行逻辑 在退款订单上。
    • 复制： testDirectInvoiceRefundOfPaidOrderLeavesOrderPaid — 订单支付方式 钱包网关→直接在发票上退款→订单仍然paid，paymentStatus=refunded， 用户钱包已恢复。
    • 提议的修复： 阻止与无法退款的订单关联的发票的直接退款 已退款（验证 refund()/controller 中的订单状态），或添加补偿 转换paid → refunded（有资金退回的记录），或至少 在响应中显示警告。

    4.3 BUG-003（中，设计差距）——钱包退款需要重新提供systemWalletId；发票没有记录付款地点¶

    • 地点： src/Wallet/Service/Payment/WalletGateway.php:80-83（退款内容为 来自 $options 的 systemWalletId 或注入的默认 payment.system_wallet_id， 即 0 — config/packages/payment.yaml:2)； src/Payment/Service/InvoiceService.php:253 （退款从发票中获取网关，但发票中不存储接收钱包 ID）。
    • 描述：钱包网关退款不知道拉哪个系统钱包 除非调用者在退款请求中重复systemWalletId，否则退款。随着 0的默认参数，钱包支付的订单/发票不能退款，除非 客户端再次提供systemWalletId。
    • 影响： 退款呼叫失败，并显示 400 systemWalletId is required for wallet refund. 当省略时；管理订单退款端点取决于调用者的记忆 原始付款的价值。 （注意：WalletPaymentDeduction确实保留了自己的 systemWalletId，但仅适用于扣除调整，不适用于WalletGateway付款。）
    • 复制： testWalletRefundRequiresSystemWalletIdToBeResupplied — 通过钱包支付 网关，然后通过订单退款接口退款，不带systemWalletId → 400。
    • 建议的修复： 在付款时保留发票上的接收系统钱包 ID （重用 WalletPaymentDeduction.systemWalletId 模式或发票字段），并且有 钱包网关在退款时会退回到它。

    4.4 BUG-004 (低/中) — InvoicePaidEvent 金额/货币不匹配守卫默默吞下订单付款¶

    • 位置： src/Trade/EventListener/OrderInvoiceListener.php:48-51。
    • 描述： 如果已付款发票的 amount/currency 与链接订单的不同 totalAmount/currency（例如，为同一 trade_order 手动创建发票 源数量错误），onInvoicePaid 记录 critical 行并返回。的 发票为 paid 但订单从未进展；调用者不会看到任何错误。
    • 影响： 无声分歧 — 资金被捕获，订单未支付，只有日志条目 表明问题所在。生产中很难检测到。
    • 复制： testInvoicePaidWithMismatchedAmountDoesNotAdvanceOrder — 顺序 已确认，手动发票（来源 trade_order，金额 999 ≠ 1500）通过模拟支付 → 发票paid，订单保持confirmed，paymentStatus而不是paid。
    • 建议的修复： 在不匹配路径上抛出/返回显式失败（和/或拒绝 当链接的订单总额不匹配时标记已付款的发票），而不是 默默地记录。

    5.环境注意事项¶

    • var/test.db 在这台机器上共享和外部变异（文件的 mtime 空闲时每约 2-8 秒改变一次；删除/创建运行发生碰撞）。这会产生间歇性 其他情况下的 no such table: users、database is locked 和 500 响应 正确的测试运行。项目说明文档重试次数最多3次；新套房 另外包含一个弹性引导程序（bootTestDatabase()覆盖与 删除/创建重试 + 架构验证）和重新引导的 自我修复 setUp 如果模式消失了。环境稳定时套房呈绿色 （14 tests, 266 assertions）。
    • 没有测试被标记为跳过 - 所有 14 个测试均通过并断言当前（正确或 暴露错误）行为。
