    发现错误¶

    Bug 1 — resetMarkingAction 路由占位符与操作参数不匹配 (HIGH)¶

    • 文件/行： src/Core/View/WorkflowApiViewMixin.php:104-105 
      #[Route('/{id}/status-reset', name: 'reset-status', methods: ['PUT'])]
public function resetMarkingAction($entity)
    • 说明： 路由声明占位符{id}，但操作参数名为$entity。 Symfony 的 ControllerArgumentResolver 将路由占位符解析为按名称的参数，因此 {id} 永远不能注入到 $entity 中。
    • 影响： 对 PUT /{id}/status-reset 的每个请求都会失败，并出现无法解析的控制器参数 RuntimeException (500)。端点完全损坏。此外，即使参数是可解析的，代码也会直接在注入的内容上调用 $entity->setStatus([]) — 即原始 id （字符串/整数），而不是实体，并且它永远不会从服务加载实体。第二条失败路径。
    • 复制：
    • 构建一个由WorkflowApiViewMixin和#[Route('/{id}/status-reset')]组成的控制器。 2.PUT /1/status-reset。 3.观察到：RuntimeException: Controller "...::resetMarkingAction()" requires that you provide a value for the "$entity" argument.
    • 正确行为测试： WorkflowApiViewMixinTest::testResetMarkingRoutePlaceholderMatchesActionArgument 断言每个路由占位符映射到控制器参数。它针对当前代码失败，因此被跳过（请参阅跳过的项目）。
    • 建议的修复： 
      public function resetMarkingAction(int|string $id): Response
{
    $entity = $this->service->get(['id' => $id]);
    if (!$entity) {
        return $this->warning(ApiViewMessages::ENTITY_NOT_FOUND, 404, '', 404);
    }
    $entity->setStatus([]);
    $this->container->get('doctrine')->getManager()->flush();
    return $this->success();
}
    • 注意： 该特征目前未被 src/ 中的任何控制器使用（仅 OrderController 重新实现了相同的内联端点），因此今天没有实时生产中断 - 但任何采用该特征的控制器都会继承此错误。

    Bug 2 - 工作流操作没有实体未找到防护（中）¶

    • 文件/行： src/Core/View/WorkflowApiViewMixin.php:52-58 (availableTransitionsAction)、69-94 (doTransitionAction)。
    • 描述： 两个操作都不检查 $service->get(['id' => $id]) 之后的 $entity （第 55、74 行）。缺少的实体会产生 null，它会直接传递给类型为 object $subject 的 WorkflowInterface 方法。
    • 影响：
    • availableTransitionsAction：getEnabledTransitions(null)引发未捕获的TypeError → 500而不是404。
    • doTransitionAction：TypeError被catch (\Throwable)吞没 → 200警告包含令人困惑的“必须是对象类型”消息而不是404。
    • 复制： GET/POST 具有未知 ID 的工作流程路线。
    • 证据： WorkflowApiViewMixinTest::testAvailableTransitionsActionMissingEntityThrowsTypeError 和 testDoTransitionActionMissingEntityWarnsAboutTypeError 锁定当前（错误）行为。
    • 建议的修复： 镜像 Trade/Controller/Manage/OrderController::transitionsAction()/doTransitionAction()： 
      if (!$entity) {
    return $this->warning(ApiViewMessages::ENTITY_NOT_FOUND, 404, '', 404);
}

    Bug 3 - todoAction 不会重新索引过滤后的数组（低/修饰）¶

    • 文件/行： src/Core/View/WorkflowApiViewMixin.php:37-42。
    • 描述： array_filter() 保留原始数组键。当前导（或非连续）实体没有启用的转换时，幸存数组有间隙，并且 JSON 序列化程序在 data 有效负载中发出 对象 ({"1": {...}}) 而不是 数组 ([{...}])。
    • 影响： 待办事项列表的客户端形状不一致/不正确。
    • 复制：两个实体，其中第一个实体没有启用转换 - data 变为 {"1": {...}}。
    • 建议的修复： return $this->success(array_values($entities)); （src/Trade/Controller/Manage/OrderController.php:291 处的等效 OrderController::todoAction() 已经执行此操作）。

    Bug 4 - CreateApiViewMixin::createAction 中的死分支（低）¶

    • 文件/行： src/Core/View/CreateApiViewMixin.php:92-94 ($contents = [];) 和 :148-150 (throw new ValidatorException();)。
    • 描述：
    • 每当 FixJSON::getJSONType($request->getContent()) === false 时，第 67 行已经退出。 getJSONType() 仅返回 'object'、'array' 或 false (src/Core/Utils/FixJSON.php:23-38)，因此第 92 行的 else（以及第 81 行的 $inputType 重新计算）永远不能使用 'object'/'array' 以外的值运行。
    • 第 149 行位于 $processItem 内部，仅当 $contents 为非空时才运行 — 这只发生在对象/数组输入中。因此，抛出 new ValidatorException() 的 else 也是无法访问的。
    • 影响：运行时无影响；分支无法到达，并且无法被任何测试覆盖（无论如何，第 93/149 行在覆盖范围内保持红色）。
    • 建议的修复： 删除 else { $contents = []; } 分支和 else { throw new ValidatorException(); } 分支，或进行重组，以便 $inputType 验证一次。

    Bug 5 — batchUpdateAction 的 BATCH_UPDATE_ERROR 无法访问（低）¶

    • 文件/行： src/Core/View/UpdateApiViewMixin.php:241-243。
    • 描述： batchUpdateAction() 调用 updateRecords($request) 没有 id。 updateRecords() 要么返回单次更新结果（实体或 false，从不 null），返回批处理 $response 数组，或者在第 217 行抛出非数组内容。因此它永远不会返回 null，并且 if ($response === null) { throw new ValidatorException(ApiViewMessages::BATCH_UPDATE_ERROR); } 守卫是死代码（第 242 行永远不会被覆盖）。
    • 影响： BATCH_UPDATE_ERROR 消息永远不会发出；任何真正的“空”响应都会流入 success(null)。
    • 建议的修复：删除空保护（并确认批处理路径始终返回数组），或使 updateRecords() 在真正的失败信号上返回 null。

    已验证非 bug — todoAction 的 list() 调用¶

    • 文件/行： src/Core/View/WorkflowApiViewMixin.php:33 — $service->list(null, null, false)。
    • 发现： 该任务建议如果 BaseService::list() 接受一个参数，则可能会抛出 ArgumentCountError 。 事实并非如此。 BaseServiceReadListTrait::list(mixed $object = null, mixed $order = null, bool $disableRequest = true) (src/Core/Service/Concern/BaseServiceReadListTrait.php:57-61) 和 BaseServiceInterface::list(...) 都接受 3 个参数，因此调用有效。没有错误。 （由 testTodoActionReturnsOnlyEntitiesWithEnabledTransitions 覆盖，断言 list 是通过 (null, null, false) 调用的。）

    跳过的项目¶

    • WorkflowApiViewMixinTest::testResetMarkingRoutePlaceholderMatchesActionArgument — 跳过，因为它断言正确的行为（每个路由占位符必须映射到控制器参数），并且根据当前代码（错误 1）将失败。跳过使套件保持绿色，同时记录缺陷。
