    发现错误¶

    下面的所有 src/ 错误仅记录 - 未应用任何修复。

    Bug 1 — matchesSnapshot() 将快照与顺序敏感的 === 进行比较（中等，幂等性）¶

    • 文件/行： src/Store/Service/StoreOrderService.php:180
    • 说明： $storeOrder->getOrderSnapshot() === $data['orderSnapshot'] 使用 PHP 严格的数组比较，需要相同的键顺序。规范化快照始终以一个固定顺序构建，但存储行的 order_snapshot JSON 可以合法地以不同的顺序携带键（从首先序列化 channel 的生产者或任何手动构建的顺序来回）。在这种情况下，matchesSnapshot() 返回 false，并且重新传递完全相同的交易订单事件会抛出 LogicException('Trade order snapshot conflicts with the existing Store order.')（第 85/111 行），而不是返回现有订单。
    • 影响： 对于 JSON 键顺序不同的其他相同快照，核心“创建一次，然后返回现有投影”幂等性保证失败；重复 trade.order.created.v1 事件 500 次并永远重试。
    • 复制： 持久化一个StoreOrder，其order_snapshot是['channel' => 'mini_program', 'items' => [], 'delivery' => [], 'placedAt' => '…']；使用由服务规范化的相同值（生成 ['items' => …, 'delivery' => …, 'placedAt' => …, 'channel' => …]）调用 createFromTradeOrderSnapshot()。 matchesSnapshot() 返回 false → LogicException。 （通过下面跳过的测试确认。）
    • 建议的修复： 比较顺序不敏感，例如使用 == 进行快照比较，或在 === 之前使用 ksort() 两个数组。

    Bug 2 — acceptAction() 接受空的 reservationId 并默默地清除预留（低-中，数据完整性）¶

    • 文件/行： src/Store/Controller/Staff/StoreOrderController.php:64-68 （和 src/Store/Entity/StoreOrder.php:129）
    • 描述： $reservationId = $data['reservationId'] ?? null; 只拒绝非字符串值。空字符串 '' 传递，然后 StoreOrder::accept('') 设置 $this->reservationId = '' ?? $this->reservationId → ''，覆盖先前分配的预留 ID。然后发件箱事件记录reservationId => ''。
    • 影响： 客户端可以 POST {"reservationId": ""} 并默默地擦除已接受（或等待库存）订单的预订 ID，从而产生下游消费者点击的误导性 store.order.accepted.v1 有效负载。
    • 复制： awaitInventory('r-1')，然后用正文{"reservationId": ""}接受 - getReservationId()变成''并且发件箱有效负载携带空保留。
    • 建议的修复： 将空/空白reservationId视为null（或拒绝它）：在调用accept()之前if ($reservationId !== null && trim($reservationId) === '') { $reservationId = null; }。

    Bug 3 — grantMemberAction() 吞噬 \Throwable 并将编程错误屏蔽为客户端错误（低、可观察性）¶

    • 文件/行： src/Store/Controller/Manage/StoreController.php:102-106
    • 描述： catch (\Throwable $exception) 捕获 所有 错误 - 包括 TypeError、AssertionError、PDOException - 并将它们作为 400 warning 和 $exception->getMessage() 返回。
    • 影响： 真正的服务器/编程错误隐藏在 HTTP 400 响应后面，并且原始异常消息回显给调用者（轻微信息泄漏）；失败模式与错误请求无法区分。
    • 复制：使StoreMembershipService::grant()抛出任何非InvalidArgumentException（例如数据库错误） - 控制器返回400“数据库连接丢失...”而不是500。
    • 建议的修复： 捕获授权实际上可以引发的域异常（例如 \InvalidArgumentException），并让 Error/其他异常冒泡到正常的错误处理程序。

    Bug 4 — grant() 默默地重新激活已撤销的成员资格（低，语义）¶

    • 文件/行： src/Store/Service/StoreMembershipService.php:42-43
    • 描述：当会员已经存在时，grant()总是调用$membership->setRole($role)->activate()。明确revoke()d 的成员资格将通过同一商店+用户的任何后续授权重新激活。
    • 影响： 撤销用户访问权限的管理员可以通过任何以后的授权调用（例如重播请求或自动授权）静默撤消该撤销 - 撤销不具有粘性。
    • 复制： revoke() 会员资格，然后 grant($store, $userUuid, ROLE_CLERK) — 同一行再次是 active，没有迹象表明它已被撤销。
    • 建议的修复： 如果意图是“仅授予创建/更新活动成员资格”，则跳过已撤销行的重新激活（或需要显式重新激活步骤）；否则记录并断言预期的语义。

    Bug 5 — 空的 X-Store-Channel 标头覆盖 'api' 默认值（可忽略，边缘）¶

    • 文件/行： src/Store/Service/StoreContextResolver.php:37
    • 描述： $request->headers->get('X-Store-Channel', 'api') 逐字返回标头；显式存在但为空的标头会产生通道 '' 而不是 'api'。
    • 影响： 对于此类客户端，StoreContext->channel 变为 ''，这可能会破坏下游的通道条件逻辑。
    • 复制：发送X-Store-Code: xuhui和X-Store-Channel:（空）- resolve()->channel === ''。
    • 建议的修复： 使用 $request->headers->get('X-Store-Channel') ?: 'api'。

    跳过测试¶

    一个正确行为测试被跳过，因此套件保持绿色，而 Bug 1 保留在 src/ 中：

    • StoreOrderServiceTest::testCreateFromSnapshotIsIdempotentDespiteSnapshotKeyOrder — 断言幂等性契约（具有不同 JSON 键顺序的相同快照值返回现有顺序）。对于当前的 src/ ，它会失败并显示 LogicException('Trade order snapshot conflicts…') ；已跳过并记录在 Bug 1 下。一旦 matchesSnapshot() 变得对顺序不敏感，删除 markTestSkipped 测试就会通过。

    所有其他测试都通过当前 src/ 代码。

    注释¶

    • 控制器单元测试遵循 tests/Trade/Controller/Manage/OrderControllerTest.php 模式（模拟协作者、#[AllowMockObjectsWithoutExpectations]、setRequestStack/setSerializer/setTranslator），加上带有存根 security.token_storage 的 setContainer()，以便 AbstractController::getUser() 为作用域授权路径解析真实的 User。
    • 任何地方都没有使用ReflectionProperty::setAccessible()；两种反射用法是 ReflectionProperty->setValue() （授予测试，给 Store 一个假 ID）和 ReflectionMethod->invoke() （到达受保护的控制器助手），在 PHP 8.5 上都很好。
    • 该套件以 phpunit.dist.xml (failOnDeprecation/Notice/Warning) 运行 — 未发出任何弃用/通知/警告。
