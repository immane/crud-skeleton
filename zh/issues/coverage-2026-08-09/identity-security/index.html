    可测试性说明 — RedisOtpStorage（没有可用的 redis 服务器）¶

    • RedisAdapter::createConnection($dsn) 解析为 Predis （未加载 redis/relay 扩展；php -m 仅显示 Xdebug）。 Predis 是惰性的，因此 RedisOtpStorage 构造函数永远不会抛出 - 但每个操作都会抛出 Predis\Connection\Resource\Exception\StreamInitException （“连接被拒绝”），因为此环境中不存在 redis-server 二进制文件/守护进程。
    • 使用的解决方法：在空闲的本地主机端口上作为子进程启动小型 RESP 服务器 (tests/Identity/Service/Resources/fake_redis_server.php)，并使用 redis://127.0.0.1:<port>/0 构造 RedisOtpStorage。假冒服务器准确地实现了所使用的命令（SELECT/EXISTS/GET/SETEX/DEL/TTL），并针对 err_* 键回答 -ERR，以便执行防御性 is_string/is_int 强制分支。这无需安装任何扩展即可产生真正的（集成式）覆盖范围。
    • 长期建议：通过接口/构造函数参数而不是 DSN（基于接口的 DI）注入类似 Redis 的客户端，这将使类在没有服务器的情况下可以进行单元测试，并且还可以让调用者重用共享连接。在此之前，LocalCacheOtpStorage 仍然是经过测试的后备路径。

    发现错误¶

    Bug #1 — 当商店回答错误时 RedisOtpStorage::exists() 报告 true¶

    • 文件/行： src/Identity/Service/RedisOtpStorage.php:23 — return (bool) $this->redis->exists($key);。
    • 描述： 对于 exceptions=false（由 RedisAdapter::createConnection 设置），RESP 错误回复将显示为 Predis\Response\Error 对象，而不是抛出。该对象的 (bool) 是 true，因此存储故障使 exists() 声明密钥存在。所有其他方法都会将错误强制转换为安全的“不存在”默认值（get() → false、del()/ttl() → 0），因此 exists() 是奇怪的。
    • 影响： 如果 OTP 存储在流程中失败，exists() 看起来就像代码存在 — OTP 可以被视为存在/已使用，并且有效登录被阻止，从而掩盖存储中断。严重性低（要求商店本身失败），但不一致且具有误导性。
    • 复制（已验证）：将存储指向假RESP服务器并调用exists('err_exists')（服务器回复-ERR fake failure for EXISTS）→返回true。
    • 建议的修复： 将错误强制为安全默认值，例如 
      $result = $this->redis->exists($key);
return $result === 1 || $result === true;
      （并且，为了对称，将 Predis\Response\Error 视为“不存在”）。
    • 跳过测试： RedisOtpStorageTest::testExistsReturnsFalseWhenServerErrors 断言正确的行为，并且 markTestSkipped 使套件保持绿色直至修复。

    Bug #2（死代码）- TokenManager::decodeAccessToken() 重复已经执行的黑名单检查¶

    • 文件/行： src/Identity/Security/TokenManager.php:119-122。
    • 描述： decodeAccessToken() 调用 decodeAccessTokenWithoutBlacklist()，它已经在第 183-186 行检查 isAccessTokenRevoked($jti) 并返回已撤销令牌的 null。因此，第 120-121 行的重新检查是无法到达的（黑名单在请求内是确定性的）——第 121 行永远不会执行。
    • 影响：在运行时没有影响（无害的冗余），但额外的分支是死代码，这意味着私有方法会跳过检查，但事实并非如此。它还悄悄地增加了 1 条未覆盖线路的覆盖范围。
    • 建议的修复：删除第 119-122 行（decodeAccessToken() 仅返回私有方法的结果）。

    Bug #3（死代码）- revokeAccessToken() 无法访问 $jti === null 守卫¶

    • 文件/行： src/Identity/Security/TokenManager.php:330-333。
    • 描述： decodeAccessTokenWithoutBlacklist() 要求 jti 是一个字符串（第 169 行），否则返回 null （在第 325-328 行处理）。因此$payload['jti']在这里永远不能是null并且第332行是无法到达的。
    • 影响：无（仅防御）；死枝。
    • 建议的修复： 拆除防护罩。

    Bug #4（死代码）——私钥“devfallback”密码分支永远不会触发¶

    • 文件/行： src/Identity/Security/TokenManager.php:48-51。
    • 描述： 对于 未加密 密钥，PHP 8.5 的 openssl_pkey_get_private($pem, $passphrase) 会忽略密码短语并返回密钥（根据经验验证），因此 $privateKey === false 为 false，并且会跳过第 50 行的回退。对于密码错误的真正加密密钥，密码尝试和后备（无密码）都会失败，到达第 54 行。不存在第一次调用失败但无密码重试成功的密钥状态。
    • 影响：无 - 预期的“即使配置了密码短语也允许未加密的密钥”行为已经起作用（密码短语被简单地忽略），但后备分支本身无法访问/具有误导性。
    • 建议的修复：删除第 48-51 行，或记录密码短语仅对真正加密的密钥有意义。

    无法访问的防御分支 — openssl_sign() 失败路径¶

    • 文件/行： src/Identity/Security/TokenManager.php:100-101。
    • 说明：构造函数保证私钥有效； openssl_sign() 在此环境中，使用 SHA-256 成功实现 RSA、EC 和 DSA 密钥。在不使构造函数合约无效的情况下，无法触发 $signed !== true 分支。
    • 建议： 保留纵深防御；无法在单元测试中进行测试。记录下来而不是经过强制测试。

    观察结果（不是错误）¶

    • User::setProfile()（第153-160行）不会分离先前分配的配置文件。在setProfile($a)和setProfile($b)之后，$a->getUser()仍然指向$user。如果刷新两个配置文件，则可能会违反 OneToOne user_id 唯一约束。正常流程仅设置一次配置文件，因此严重性较低； setProfile(null)/detach 步骤将使更换更加安全。 （失败的测试未涵盖 - 为修复程序记录。）
    • JwtAuthenticator::supports()（第33行）区分大小写（'Bearer '）； Authorization: bearer xyz 未被识别。许多 JWT 堆栈接受不区分大小写的方案名称；次要的。
    • TokenManager::rotateRefreshToken() 重用检测（第 249-253 行）有意仅将旋转替换令牌视为盗窃；根据设计，手动撤销（例如注销）且没有替换的令牌会产生“无效或过期”，而不是“检测到重用”。
    • RedisOtpStorage构造函数不执行I/O（Predis惰性客户端）；配置错误的 DSN 仅在第一个命令时失败，而不是在构建时失败。

    跳过测试¶

    • RedisOtpStorageTest::testExistsReturnsFalseWhenServerErrors — Bug #1 的正确行为测试（错误回复不得使 exists() 返回 true）。当前的实现失败，因此它被跳过并记录预期的行为+修复。
