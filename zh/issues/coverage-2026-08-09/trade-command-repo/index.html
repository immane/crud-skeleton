    交易模块 — 发件箱命令、存储库和实体：覆盖率约 100% 并寻找 bug (2026-08-09)¶

    发现错误¶

    Bug #1 - 有毒消息会永远重试：没有最大尝试次数上限，没有死信¶

    • 文件/行： src/Trade/Command/PublishOutboxCommand.php:36-39（不支持的主题）和:58-60（调度失败）； src/Trade/Repository/TradeOutboxMessageRepository.php:47-61 (defer())。
    • 描述： defer()仅守卫publishedAt IS NULL。它总是递增 attempts 并重新安排 availableAt = +5 minutes。没有尝试上限，也没有死信/隔离状态，因此不受支持的主题或永久失败的消息将每隔 5 分钟重新声明并重新推迟一次。
    • 影响： attempts 在行上无限增长，消息永远不会离开未发布的集合，并且每次运行都会执行浪费的声明+调度尝试。单个配置错误/拼写错误的主题会永久污染发件箱表和发布循环。
    • 复制（已验证）：插入带有 topic = 'trade.custom.topic.v1' 的行；重复运行 app:trade:outbox:publish — 每次运行都会递增 attempts (0 → 1 → 2 → …)、设置 last_error，并且该行永远不会发布或删除。对于任何调度总是抛出异常的主题来说都是如此。
    • 建议的修复： 限制尝试（例如，在 attempts < N 时仅使用 defer()，然后将该行移至死信/隔离状态或将其删除），和/或添加 status/dead_lettered 列，以便 findUnpublished() 跳过有害消息。

    Bug #2 — 成功发布不会清除以前的失败元数据¶

    • 文件/行： src/Trade/Command/PublishOutboxCommand.php:56-57 (markPublished() + flush()); src/Trade/Repository/TradeOutboxMessageRepository.php:47-61 (defer()); src/Trade/Entity/TradeOutboxMessage.php:73 (markPublished())。
    • 说明： claim()/defer() 是绕过工作单元的 DQL 批量更新； markPublished() 仅在内存中设置publishedAt。如果消息失败一次（defer → attempts=1、lastError 设置），并且稍后在重试时成功发布，则该行将使用 published_at 设置写入，但 attempts 和 last_error 仍保留之前的失败 — 不会重置它们。
    • 影响：成功交付的事件带有陈旧的、误导性的失败计数器/错误； attempts/last_error（监控、仪表板、协调）的任何使用者都会报告已交付事件的错误失败。
    • 复制（经过验证的推理，由跳过的测试覆盖）： 创建一条消息，defer() 它（attempts=1，lastError='realbus down'），然后使用工作总线运行命令 - 已发布的行仍然具有 attempts=1 和 last_error='real bus down'。
    • 建议的修复：成功发布时，清除失败状态，例如设置 published_at = now、attempts = 0、last_error = NULL 的存储库 markPublished() （或让实体 markPublished() 重置它们并保持当前基于刷新的流程）。

    Bug #3（潜在）- Envelope aggregateType 是硬编码的，而不是从实体中读取¶

    • 文件/行： src/Trade/Command/PublishOutboxCommand.php:45; src/Trade/Entity/TradeOutboxMessage.php（存储aggregate_type，但公开没有getAggregateType() getter）。
    • 描述： 该命令按字面意义发出 'aggregateType' => 'trade_order' 而不是 $message->getAggregateType()。该实体已存储该值（构造函数 arg $aggregateType）。
    • 影响： 当前没有运行时影响 — 每个交易发件箱行均记录有 aggregate_type = 'trade_order'（OrderService::createOrder 和 OrderWorkflowListener）。这是一个潜在的一致性差距：当任何生产者记录不同的聚合类型时，发布的信封仍然会声明 trade_order，从而破坏下游信封语义。
    • 复制：用'trade_order'以外的任何aggregateType记录一行；观察已发送的 TradeOrderCreatedMessage/TradeOrderCancelledMessage 信封，其中仍载有 'aggregateType' => 'trade_order'。
    • 建议的修复： 将 getAggregateType(): string 添加到 TradeOutboxMessage 并在 PublishOutboxCommand.php:45 中使用它（镜像已经公开 getAggregateType() 等的更丰富的 StoreOutboxMessage API）。

    观察结果（不是错误）¶

    • 成功发布后，该行上的 available_at 保留在 claimTime + 1 minute （永远不会重置为 published_at）。无害 — findUnpublished() 首先过滤 published_at IS NULL — 但如果有人在已发布的行上读取 available_at，则会产生轻微误导。
    • claim() 然后 dispatch() 故意是非原子的（两个查询）。他们之间发生崩溃，1 分钟后重试消息；并发工作线程无法双重发布，因为 claim() 还需要 available_at <= now，这是第一个声明所提出的。由 testClaimReturnsTrueThenPreventsDoubleClaim 验证。
    • TradeOutboxMessage 缺少其 Store 孪生拥有的几个 getter（getAggregateType、getAvailableAt、getAttempts、getLastError、isPublished）——仅 API 不对称；今天，src/Trade 中没有任何内容可以调用它们。

    跳过测试¶

    • TradeOutboxMessageRepositoryTest::testUnsupportedTopicIsEventuallyQuarantined — 断言不受支持的主题停止重试/是死信的正确行为测试。当前实现失败（错误#1：无限制重试），因此 markTestSkipped 保持套件绿色并记录预期的行为/修复。
    • TradeOutboxMessageRepositoryTest::testSuccessfulPublishClearsPreviousFailureMetadata — 断言先前失败后发布的行具有 attempts = 0 和 last_error = null 的正确行为测试。当前实现失败（Bug #2），因此 markTestSkipped 保持套件绿色并记录预期的行为/修复。
