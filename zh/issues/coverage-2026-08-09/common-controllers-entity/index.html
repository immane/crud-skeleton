    通用模块控制器和实体 - 覆盖范围和错误报告¶

    • 范围：src/Common/Controller/App/ContentController.php、src/Common/Controller/App/CommentController.php、src/Common/Entity/Content.php、src/Common/Entity/Category.php

    技术注意事项¶

    • ContentController 没有自己的控制器逻辑 - 它是一个瘦特征控制器 (use ApiView, DetailApiViewMixin, ListApiViewMixin)。它唯一自己的可执行代码是构造函数，因此只需将 HTTP 请求路由到它即可 100% 覆盖。测试命中 /api/v1/app/contents （列表）和 /api/v1/app/contents/{id} （详细信息），它们依次执行 ListApiViewMixin::listAction / DetailApiViewMixin::detailAction 特征代码。在每次读取之前，Content 行会通过测试EntityManager 保留下来。
    • CommentController 第 50 行 是 defaultCreateValues() 的匿名用户后备。它无法通过 HTTP 访问，因为 config/packages/security.yaml 阻止 IS_AUTHENTICATED_FULLY 后面的所有 /api 路由，因此必须对其进行单元测试。匿名子类覆盖 AbstractController::getUser() 和 FakeCommentService （一个实现 CommentServiceInterface 的真实类，因为 PHPUnit 12 不模拟 PHPDoc 声明的 wrapInTransaction()）运行完整的 CreateApiViewMixin::createAction() 路径。 setRequestStack()/setSerializer()/setTranslator() 的注入与现有的 MediaControllerUploadTest 完全相同。
    • Content::getTags()（第103行）/Category::getChildren()（第121行）是惰性if ($this->tags === null)分支。它们的执行方式是通过 ReflectionProperty::setValue() 不 setAccessible() （有意避免 PHP 8.5 已弃用的调用）和 newInstanceWithoutConstructor() 将属性清空。

    发现错误¶

    Bug 1 - Content::setTitle()/addTag()/removeTag()不刷新updatedAt（低）¶

    • 文件/行： src/Common/Entity/Content.php:65-70 (setTitle)、:108-120 (addTag/removeTag)。
    • 描述： 文件中的每个其他 setter（setBody() 第 77-83 行、setCategory() 第 90-95 行）在突变时调用 $this->touch()，并且兄弟通用实体中的 每个 setter — Category、Comment、Page、Setting、Tag、Media、Picture — 遵循相同的“触及每个突变”约定。 Content::setTitle() 是模块中唯一一个在不接触的情况下改变字段的 setter，标签集合改变器也不会。
    • 影响： 仅标题编辑（例如 PUT /api/v1/manage/contents/{id} 仅包含 title，或代码中的 $content->setTitle(...)）使 updatedAt 保持不变，因此依赖 updatedAt 检测更改的 API 消费者/数据库会错过突变。因此，与模块中的所有其他实体不同，updatedAt 不是 Content 的可靠更改指示符。 （现有的 ContentTest::testSettersAreFluentAndTouchUpdatesTimestamp 通过链接 setTitle(...)->setBody(...) 来掩盖这一点，因此触摸归因于 setBody。）
    • 复制： 
      $content = new Content('before');
$content->setTitle('after');
var_dump($content->getUpdatedAt()); // null — bug: setBody() would set a DateTimeImmutable
    • 正确行为测试： App\Tests\Common\Entity\ContentEntityCoverageTest::testSetTitleTouchesUpdatedAt 和 ::testAddTagTouchesUpdatedAt 断言 updatedAt 在 setTitle/addTag 之后设置；它们在当前代码中失败，因此被跳过。
    • 建议的修复： 将 $this->touch(); 添加到 setTitle()、addTag() 和 removeTag()，镜像 setBody() 和其他实体。

    Bug 2 - 应用程序评论创建接受来自不同实体范围的 parent (MEDIUM)¶

    • 文件/行： src/Common/Controller/App/CommentController.php:22 (protected array $acceptedCreateProperties = ['parent'];)，与 CreateApiViewMixin::createAction() (src/Core/View/CreateApiViewMixin.php:118-124) 结合，将 parent 直接转发到 CommentService::update()。流程中的任何位置都不会验证父级的 entityType/entityId（CommentService 是一个空的 BaseService 子类；Comment 对父级关系没有任何约束）。
    • 描述： POST /api/v1/app/comments 接受任何整数 parent id。 update() (src/Core/Service/Concern/BaseServiceMutationTrait.php:70-89) 仅通过 id 解析 ManyToOne 目标；它从不验证父评论是否与新评论共享相同的 entityType/entityId。
    • 影响： 客户端可以构建一个“回复”，其 entityType/entityId 指向内容 A，而其 parent 属于内容 B。CommentRepository::findByEntity()（驱动每个实体批准的线程列表）将在 A 的线程下呈现回复，即使其父级位于 B 下 - 无法一致遍历的孤立/跨实体线程，并且一个实体线程的审核状态会泄漏到另一个的。
    • 复制： 在 Page/1 上创建父级注释（已批准），然后使用 POST /api/v1/app/comments 和 {"entityType":"Content","entityId":99,"parent":<parentId>} → 返回 201，而不是拒绝不匹配。
    • 正确行为测试： App\Tests\Common\Controller\CommentParentScopeIntegrationTest::testReplyParentMustBelongToSameEntityScope 断言跨实体回复为 400；它根据当前代码（201）失败，因此被跳过。
    • 建议的修复：在设置 parent 和 parent.entityType !== entityType || parent.entityId !== entityId （返回 400）时拒绝 CommentController::processCreateContent() （或在服务中），镜像已由 CommentRepository::findByEntity() 强制执行的实体范围约束。

    已验证的非错误（已调查并清除）¶

    • CommentController::defaultCreateValues() 第 50 行（非 User 分支）无法通过 HTTP 访问 — security.yaml 控制 IS_AUTHENTICATED_FULLY 后面的每个 /api 路由，因此 getUser() 始终在 API 流中返回真实的 User。该分支是防御性死代码；它现在已被单元测试覆盖，但不是一个错误。
    • CommentController::commonFilter() 返回 ['author' => $this->getUser()] — 应用程序列表/详细信息端点有意将评论范围限制为当前用户。待处理评论是否应从应用程序列表中排除是产品决定；当前行为（仅限作者过滤器）与现有集成套件一致（testAppCommentPendingNotVisibleInAppList 显式断言待处理评论确实出现），因此名为 testAppCommentListOnlyReturnsApproved 的测试只是命名错误，而不是有错误。
    • Content/Category 延迟集合重新初始化和 prePersist — getTags()/getChildren() 当属性为 null 时返回新的 ArrayCollection 与存储库/列表视图使用集合的方式一致；未发现正确性问题。
