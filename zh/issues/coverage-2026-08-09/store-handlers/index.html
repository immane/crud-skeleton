    发现错误（仅报告 - 未更改来源）¶

    没有正确行为测试失败，因此不需要将任何内容标记为跳过；下面的调查结果 通过端到端地读取每个处理程序及其对应的处理程序，是否会出现鲁棒性/正确性差距 生产者（贸易）和消费者（库存）。

    Bug 1（中）- 商店发布库存预订请求 库存永远无法接受¶

    • 文件/行： src/Store/MessageHandler/TradeOrderCreatedHandler.php:132-137 (inventoryItems()) — 仅需要 is_string($item['catalogReference'] ?? null)。
    • 描述： 贸易序列化 catalogReference 为 $item->getSpecification()?->getUuid() ?? '' (src/Trade/Service/OrderService.php:128)，所以 无规范的订单项目会生成 catalogReference = ''。 Store 处理程序接受 （空字符串是字符串），构建 inventory.reservation.requested.v1 发件箱 负载，但库存消费者（src/Inventory/MessageHandler/InventoryReservationRequestedHandler.php:119-120） 要求 catalogReference 匹配 UUID 并抛出 InvalidArgumentException。
    • 影响： 预订请求是有害消息（重试 3 次，然后 failed 运输），并且商店订单永久卡在awaiting_inventory中 - 确认永远无法到达。具有任何无规格行的交易订单永远不会 INVENTORY_ENABLED=1 时由 Store 投影接受。
    • 复制： 创建一个项目没有规格的贸易订单（规格已删除 / 空）；观察 trade.order.created → 存储订单 awaiting_inventory，发件箱请求 items[0].catalogReference = ''；库存 InventoryReservationRequestedHandler 抛出 每次交付时Invalid inventory reservation request item.。
    • 建议的修复： 根据 UUID 格式验证 catalogReference （和 lineId）（和 非空）在 inventoryItems() 中，在 Store 边界处确定性失败；和/或使 Trade 为无规范的项目发出稳定的 UUID 参考，而不是 ''。

    Bug 2 (MEDIUM) — 确定性无效的 trade.order.created 有效负载变成有害消息¶

    • 文件/行： src/Store/MessageHandler/TradeOrderCreatedHandler.php:37-38（浅 信封验证），:56-61（StoreConsumedEvent在交易中持续存在）， :106-107（recordRejected() orderUuid 抛出）、:126-137（inventoryItems() 抛出）、 加上 src/Store/Service/StoreOrderService.php:84-86,110-111 （快照上的 LogicException 冲突）。
    • 描述： 只有 is_string($eventId) && is_array($payload) 被预先验证。任意 更深层次的失败（recordRejected() 中缺少 orderUuid、空/无效项、冲突 snapshot) 抛出 inside wrapInTransaction，这会回滚已经持久化的 StoreConsumedEvent。因此，该事件永远不会被标记为已消耗，并且会重试 (3×) 在failed交通工具着陆之前成功的机会。对比取消处理程序， 验证完整的信封（type/version/eventId/payload/orderUuid/storeUuid/cancelledAt/ 时间戳）在任何持久性之前。
    • 影响： 单个格式错误但结构有效的 trade.order.created 事件会阻止 该贸易订单的订单接受，需要手动failed-传输干预，并且 每次重试时重新运行整个事务（重新创建并回滚商店订单）。
    • 复制： 使用包含有效 store.uuid 的有效负载调度 trade.order.created 但每次重新投递时都没有 orderUuid 且不存在商店 → InvalidArgumentException: Trade order event does not include an order UUID.； store_consumed_event 从不包含 事件 ID。
    • 建议的修复：移动确定性结构验证（orderUuid存在，项目格式良好 当启用库存时，在交易之前存储快照形状），或消耗并记录 终端 StoreConsumedEvent 用于无效信封而不是抛出。

    Bug 3（低/中）- 存储端重复数据删除没有有效负载哈希完整性检查¶

    • 文件/行： src/Store/MessageHandler/TradeOrderCancelledHandler.php:48,53， TradeOrderCreatedHandler.php:40,51、InventoryReservationConfirmedHandler.php:42,47、 InventoryReservationRejectedHandler.php:42,47、InventoryReservationReleasedHandler.php:34,39。
    • 描述： 所有五个处理程序仅通过 eventId 进行重复数据删除 (findOneBy(['eventId' => ...])) 并默默返回。库存处理程序 (src/Inventory/MessageHandler/InventoryReservationRequestedHandler.php:181-192, InventoryReservationReleaseRequestedHandler.php:122-133) 另外比较有效负载 当 eventId 与不同的事件重用时，散列并引发 InventoryMessageIntegrityException 有效负载。
    • 影响： 如果生产者重用带有修改后的有效负载的 eventId（重新交付或 被篡改/损坏的消息），存储会默默地忽略新的有效负载而不是标记 违反诚信行为；对于同一故障，双方的行为有所不同。
    • 重现： 传递 inventory.reservation.confirmed 和 eventId E，然后传递它 再次使用 eventId E 和不同的 storeOrderUuid。商店：默默消费（订单从未 接受）。库存（在其自己的处理程序上的情况相同）：InventoryMessageIntegrityException。
    • 建议的修复： 存储 hash('sha256', json_encode($envelope)) （已经为 StoreConsumedEvent) 和 hash_equals() 进行重复数据删除，抛出完整性异常 不匹配，反映库存方面。

    Bug 4（低）- confirmedAt/rejectedAt/releasedAt 是必需的，但从未使用过¶

    • 文件/行： InventoryReservationConfirmedHandler.php:37-40， InventoryReservationRejectedHandler.php:37-40、InventoryReservationReleasedHandler.php:30-31； src/Store/Entity/StoreOrder.php:129-130。
    • 描述： 三个结果处理程序需要存在 ISO-8601 时间戳字段 （非字符串有效负载抛出）但从不解析它、验证其格式或保留它。 StoreOrder::accept()/reject() 标记 acceptedAt/rejectedAt 以及处理时间 (new \DateTimeImmutable())，而不是事件时间戳。确认 confirmedAt: 'not-a-date' 被接受并且订单无论如何都被接受。
    • 影响： 商店订单上的审核时间戳反映了商店处理结果的时间， 不在库存确认/拒绝时（延迟消息可能会休息几个小时），并且事件的 时间戳被丢弃。无效的时间戳会被静默接受。
    • 复制： InventoryReservationConfirmedHandler 接受 ['reservationId' => ..., ..., 'confirmedAt' => 'garbage'] 并标记订单已接受；的 生成的 store.order.accepted.v1 有效负载携带 acceptedAt = <now> 而不是 确认时间。
    • 建议的修复： 验证时间戳格式和/或显示它 - 例如StoreOrder::accept() 获得可选的 $acceptedAt，处理程序传递解析的事件时间戳和接受的/ 被拒绝的发件箱有效负载使用它。

    Bug 5（低）——发布确认被盲目消耗¶

    • 文件/行： src/Store/MessageHandler/InventoryReservationReleasedHandler.php:34-47。
    • 说明：释放的handler只持久化一个StoreConsumedEvent；它从不抬头 商店订单，从不验证 reservationId 是否匹配（与已确认/拒绝的订单不同） 处理程序的相关性检查），并且从不向 Trade 发布任何确认（ 商店订单已被 TradeOrderCancelledHandler 标记为取消）。
    • 影响： 未知或从未取消的预订的释放事件会被默默标记 已消耗，并且取消流程不会从 Store 端产生终端发件箱消息， 因此，Trade 没有商店方确认库存释放已完成。
    • 复制： 交付带有随机reservationId的inventory.reservation.released；的 事件被消耗（store_consumed_event行），没有商店订单验证，也没有发件箱 消息。
    • 建议的修复： 将 reservationId 与商店订单相关联（作为已确认/ 被拒绝的处理程序执行），并决定 Store 是否应该发出 store.order.cancelled.v1 （或类似的）发布完成后的确认。
