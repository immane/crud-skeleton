    发现错误¶

    下面的所有 src/ 错误仅记录 - 未应用任何修复。

    Bug 1 - defer()没有声明所有权/可用性保护（中，并发）¶

    • 文件/行： src/Store/Repository/StoreOutboxMessageRepository.php:47-61
    • 描述： DQL WHERE 仅匹配 id 和 publishedAt IS NULL。它不需要需要 availableAt <= :now，因此它不会验证调用者是否仍然拥有 claim() 设置的声明窗口。
    • 影响：在多工作人员部署中，工作人员 A 声明消息 M (availableAt = now+1m)，其调度速度很慢（>1 分钟）并随后抛出；同时，工人 B 重新声明了 M。A 的晚期 defer(M) 仍然匹配（M 未发布），因此它递增 attempts 并覆盖 availableAt，破坏 B 的声明状态。重试元数据被损坏，并且消息可能会相对于其真实所有者无序地延迟/重试。
    • 复制： 索赔 M；睡眠 61 秒；工人 B 主张 M（返回 true）；工人 A 的 dispatch 抛出； A 调用 defer(M) — 成功并覆盖 B 的 availableAt。
    • 建议的修复： 将 andWhere('message.availableAt <= :now') 添加到 defer() （镜像 claim()），或者要求调用者传递声明的 until 并对其进行匹配。

    Bug 2 — 无限制重试/无死信或最大尝试次数（中等，可操作）¶

    • 文件/行： src/Store/Repository/StoreOutboxMessageRepository.php:51 (message.attempts + 1), src/Store/Command/PublishOutboxCommand.php:53,61
    • 描述： defer() 无限期地递增attempts； findUnpublished() 永远不会过滤 attempts，并且不存在死信路径。
    • 影响： 永久失败的消息（总线永久关闭，不受支持的主题）每 5 分钟永久重试一次，并永远在 store_outbox_message 中累积行，从而增加表并在不可见的情况下进行重试。
    • 复制：插入一条包含不支持主题的消息并重复运行 app:store:outbox:publish — attempts 无限增长。
    • 建议的修复： 限制重试（例如，在最大 attempts 处停止 findUnpublished，或在 N 次尝试后将行移至死信表）并显示错误。

    Bug 3 - 脆弱的信封 type/version 推导（低，稳健性）¶

    • 文件/行： src/Store/Command/PublishOutboxCommand.php:40-41
    • 描述： 'type' => str_replace('.v1', '', $message->getTopic()) 从主题中的 任何地方 剥离 .v1（不仅仅是尾随版本），并且 'version' => 1 是硬编码的。
    • 影响：对于当前的四个 *.v1 主题是正确的，但任何未来的 .v2 主题（或域名中包含 .v1 的主题）生成的 type 仍带有后缀（例如 ...v2），而 version 仍为 1。诸如 InventoryReservationRequestedHandler 之类的消费者（验证 type === 'inventory.reservation.requested' 和 version === 1）将拒绝这样的信封，从而永远推迟消息。
    • 复制：添加主题inventory.reservation.requested.v2；生成的信封是type: 'inventory.reservation.requested.v2'，version: 1→消费者抛出Invalid ... envelope type or version。
    • 建议的修复： 仅删除尾随版本后缀（例如 preg_replace('/\.v\d+$/', '', $topic)），并从删除的后缀派生 version，而不是硬编码 1。

    Bug 4 — 发布持久性依赖于 finally 外部的单个尾随 flush()（低-中，持久性）¶

    • 文件/行： src/Store/Command/PublishOutboxCommand.php:56-64
    • 描述： markPublished() 改变托管实体，但唯一的 flush() 在循环之后运行（第 64 行），并且不受 finally 或事务保护。 claim()/defer() 是绕过工作单元的 DQL 批量更新，使加载的实体在内存中留下陈旧的 availableAt。循环中任何意外的异常 - 例如findUnpublished()、claim() 或 defer() 抛出数据库错误（这些都不在每条消息 try/catch 内） - 在 flush() 之前中止 execute()，因此较早的 markPublished() 突变会默默丢失。
    • 影响： 成功发送的消息将在下次运行时重新发送（重复发送）。消费者通过消费事件去重实现幂等，因此可以容忍重复，但设计存在重复交付和不一致的部分批次的风险（一些消息标记为在数据库中发布，另一些则没有）。
    • 复制： 模拟存储库，因此 claim() 在第一条消息成功分派后抛出第二条消息； flush() 永远不会运行，并且第一条消息不会按发布的方式保留。
    • 建议的修复： 将每个调度包装在其自己的事务中（或按消息刷新），和/或将刷新放在 finally 中；可以选择在 findUnpublished 上使用 Query::HINT_READ_ONLY，这样批量更新和 UoW 就不会出现分歧。

    Bug 5 — $id === null 默默地丢弃一条消息（可以忽略不计，实际上已失效）¶

    • 文件/行： src/Store/Command/PublishOutboxCommand.php:35
    • 说明：如果getId()返回null，则跳过该消息（continue），不延迟或重试；它永远保持未发布状态。
    • 影响： 在实践中无法访问（findUnpublished() 返回的实体始终具有数据库 ID），但分支隐藏了编程错误而不是显示它。
    • 建议的修复： 当消息没有 id 时记录或抛出而不是默默地跳过。

    跳过测试¶

    无。 为这五个文件编写的每个正确行为测试都通过了当前的 src/ 代码；没有 src 错误强制跳过。 claim()/defer()/findUnpublished() 的功能性单工作语义和命令的 happy-path/error-path 分支均已验证且绿色。

    测试说明（不是 src bug）¶

    在模拟 MessageBusInterface 时，发现 dispatch() 有一个不可为 null 的 Envelope 返回类型：使用 with() 配置但没有 willReturn* 的模拟返回 null，PHP 引擎将其转换为模拟调用内部的 TypeError - 命令的 catch (\Throwable) 然后将其视为调度失败并推迟。这是标准的 PHPUnit/默认值行为，不是命令中的缺陷；测试必须从调度存根返回一个真实的 Envelope （添加的命令 test 会这样做）。
