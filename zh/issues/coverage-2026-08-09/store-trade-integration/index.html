    商店 ↔ 交易 ↔ 库存 — 跨模块 E2E 集成覆盖率和错误报告¶

    • 日期：2026-08-09
    • 范围：完整的跨模块消息路径贸易→商店→贸易和贸易→商店→库存→商店→贸易（收件箱/发件箱/Messenger），通过真正的HTTP API +真正的发件箱发布命令驱动。
    • 遵守约束：src/ 下没有任何内容被修改 — 仅 tests/ 下的新测试文件加上此报告。
    • 跑步者：XDEBUG_MODE=off /opt/homebrew/opt/php@8.5/bin/php vendor/bin/phpunit <files> --no-coverage。

    添加测试文件（3 个文件，11 个测试：10 个通过 + 1 个记录跳过）¶

    全部位于tests/Integration/、命名空间App\Tests\Integration、declare(strict_types=1);下。

    文件 亲切 封面
    tests/Integration/StoreTradeFlowTestCase.php 抽象基础（扩展IntegrationWebTestCase，使用DatabaseBootstrapTrait） 共享表清理、同步 MessageBus 帮助程序将每个 Store/Trade/Inventory 集成消息路由到真实注册的处理程序，以及针对真实 SQLite DB 在 CommandTester 上构建的真实 app:trade:outbox:publish / app:store:outbox:publish / app:inventory:outbox:publish 运行程序。
    tests/Integration/StoreTradeFlowTest.php StoreTradeFlowTest（禁用库存，默认）— 8 次测试 完整交易→存储接受 (202 → awaiting_store_acceptance → StoreOrder accepted → store_accepted → confirmed)、通过真实员工 HTTP 端点存储拒绝、存储变得不可用、未知存储代码 400、收件箱重复数据删除、跨 eventId 幂等性、取消逻辑删除、无序逻辑删除流程。
    tests/Integration/StoreTradeInventoryEnabledFlowTest.php StoreTradeInventoryEnabledFlowTest (INVENTORY_ENABLED=1) — 2 次测试 + 1 次跳过 完整的预订接受→取消时释放链（请求→确认→接受→取消→释放请求→释放→库存恢复）并将预订拒绝传播到store_rejected。另外还跳过了针对保留前释放间隙的正确行为测试。

    INVENTORY_ENABLED 切换（根据任务记录）¶

    StoreTradeInventoryEnabledFlowTest::setUpBeforeClass() 设置 在任何内核启动之前：

    $_ENV['INVENTORY_ENABLED'] = '1';
$_SERVER['INVENTORY_ENABLED'] = '1';
putenv('INVENTORY_ENABLED=1');

    src/Store/MessageHandler/TradeOrderCreatedHandler.php:28 通过读取切换 #[Autowire('%env(bool:INVENTORY_ENABLED)%')]，Symfony 在运行时解析 来自 $_ENV / $_SERVER / getenv()。因为IntegrationWebTestCase::createKernel() 使用 APP_DEBUG=true 启动（无编译容器缓存）并且每个测试调用 ensureKernelShutdown()，类中的每个内核启动都会看到INVENTORY_ENABLED=1 并且处理程序请求预订而不是自动接受。切换 在整个 PHPUnit 进程中持续存在，因此该文件必须单独运行 (phpunit tests/Integration/StoreTradeFlowTest.php tests/Integration/StoreTradeInventoryEnabledFlowTest.php) 并在课堂上记录下来。这两个文件在一次调用中运行，因此 共享 var/test.db 仅引导一次（DatabaseBootstrapTrait 静态标志）。

    E2E 线束的作用¶

    实际执行生产中继：

    1. 带有可信 X-Store-Code 标头的 HTTP POST /api/v1/app/orders → 202，交易订单位于 awaiting_store_acceptance 中，trade.order.created.v1 位于交易发件箱中。
    2. app:trade:outbox:publish针对真实数据库运行；它的 MessageBusInterface 是一个同步 MessageBus([HandleMessageMiddleware(HandlersLocator([...]))])，将每个消息类映射到 真实 注册的处理程序。因此，claim/publish/markPublished/flush 代码路径和处理程序都会执行。
    3. app:store:outbox:publish / app:inventory:outbox:publish 同样，按照实际中继使用的顺序。
    4. 每一步都会断言存储/交易状态。

    同步总线映射：TradeOrderCreatedMessage|TradeOrderCancelledMessage → Store\MessageHandler\*、StoreOrderAcceptedMessage|StoreOrderRejectedMessage → Trade\MessageHandler\*、InventoryReservationRequestedMessage|InventoryReservationReleaseRequestedMessage → Inventory\MessageHandler\*、InventoryReservationConfirmedMessage|InventoryReservationRejectedMessage|InventoryReservationReleasedMessage → Store\MessageHandler\*。

    每个测试练习什么（快乐+糟糕的路径）¶

    StoreTradeFlowTest（禁用库存）

    1. testFullTradeToStoreAcceptanceThroughHttpAndOutboxCommands — 202 → awaiting_store_acceptance → trade.order.created.v1 发件箱 → app:trade:outbox:publish（同步总线，输出“已发布 1”）→ StoreOrder accepted + store.order.accepted.v1 发件箱 → app:store:outbox:publish → 交易 store_accepted → 幂等第二次发布（“已发布 0”）→ HTTP confirm → confirmed。
    2. testStoreRejectionLeavesTradeOrderInStoreRejectedUntilExplicitCancel — 真实员工POST /store/stores/{uuid}/orders/{uuid}/reject（具有会员资格）→ store.order.rejected.v1发件箱→发布→交易订单store_rejected（参见错误1）→显式HTTP cancel→cancelled。
    3. testStoreBecomingUnavailableAfterPlacementRejectsTheOrder — 商店处于活动状态时下订单，交易发件箱转发之前商店暂停 → 商店处理程序发出 store.order.rejected.v1 (STORE_UNAVAILABLE) → 发布 → 交易 store_rejected。
    4. testUnknownStoreCodeReturnsBadRequestAndCreatesNoOrder — 未知 X-Store-Code → HTTP 400，没有交易发件箱，没有商店订单。
    5. testDuplicateEventDeliveryIsDeduplicatedByInbox — 同一事件两次发送到 TradeOrderCreatedHandler → 一个 StoreOrder、一个 store.order.accepted.v1 发件箱、一个 store_consumed_event 行。
    6. testStoreOrderAlreadyProcessedIsIdempotentAcrossEventIds — 两个 eventId 下相同的负载 → createFromTradeOrderSnapshot 幂等性保持 → 一个 StoreOrder，一个接受的发件箱。
    7. testCancellationForUnknownStoreOrderPersistsTombstoneAndIsIdempotent — 取消从未创建的商店订单 → store_trade_order_cancellation 墓碑持续存在，忽略重复交付，无商店订单。
    8. testOutOfOrderCancellationTombstoneIsHonoredWhenOrderCreatedLater — 在交易创建事件到达 Store 之前 HTTP 取消；首先发送的已取消消息（无序）→ 墓碑；然后 app:trade:outbox:publish → StoreOrder 创建为 cancelled，没有预订，没有发件箱。

    StoreTradeInventoryEnabledFlowTest (INVENTORY_ENABLED=1)

    1. testInventoryReservationAcceptAndReleaseOnTradeCancellation — 全链：202 → 交易发布 → StoreOrder awaiting_inventory + inventory.reservation.requested.v1 → 商店发布 → 预订 confirmed、库存 10 → 8 available、inventory.reservation.confirmed.v1 → 库存发布 → StoreOrder accepted + store.order.accepted.v1 → 商店发布 → 交易 store_accepted → HTTP 取消 → cancelled + trade.order.cancelled.v1 → 交易发布 → StoreOrder cancelled + inventory.reservation.release.requested.v1→商店发布→预订released，库存恢复到10 available，inventory.reservation.released.v1→库存发布。
    2. testReservationRejectionPropagatesToTradeStoreRejected — 没有符合规格的配方/材料 → 预订被拒绝 SPECIFICATION_NOT_STOCKABLE → StoreOrder rejected → store.order.rejected.v1 → 贸易 store_rejected。

    发现错误（仅记录 - 未更改源）¶

    Bug 1（中）——商店拒绝不会取消交易订单；它停在store_rejected¶

    • 文件/行： src/Trade/MessageHandler/StoreOrderRejectedHandler.php:37-41（仅适用于store_reject）；状态机config/packages/workflow.yaml（store_rejected是一个非终端的地方，cancel从中它是一个用户操作）。
    • 描述：商店拒绝后，StoreOrderRejectedHandler应用store_reject并停止。交易订单变为 store_rejected，不是 cancelled。因此，任务的预期最终状态“存储拒绝 → 交易订单取消”不成立：订单位于 store_rejected 中，直到用户显式调用 POST /app/orders/{id}/cancel。没有任何自动取消、没有超时、没有补偿。
    • 影响： 被拒绝的订单在报告/状态列表中保持“开放”状态，并且仍然可以通过通用 /do/{transition} （工作流程允许 cancel）进行更改，并且 store_rejected 订单永远不会自行达到最终 cancelled 状态。跨模块补偿是不对称的：存储端拒绝是终结的，交易端不是。
    • 复制： StoreTradeFlowTest::testStoreRejectionLeavesTradeOrderInStoreRejectedUntilExplicitCancel — 在中继拒绝后断言 store_rejected，然后显示需要显式取消才能到达 cancelled。
    • 建议的修复：让 StoreOrderRejectedHandler 应用 store_reject **和 ** cancel （或使工作流程的 store_reject 转换直接进入 cancelled），以便商店拒绝将交易订单置于最终状态，或明确将 store_rejected 记录为预期的最终状态。

    Bug 2（中，已记录的 TODO）——release-before-reserve 是一条有害消息¶

    • 文件/行： src/Inventory/MessageHandler/InventoryReservationReleaseRequestedHandler.php:39-42（findOneByReservationId→null→抛出InvalidArgumentException('Reservation was not found.')）。
    • 描述： 如果在 inventory.reservation.requested 仍在飞行中时转发交易取消，则商店 TradeOrderCancelledHandler 会记​​录尚不存在的预订的 inventory.reservation.release.requested.v1。 Inventory 释放处理程序抛出异常，因此消息会重试 3 次，然后到达 failed 传输中（只有在处理预订请求后发生重试时，消息才会自我修复 — 使用默认重试策略无法保证）。
    • 影响： 取消路径可能会产生失败消息，更重要的是，一旦稍后创建预订，释放就永远不会完成，从而无限期地保留库存。
    • 复制： StoreTradeInventoryEnabledFlowTest::testReleaseBeforeReserveIsHandledGracefully — 跳过，因为它断言正确的行为（在预留请求之前分派释放请求；期望不会抛出且不会创建预留）。针对当前 src 失败。 docs/ai/context.md §22.1 已将“保留前释放处理”列为尚未实现。
    • 建议的修复： 将丢失的预订视为无序事件（无操作+消耗事件记录，或墓碑）而不是抛出，因此一旦预订到达，释放自然是幂等的。

    Bug 3（低，先前记录） - StoreOrder 快照幂等性对键顺序敏感¶

    • 文件/行： src/Store/Service/StoreOrderService.php:180 （matchesSnapshot 在 order_snapshot JSON 数组上使用 ===）。
    • 描述： E2E跨eventId幂等性测试（testStoreOrderAlreadyProcessedIsIdempotentAcrossEventIds）通过，因为中继的负载是字节相同的。但是，重新传递的 trade.order.created 其 JSON 键顺序不同（例如不同的生产者序列化）将被视为快照冲突 → LogicException → 有害消息。已记录在 docs/issues/coverage-2026-08-09/store-command-repo-entity.md 中并在 tests/Store/Service/StoreOrderServiceTest.php::testCreateFromSnapshotIsIdempotentDespiteSnapshotKeyOrder 中跳过。
    • 建议的修复： 将快照与规范的、对键顺序不敏感的规范化（例如 ksort 递归地）或哈希进行比较。

    跳过测试¶

    • App\Tests\Integration\StoreTradeInventoryEnabledFlowTest::testReleaseBeforeReserveIsHandledGracefully — 断言正确的行为（在其保留之前到达的释放请求不得抛出）。针对当前 src 失败（错误 2）。跳过以保持套件绿色；该差距已记录为 TODO (context.md §22.1)。

    观察结果（不是错误）¶

    • InventoryOutboxMessage API 不对称性： 与 StoreOutboxMessage / TradeOutboxMessage 不同，库存发件箱实体仅公开 getId()/getEventId()/isPublished()/markPublished()/recordAttempt() — 不公开 getTopic()/getPayload()。测试必须使用返回数组的 findUnpublishedForPublishing()。化妆品;今天 src/ 中没有任何内容读取这些吸气剂。
    • 真正的存储/贸易发布命令仅在总线同步时才驱动处理程序完成。在生产中，消息通过 config/packages/messenger.yaml 路由到 async（Doctrine）传输，因此命令将它们标记为已发布，同时单独的 worker 使用它们 - E2E 同步总线工具是测试时的等效项，并执行完全相同的命令 + 处理程序代码。
