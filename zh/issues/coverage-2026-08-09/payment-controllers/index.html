    3. 发现错误（未更改源代码）¶

    BUG-1 — 异常消息泄露给 API 客户端（高）¶

    • 位置：src/Payment/Controller/Manage/InvoiceController.php:67,83,99,122 和 src/Payment/Controller/App/InvoiceController.php:50
    • 描述：每个 catch (\Throwable $e) 在 HTTP 400 正文 (return $this->warning($e->getMessage(), 400, '', 400);) 中逐字返回 $e->getMessage()。内部异常（Doctrine/SQL 故障、网关内部、意外的运行时错误）会向最终用户显示，而不是通用消息。
    • 影响：信息披露；内部/文件路径/SQL 文本泄漏；与 Webhook 控制器不一致，它故意将非验证错误屏蔽为 FAIL。
    • 复制：发布触发任何 \Throwable（例如未注册网关）的发票支付/取消/退款，并观察 400 响应正文中的原始异常文本。
    • 建议的修复：捕获域异常（例如 InvoiceInvalidTransitionException、InvoiceAmountMismatchException、InvalidArgumentException）并将它们映射到其消息，但将意外的 \Throwable 包装在通用 warning 消息中（可以选择记录原始消息）。

    BUG-2 — markPaid 未验证通知网关/付款与发票是否匹配（中）¶

    • 位置：src/Payment/Service/InvoiceService.php:182 ($invoice->setPayment($result->payment);)； :153 的查找仅由 outTradeNo 进行。
    • 描述：markPaid 验证金额和货币，但从不检查 $result->payment 是否等于发票上记录的付款方式（在 pay() 期间设置）。任何具有匹配金额+货币的通知结果都会将发票转换为已付款状态，并以静默方式覆盖 payment 字段。
    • 影响：纵深防御缺口——路由到错误网关的通知，或者带有错误 payment 的直接服务调用将被接受，并可能重写记录的支付方式；然后下游逻辑（退款路由、报告）使用错误的网关。
    • 复制：pay() 通过 mock 获取发票，然后使用 payment: 'wechat' 和正确的金额/货币调用 handleNotifyResult()/markPaid()；发票变为 paid 和 payment = wechat。
    • 建议的修复：在markPaid中，在应用转换之前需要$result->payment === $invoice->getPayment()（或预期的网关）；否则抛出 InvoiceAmountMismatchException/InvoiceInvalidTransitionException。

    BUG-3 — 退款将原始请求正文作为网关 $options 转发（中/低）¶

    • 位置：src/Payment/Controller/Manage/InvoiceController.php:118（... $content 作为选项）→ src/Payment/Service/InvoiceService.php:264 ($gateway->refund(..., $options))。
    • 描述：完整的请求正文作为 $options 传递到网关退款调用。客户端可以在正文中包含提供者选项，例如 refundId； MockGateway 直接使用 $options['refundId'] 作为幂等键，因此调用者可以覆盖提供者退款引用。
    • 影响：不受信任的输入到达网关选项；退款幂等性密钥由攻击者控制（对 MockGateway 的影响较小，对于尊重选项密钥的真实网关来说是潜在的）。
    • 复制：POST /api/v1/manage/invoices/{id}/refund 和 {"amount": 100, "reason": "x", "refundId": "spoofed-id"} — 存储的 extraData 和返回的 refundId 变成 spoofed-id。
    • 建议的修复：将转发到InvoiceService::refund()（和pay()）中网关的选项列入白名单，或在转发之前剥离仅正文键（amount、reason）。

    BUG-4 — parseAmount 错误解析非十进制字符串数量（低）¶

    • 地点：src/Payment/Controller/Manage/InvoiceController.php:137-142
    • 描述：parseAmount通过str_contains($amount, '.')决定小数还是整数。诸如 "1e3" 之类的科学记数法字符串不包含 '.'，而是直接转换：(int) "1e3" → 1（默默地将 1000 截断为 1 分）。 "1E2"、"0.5e2" 等字​​符串或本地化分隔符的行为异常。
    • 影响：客户端发送有效的 JSON 字符串 "1e3" 作为 amount 创建 1 美分而不是 1000 美分的发票；金额是默默地错误的。
    • 复制：POST /api/v1/manage/invoices 与"amount": "1e3" → 发票amount = 1。
    • 建议的修复：仅当值还不是整数字符串 ((string)(int)$v === $v) 时才将字符串视为小数，或将解析委托给严格的十进制解析器（例如，通过 is_numeric + 正则表达式进行 MoneyParser / decimal 比较）。

    BUG-5 — Webhook 将暂时性故障掩盖为永久性 FAIL 400（低）¶

    • 地点：src/Payment/Controller/Webhook/PaymentNotifyController.php:33-34
    • 描述：通用 \Throwable catch 返回带有正文 FAIL 的 HTTP 400。这涵盖了瞬时条件（未找到发票，因为 Webhook 在发票持久化之前到达 - 可重试的条件）和永久条件（未知网关名称）。
    • 影响：支付提供商通常会在 4xx 后停止重试。无序到达的网关 Webhook（在创建/支付事务提交之前）将被永久删除，从而永远留下发票 paying。
    • 复制：具有有效秘密的 POST /api/payment/notify/mock 和尚不存在的 outTradeNo → 400 FAIL（未找到发票），与永久配置错误无法区分。
    • 建议的修复：针对未找到发票等暂时情况返回重试友好的代码（例如带有 FAIL 正文的 HTTP 200，或 5xx），并为验证/永久失败保留 4xx。通过异常类型来区分。

    4. 注释¶

    • 覆盖运行期间遇到的 database is locked 错误是已记录的共享 var/test.db 问题；等待 10-15 秒后重试会产生干净的 OK (76 tests, 341 assertions) 运行。
    • webhook/App/Manage 控制器测试是纯单元测试（无数据库）；预先存在的 tests/Payment/Integration/* DB 测试保持不变并继续通过。
    • 没有更改src/文件；没有跳过任何测试。
