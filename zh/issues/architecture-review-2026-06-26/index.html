    架构审查问题 - 2026-06-26¶

    本文档记录了在审查 docs/ai/context.md 和当前代码库期间发现的架构和生产就绪性问题。

    总结¶

    整体模块化架构对于 Symfony API 框架来说是合理的。模块边界清晰，Core提供可重用的CRUD/API基础设施，业务模块按领域分隔，支付网关、定价计算器、工作流程和领域事件等扩展点与项目目标很好地契合。

    主要风险不是结构性故障，而是默认暴露的过于广泛的通用功能、需要收紧的生产安全边界以及围绕支付流的交易边界。

    高优先级¶

    1.微信支付网关可能未注册¶

    影响： 即使WechatPayGateway实现了PaymentGatewayInterface，payment=wechat也可能因PaymentGatewayNotFoundException而失败。

    证据：

    • PaymentGatewayRegistry仅收集标记有payment.gateway：src/Payment/Service/PaymentGatewayRegistry.php的服务。
    • config/services.yaml 将 src/Wechat/Service/Gateway/WechatPayGateway.php 从全局 App\ 服务资源中排除。
    • src/Wechat/Resources/config/services_wechat.yaml显式定义WechatPayGateway，但不添加payment.gateway标签。

    推荐：

    在 services_wechat.yaml 中添加显式标签：

    App\Wechat\Service\Gateway\WechatPayGateway:
    arguments:
        $notifyUrl: '%env(WECHAT_PAY_NOTIFY_URL)%'
    tags: ['payment.gateway']

    或者，在 PaymentGatewayInterface 的微信服务配置中添加 _instanceof 规则。

    2. /system/* 内省端点实际上是公开的¶

    影响： 实体元数据和路由结构可以在生产中公开。

    证据：

    • 系统控制器在/system下路由，例如src/Core/Controller/System/EntityController.php。
    • 配置的API防火墙仅匹配config/packages/security.yaml中的^/api。
    • access_control规则仅限制/api路径，不覆盖/system。

    推荐：

    选择以下方法之一：

    1. 将系统路由移至 /api/system 下，以便应用 API 防火墙。
    2. 为需要 ROLE_ADMIN 的 ^/system 添加显式 access_control 规则。
    3. 在生产中禁用系统路由并使其仅用于开发/测试。

    3.动态查询功能对于默认的公共API使用来说太强大了¶

    影响： 客户端可以提交原始或接近原始的查询控件，这会增加数据暴露和性能风险。

    证据：

    • @dql 从请求中读取并传递到 BaseServiceReadListTrait 中的 Doctrine 查询创建。
    • 请求参数还支持@select、@groupBy、@hints和@showDQL。
    • ListApiViewMixin 记录所有通用列表端点的这些参数。

    推荐：

    引入查询参数的能力级别：

    • 公共/应用程序端点：仅允许 page、limit、受限 @order 和安全 @filter。
    • 管理端点：可选择为管理员提供更丰富的查询功能。
    • 仅调试/开发：允许 @dql、@hints 和 @showDQL。

    另请考虑从生成的公共 OpenAPI 文档中删除这些危险参数。

    4.支付和钱包交易边界需要收紧¶

    影响： 数据库事务打开时可能会执行外部支付调用。如果没有明确的保存点支持，嵌套钱包交易可能不会按预期运行。

    证据：

    • InvoiceService::pay() 打开一个事务，然后在其中调用 $gateway->pay()。
    • WechatPayGateway::pay()执行出站微信API调用。
    • TransferService手动启动与beginTransaction()的事务。
    • Trade\Controller\Manage\OrderController 中的注释假设嵌套保存点行为，但未找到显式 Doctrine 保存点配置。

    推荐：

    独立的本地和外部支付流程：

    • 钱包网关：保持本地余额移动和发票状态更新原子性。
    • 微信等外部网关：将发票保留为paying，提交，调用提供商，然后通过回调/通知完成。
    • 如果需要嵌套事务，请显式启用并测试保存点行为。

    中优先级¶

    5.应用程序订单生命周期可能不完整¶

    影响： 应用用户可以在draft中创建订单，但付款要求订单能够从confirmed转换为paid。

    证据：

    • Order初始状态为draft。
    • 工作流程需要draft -> pending -> confirmed -> paid。
    • 应用程序付款操作检查workflow->can($order, 'pay')。
    • 未找到用于提交/确认的应用程序端点。

    推荐：

    明确预期的业务流程：

    • 如果需要管理员确认，请清楚地记录下来。
    • 如果用户需要立即付款，请直接创建订单作为confirmed，或添加应用程序提交流程，将订单移至应付状态。

    6. BaseService 将服务逻辑与请求级关注点混合在一起¶

    影响： 服务类变得更难在 HTTP 外部重用，并且更难在测试或 CLI 上下文中进行推理。

    证据：

    • BaseService 从令牌存储中捕获当前用户。
    • BaseServiceReadListTrait::list() 从当前请求中读取查询参数。
    • 查询语法、请求过滤、Doctrine、序列化和验证集中在基础服务层。

    推荐：

    随着时间的推移，将请求解析移向控制器或专用查询 DTO/查询构建器对象。让服务方法专注于显式输入和域操作。

    7. BaseService::new() 可以绕过实体构造函数¶

    影响： 具有所需构造函数不变量的实体可能会在无效状态下创建。

    证据：

    • 当实体构造函数具有必需参数时，BaseServiceMutationTrait::new() 使用newInstanceWithoutConstructor()。
    • Wallet 在其构造函数中需要 User 和货币。

    推荐：

    对具有所需不变量的实体使用专用工厂/创建方法。避免公开这些实体的通用创建端点，除非控制器安全地构造它们。

    8.分页没有最大限制¶

    影响： 客户端可能会请求非常大的 limit，从而导致大量数据库查询或大量序列化响应。

    证据：

    • RestController::pagination() 使用 max(1, request limit) 和默认的 100，但不限制上限。

    推荐：

    添加全局最大值，例如 min(200, max(1, $request->query->getInt('limit', 100)))，或使最大值可配置。

    9.内存回退过滤可能会加载太多数据¶

    影响： 如果 DQL 编译失败，该服务会在 PHP 中加载完整的结果集和筛选器，这对于大型表来说可能会很昂贵。

    证据：

    • 当过滤器编译失败或使用 @sort 时，BaseServiceReadListTrait::list() 回退到 $query->getResult()，然后回退到 array_filter()。

    推荐：

    对于生产 API 端点，当过滤器编译失败时，使用 400 Bad Request 快速失败。仅针对开发/调试或显式较小的集合保留内存中回退。

    低优先级/清理¶

    10. 通用 OpenAPI 文档公开实现控制¶

    影响： 公共 API 文档宣传内部查询控件，例如 @dql、@hints 和 @showDQL。

    推荐：

    按端点类型拆分 OpenAPI 参数文档或从通用 mixin 文档中删除危险控件。

    11. 服务接线具有重复的网关标记约定¶

    影响： src/Payment/Service/Gateway/下的支付网关由根_instanceof规则和services_payment.yaml同时标记，而微信网关是单独定义的，目前没有标记。

    推荐：

    将网关标记集中在一个一致的约定中，最好是所有导入的模块服务配置的 _instanceof PaymentGatewayInterface。
