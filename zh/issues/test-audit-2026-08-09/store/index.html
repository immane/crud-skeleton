    保留¶

    • 集成流程（关键路径）。 TradeOrderCreatedHandlerTest、InventoryReservationOutcomeHandlerTest、 TradeOrderCancelledHandlerTest、StoreScopedOrderFlowTest、StoreControllerViewIntegrationTest 保护 存储接受/拒绝、创建逻辑删除前取消、发件箱→收件箱重复数据删除和存储边界 来自 BUSINESS_INVARIANTS.md / 矩阵关键路径 #6 的授权不变量。不要删除。
    • 并发测试。 TradeOrderCreatedHandlerConcurrencyTest、TradeOrderCancelledHandlerConcurrencyTest、 InventoryReservationOutcomeConcurrencyTest 在wrapInTransaction中执行双重检查findOneBy （“支票和交易之间消耗的事件”竞赛）。根据审计摘要，并发测试是保留的。
    • 跳过错误记录测试。 StoreOrderServiceTest::testCreateFromSnapshotIsIdempotentDespiteSnapshotKeyOrder （已跳过；文档 matchesSnapshot 顺序敏感 ===，覆盖 README bug 28）。保持。
    • Repository. StoreOutboxMessageRepositoryTest 是 findUnpublished 唯一持久化绑定的覆盖范围， claim 和 defer SQL（包括 defer() 声明所有权保护间隙，覆盖 README bug 15）。保留所有 11 个。
    • Command. PublishOutboxCommandTest 涵盖完整的发布/声明/延迟/调度合同（错误 16/52/53/54）。 四个 claim 错误分支测试是不同的防护，而不是重复。保持。
    • 服务单元测试。 StoreServiceTest、StoreMembershipServiceTest、StoreContextResolverTest、 StoreOrderServiceTest 是用于验证/幂等性/授权决策的规范单元层。 StoreOrderServiceTest::testCreateFromSnapshotRethrowsUniqueConstraintWhenExistingDisappears / ...RethrowsConflictWithUniqueConstraintCause / ...ReturnsExistingAfterUniqueConstraint涵盖三个不同的 createFromTradeOrderSnapshot 中的竞赛路径（预检查与 unique-constraint-catch）——互补，而不是重复。
    • 处理“覆盖”文件。 尽管有活动名称，TradeOrderCreatedHandlerCoverageTest 和 InventoryReservationOutcomeCoverageTest 覆盖不同的保护分支：
    • 创建处理程序幂等性测试使用 不同 机制：TradeOrderCreatedHandlerTest 上的 dedups 相同 eventId （StoreConsumedEvent 查找）而 TradeOrderCreatedHandlerCoverageTest::testDuplicateCreatedEventWithDifferentEventIdIsIgnored 对相同 tradeOrderUuid 和不同 eventId 进行重复数据删除（StoreOrderService 快照幂等性）。这些 是至少一次合约的不同层，因此不是精确的重复对。
    • 确认/拒绝IsIgnoredWhen…测试（未知订单、商店不匹配、交易订单不匹配、预订 不匹配，不等待）每个都覆盖了处理程序保护子句的不同连接 InventoryReservationConfirmedHandler / InventoryReservationRejectedHandler。
    • 信封验证测试涵盖了有毒消息合约（涵盖自述文件错误 2、3、18）。
    • 控制器单元测试。 Staff/StoreOrderControllerTest 和 Manage/StoreControllerTest 断言公众 单元层的响应信封+状态码合约； 404-vs-400 分支是不同的守卫。的 反射调用的 scopedListFilter/scopedDetailFilter 测试保护存储边界授权不变式。
    • 实体测试。 StoreTest、StoreMembershipTest、StoreOrderTest、StoreOutboxMessageTest、 StoreConsumedEventTest 断言真实实体行为（状态转换、setter 上的 touch()、发件箱重试 元数据、角色验证）。它们是策略的“实体方法”单元层，不会在其他地方重复。

    合并建议¶

    1. StoreOutboxMessageLifecycleTest → StoreOutboxMessageTest. testNewMessageHasNoIdAndOccurredAtDefaultsToAvailableAt 和testConstructorAcceptsExplicitOccurredAt断言相同实体的真实构造函数行为 StoreOutboxMessageTest;竞选活动将它们分成第二个文件，纯粹是为了覆盖范围统计。将两个对折 将测试保留在 StoreOutboxMessageTest 中（并删除每个 DELETE CanDIDATES 的同义反复 id-reflection 测试）。
    2. StoreConsumedEventLifecycleTest::testNewEventHasNoIdUntilPersisted → StoreConsumedEventTest. 单 断言，同一实体；折叠到基本文件中（删除 id-reflection 同级文件）。
    3. StoreOrderServiceTest::testRejectWithoutOutboxThrows→折叠成testAcceptRequiresAnOutboxService （原因 2，中等）。两者都断言由 相同的 outboxService === null 保护模式（src/Store/Service/StoreOrderService.php:30 和 :48）。一个 表驱动的 accept/reject 对或单个保留的保护测试就足够了。
    4. StoreTradeOrderCancellationTest → 仅注释。 对 3 字段实体进行单一 getter-only 测试；墓碑 它所反映的行为被 TradeOrderCancelledHandlerTest::testTombstoneForUnknownOrderIsIdempotent 彻底运用 和TradeOrderCreatedHandlerTest::testCancellationBeforeCreationCreatesCancelledOrderWithoutReservation。保持原样 （无害）或将其三个断言折叠到取消处理程序集成测试中。
    5. 信封验证测试密度。 InventoryReservationOutcomeCoverageTest（19 个测试）加上信封 TradeOrderCancelledHandlerTest / TradeOrderCreatedHandlerCoverageTest 中的测试遵循相同的 每个处理程序抛出-InvalidArgumentException-with-message 模式。如果修剪，更喜欢表驱动 每个处理程序的数据提供者（保留有毒消息合同）而不是删除分支。

    验证步骤¶

    在对任何 DELETE 候选人采取行动之前：

    1. 运行全套套件以建立绿色基线： /opt/homebrew/opt/php@8.5/bin/php ./vendor/bin/phpunit
    2. 对于每个候选，暂时删除测试方法并重新运行 tests/Store/ 以及 “covered by”指向，确认在幸存的测试中没有断言计数/行为变化。
    3. 对于两个 HIGH-confidence 候选实体，通过 保留的构造测试（线路覆盖不是删除门；行为价值是）。
    4. 对于两个Manage/StoreControllerTest候选者，确认StoreControllerViewIntegrationTest仍然返回 201/200 用于创建/更新，证明幸福路径没有丢失。 5.删除后运行composer phpstan和composer rector:types:check；不允许 src/ 进行更改 此次审计。
