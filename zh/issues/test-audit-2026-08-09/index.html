    测试套件审核 2026-08-09 — 主要摘要¶

    日期：2026-08-09 活动：14 个并行子代理根据 docs/testing/crud-skeleton-production/ 中的质量合同（TEST_STRATEGY.md、TEST_MATRIX.md、BUSINESS_INVARIANTS.md）审核整个 PHPUnit 套件（300 个测试文件），以查找不必要/冗余的测试，这些测试是稍后删除的候选。 遵守约束：未修改 src/ 或 tests/ 文件 — 仅创建 docs/issues/test-audit-2026-08-09/ 下的报告。

    计时热点¶

    • 145 次测试 ≥ 100 ms 消耗了 51.3 秒总时间中的 35.5 秒 (69.3 %)。
    • 最慢类别：TradeApiIntegrationTest 6.4 秒、OrderWorkflowApiTest 5.5 秒、CoreOpenApiEnricherApiTest 3.1 秒、PaymentTradeIntegrationTest 2.3 秒、WalletApiRegressionTest 2.0 秒、UserApiIntegrationTest 1.9 秒。
    • 最慢的单项测试：OrderWorkflowApiTest::testTransitionsEndpointListsEnabledTransitionsPerState 1.22 s； RedisOtpStorageTest::testTtlExpiredKeyBehavesLikeMissing 1.10 s（可能是真正的Redis等待，值得确认）。

    大部分集成成本是每个测试类的内核+数据库引导。合并重复的全流程集群（请参阅交易/集成报告）是最有效的运行时节省方式。

    价值最高、风险最低的删除集群（从这里开始）¶

    这些是完全重复的集群，其中幸存的测试通过更强的断言来断言相同的行为，并且标记的测试是昂贵的（内核引导）：

    1. tests/Trade/Integration/TradeApiIntegrationTest.php（26 个测试，~6.4 s 文件） — 全流程/取消/支付/履行/退款/转换/todo 测试按 OrderWorkflowApiTest 1:1 重复（确切的状态代码 + 消息 + 未更改状态断言）。请参阅 trade-controllers-integration.md。
    2. tests/Trade/Integration/TradeRepositoryIntegrationTest.php（整个文件，4 个测试） — TradeRepoFullTest 的较弱的 assertNotEmpty() 版本。
    3. tests/Integration/CommonModulesIntegrationTest.php — CommonModulesApiRegressionTest 的重复（请参阅integration.md）。
    4. tests/Integration/CoreListenerHttpIntegrationTest.php — 信封测试的近乎空/重复（请参阅integration.md）。
    5. tests/Payment/Controller/* App + Manage + Webhook 单元测试（约 21 个测试） — HTTP 层拥有这些路由； PaymentApiIntegrationTest/PaymentTradeIntegrationTest 已经断言它们（参见 payment.md）。
    6. tests/Wallet/Service/TransferServiceTest + WalletGatewayTest 单元层 — 由持久状态集成副本复制（请参阅 wallet.md）。
    7. tests/Identity/Controller/OtpControllerTest + OtpControllerCoverageTest（13 个可运行的测试） — OtpController 是 AuthController 的 OTP 方法的隐藏复制粘贴（通过 debug:router 验证），请参阅identity.md。
    8. 跨模块的实体访问器/覆盖残留——没有逻辑的琐碎的setter/getter/流畅/恒定的往返（贸易实体中约25个，加上钱包/微信/通用/库存/身份等价物）。仅删除行为测试仍在执行的部分（验证每个模块的报告）。

    跨模块重复集群（被多个代理发现）¶

    • UserApiIntegrationTest (Identity dir) 重新测试钱包（转移负数/相同钱包/缺失字段）和具有专用模块测试的交易端点 - 移动或删除候选者 (identity.md)。
    • OrderWorkflowApiTest 是 Trade HTTP 工作流程合约的幸存所有者； TradeApiIntegrationTest、TradePaymentIntegrationTest::testAppOrderTransitionFailures、Manage/OrderControllerTest 将所有地图复制到其上。
    • PaymentAdjustmentIntegrationTest（5 项测试中的 4 项） ≈ PaymentAdjustmentMultiGatewayIntegrationTest ( payment.md)。
    • OpenApiIntegrationTest ≈ CoreOpenApiEnricherApiTest； CoreDynamicQueryApiTest 有 5 个由 CoreExceptionInterceptorApiTest/others (integration.md) 重复的测试。
    • QiniuStorageTest 缺少 SDK/配置测试 ≈ StorageServiceTest 相同抛出测试 (storage.md)。
    • PublishOutboxCommandTest（仅模拟，贸易） ≈ 真实数据库 TradeOutboxMessageRepositoryTest (trade-core.md)。
    • OrderWorkflowStateMachineTest 第 5 节时间戳测试 = OrderWorkflowListenerTest 的逐字重复 (trade-core.md)。

    绝对不能删除的内容¶

    • 所有 38 个跳过的测试 — 每个测试都记录了一个真正的 src/ bug（请参阅coverage-2026-08-09 README）；默默地删除它们会重新启用回归。
    • 货币不变测试：整数美分、幂等存款/转账、乐观锁定、回滚、对账（钱包/支付）。
    • 身份验证/安全测试：令牌轮换+重用检测、JWt 故障处理、所有者/商店/管理员边界（身份/核心/商店）。
    • 发件箱/收件箱、排序、逻辑删除和并发测试（商店/库存/贸易）——异步合约。
    • DSL 词法分析器/解析器/评估器行为测试和定价管道集成（促销）。
    • 唯一分支覆盖率，其中标记的测试是 src 行的 唯一 覆盖者（在每个报告中标记为“唯一覆盖率” - 在删除之前根据覆盖率门进行验证）。

    覆盖范围警告¶

    CI 在 src/ 上强制执行 90% 的行覆盖率（目前约为 99%）。许多覆盖率追踪测试是死亡/防御性/无法访问的分支（BaseService 防护、ExpressionDqlParser 无法访问的 EOL 分支、QiniuStorage 配置抛出、琐碎的实体构造函数）的唯一练习者。删除它们不会降低覆盖率仅当相应的 src/ 死代码也被删除时 - 这是一个 src/ 更改，因此超出了本次审核的范围。每个报告的验证部分都会说明此警告适用的情况（特别是 core-rest-utils、wechat、inventory、common）。

    后续删除工作的建议执行顺序¶

    1. 第 1 轮（零覆盖风险）： 删除完全重复的 HTTP/集成集群（TradeApiIntegrationTest 重复项、TradeRepositoryIntegrationTest、CommonModulesIntegrationTest、CoreListenerHttpIntegrationTest、支付控制器单元测试、重复回归孪生）。重新运行完整套件 + --coverage-filter src/Trade 等 → 零增量，套件绿色，快约 10–15 秒。
    2. 第 2 轮： 删除琐碎的实体访问器/流畅性/常量测试，其中行为测试仍然覆盖该行（每个模块的高行）。重新运行每个模块+全套。
    3. 第 3 轮（需要 src/ PR）： 首先删除 src/ 中记录的死分支，然后删除仅提供这些分支的覆盖率追踪测试；保持 90% 的门绿色。
    4. 第 4 轮： 应用 MERGE 建议（表驱动的重构）来减少引导程序数量 - 最大的运行时胜利是整合内核引导集成类。

    这次审计是如何进行的¶

    • 基线：使用 --log-junit 运行完整串行 PHPUnit → 2686 次测试 / 9264 次断言 / 51.3 秒；从 JUnit XML 中提取的每个测试和每个类的计时。
    • 并行 14 个子代理，每个模块集群一个，每个指示 (a) 读取 docs/testing/ 合约，(b) 读取范围内的每个测试文件，(c) 将每个测试分类为保留/删除候选（原因 1-5）/合并，(d) 为每个高置信度重复引用准确的覆盖测试，(e) 编写一份报告，以及 (f) 永远不要修改 src/ 或tests/。
    • 所有 14 份报告均按照 docs/issues/test-audit-2026-08-09/ 撰写；该套件之后没有重新运行（没有任何改变）。
