    扩展点目录¶

    系统中每个可插拔扩展点的中央目录： 自动标签、合约接口、所属模块、注册表 收集实现、具体提供者所在的位置以及谁在消费 他们。使用本文档无需 grep 即可发现或添加提供程序。

    1. 放置规则¶

    有两条规则决定扩展点及其实现所在的位置：

    1. 合约（接口+注册表）存在于拥有/使用该行为的模块中。 Payment 定义了PaymentGatewayInterface，因为它协调网关。 钱包定义了 DepositProviderInterface 因为它控制着每一个信用。 Trade 定义了 PriceCalculatorInterface，因为它运行着价格管道。
    2. 实现位于拥有副作用的模块中。 WalletGateway 存在于 Wallet 中，因为它会移动钱包余额； WechatPayGateway 住在微信里，因为它驱动 EasyWeChat； ManualDepositProvider 居住在 钱包，因为它授权钱包信用。一个实现可能存在于 与接口不同的模块，只要依赖方向是 允许（实现模块导入接口的模块）。

    使 Payment 保持通用外观的规则是契约性的：

    付款不得依赖于电子钱包（服务或实体）。钱包、微信、 和其他模块可以实现支付定义的接口。任何提供商支持 钱包积分因此实现了 Wallet 的 wallet.deposit_provider 扩展 点，而不是付款点 - 即使资金来源是付款发票。

    2. 自动标记¶

    每个扩展点都集中注册在 config/services.yaml 下 _instanceof。任何实现该接口的类——在任何模块命名空间中—— 自动接收标签。不需要每个提供商的接线：

    services:
    _instanceof:
        App\Payment\Service\PaymentGatewayInterface:
            tags: ['payment.gateway']
        App\Payment\Service\Adjustment\PaymentAdjustmentProviderInterface:
            tags: ['payment.adjustment_provider']
        App\Wallet\Service\Deposit\DepositProviderInterface:
            tags: ['wallet.deposit_provider']
        App\Wallet\Service\Withdraw\WithdrawProviderInterface:
            tags: ['wallet.withdraw_provider']
        App\Storage\Service\MediaStorageInterface:
            tags: ['media.storage']

    标签与 #[AutowireIterator('tag.name')] 一起使用。

    3.1 注册表模式¶

    注册表通过 ::getName() 索引提供者并公开类型化访问：

    final class DepositProviderRegistry
{
    /** @param iterable<DepositProviderInterface> $providers */
    public function __construct(#[AutowireIterator('wallet.deposit_provider')] iterable $providers) {}

    public function has(string $name): bool;
    public function get(string $name): DepositProviderInterface;   // throws when unknown
    public function forVoucherType(string $voucherType): ?DepositProviderInterface; // whitelist routing
}

    支持多个具体名称的提供者使用supports()进行路由；一个 本身就是一个名称的提供者从 supports() 返回其 getName()。

    4. 提供商合同¶

    4.1 优惠券支持的提供商（存款/取款）¶

    DepositProviderInterface 和 WithdrawProviderInterface 具有相同的形状：

    方法 合同
    getName() 稳定的提供商/凭证类型名称
    supports(string $type) 该提供商是否处理所请求的优惠券类型
    assertPermitted(array $options) 拥有权限规则；当不允许调用者时抛出 AccessDeniedException。没有活动的安全上下文（CLI/队列/系统）是可信的调用者并且必须通过
    authorize(Voucher, array $options) 验证支持凭证的来源是否已准备好（例如发票已支付且匹配）。存款/取款交易内部调用
    reverse(Voucher, string $reason, array $options) 已申请的凭证被冲销时的源端处理。在钱包移动交易后运行

    当安全上下文处于活动状态时，内置 manual 提供程序仅适用于管理员 并使用 authorize()/reverse() 作为无操作。域支持的提供商（例如 InvoiceDepositProvider) 在 authorize() 中编码其源检查。

    4.2 支付网关¶

    PaymentGatewayInterface 接收 显式 $amount 参数，并且不得 从发票中得出应付金额或检查调整选项。参见 docs/design/bundles/payment.md §6。

    4.3 支付调整提供商¶

    PaymentAdjustmentProviderInterface 减少网关必须处理的数量 （例如钱包余额扣除）。实现位于所属模块中，并且 仅返回通用 PaymentAdjustmentResult 数据。参见payment.md§5.3。

    5.跨模块卫士（服务装饰）¶

    并非每个跨模块规则都需要注册表。拦截现有规则的规则 服务入口点可以分层为服务装饰器：

    • App\Wallet\Service\Payment\InvoiceDepositRefundGuard decorates App\Payment\Service\InvoiceService and blocks refund() while an APPLIED invoice deposit voucher exists. The derived "deposited" state (paid invoice
    • applied voucher) unlocks automatically when the voucher is reversed.
    • Wiring in config/services.yaml: 
      App\Wallet\Service\Payment\InvoiceDepositRefundGuard:
    decorates: App\Payment\Service\InvoiceService
    arguments: ['@.inner']
App\Payment\Service\InvoiceServiceInterface: '@App\Wallet\Service\Payment\InvoiceDepositRefundGuard'
    • The explicit interface alias is required once decoration creates two candidates for the interface.

    Decoration applies to every consumer of the interface (controllers, Trade), so no call-site changes are needed.

    6. Adding a New Provider¶

    1. Decide the owner of the side-effect → that module hosts the implementation. Keep the contract in its owning module unless the behavior being added is the contract itself.
    2. Implement the interface (contract from §3). Rely on the global _instanceof tag — do not register the service manually.
    3. If a registry needs no change (it collects by tag), stop there. If the new provider owns a new permission rule or source check, put it in assertPermitted()/authorize() per the contract.
    4. Add translation keys for every user-facing message the provider can throw.
    5. Add unit tests for the provider (success + every rejection path) and an integration test that drives the real registry, plus a lifecycle test for any domain-derived guard.
    6. Verify PHPStan Level 8 and the 90% coverage gate.
