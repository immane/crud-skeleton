    支付捆绑设计¶

    基于发票的支付编排的支付模块设计。 第一个实现必须提供通用支付框架，而不是特定于提供商的 Fuiou/Huifu 代码。 Fuiou 和 Huifu 仅作为未来网关适配器经过验证的遗留架构输入而被引用。

    1.范围¶

    1.1 目标¶

    支付模块为所有支付流程提供统一的发票抽象：

    能力 目的
    发票创建 代表独立于支付提供商的应付业务单据
    网关调度 将支付/通知/退款操作路由至指定网关适配器
    付款调整 允许其他模块在网关付款之前应用预付款调整
    状态管理 强制执行合法发票状态转换
    Webhook 处理 验证提供商回调并幂等更新发票
    跨模块事件 发票支付/退款时通知贸易等业务模块

    1.2 第一阶段无目标¶

    第一阶段不得包含具体的 Fuiou/Huifu 集成代码。

    排除 原因
    Fuiou/汇付天下真实API客户端 需要提供商凭据、SDK/运行时验证和单独的认证
    提供商帐户注册 属于稍后的提供者子模块阶段
    POS设备管理 特定于提供商的操作模块，而非核心发票框架
    自动提款/结算 关注财务结算，而非首期货款催收
    分割结算/费用 需要发票付款之外的会计设计
    多发票聚合付款 第一阶段编排复杂度过高；使用一张带有调整的发票
    多种调节类型 首次调整实施仅支持特定币种的钱包余额扣除
    付款申请 对外付款审批工作流程，与收款发票分开

    1.3 旧版参考¶

    遗留的 farm-neighbor 实现提供了有用的概念：

    传统概念 保留 适应
    Invoice作为中央支付凭证 是的 现代 PHP 8 实体、整数分、字符串状态
    outTradeNo 唯一的系统交易号 是的 保留为外部付款号码
    transactionId 提供商交易 ID 是的 保持可为空，直到提供者确认为止
    scene 适用于业务场景 是的 与 sourceType/sourceId
    payment/gateway/tradeType分离 是的 保留提供者路由和报告
    extraData 用于提供者有效负载 是的 仅存储经过清理的有效负载快照
    PayStrategy pay/notify/refund 形状 是的 替换为标记的 PaymentGatewayInterface 服务
    InvoiceAdditionalService现场调度 部分 替换为 Symfony 事件
    动态 new $paymentClassName 没有 使用 DI 注册表和显式服务标签
    听者主义商业副作用 没有 使用服务方法和领域事件
    DBAL 直接插入/更新 没有 通过服务使用 Dotrine 实体
    返回 die() 或来自服务的原始响应的网关代码 没有 控制器响应者拥有 HTTP 响应

    2.2 依赖方向¶

    来自 至 允许 规则
    付款 核心 是的 BaseService、RestController、序列化器、事件
    付款 身份 是的 可选的付款人关系或当前用户查找
    付款 钱包 没有 付款定义了扩展点，但不得导入钱包服务或实体
    付款 贸易 没有 付款不得进口贸易服务或实体
    贸易 付款 是的 交易消耗 InvoiceServiceInterface 和支付事件
    钱包 付款 是的 钱包可能提供支付网关和调整提供商
    网关适配器 付款 是的 实施 PaymentGatewayInterface
    调整提供商 付款 是的 实施PaymentAdjustmentProviderInterface

    支付是一个通用的收款模块。业务模块决定如何对发票事件做出反应。 钱包余额扣除属于 Wallet 作为提供商的实现。付款仅协调一般调整。

    3.发票域模型¶

    3.1 实体合约¶

    文件：src/Payment/Entity/Invoice.php

    命名空间：App\Payment\Entity

    表：payment_invoice

    发票是应付单据的聚合根。它不属于 Trade、Wallet 或任何网关提供商所有。

    3.2 字段¶

    领域 类型 必填 描述
    id 整数 是的 内部主键
    uuid 字符串(36) 是的 公共稳定标识符
    outTradeNo 字符串（64） 是的 发送给提供商的唯一系统付款号码
    transactionId ？字符串（128） 没有 支付成功后提供商交易id
    sourceType 字符串（50） 是的 业务来源，例如trade_order
    sourceId 字符串（64） 是的 源 id，最好是源 UUID
    scene 字符串（50） 是的 业务场景，例如order、deposit、wallet_topup
    payment ？字符串（50） 没有 网关适配器名称，例如wallet、mock
    gateway ？字符串（50） 没有 提供商子网关或通道
    tradeType ？字符串（50） 没有 提供商贸易类型，例如 jsapi、h5、pos
    status 字符串（30） 是的 工作流程标记
    amount 整数 是的 应付金额（以美分为单位）
    refundedAmount 整数 是的 退款金额（以美分为单位）
    currency 字符串（10） 是的 类ISO货币代码，默认CNY
    payer ？用户 没有 可选的付款人关系
    subject ？字符串（255） 没有 提供商可见的主题/标题
    description ？字符串 没有 人类可读的详细信息
    extraData ？数组 没有 净化的提供商/业务元数据
    createdAt 日期时间不可变 是的 创建时间戳
    paidAt ?日期时间不可变 没有 付款完成时间戳
    cancelledAt ?日期时间不可变 没有 取消时间戳
    refundedAt ?日期时间不可变 没有 全额退款时间戳
    updatedAt ?日期时间不可变 没有 最后更新时间戳

    3.6 限制¶

    约束 要求
    uuid 独特
    outTradeNo 独特
    sourceType + sourceId + status 索引
    sourceType + sourceId + scene 索引
    payment + transactionId 已索引、可为空的事务 ID
    amount >= 0
    refundedAmount >= 0、<= amount

    3.7 金额合同¶

    所有发票金额必须存储为整数美分。

    Invoice::amount 必须代表应付业务总额，而不是外部网关费用金额。如果应用预付款调整，则网关费用金额计算如下：

    gatewayPayAmount = invoice.amount - sum(applied adjustments)
    方向 格式
    实体存储 积分美分
    服务DTO 积分美分
    外部API请求 接受的十进制字符串或数字，在服务/控制器中转换
    提供者有效负载 特定于提供商，在网关边界进行转换

    网关适配器负责将美分转换为提供者格式，例如元十进制字符串或分整数。

    3.8 调整域边界¶

    支付不拥有钱包扣除内部机制。付款仅拥有发票和用于减少必须由网关处理的金额的通用调整合同。

    钱包余额扣除是钱包模块关心的问题，因为它是通过钱包余额转移和冲销来实现的。钱包模块可以保留自己的推导实体，例如 WalletPaymentDeduction，以及钱包交易 ID、幂等性引用和操作元数据。

    贸易等业务模块应继续对发票事件做出反应，并且不应了解调整或扣除的内部情况。

    第一阶段实施仅支持通过电子钱包提供的调整提供商对每张发票和每种货币进行一次电子钱包余额扣除。

    调整结果合约¶

    返回到付款的应用调整必须仅公开面向付款的通用字段：

    领域 类型 必填 描述
    provider 字符串 是的 调整提供者名称，例如wallet_balance
    amount 整数 是的 申请金额（以分为单位）
    currency 字符串 是的 必须等于发票币种
    referenceId 字符串 是的 提供者幂等性参考
    payload 数组 没有 净化后的元数据可以安全地存储在发票上的额外数据

    付款不得在通用调整结果中要求钱包交易 ID 或钱包实体引用。这些详细信息属于 Wallet。

    钱包全扣¶

    当调整涵盖全部发票金额时，不应调用外部提供商网关。当唯一的调整是钱包余额扣除时，付款可以记录invoice.payment = wallet，并且可以在调整成功应用后标记已支付的发票。

    4. 发票状态机¶

    4.1 工作流程要求¶

    发票必须使用 Symfony Workflow 作为 state_machine。

    文件：config/packages/workflow.yaml

    framework:
    workflows:
        invoice:
            type: 'state_machine'
            marking_store:
                type: 'method'
                property: 'status'
            supports:
                - App\Payment\Entity\Invoice
            initial_marking: pending
            places:
                - pending
                - paying
                - paid
                - failed
                - cancelled
                - partial_refunded
                - refunded
            transitions:
                start_pay:
                    from: pending
                    to: paying
                mark_paid:
                    from: [pending, paying]
                    to: paid
                fail:
                    from: [pending, paying]
                    to: failed
                cancel:
                    from: [pending, paying, failed]
                    to: cancelled
                partial_refund:
                    from: paid
                    to: partial_refunded
                refund:
                    from: [paid, partial_refunded]
                    to: refunded

    4.2 所有权转移¶

    过渡 呼叫者 当
    start_pay InvoiceService::pay() 网关支付请求开始
    mark_paid InvoiceService::markPaid() 网关确认成功或钱包转账成功
    fail InvoiceService::markFailed() 网关确认终端故障
    cancel InvoiceService::cancel() 用户/管理员/系统取消未付发票
    partial_refund InvoiceService::refund() 退款金额小于剩余付款金额
    refund InvoiceService::refund() 退款完成全额付款

    控制器和网关适配器不得直接调用$invoice->setStatus()。

    4.3 幂等性规则¶

    活动 当前状态 行为
    重复付费通知 paid 无需重新调度业务事件即可返回成功
    cancelled 之后付费通知 cancelled 默认拒绝；未来特定于提供商的补丁流程必须是明确的
    paid 之后通知失败 paid 忽略并记录警告
    refunded后退款通知 refunded 退货成功不双重退款
    部分退款重复 partial_refunded 使用提供商退款 ID 或幂等密钥来防止重复计算

    5. 服务设计¶

    5.1 发票服务接口¶

    文件：src/Payment/Service/InvoiceServiceInterface.php

    interface InvoiceServiceInterface extends BaseServiceInterface
{
    public function createInvoice(CreateInvoiceRequest $request): Invoice;

    public function pay(Invoice $invoice, string $payment, array $options = []): PaymentResult;

    public function handleNotifyResult(PaymentNotifyResult $result): Invoice;

    public function markPaid(Invoice $invoice, PaymentNotifyResult $result): Invoice;

    public function markFailed(Invoice $invoice, PaymentNotifyResult $result): Invoice;

    5.2 发票服务职责¶

    责任 详情
    创建发票 分配 uuid、outTradeNo、源字段、金额、货币、付款人
    验证金额 拒绝负金额和无效退款金额
    应用工作流程转换 使用state_machine.invoice，切勿直接写入状态
    呼叫网关注册表 解析付款/退款的指定网关
    处理通知结果 通过 outTradeNo 或交易 ID 查找发票并安全更新
    应用调整 在网关付款请求之前应用已注册的付款调整
    计算网关支付金额 使用 invoice.amount - appliedAdjustmentAmount 作为提供商收费金额
    保留提供者快照 将清理后的通知/退款数据存储在 extraData
    调度事件 状态更改成功后发出发票域事件
    保持幂等性 将重复的终端回调视为成功的无操作

    5.3 支付调整提供商的责任¶

    文件：src/Payment/Service/Adjustment/PaymentAdjustmentProviderInterface.php

    PaymentAdjustmentProviderInterface 是模块的扩展点，可以减少所选支付网关处理的金额。支付定义了接口和编排规则。提供者实现位于所属模块中，例如钱包。

    interface PaymentAdjustmentProviderInterface
{
    public static function getName(): string;

    public function supports(Invoice $invoice, string $payment, array $options): bool;

    public function apply(PaymentAdjustmentContext $context): PaymentAdjustmentResult;

    /** @return PaymentAdjustmentResult[] */
    public function applied(Invoice $invoice): array;

    public function release(Invoice $invoice, PaymentAdjustmentResult $adjustment, string $reason): PaymentAdjustmentResult;

    public function refund(Invoice $invoice, PaymentAdjustmentResult $adjustment, string $reason): PaymentAdjustmentResult;
}
    责任 详情
    检测适用性 决定请求选项是否要求进行此调整
    验证请求 拒绝无效的金额、货币、付款人或特定于提供商的配置
    应用调整 执行提供商拥有的突变，例如钱包转账
    查询应用的调整 返回已应用的通用调整结果以进行通知/退款验证
    强制幂等性 使用稳定的提供商参考 ID，例如 invoice-adjustment-{provider}-{invoice.uuid}
    释放调整 当网关付款创建失败或未付发票被取消时，撤消已应用的调整
    退款调整 已付款发票退款时撤消已应用的调整
    隐藏内部结构 仅向付款

    第一阶段必须支持每张发票仅进行一次钱包余额调整。未来的调整类型（例如优惠券或积分）必须通过同一提供商界面添加，并且不应要求更改网关。

    InvoiceService 必须通过提供商或调整登记处获取应用的调整总额。它不得直接查询钱包扣除实体。

    5.4 付款调整流程¶

    调整后的发票付款遵循以下顺序：

    InvoiceService::pay(invoice, payment, options)
  -> PaymentAdjustmentRegistry resolves applicable providers
  -> apply each provider and collect PaymentAdjustmentResult values
  -> compute gatewayAmount = invoice.amount - appliedAdjustmentAmount
  -> if gatewayAmount == 0: mark invoice paid without calling an external gateway
  -> if gatewayAmount > 0: call gateway->pay(invoice, gatewayAmount, options)
  -> gateway returns PaymentResult
  -> provider notify later confirms gatewayAmount
  -> InvoiceService::markPaid() verifies notify amount plus applied adjustments covers invoice.amount

    如果调整成功但网关支付创建失败，InvoiceService 必须在显示错误之前调用 PaymentAdjustmentProviderInterface::release()。

    6. 网关框架¶

    6.1 网关接口¶

    文件：src/Payment/Service/PaymentGatewayInterface.php

    interface PaymentGatewayInterface
{
    public static function getName(): string;

    public function pay(Invoice $invoice, int $amount, array $options = []): PaymentResult;

    public function notify(Request $request): PaymentNotifyResult;

    public function refund(Invoice $invoice, int $amount, int $paidAmount, string $reason, array $options = []): PaymentRefundResult;

    public function getNotifySuccessResponse(PaymentNotifyResult $result): Response;
}

    网关适配器必须将显式 $amount 参数视为要处理的数量。当提供明确金额时，他们不得从 Invoice::amount 中得出应付金额，并且不得检查调整或扣除选项。

    付款方式：

    $gateway->pay($invoice, $gatewayAmount, $options);

    如需退款：

    $gateway->refund($invoice, $gatewayRefundAmount, $gatewayPaidAmount, $reason, $options);

    Invoice::amount 仍然是应付业务总额。网关支付/退款金额是在应用通用支付调整后由InvoiceService计算的。

    9.1 源映射¶

    贸易订单使用这些发票来源值：

    领域 价值
    sourceType trade_order
    sourceId Order::getUuid()首选
    scene order
    amount Order::getTotalAmount()
    currency Order::getCurrency()

    9.2 订单字段¶

    贸易 Order 应该仅存储轻量级发票参考：

    领域 类型 目的
    invoiceId ？字符串 付款发票 uuid 或 id 作为字符串
    invoiceNo ？字符串 发票outTradeNo用于显示和查找
    paymentStatus ？字符串 列表视图的缓存发票状态

    在第一阶段，交易不得要求 ORM ManyToOne 与 Payment\Entity\Invoice 关系。

    交易不得模拟或持续调整内部结构。当使用钱包余额扣除时，在 invoice.amount 被网关支付加上应用的调整完全覆盖后，付款仍会发出正常的 InvoicePaidEvent。

    9.3 付款请求流程¶

    POST /api/v1/app/orders/{id}/payment
  -> Trade OrderController validates owner and order status
  -> Trade OrderService calls InvoiceServiceInterface::createInvoice()
  -> Trade OrderService calls InvoiceServiceInterface::pay()
  -> Payment gateway returns PaymentResult
  -> response contains invoice and payment instructions

    9.4 付款确认流程¶

    Provider webhook or wallet success
  -> PaymentNotifyController
  -> Gateway::notify()
  -> InvoiceService::handleNotifyResult()
  -> invoice workflow mark_paid
  -> dispatch InvoicePaidEvent
  -> Trade listener validates source/amount/currency
  -> order workflow pay
  -> OrderService persists paidAt/paymentMethod/paymentStatus

    对于经过调整的发票，Trade 仍会验证 invoice.amount == order.totalAmount。调整是支付编排的内部调整，不应改变 Trade 的金额比较。

    9.5 退款流程¶

    POST /api/v1/manage/orders/{id}/refund
  -> Trade validates order can refund
  -> Trade calls InvoiceServiceInterface::refund()
  -> Payment gateway refunds external pay amount
  -> Payment adjustment providers refund applied adjustments when present
  -> invoice workflow partial_refund/refund
  -> dispatch InvoiceRefundedEvent
  -> Trade listener applies order refund transition when full refund is confirmed

    第一阶段钱包调整支持应该仅在存在调整时允许全额发票退款。网关支付和钱包扣除之间的部分退款分配显然超出了范围。

    文件：src/Trade/EventListener/OrderInvoiceListener.php

    T-PAY-1 忽略 sourceType 不是 trade_order 的发票

    T-PAY-3 验证发票金额等于订单总金额

    12. 交易合约¶

    12.1 服务级别事务¶

    支付突变必须在服务层进行管理。

    运营 交易边界
    创建发票 InvoiceService::createInvoice()
    应用付款调整 PaymentAdjustmentProviderInterface::apply() 使用提供商拥有的幂等性
    开始钱包支付 InvoiceService::pay()和WalletGateway接送服务
    处理网络钩子 InvoiceService::handleNotifyResult()
    退款发票 InvoiceService::refund() 当存在调整时，加上调整提供商退款

    12.1.1 调整交易规则¶

    场景 规则
    调整已应用，网关支付成功 保持调整；发票保持paying直到通知或立即支付结果
    应用调整，网关付款创建失败 返回错误之前调用提供者 release()
    钱包全扣 将发票标记为payment = wallet；不调用外部网关
    已付款发票退款 先退外部网关支付金额，再退钱包扣款
    未付发票取消 发布已应用的调整

    钱包调整传输参考 ID 必须稳定且幂等。推荐第一期参考文献：

    invoice-adjustment-wallet-balance-{invoice.uuid}
invoice-adjustment-wallet-balance-release-{invoice.uuid}
invoice-adjustment-wallet-balance-refund-{invoice.uuid}

    12.2 跨模块一致性¶

    支付和交易不应尝试分布式交易。

    相反：

    关注 机制
    发票已支付但订单更新失败 事件侦听器记录失败和重试命令可以重播发票事件
    重复的提供商回调 发票幂等性规则
    订单已付款 如果订单已支付，则交易侦听器无操作
    金额不匹配 交易侦听器拒绝转换并记录严重错误

    12.3 Webhook 锁定¶

    Webhook 处理应该使用以下幂等机制之一：

    机制 使用
    独特outTradeNo 查找发票
    提供者transactionId 防止重复提供者成功处理
    可选锁钥匙 payment_notify_{payment}_{outTradeNo}
    存储的原始事件 ID 未来特定于提供商的重复检测

    13. 错误处理¶

    13.1 例外情况¶

    例外 当
    PaymentGatewayNotFoundException 未知网关名称
    PaymentVerificationException 签名或提供商有效负载验证失败
    InvoiceInvalidTransitionException 不允许工作流程转换
    InvoiceAmountMismatchException 通知/退款金额与发票规则不符

    所有异常必须由服务或网关适配器抛出，而不是由实体抛出。

    13.2 控制器映射¶

    业务 API 控制器将异常转换为 warning() 响应。

    当验证失败时，Webhook 控制器返回与提供程序兼容的失败响应。

    14. 安全¶

    14.1 应用程序和管理 API¶

    范围 安全
    /api/v1/app/invoices* 经过身份验证的用户，范围为付款人/来源所有权
    /api/v1/manage/invoices* ROLE_ADMIN
    贸易便利端点 与现有贸易路线安全相同

    14.2 Webhook API¶

    Webhook 端点可公开访问，但必须验证提供者签名或共享密钥。

    规则：

    规则 要求
    W1 验证前切勿信任请求正文
    W2 仅记录已清理的有效负载
    W3 不要记录密钥、带有私人材料的签名、访问令牌或完整的 PII
    W4 Webhook 必须是幂等的
    W5 Webhook 响应必须遵循提供商协议

    15. 提供者适配器框架参考¶

    15.1 富欧/惠福课程¶

    旧的提供程序捆绑包表明提供程序集成可能包含多个独立的功能：

    能力 示例 第一期

    POS设备管理 实体POS终端 排除
    提款/结算 自动撤回命令 排除

    PaymentWebhookIntegrationTest Webhook 成功、签名无效、重复通知

    16.3 回归案例¶

    案例 预计
    重复付费通知 无重复订单转换
    通知金额不匹配 发票未标记为已付款；警告/失败处理记录
    退款金额超过支付金额 被拒绝
    支付取消的发票 被拒绝
    未知网关 API 400 警告、Webhook 提供程序失败响应
    调整货币错配 钱包转账前被拒绝
    调整金额超过发票金额 钱包转账前被拒绝
    钱包调整+模拟支付 模拟通知金额必须等于剩余的显式网关金额
    钱包全扣 发票支付为wallet且未调用外部网关
    调整后网关支付失败 通过供应商逆转释放调整
    调整后的发票全额退款 外部支付金额和钱包扣款双双返还

    17. 实施计划¶

    第 1 阶段：核心发票框架¶

    1. 创建Payment模块骨架。
    2. 添加Invoice实体和存储库。
    3. 添加发票工作流程配置。
    4. 添加 DTO 和例外。
    5. 添加PaymentGatewayInterface和PaymentGatewayRegistry。
    6. 添加InvoiceServiceInterface和InvoiceService。
    7. 添加MockGateway。
    8. 添加应用程序/管理发票控制器。
    9. 添加 webhook 控制器。 10.添加单元和集成测试。

    第 2 阶段：钱包网关和交易集成¶

    1. 使用TransferServiceInterface添加钱包拥有的WalletGateway。
    2. 在Trade\Entity\Order中添加轻量级发票参考字段。 3.添加贸易支付便捷端点。
    3. 为发票支付/退款事件添加OrderInvoiceListener。
    4. 将直接钱包支付路径替换为支付支持路径，或暂时保留直接路径以支持显式兼容性。 6.添加贸易支付集成测试。

    第三阶段：付款调整和钱包余额扣除¶

    1. 支付下添加PaymentAdjustmentProviderInterface、PaymentAdjustmentRegistry、PaymentAdjustmentContext、PaymentAdjustmentResult。
    2. 新增Wallet自有钱包余额调整提供商，用于发票币种第一阶段wallet_balance扣除。
    3. 让 Wallet 拥有审计、幂等性、钱包交易 ID、释放和退款撤销所需的任何钱包扣款实体/存储库。
    4. 更新InvoiceService::pay()以在网关付款之前应用已注册的调整并将显式剩余金额传递给网关。
    5. 更新InvoiceService::markPaid()以验证notify.amount == invoice.amount - appliedAdjustmentAmount。
    6. 更新InvoiceService::refund()以退还外部网关金额，并要求调整提供商退还其所应用的调整以获得全额退款。
    7. 更新网关接口和实现，以便 MockGateway、WalletGateway、WechatPayGateway 和提供商网关接收显式金额且不读取 $options['payAmount']。
    8. 更新贸易支付便利端点以接受 walletAmount 和结构化 deduction 有效负载作为钱包调整输入。 9.添加调整单元和集成测试。

    第 4 阶段：提供商适配器准备就绪¶

    1. 定义外部网关的提供商配置架构。
    2. 如果需要，添加抽象签名者/解析者客户端模式。
    3. 添加具有虚假有效负载的提供者适配器测试。
    4. 记录所需的认证/手动验证步骤。

    第五阶段：富友/汇付天下提供商¶

    此阶段有意超出第一个实施范围。

    启动后，首先仅迁移提供商支付网关职责：

    1. FuiouGateway和FuiouPosGateway。
    2. HuifuGateway和HuifuPosGateway。 3.签名验证助手。
    3. 通知负载解析器。
    4. 退款请求助手。
    5. 提供商特定的原始响应格式。

    除非明确要求，否则请勿在此阶段迁移账户注册、POS 管理或自动提款。

    18. 开放性问题¶

    问题 默认决定
    发票来源 ID 应该使用订单 ID 还是 UUID？ 使用订单 uuid 实现外部稳定
    发票应该与用户直接相关吗？ 可选 payer，加上源元数据
    Trade 是否应该持有与 Invoice 相关的 ORM？ 否，存储轻量级发票参考字段
    提供商网关是否应该直接更新订单？ 不，仅限活动
    Fuiou/Huifu 应该是独立捆绑包吗？ 不，付款
    应包括 PaymentRequisition 吗？ 不，稍后单独财务/审批模块
    钱包余额扣除是否应归Payment所有？ 不，Wallet 拥有钱包扣除内部结构并实现支付调整提供商
    首先实施哪种调整类型？ 发票货币仅限 wallet_balance
    钱包全额扣款该如何记录？ 设置invoice.payment = wallet并标记扣除后已付款的发票适用
    已扣除的发票是否可以先支持部分退款？ 不，只有全额退款，直到分配规则设计出来

    19. 验收标准¶

    支付模块设计在以下情况下实施：

    标准 要求
    发票实体 存在基于美分的金额和工作流程状态
    网关注册 按名称解析标记的网关
    模拟网关 支持确定性支付/通知/退款测试
    网络钩子 通过服务更新发票，而不是控制器逻辑
    活动 已发送发票支付/退款/取消事件
    贸易一体化 订单可通过发票事件流支付
    调整 支付支持通用调整提供商；钱包支持首期wallet_balance扣款，无需网关payAmount耦合
    测试 单元和集成测试涵盖幂等性和无效转换
    CI 覆盖率保持在或高于要求的阈值
