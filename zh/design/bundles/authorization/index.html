    授权包设计¶

    状态：第一阶段实施 - 基础 + 内容试点。 授权包 (src/Authorization/) 是 模块化整体的授权边界。身份仍然负有责任 用于身份验证和用户身份。本文件为实施合同 对于 RBAC、范围数据访问和故意限制的字段级扩展。

    1. 决策摘要¶

    1.1 决定¶

    创建一个独立的Authorization模块而不是添加授权表和 逻辑为Identity。

    Identity: authenticate a principal
Authorization:   decide what an authenticated principal may do
Store:    own store membership and operational facts
Business: own resources and enforce their data scope through Authorization

    这将身份保留为身份验证模块（用户、密码、JWT、刷新 令牌、OTP、微信登录）并防止其依赖于每个业务模块 资源和行动。

    1.2 目标¶

    • 逐步替换全局 ROLE_ADMIN-only 授权模型 格式为 module:resource:action 的权限代码。
    • 全局或在存储范围内分配角色，无需跨模块外键。
    • 将权限决策集中在 Symfony Voter 和 AuthorizationServiceInterface 中。
    • 提供可重用的范围和字段过滤挂钩，以便控制器不会重复 授权业务逻辑。
    • 保留Store\Entity\Membership作为权威的商店会员记录；商店 将成员资格检查与授权授权相结合。
    • 在迁移期间保留现有的 User.roles 和 ROLE_ADMIN 行为。
    • 在仅附加审核日志中记录授权管理更改。

    1.3 非目标¶

    第一个实现不得：

    • 替换身份验证、JWT 签名、刷新令牌轮换或身份用户 UUID 合约。
    • 将商店成员资格行移至授权或使授权成为商店角色的所有者。
    • 引入通用策略语言、Casbin、OPA 或用户编写的表达式。
    • 将每个字段转换为权限代码，例如common:content:metadata:update。
    • 将外键添加到users、store、交易、支付、钱包或其他模块 表。
    • 需要分布式交易或将经纪人交付作为先决条件 授权。

    ABAC 式的条件是未来的明确扩展。第一个版本的范围 RBAC 加上角色定义的字段允许列表。

    2.现状审计¶

    2.1 认证成熟；授权比较粗略¶

    Identity\Entity\User 保留 JSON roles 数组并始终公开 ROLE_USER。 config/packages/security.yaml 仅定义此层次结构：

    ROLE_ADMIN: [ROLE_USER]

    API防火墙通过JwtAuthenticator验证/api。 TokenManager 签署包含当前角色的 JWT，但身份验证器通过以下方式重新加载用户 JWT 主题，并且不做出资源级授权决策。

    security.yaml 目前使用 ROLE_ADMIN 保护每个 /api/v1/manage 路由。 大多数管理控制器都会使用类级别来重复此操作 #[IsGranted('ROLE_ADMIN')]。这作为粗略的平台管理员门是安全的， 但不能表达模块、操作、存储、行或字段范围。

    2.2 现有的行范围挂钩很有价值¶

    核心视图 mixin 已经传递了每个列表、详细信息、更新和删除查找 通过控制器过滤器：

    commonFilter() -> mixIdToCommonFilter() -> service.get()/list()
deletionFilter() -> service.get() -> service.remove()

    控制器将这些钩子用于所有权过滤器，例如 ['user' => $user] 和 拒绝所有哨兵 ['id' => -1]。 QueryBuilder 过滤器可用于更多用途 复杂的谓词。授权必须使用这些现有的执行点；它一定不能 绕过 BaseService 或直接从控制器查询存储库。

    2.3 商店有一个独立的、正确的域边界¶

    Store\Entity\Membership 存储本地的有效/暂停/撤销的会员资格 存储加上标量 userUuid。它具有角色 owner、manager、clerk 和 fulfillment。 MembershipService::isAuthorized() 目前被直接调用 每个操作的 Store Staff 控制器。

    这是一个有效的存储域授权实现，但它有两个限制：

    • 授权代码和允许的 Store 角色在控制器方法中重复。
    • 其他模块无法在不知情的情况下一致地重用 Store 范围的功能 存储会员详细信息。

    商店将会员资格支票保存在 MembershipServiceInterface 中。商店员工控制器 将通过 Store 拥有的助手与 AuthorizationServiceInterface 组成该检查。 因此Authorization不依赖于Store，无法形成Store <-> Authorization模块 循环。它既不修改成员资格模式也不重复成员资格 生命周期。

    2.4 内容是现场层面的试点¶

    Common\Entity\Content 具有 id、title、body、类别、标签、metadata（可为 null 的 JSON）和 时间戳。它没有有 storeUuid — 商店关联不是内容模型的一部分。现有应用内容 普通经过身份验证的 API 用户可以读取端点；管理内容控制器是 ROLE_ADMIN CRUD，现在 接受 metadata 作为白名单字段，以证明严格的字段授予执行。

    内容的字段级授权由 common:content create/update 字段授权提供（metadata 与非 metadata 角色）。商店范围的内容路由 (/store/{storeUuid}/contents) 在此阶段不存在；存储范围仍用于其他资源（例如 store:order:*），但内容的范围仅由字段授予确定，而不是由存储行范围确定。

    2.5 审计过程中发现的限制¶

    • BaseService 在其构造函数中捕获当前安全令牌的用户。新 授权代码必须在请求时获取当前用户，其中长期有效 否则服务可能会保留陈旧的请求状态。
    • 动态查询权限（@dql、@sort、@hints）当前检查文字 ROLE_ADMIN。他们在第一次授权迁移之外，并保持平台管理员身份 直到专用的核心合约取代此检查。
    • 通用创建/更新混合之前运行静态接受属性过滤 processCreateContent() 和 processUpdateContent()。动态字段权限 在静态架构允许列表删除未知字段后属于这些挂钩。
    • @filter、@select和@display是用户查询功能，而不是授权 政策。它们不得用于存储或评估管理员定义的授权 规则。

    3. 架构边界¶

    3.1 依赖方向¶

    flowchart LR
    identity["Identity<br/>User UUID, JWT, authentication"] --> authorization["Authorization<br/>role and permission decisions"]
    store["Store<br/>membership and store lifecycle"] --> authorization
    common["Common<br/>Content scope enforcement"] --> authorization
    trade["Trade / Wallet / Payment<br/>future consumers"] --> authorization

    箭头仅表示服务接口依赖性。授权存储 身份和 将引用存储为 UUID 字符串。它不得导入 Store 实体、存储库或 服务。业务模块消耗AuthorizationServiceInterface；他们不得进口 授权存储库或实体。

    3.2 责任矩阵¶

    关注 业主 授权责任
    用户身份、凭证、角色 JSON、JWT 身份 读取用户 UUID 并在需要时使授权会话无效
    平台打破玻璃管理员 身份ROLE_ADMIN 识别为无条件兼容性覆盖
    商店会员生命周期 商店 在做出商店范围的授权决定之前需要有效的会员资格
    权限目录和角色授予 授权 权威
    全局/商店角色分配 授权 权威
    资源所有权和生命周期 业务模块 提供范围属性并强制返回过滤器
    HTTP 授权决策 授权投票者 权威声明授权权限
    字段突变允许列表 授权角色授予+业务控制器架构限制 返回有效的允许字段

    3.3 术语¶

    术语 意义
    许可 稳定的能力代码，例如common:content:update
    角色 命名权限集和可选字段授予
    作业 全局或在一个范围内授予一个身份用户 UUID 的角色
    范围 资助适用的边界：第一个版本中的 global 或 store
    资源范围 目标记录拥有的范围，例如Content.storeUuid
    实地补助金 角色定义的一项资源操作允许的字段；它缩小了操作权限
    平台覆盖 现有的ROLE_ADMIN；迁移期间不受限制

    4. 权限模型¶

    4.1 权限代码¶

    所有代码都使用小写 ASCII 段：

    {module}:{resource}:{action}

    示例：

    authorization:role:manage
authorization:assignment:manage
common:content:read
common:content:create
common:content:update
common:content:delete
store:order:read
store:order:accept
store:order:reject
store:order:fulfill
wallet:voucher:manual

    *:* 和通配符匹配不是持久的权限代码。兼容性 ROLE_ADMIN 的覆盖是在授权决策服务中实现的，而不是作为 数据库记录。系统角色可能包含每个种子具体权限。

    4.2 RBAC 决策规则¶

    对于请求的权限 P、经过身份验证的用户 U 和可选的 Store UUID S：

    1. 匿名委托人被拒绝。
    2. 允许使用ROLE_ADMIN的用户。这是暂时的兼容性行为，并且 也是打破玻璃的操作路径。
    3. 允许对包含 P 的角色进行全局主动分配。
    4. 如果存在S，则作用域为S且角色包含P的活动分配是 允许。
    5. 否则请求被拒绝。

    对于 Store 操作，Store 的 StoreAuthorizationService 首先需要有效的会员资格 使用 MembershipServiceInterface，然后调用范围权限的授权。安 仅凭授权分配绝不能创建商店成员资格。

    一个存储中的允许不得授予另一存储中的访问权限。全球内容编辑器 稍后可能会作为明确的全局角色引入；它不是从 a 推断出来的 商店范围的编辑器分配。

    4.3 角色范围兼容性¶

    角色声明其最大范围：

    角色范围 允许的分配范围
    global 仅global
    store 仅store

    该服务拒绝不匹配的角色/分配范围。一个角色并不默默无闻 从 Store 提升到全球范围。

    4.4 字段级授权¶

    现场访问是成功行动决策的延伸，而不是替代 它。例如，以下两个角色都需要 common:content:update：

    角色 范围 有效内容更新字段
    store_content_editor 商店 title、body、category、tags
    store_content_metadata_editor 商店 title、body、category、tags、metadata

    有效字段是请求的匹配活动角色授予的并集 范围，然后与控制器的静态架构允许列表相交。未知或 服务器拥有的字段，例如 id、所有权、状态和时间戳 从未通过授权授予而变得可写。

    第一个版本使用严格拒绝：如果请求包含任何接受的架构 超出其有效字段授权的字段，API 返回 403 并执行 没有突变。禁止静默剥离输入，因为它会创建一个成功的 响应意外的部分写入。

    具有操作权限但没有 RoleFieldGrant 的角色不会收到客户端可写的权限 该操作的字段。此失败关闭规则可防止新添加的实体字段 意外变得可写。

    5. 持久化模型¶

    5.1 表格¶

    授权拥有六张表。所有时间戳均为 UTC datetime_immutable 值。

    表 目的
    authorization_permission 稳定的权限目录
    authorization_role 命名的全局或存储范围的角色
    authorization_role_permission 角色到权限加入
    authorization_assignment 用户 UUID 在范围内授予角色
    authorization_role_field_grant 角色/资源/操作的字段允许列表
    authorization_audit_log 仅追加授权管理审核

    5.2 许可¶

    authorization_permission
  id              int PK
  code            varchar(120) UNIQUE NOT NULL
  module          varchar(60) NOT NULL
  resource        varchar(60) NOT NULL
  action          varchar(60) NOT NULL
  name            varchar(120) NOT NULL
  description     text NULL
  isSystem        boolean NOT NULL DEFAULT false
  createdAt       datetime_immutable NOT NULL
  updatedAt       datetime_immutable NULL

    一旦在分配图中使用，唯一代码就是不可变的。权限删除是 不是普通的 CRUD 删除：只有在没有角色授予后才可以禁用系统权限 它们，并且代码更改需要迁移加上新代码。

    5.3 角色与权限加入¶

    authorization_role
  id              int PK
  uuid            varchar(36) UNIQUE NOT NULL
  code            varchar(80) UNIQUE NOT NULL
  name            varchar(120) NOT NULL
  scopeType       varchar(20) NOT NULL  # global | store
  isSystem        boolean NOT NULL DEFAULT false
  createdAt       datetime_immutable NOT NULL
  updatedAt       datetime_immutable NULL

authorization_role_permission
  role_id         int NOT NULL FK authorization_role(id) ON DELETE CASCADE
  permission_id   int NOT NULL FK authorization_permission(id) ON DELETE RESTRICT

    authorization_role_permission 是本地授权并且可以使用外键。系统角色和 无法通过正常的 Manage CRUD 修改或删除权限；只有一个版本 种子命令可以使它们一致。

    5.4 作业¶

    authorization_assignment
  id              int PK
  uuid            varchar(36) UNIQUE NOT NULL
  user_uuid       varchar(36) NOT NULL
  role_id         int NOT NULL FK authorization_role(id) ON DELETE RESTRICT
  scope_type      varchar(20) NOT NULL  # global | store
  scope_uuid      varchar(36) NULL      # normalized; NULL remains readable
  scope_key       varchar(36) NOT NULL  # '' for global, Store UUID for store — portable UNIQUE key
  granted_by_uuid varchar(36) NULL
  createdAt       datetime_immutable NOT NULL
  revokedAt       datetime_immutable NULL

    索引和约束：

    • 可移植唯一性：UNIQUE(user_uuid, role_id, scope_type, scope_key)，其中scope_key是COALESCE(scope_uuid,'')。这保留了撤销行重新激活，而不依赖于 UNIQUE 中的 NULL 语义（MySQL/PostgreSQL/SQLite 允许重复的 NULL）。 Doctrine 在应用层验证 global→scope_uuid IS NULL / store→valid UUID。
    • 索引(user_uuid, revoked_at)支持有效权限查找。
    • 索引(scope_type, scope_uuid, revoked_at)支持Store范围查找。
    • scope_type=global需要scope_uuid IS NULL； scope_type=store 需要一个 规范商店 UUID。学说验证在所有数据库引擎中强制执行这一点； 迁移在支持的情况下添加了 CHECK 约束。
    • 故意没有对 users 或 store 进行 FK。用户和商店 UUID 稳定 跨模块标量引用。

    分配会被撤销，而不会被硬删除，以保留授权历史记录。

    5.5 角色字段授予¶

    authorization_role_field_grant
  id              int PK
  role_id         int NOT NULL FK authorization_role(id) ON DELETE CASCADE
  resource        varchar(80) NOT NULL       # common:content
  action          varchar(60) NOT NULL       # create | update
  fields          json NOT NULL               # ordered unique field names
  createdAt       datetime_immutable NOT NULL
  updatedAt       datetime_immutable NULL
  UNIQUE(role_id, resource, action)

    JSON 在这里是有意为之的：授权是一个可审计的策略对象，并且字段始终是 作为一个完整的集合来阅读。每个字段单独的行会使写入变得复杂，而不需要 改进查询行为。该服务根据注册的字段名称进行验证 持久化之前的资源模式；它不接受任意字符串。

    AuthorizationServiceInterface是唯一导出到其他的授权合约 业务模块。它仅评估授权拥有的分配数据。它提供了方法 相当于：

    can(User $user, string $permission, ?AuthorizationScope $scope = null): bool;
require(User $user, string $permission, ?AuthorizationScope $scope = null): void;
allowedStoreUuids(User $user, string $permission): list<string>;

    FieldAuthorizationServiceInterface 提供：

    filterWritableFields(
    User $user,
    string $resource,
    string $action,
    array $input,
    array $schemaFields,
    ?AuthorizationScope $scope,
): array;

    当输入包含未经授权的接受字段时，它会引发授权异常。 控制器将其转换为项目现有的 403 响应信封。

    AuthorizationResourceRegistry 是代码拥有的配置，管理员不可编辑 元数据。它将授权资源映射到有效的可写模式字段：

    'common:content' => [
    'create' => ['title', 'body', 'category', 'tags', 'metadata'],
    'update' => ['title', 'body', 'category', 'tags', 'metadata'],
]

    它可以防止角色管理员授予不存在的、敏感的或 只需编辑 JSON 字段即可授予服务器拥有的属性。

    7. 请求授权流程¶

    7.1 身份验证和投票者决策¶

    sequenceDiagram
    participant C as Client
    participant J as JwtAuthenticator
    participant V as AuthorizationVoter
    participant A as AuthorizationService
    participant B as Business Controller

    C->>J: Bearer JWT + request
    J->>J: Verify RS256, expiry, revocation; load User
    J->>V: #[IsGranted('common:content:update', subject)]
    V->>A: can(user, permission, scope)
    A-->>V: allow or deny
    V-->>B: permitted request only
    B->>A: obtain allowed Store UUIDs / field filter

    投票者执行授权拥有的操作级别门。它必须收到一个明确的 AuthorizationScope 或实现小型 ScopedResourceInterface 的主题；它必须 不从客户端主体数据推断商店。在此门之后，存储端点调用 商店拥有的 StoreAuthorizationService 检查活跃会员资格并获取 授权派生的数据过滤器。如果没有两者，请求无法读取或更改存储行 检查，而模块依赖性仍然是单向的：Store -> Authorization。

    7.2 数据范围执行¶

    单独的操作授权并不能使行可写。控制器服务于 商店拥有的资源必须将每次查找限制为允许的商店 UUID：

    ROLE_ADMIN                    -> no Store predicate
0 permitted Store UUIDs       -> ['id' => -1]
1 permitted Store UUID        -> ['storeUuid' => uuid]
multiple permitted Store UUID -> QueryBuilder WHERE entity.storeUuid IN (:storeUuids)

    QueryBuilder 必须从资源的服务创建，以便它与 现有的 mixin 过滤器管道。相同的范围过滤器适用于列表、详细信息、更新、 删除和批量更新查找库。仅当行为 通过该过滤器可见。如果不希望披露，则超出范围的记录 返回 404 而不是 403。

    7.3 安全创建作用域（当为存储作用域时）¶

    当资源属于 Store 范围时，创建路由时将 Store 范围包含在路由中，而不是请求正文中：

    POST /api/v1/store/{storeUuid}/orders

    控制器需要{storeUuid}的相关权限（例如store:order:create）并设置 仅来自路线的商店关联。接受的客户端中缺少商店标识符 属性。这可以防止客户端通过发送不同的消息来选择另一个商店 JSON 字段。在此阶段，内容不是商店范围（仅限 metadata 现场授予试点）。

    7.4 字段过滤¶

    对于创建和更新，顺序是：

    static controller schema allow-list
  -> server-owned scope defaults
  -> FieldAuthorizationService strict field validation
  -> processCreateContent/processUpdateContent
  -> service.update()

    授权字段授权缩小了静态控制器模式；它永远不会扩展它。 特定于资源的验证保留在业务服务/控制器挂钩中。

    10. JWT、缓存和撤销¶

    10.1 首次发布决定¶

    授权是在服务器端从授权表和缓存中解析的。 JWT 继续 仅包含身份声明（sub、用户名、电子邮件、角色、时间声明、JTI、颁发者）。 在第 1 阶段，权限和存储范围未添加到 JWT。

    这使得授权缓存失效后分配撤销有效，而无需 等待 7200 秒的访问令牌到期，并避免用户使用大量令牌 许多商店任务。

    10.2 缓存合约¶

    缓存键：

    authorization:effective:{userUuid}

    缓存值仅包含有效权限代码、存储范围 UUID、字段授予、 和版本/时间戳。作为后备措施，缓存 TTL 很短（默认为五分钟）； 角色权限、字段授予或分配的每次突变都会驱逐受影响的人 事务提交后同一请求中的用户密钥。

    更改角色的授权必须使该角色的每个活动分配失效。的 存储库在提交之前查询受影响的用户 UUID，并且失效器会清除密钥 提交成功后。失败的事务不得因更改而逐出缓存条目 但这种情况并没有持续下去。

    10.3 高风险撤销¶

    撤销分配会删除缓存逐出后下一个请求的权限。 它不需要撤销身份刷新令牌，因为 JWT 不携带任何授权 权限。商店会员资格撤销是独立有效的，因为商店 在每次存储操作时检查它。如果未来版本在 JWT 中嵌入权限 声称，它必须另外撤销主动访问和刷新令牌或引入 授权版本声明。

    11. 故障处理和安全规则¶

    状况 结果
    JWT 缺失/无效 现有401认证响应
    已通过身份验证但无操作权限 403
    商店路线没有有效的会员资格或分配 403创建； 404 表示现有的超出范围的记录
    范围 UUID 格式错误或角色/范围不匹配 400 管理写
    请求领域以外的有效拨款 403；没有部分写入
    作业已激活 现有赋值的幂等返回或409；端点合约选择一个并测试它
    Grant 指的是未知资源/领域 400；注册表拒绝它
    审核写入失败 整个授权管理事务回滚
    缓存失败 对于具有突变能力的路由，故障关闭；仅当显式测试时，只读决策才可能回退到数据库

    附加强制性规则：

    • 权限代码、角色代码、Store UUID 和字段名称被验证为有界的 ASCII 字符串；不评估任何用户表达式。
    • ROLE_ADMIN 绕过敏感存储/授权突变进行记录。
    • 授权审核列表仅供管理员使用，不得暴露不必要的用户配置文件数据。
    • 存储范围来自路由参数或持久目标实体，而不是客户端 body 字段或 X-Store-Code 没有受信任的存储上下文解析。
    • 字段授予不能授予序列化可见性。序列化器组/#[Ignore] 仍然对敏感的读取字段负责。

    第一阶段：授权基础和内容试点（Field-Grant）¶

    第 3 阶段：可选的 ABAC 政策¶

    只有在scoped RBAC稳定之后，才引入单独的access_policy设计，如果 业务需求需要时间窗口、订单金额或内容等条件 状态。它必须使用包含主题的受限制的、经过代码审查的表达式上下文， 资源、范围和环境属性。它不得重用客户端提供的 作为策略记录的 @filter 表达式。

    • 将授权迁移添加到 MySQL 迁移链验证。
    • 运用 SQLite 和 PostgreSQL 语义来实现赋值唯一性和可为 null 的范围 领域；不要依赖于一个目标数据库不支持的部分唯一索引。
    • 运行 PHPStan Level 8 和 Rector type-rule 试运行。
    • 不要取消跳过与授权无关的记录测试。

    14. 验收标准¶

    授权基础在以下情况下完成：

    • [ ] 授权是一个独立的模块，任何授权实体都没有另一个实体的外键 业务模块。
    • [ ] 权限、角色、分配、现场授予和审计记录已说明 完整性约束和生命周期规则。
    • [ ] 商店范围的决策需要授权授予和有效的商店会员资格。
    • [ ] 控制器可以声明操作权限而无需重复权限 查找逻辑。
    • [ ] 每个存储范围的查找都使用授权派生的范围过滤器来进行列表、详细信息、 更新、删除和批量突变路径。
    • [ ] 存储范围是服务器从路由/记录派生的，从不接受 JSON 输入。
    • [ ] 字段授权是严格的、经过注册表验证的，并且不能扩大控制器架构。
    • [ ] 分配和角色更改使有效访问缓存和追加审核无效 记录他们的成功交易。
    • [ ] 现有ROLE_ADMIN、身份认证、普通用户内容读取行为 在整个第一阶段保持兼容。
    • [ ] 内容试点测试证明用户 A 无法写入 metadata (field-grant 403)，而用户 B 可以。

    15. DqlExpression 行范围基础¶

    15.1 目的和边界¶

    commonFilter() 已经接受数组条件和 Doctrine QueryBuilder 实例。 这些机制足以强制执行行级授权，但策略意图 通常会被别名、连接和参数管道所掩盖。 DqlExpression 是一个 小核心值对象，让控制器使用声明服务器拥有的行策略 现有的表达式到 DQL 语法：

    use App\Core\Query\DqlExpression;

protected function commonFilter(): DqlExpression
{
    return new DqlExpression(
        'entity.getUser() == this.getUser()',
    );
}

    它是 SQL 强制行范围的声明性表示。它不是通用的 ABAC 策略引擎、用户提供的查询功能或 QueryBuilder 的替代品。

    过滤器类型 正确使用
    数组条件 简单的相等，例如 ['user' => $user]
    DqlExpression 使用当前表达式语法的可读服务器拥有的所有权、存储、状态、租户或多值 in/not in 规则
    查询生成器 聚合、子查询、数据库函数或性能敏感的自定义 SQL 形状

    DqlExpression 支持 in 和 not in 作为集合成员资格，例如：

    new DqlExpression('entity.getStoreUuid() in storeUuids', ['storeUuids' => $allowedStoreUuids]);
new DqlExpression('entity.getStoreUuid() in this.getAllowedStoreUuids()');

    空的 in 集合编译为 1 = 0 （无行，失败关闭）；空的 not in 集合编译为 1 = 1。集合始终绑定为数组参数，并且可以通过 this.getAllowed...() 提供。

    15.2 不可协商的规则¶

    • 只有 PHP 代码可以构造 DqlExpression。 HTTP参数、数据库记录、 管理员管理的授权数据不得提供表达式源。
    • 变量仅通过构造函数值数组提供，并且始终绑定为 学说查询参数。它们永远不会插入到 DQL 中。
    • 仅在 ApiView::commonFilter() 中，this 是内部只读上下文 绑定到当前控制器的变量。因此 this.getUser() 是简写 用于显式传递 ['user' => $this->getUser()] 并引用 user。 永远无法请求 @filter 表达式或直接服务调用。
    • 编译、Doctrine 元数据验证、参数绑定或标准验证 失败是服务器配置错误。它返回 HTTP 500 并拒绝请求。
    • DqlExpression 绝不使用 LegacyEvaluator、内存中过滤或未过滤的 后备。安全范围必须无法关闭。
    • 该表达式与 mixin 生成的 id/uuid 查找条件结合使用 AND，因此detail、update、delete和batch-update路径不能绕过作用域。
    • 它不会改变创建的授权。创建操作没有现有行 过滤；控制器/服务必须从受信任的上下文设置用户/存储所有权。

    15.3 最小运行时更改集¶

    该实现有意避免更改 BaseServiceInterface， ExpressionServiceInterface、ExpressionService、QueryBuilderFactory 或 现有的公共 @filter 行为。它有十个必需的核心源代码更改以及 测试。

    文件 改变 原因
    src/Core/Query/DqlExpression.php 新的不可变值对象 携带表达式、绑定变量、内部控制器上下文和 mixin 添加的条件
    src/Core/Parser/ExpressionDqlParser.php 添加变量/in/not in/数组编译 之前的解析器使用空右操作数编译 entity.getUser() == user 并且没有集合处理
    src/Core/Service/Concern/BaseServiceReadListTrait.php 识别并编译get()和list()中的DqlExpression 单一服务层执行点
    src/Core/View/ApiView.php 绑定控制器this；将 ID/UUID 条件合并到 DqlExpression 保留控制器上下文和范围以进行详细信息/更新/删除/批量查找
    src/Core/View/ListApiViewMixin.php 仅加宽钩型 允许列表过滤器接收值对象
    src/Core/View/DetailApiViewMixin.php 仅加宽钩型 允许详细过滤器接收值对象
    src/Core/View/DeleteApiViewMixin.php 仅加宽钩型 允许删除过滤器接收值对象
    src/Core/View/SingleDetailApiViewMixin.php 通过ApiView解析普通过滤器 绑定 this 以获取单例详细信息

    ScopedListApiViewMixin 和 ScopedDetailApiViewMixin 在第一个中保持不变 释放。他们已经要求每个范围控制器构建一个显式过滤器并且 仅当实际作用域资源需要时才可以采用 DqlExpression。

    15.4 价值对象合约¶

    final readonly class DqlExpression
{
    /**
     * @param array<string, mixed> $values
     * @param array<string, mixed> $criteria
     */
    public function __construct(
        public string $expression,
        public array $values = [],
        private array $criteria = [],
        private ?object $context = null,
    ) {}

    public function withContext(object $context): self;

    /** @param array<string, mixed> $criteria */
    public function withCriteria(array $criteria): self;

    /** @return array<string, mixed> */
    public function criteria(): array;
}

    构造函数验证：

    • expression 必须非空。
    • values中的每个变量名称必须匹配[A-Za-z_][A-Za-z0-9_]*。
    • entity和this被保留。它们不能在 values 中提供。
    • withCriteria()永远不会覆盖现有标准；重复的键被拒绝 作为配置错误而不是削弱原始表达。
    • withContext()对于同一对象是幂等的，并且拒绝不同的对象。它 仅在 ApiView 过滤器解析期间添加内部 this 绑定。

    criteria 不是公共控制器输入功能。 ApiView::mixToCommonFilter() 在内部将其用于 id 和 uuid 等键。

    15.5 控制器this绑定¶

    Symfony ExpressionLanguage 中没有环境控制器 this。现有的 表达式编译器仅接收 entity 和显式提供的值。在 特别是，BaseService的$this是服务实例，而不是控制器，所以它 绝不能用于此功能。

    ApiView 引入一个私有解析器：

    protected function resolvedCommonFilter(): array|QueryBuilder|DqlExpression
{
    $filter = $this->commonFilter();

    return $filter instanceof DqlExpression
        ? $filter->withContext($this)
        : $filter;
}

    所有直接获取 commonFilter() 的现有 Core mixins 都使用此解析器：

    ListApiViewMixin
SingleDetailApiViewMixin
SingleCreateAndUpdateApiViewMixin
ApiView::mixToCommonFilter() for detail/update/delete/batch paths

    这保留了所需的简洁控制器代码：

    return new DqlExpression('entity.getUser() == this.getUser()');

    并使其等价于：

    return new DqlExpression(
    'entity.getUser() == user',
    ['user' => $this->getUser()],
);

    第一种形式只能作为 commonFilter() 返回值使用。直接一个 BaseService::list(new DqlExpression(...)) 调用没有控制器上下文，必须 请改用显式值。

    15.6 解析器更改：安全绑定变量¶

    ExpressionDqlParser 目前处理常量和 getter 链，但失败了 对于 Symfony ExpressionLanguage 变量节点。对于这个表达式：

    entity.getUser() == user

    当前编译器生成的无效片段相当于：

    filter_entity.user =

    狭窄的变化增加了对 NameNode 的显式处理：

    1. 读它的名字。
    2. 拒绝entity、未声明的值和任何保留/内部名称。
    3. 分配下一个现有的filter_parameter_N名称。
    4. 添加new Parameter($name, $this->values[$variableName])。
    5. 将:$name返回到DQL片段。

    这保留了解析器现有的 getter-chain 编译、Doctrine 元数据 验证和参数命名空间。诸如身份用户之类的对象绑定为 Doctrine 关联参数；标量 将 UUID 和状态绑定存储为标量参数。

    当解析器看到 this.getX() getter 链时，仅当 this 为 由 ApiView 内部绑定，在服务器端评估一次无参 getter 编译，并将返回值绑定为相同的生成 Doctrine 参数。 它不会向 HTTP 输入公开任意表达式 this 变量。

    没有新的运算符、函数、动态属性访问或表达式求值 介绍了。

    15.7 基础服务执行¶

    BaseServiceReadListTrait 是唯一的运行时编译器集成点。它创造了 普通根 QueryBuilder (entity)，根据服务的表达式编译表达式 托管实体类，通过 Doctrine 元数据验证片段，并应用 直接使用现有的片段：

    ExpressionQueryBuilderAssembler::applyToQueryBuilder($qb, $parser)

    这种直接应用优于当前公共 @filter 实现， 它在 entity.id IN (subquery) 中包装了第二个过滤器查询。行范围是 主查询的强制部分，应保留正常的连接和分页。

    应用表达式片段后，该特征会添加 criteria 谓词 私人帮手：

    1. 获取根别名。
    2. 确认每个条件键是受管实体上的映射字段或关联。
    3. 生成一个内部唯一的参数名称，例如 _common_filter_criterion_1。
    4. 使用经过验证的映射名称附加 rootAlias.field = :parameter。
    5. 绑定值。

    在元数据验证之前，字段名称永远不会连接。这很重要，因为 批量更新 @basis 路径最终可以将客户端选择的基础密钥传递到 mixToCommonFilter()。

    get(DqlExpression) 重用相同的 QueryBuilder 构造并保留 现有的 NoResultException / NonUniqueResultException 行为。 list() 接受 相同的对象，否则准确保留所有数组和 QueryBuilder 分支。

    此服务器拥有的编译路径中的任何异常都会作为描述性重新抛出 LogicException（例如，Invalid server DQL common filter: ...）。现有API 异常处理将其转换为 HTTP 500。与请求 @filter 不同，没有 catch 可以实现内存中评估。

    15.8 ApiView 组合¶

    ApiView::mixToCommonFilter() 在合并之前解析并绑定其公共过滤器 详细信息/更新/删除查找的标量标准。它的新分支故意很小：

    if ($base instanceof DqlExpression) {
    return $base->withCriteria($data);
}

    例如，Detail 获取：

    commonFilter(): entity.getUser() == user
route:          {id}=42
effective SQL:  entity.user = :user AND entity.id = :id

    这意味着行范围仍然强制执行，而无需更改每个控制器或添加 对 CRUD 操作的单独授权调用。

    现有的数组行为保持不变，包括其拒绝所有约定：

    return ['id' => -1];

    返回 QueryBuilder 的现有控制器保持不变。

    15.9 为什么ExpressionService现在没有改变¶

    ExpressionService::buildFilter() 有一个缓存路径，用于存储参数值 仅由实体类和表达式源组成的键。依赖于用户的表达式 因此可以为不同的用户重复使用先前缓存的参数值。

    DqlExpression 不得在这个狭窄的实现中使用该路径。它构建了 ExpressionDqlParser直接不带缓存，通过现有的应用 汇编器。这使得用户/存储参数绑定请求本地且正确，同时 避免对公共 @filter 行为进行不相关的重构。

    现有的 @filter 缓存问题仍然是单独的技术债务，必须修复 before ExpressionService 被服务器拥有的授权过滤器重用。

    15.10 所需测试¶

    层 案例
    解析器单元 entity.getUser() == user 编译为绑定参数；缺少变量被拒绝；保留的 entity/this 值被拒绝
    值对象单位 空源、无效变量名、不可变条件组合、上下文绑定幂等性、重复条件拒绝
    基地服务单位 list() 和 get() 识别值对象并传播编译错误而不是回退
    核心整合 保留两个用户和两个用户拥有的实体；用户 A 的列表/详细信息/更新/删除永远不会返回或改变用户 B 的实体
    核心整合 this.getUser() 和显式 user 语法通过列表和单例混合产生相同的作用域结果
    核心整合 Getter 链加上标量变量，例如存储 UUID/状态、验证并应用于根 QueryBuilder
    回归 现有数组条件和直接 QueryBuilder 通用过滤器保留其当前输出

    集成测试必须执行正常的 View mixins，而不仅仅是 BaseService，所以 证明mixIdToCommonFilter()添加了detail、update、delete的ID条件。

    15.11 采用示例¶

    // Existing, preferred for a simple equality scope.
protected function commonFilter(): array
{
    return ['user' => $this->getUser()];
}

// DqlExpression, preferred when the policy itself benefits from a readable rule.
protected function commonFilter(): DqlExpression
{
return new DqlExpression(
        'entity.getUser() == this.getUser() && entity.getStatus() != archived',
        ['archived' => 'archived'],
    );
}

// Continue to use QueryBuilder for a variable-size Store set.
protected function commonFilter(): QueryBuilder
{
    return $this->storeScopeQueryBuilder($allowedStoreUuids);
}

    现有控制器不会作为核心功能的一部分进行迁移。第一次迁移 必须是具有列表/详细信息/更新/删除集成测试的小型用户拥有的资源。 只有这样授权才可以使用 DqlExpression 作为其可读的单一存储/所有权范围 原始的。
