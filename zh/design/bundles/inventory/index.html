    库存捆绑设计¶

    状态：预览，已实施，但尚未准备好投入生产。 Inventory 捆绑包 (src/Inventory/) 拥有材料、每店库存、规格配方、 预订和库存分类帐。这是定义的延迟保留边界 通过商店捆绑包。贸易仍然是商业秩序的权威；商店仍然是 商店接受和操作订单的权限。批准的目录目标 将产品/规格所有权移至商店；库存继续使用标量 规范UUID，不需要跨模块实体关系。

    INVENTORY_ENABLED 必须保持false 独立的开发和测试之外。 确认的预订目前在没有履行驱动的消费流程的情况下过期， 并且跨消息取消竞赛没有完全序列化。架构和禁用 模块可能会被合并，但为实时订单启用库存会被阻止 下面的生产准备工作。

    生产准备 TODO¶

    • 实施履行驱动的预订消耗，自动减少现有量 和保留数量并写入consume分类帐条目。
    • 定义到期语义，以便已接受或已履行的订单不会丢失其保留 虽然这仍然取决于库存。
    • 序列化商店订单确认和取消转换以防止过时状态 恢复已取消的订单。
    • 使用持久的库存取消墓碑处理预订前发布订单 并保留每个预订的发件箱因果关系。
    • 之前为这些转换添加并发和乱序集成测试 允许在生产中使用INVENTORY_ENABLED=true。

    1. 目标和范围¶

    1.1 目标¶

    为商店提供库存控制，无需耦合贸易目录、商店订单 投影，或通过共享数据库关系未来提取的服务。

    Trade order
  -> Store validates local eligibility
  -> Store requests Inventory reservation
  -> Inventory expands the Specification recipe into materials
  -> Inventory reserves, or rejects, atomically
  -> Store accepts, or rejects, the commercial order

    该捆绑包拥有：

    • 物料主数据，包括原材料和成品。
    • 每家商店的现有数量和预订数量。
    • 每只股票的负库存政策。
    • 规范 UUID 的当前唯一配方。
    • 预订、释放、消耗、调整和审计账本记录。
    • 库存集成事件的幂等消耗和发布。
    • 全局启用库存时检查库存可用性。

    该捆绑包不拥有：

    • 产品或规格主数据、定价或 SKU 激活。
    • 面向客户的商业订单、付款、退款或取消权限。
    • 商店身份、会员资格、商店资格或商店订单接受权限。
    • 贸易、存储、身份、支付或钱包的学说关联或外键。

    1.2 非目标¶

    初始库存阶段不得：

    • 创建第二个 SKU 目录或重复的目录规格字段。
    • 创建库存行作为读取请求的副作用。
    • 将代理视为一次性、全局排序或以事务方式耦合到 SQL。
    • 在商店和库存之间使用分布式事务。
    • 保留历史食谱作为订单的可变参考；预订线路是 不可变的材质快照。
    • 预订时扣除库存。预订仅更改预订数量。
    • 支持多个有效配方、配方版本、替代品、批次、序列号、 第一阶段的到期、仓库箱或生产工单。

    1.3 所有权矩阵¶

    关注 业主 库存责任
    产品及规格目录 商店（目标） 仅参考规范UUID
    商业订单及付款状态 贸易+支付 仅使用不可变存储请求
    商店形象和接受度 商店 仅限参考存储 UUID
    材质大师 库存 权威
    储存物料平衡 库存 权威
    SKU 到材料配方 库存 权威
    预订决定和分类账 库存 权威
    全球库存绕行 部署配置 尊重它；禁用时不进行库存工作

    2. 架构原则¶

    2.1 稳定标量引用¶

    Inventory 仅通过 UUID 和不可变快照引用相邻模块：

    参考 存储为 不允许
    商店 storeUuid 字符串(36) ManyToOne Store
    贸易订单 tradeOrderUuid 字符串(36) ManyToOne Order
    店铺订单 storeOrderUuid 字符串(36) ManyToOne StoreOrder
    规格 specificationUuid 字符串(36) ManyToOne Specification
    门店预订 reservationId 字符串(36) 跨模块实体关系

    Store 提供的 catalogReference 是规范 UUID。库存永远不会加载 保留库存时编目表。这保留了未来的提取路径。

    2.2 全球可选，本地强制¶

    模块化整体支持不操作库存的部署。单个 运行时配置控制 Store 是否调用 Inventory 边界：

    # Inventory Resources/config/services_inventory.yaml
parameters:
    inventory.enabled: '%env(bool:INVENTORY_ENABLED)%'
    INVENTORY_ENABLED 店铺行为 库存行为
    false 执行商店验证并直接接受 无预订请求、无库存读/写、无库存事件
    true 创建预订 ID 并在 awaiting_inventory 中等待消费预订请求并异步响应

    全局设置优先于所有物料级库存策略。它是一个 部署问题，而不是数据库设置或请求参数。它的默认值必须是 在 .env 和部署配置中明确记录。虽然此捆绑包仍然存在 在预览版中，生产部署必须保留它 false。

    2.3 每商店、每种材料的政策¶

    库存由 (storeUuid, material) 隔离。每个余额都有自己的 allowNegativeStock 标志，默认为 false。

    availableQuantity = onHandQuantity - reservedQuantity
    全球启用 allowNegativeStock 预订规则
    没有 任意值 完全绕过库存
    是的 假 availableQuantity >= requestedQuantity 适用于每种材料
    是的 真实 即使 availableQuantity < requestedQuantity

    负库存被记录而不是隐藏：余额和分类账保留 由此产生的过度预订或后来的负现有数量。旗帜不能 默默地绕过账本条目或幂等性。

    2.4 读取永远不会实现余额¶

    缺少Stock记录意味着默认本地策略的余额为零；

    {
  "storeUuid": "store-uuid",
  "material": "material-uuid",
  "exists": false,
  "onHandQuantity": 0,
  "reservedQuantity": 0,
  "availableQuantity": 0,
  "allowNegativeStock": false
}

    管理读取 API 可能会针对明确请求的情况返回此虚拟视图 材料/商店对。列表 API 仅返回持久化的行。真正的平衡被创造出来 仅通过写操作：初始库存、调整、负库存时保留 是允许的，或者其他未来的股票突变。

    2.5 本地交易和至少一次交付¶

    每个 Inventory 突变都会在一个 SQL 中写入其本地聚合及其传出事件 交易。收件箱表通过 eventId 至少删除一次传递的重复数据；商业 记录添加唯一键以实现竞赛安全幂等性。

    Inventory transaction:
  consumed event + reservation + stock changes + ledger entries + outbox event

Delivery:
  at least once + Inbox deduplication + reservationId uniqueness

    任何处理程序都不能在事务提交之前确认消息。任何消费者不得 假设一个事件仅传递一次或者来自不同聚合的事件到达 在全球秩序中。

    3. 领域模型¶

    3.1 实体概述¶

    实体 表 目的
    Material inventory_material 原材料或成品主数据
    Stock inventory_stock 每家商店的物料平衡和当地政策
    SpecificationRecipe inventory_specification_recipe 每个目录一个当前配方 规格 UUID
    RecipeLine inventory_recipe_line 一个规格单位所需的材料数量
    Reservation inventory_reservation 幂等请求级预留聚合
    ReservationLine inventory_reservation_line 不变的材料需求和预留数量
    LedgerEntry inventory_ledger_entry 仅附加库存审计跟踪
    InventoryConsumedEvent inventory_consumed_event 收件箱重复数据删除和事件审计
    InventoryOutboxMessage inventory_outbox_message 耐用的集成事件中继

    所有外部引用的 Inventory 实体除了使用 UUID v4 标识符外，还使用 UUID v4 标识符。 内部整数主键。数量使用 decimal(20, 6)，从不浮动。单位 属于物料和配方的数量必须使用该单位。

    3.2 材料¶

    Material 代表库存控制的事物。它支持原始输入和 成品，因此规格可以直接库存或由材料组装。

    领域 类型 规则
    id 整数 内部PK
    uuid 字符串(36) 独特的外部身份
    code 字符串（64） 首次股票突变后独特的不可变业务代码
    name 字符串（255） 必需的显示名称
    kind 字符串（20） raw 或 finished
    unit 字符串（20） 所需的标准化单位，例如piece、kg、ml
    status 字符串（20） active 或 inactive
    metadata json 可为空 非会计扩展数据
    createdAt、updatedAt 日期时间不可变 审计时间戳

    非活性材料不能添加到新配方或新的手动调整中。现有 预订和历史账本行仍然可读。

    3.3 库存¶

    一个 Stock 代表一个 Store 中的一种材料。它有一个本地 FK Material，但仅存储 storeUuid 作为商店标识。

    领域 类型 规则
    id 整数 内部PK
    material 多对一材质 所需的本地关系
    storeUuid 字符串(36) 所需标量存储参考
    onHandQuantity 小数(20,6) 实物盘点数量；仅在允许的情况下消费后才可能变为负值
    reservedQuantity 小数(20,6) 活跃预订总数；绝不消极
    allowNegativeStock 布尔 默认为 false
    version 整数 Doctrine 乐观锁版本
    createdAt、updatedAt 日期时间不可变 审计时间戳

    约束条件和指标：

    • 独特的(store_uuid, material_id)。
    • 用于预留锁定和余额读取的索引(store_uuid, material_id)。
    • 管理报告索引(store_uuid, updated_at)。
    • reservedQuantity >= 0 在域代码中强制执行，并且在可移植的情况下进行数据库检查。

    故意没有公共 setOnHandQuantity() 或 setReservedQuantity()。 InventoryService 仅通过相应的分类帐条目更改数量。

    3.4 规格菜谱和菜谱行¶

    SpecificationRecipe 拥有一个目录规范的当前物料清单。 它不存储贸易实体关系。

    领域 类型 规则
    uuid 字符串(36) 外部配方标识
    specificationUuid 字符串(36) 独特的当前目录规格参考
    status 字符串（20） active 或 inactive
    lines 一对多食谱线 至少一条有效线路
    createdAt、updatedAt 日期时间不可变 审计时间戳

    每个RecipeLine都有material、quantityPerUnit decimal(20,6)和sort。其 唯一约束为(recipe_id, material_id)，因此重复的物料需求为 在编写的食谱中是不可能的。预订服务仍然通过以下方式汇总需求： 材料，因为请求可能包含重复的规范行。

    第一阶段每个规范仅允许一种配方。更新现有食谱 在影响未来的预订之前替换其当前线路。现有 ReservationLine行保存已解析的材料和数量快照，并且是 从未根据更改的配方重新计算。

    3.5 成品良好后备¶

    每个库存控制规范均由以下规则之一解析：

    1.specificationUuid存在一个有效配方：将每个配方材料保留在 orderQuantity * quantityPerUnit。 2. 不存在有效配方：保留code等于的有效finished物料 规范 UUID (catalogReference)。 3. 两者都不存在：用 SPECIFICATION_NOT_STOCKABLE 拒绝。

    直接成品约定避免了第一阶段的第二个映射表，同时 保持显式和跨模块安全。材料代码验证必须接受 UUID。 如果稍后需要人类可读的 SKU 代码，请添加库存拥有的 SpecificationMaterialMapping 通过单独版本化的迁移和事件 合同；不要将交易表视为后备。

    3.6 预订和预订热线¶

    Reservation 是幂等预留聚合。 reservationId 是 在发布请求之前由 Store 生成。

    领域 类型 规则
    id / uuid 整数/字符串(36) 内部和外部身份
    reservationId 字符串(36) 唯一存储幂等性和关联键
    storeUuid 字符串(36) 所需的标量参考
    tradeOrderUuid 字符串(36) 所需的标量参考
    storeOrderUuid 字符串(36) 所需的标量参考
    status 字符串（30） 请参阅下面的状态机
    requestHash 字符串（64） 规范化请求负载的 SHA-256
    expiresAt 日期时间不可变可为空 预订截止日期快照
    releasedAt、consumedAt 日期时间不可变可为空 终端操作时间戳
    createdAt、updatedAt 日期时间不可变 审计时间戳

    ReservationLine 存储 materialUuid、materialCodeSnapshot、unitSnapshot、 requestedQuantity、reservedQuantity 和源规范 UUID。它必须 保留足够的数据以在材料或食谱重命名后审核预订， 停用或更改。

    预订状态：

    requested -> confirmed -> released
                     \-> consumed
requested -> rejected

    requested仅在处理本地事务时存在。已承诺的预订 是 confirmed 或 rejected。 released、consumed 和 rejected 是终端。 如果重复的释放和消费请求与现有状态一致，则它们是无操作的； 冲突的请求是操作错误，不得重写历史记录。

    3.7 账本条目¶

    分类帐只能追加。它是库存突变的审计来源； Stock 是当前余额预测。

    类型 现有三角洲 保留三角洲 参考
    initial 正或零 0 手动初始化
    adjustment 积极或消极 0 计数修正/操作员原因
    reservation 0 积极 预订 UUID
    release 0 负 预订 UUID
    consume 负 负 预订 UUID / 履行参考

    每行包括storeUuid、本地material、增量数量、突变后余额 快照、referenceType、referenceId、可用的非秘密参与者参考， 和时间戳。 (type, reference_id, material_id) 上的唯一性约束可防止 相同的保留操作对相同的材料应用两次。

    4. 预订处理¶

    4.1 预订请求合同¶

    商店仅在 INVENTORY_ENABLED=true 时发布 inventory.reservation.requested.v1。

    {
  "reservationId": "inventory-reservation-uuid",
  "storeUuid": "store-uuid",
  "tradeOrderUuid": "trade-order-uuid",
  "storeOrderUuid": "store-order-uuid",
  "items": [
    {
      "lineId": "trade-order-item-uuid",
      "catalogReference": "specification-uuid",
      "quantity": "2.000000"
    }
  ],
  "expiresAt": "2026-07-26T12:30:00+00:00",
  "requestedAt": "2026-07-26T12:00:00+00:00"
}

    所需验证：

    • ID 必须是 UUID 字符串； quantity 是正十进制字符串，最多 6 个 小数位。
    • items 必须至少包含一个唯一的lineId。
    • 预订截止日期必须是 requestedAt 之后的 ISO-8601 日期。
    • 所有请求身份和规范化项目快照必须匹配重复项 reservationId 交付。
    • 商店不得为同一 storeOrderUuid 发出多个有效预订。

    4.2 预约算法¶

    在一笔库存交易中：

    1. 验证消息信封和负载版本。
    2. 插入InventoryConsumedEvent(eventId)，如果已经存在则立即确认 存在。 3、找到唯一的reservationId；如果存在，则比较其规范化请求哈希。 如果相等则返回其现有结果；如果冲突则消息失败。
    3. 使用活动配方或成品回退解决每个项目。
    4. 按材料 UUID 汇总要求。
    5. 以确定性材料 UUID 顺序锁定现有 (storeUuid, material) 余额。
    6. 当所需材料处于非活动状态、无库存或 当其本地负库存标志被禁用时，不足。
    7. 成功后，仅在负库存预留需要时才创建缺席余额 他们，增加reservedQuantity，创建预留分类账行，并持久化 不可变的预订线。
    8. 保留已确认或拒绝的预订以及匹配的库存发件箱事件。
    9. 提交，然后让 Messenger 确认该消息。

    该服务对现有余额行使用数据库行锁，并使用唯一的余额键 缺席排比赛。在平衡键碰撞时，它会重新加载并重试锁定 计算。它从不使用浮点数或不加锁的先读后写数量更新。

    4.3 拒绝代码¶

    代码 意义 重试行为
    SPECIFICATION_NOT_STOCKABLE 没有活性配方或直接成品材料 业务拒绝
    MATERIAL_INACTIVE 已解决的素材无法重新保留 业务拒绝
    OUT_OF_STOCK 一项或多项余额不足 业务拒绝
    RESERVATION_EXPIRED 请求在截止日期后到达 业务拒绝
    INVALID_RESERVATION_REQUEST 架构、数量或相关性验证失败 DLQ/算子修正
    RESERVATION_CONFLICT 内容不同的重复业务密钥 DLQ / 严重警报

    业务拒绝提交被拒绝的预订、收件箱记录以及被拒绝的预订 发件箱事件。传输或数据库故障通过 Messenger 回滚并重试。

    4.4 确认和拒绝事件¶

    Inventory 只发布每个预订的一个初始结果。

    inventory.reservation.confirmed.v1：

    {
  "reservationId": "inventory-reservation-uuid",
  "storeUuid": "store-uuid",
  "tradeOrderUuid": "trade-order-uuid",
  "storeOrderUuid": "store-order-uuid",
  "confirmedAt": "2026-07-26T12:00:02+00:00"
}

    inventory.reservation.rejected.v1：

    {
  "reservationId": "inventory-reservation-uuid",
  "storeUuid": "store-uuid",
  "tradeOrderUuid": "trade-order-uuid",
  "storeOrderUuid": "store-order-uuid",
  "reasonCode": "OUT_OF_STOCK",
  "reason": "One or more required materials are unavailable.",
  "rejectedAt": "2026-07-26T12:00:02+00:00"
}

    存储根据其本地 StoreOrder 验证所有相关 UUID。它只接受一个 当订单为awaiting_inventory时匹配已确认的事件；它只拒绝一个 匹配该状态下的拒绝事件。重复或延迟的事件是无害的空操作。 商店将库存 OUT_OF_STOCK 映射到其记录的 OUT_OF_STOCK 拒绝代码，并且 不向客户透露材料细节。

    5. 生命周期和补偿¶

    5.1 商店整合¶

    启用库存后，商店会更改其当前的自动接受行为：

    trade.order.created.v1
  -> Store creates StoreOrder
  -> validates Store policy
  -> generates reservationId
  -> StoreOrder.awaitInventory(reservationId)
  -> writes inventory.reservation.requested.v1 to Store Outbox
  -> Inventory outcome
  -> Store accepts or rejects and emits its existing Trade result event

    StoreOrder更新和Store请求发件箱插入发生在同一个Store本地 交易。不得从 Store 消费者同步调用 Inventory。

    当 Inventory 被禁用时，Store 不会创建预订 ID 或请求事件； 它遵循当前的直接接受路径。因此，如果没有预订， 故意的而非库存错误。

    5.2 取消发布¶

    Trade 最终必须为商店范围的订单发布 trade.order.cancelled.v1。商店 使用它，将本地操作标记为取消，然后发布 inventory.reservation.release.requested.v1 如果它有 reservationId。

    {
  "reservationId": "inventory-reservation-uuid",
  "storeUuid": "store-uuid",
  "tradeOrderUuid": "trade-order-uuid",
  "storeOrderUuid": "store-order-uuid",
  "reason": "trade_order_cancelled",
  "requestedAt": "2026-07-26T12:05:00+00:00"
}

    库存幂等地消耗释放。对于已确认的预订，它会递减 每个余额的 reservedQuantity，写入发布分类帐条目，标记预留 发布，并发布inventory.reservation.released.v1。对于被拒绝、释放或 消耗的保留不会产生第二个数量突变。商店不需要 等待发布确认以向 Trade 公开取消。

    5.3 消费¶

    库存仅在以后明确的商店履行边界处消耗，而不仅仅是 因为订单已付款。未来的 inventory.reservation.consume.requested.v1 必须 携带预订和商店订单 ID。它以原子方式减少现有的和 保留数量并写入consume分类帐条目。

    第一阶段创建 consume 状态和账本合约，但不添加 Store 直到产品的履行政策获得批准为止。这保持了 初始预订推出可逆，并防止库存意外减少。

    5.4 到期与对账¶

    expiresAt 是 Store 提供的快照。未来计划的清单命令发现 过期的确认保留，幂等地释放它们，并发出释放事件。 商店/贸易然后决定是否拒绝或取消商业订单。第一个 仅当商店接受截止日期和 取消发布一并实施；它不能默默地保留过期的 无限期保留。

    库存调节将每个余额与其分类账增量进行比较。任何维修都是 新的adjustment分类帐条目，绝不直接余额覆盖。

    6. 收件箱、发件箱和信使¶

    6.1 持久化消息记录¶

    InventoryConsumedEvent 遵循 StoreConsumedEvent：

    领域 目的
    eventId 唯一的代理事件幂等性密钥
    topic 版本化源事件主题
    aggregateId 来源聚合身份
    payloadHash SHA-256 全包审计值
    processedAt 消费时间

    InventoryOutboxMessage 跟随 StoreOutboxMessage 并包含 UUID eventId， 主题、聚合类型/ID、有效负载、发生时间、可用时间、发布时间、 尝试计数和最后一个错误。按 (published_at, available_at, id) 索引到期未发布的行。

    6.2 事件信封¶

    所有 Inventory 消息都使用已建立的版本化信封：

    {
  "eventId": "event-uuid",
  "type": "inventory.reservation.confirmed",
  "version": 1,
  "aggregateType": "inventory_reservation",
  "aggregateId": "inventory-reservation-uuid",
  "correlationId": "store-order-uuid",
  "causationId": "source-event-uuid",
  "occurredAt": "2026-07-26T12:00:02+00:00",
  "payload": {}
}

    发布者只是一个传输适配器。它获取到期的发件箱行，映射已知主题 尝试延迟可用性。它不做出股票决策。

    6.3 消息路由¶

    需要新的显式 DTO：

    DTO 发布者 消耗于
    ReservationRequestedMessage 商店 库存
    ReservationConfirmedMessage 库存 商店
    ReservationRejectedMessage 库存 商店
    ReservationReleaseRequestedMessage 商店 库存
    ReservationReleasedMessage 库存 存储（如果运营可视性需要）

    config/packages/messenger.yaml 将所有 DTO 路由到 async。调度程序调用 app:inventory:outbox:publish 与现有的贸易和商店发布商一起。的 工人仍然是messenger:consume async；没有消费者在 PHP-FPM 中运行。

    7. API 和授权¶

    库存API是第一阶段的管理API。顾客和店员看不到 材料名称、库存水平、配方、负余额信息或分类帐详细信息。 商店员工继续通过 StoreOrder 端点进行操作。

    方法 路径 角色 目的
    获取/发布/放置 /api/v1/manage/inventory/materials ROLE_ADMIN 管理材料
    获取/发布/放置 /api/v1/manage/inventory/recipes ROLE_ADMIN 管理一种规格配方和生产线
    获取 /api/v1/manage/inventory/stocks ROLE_ADMIN 列出持久余额
    获取 /api/v1/manage/inventory/stocks/{storeUuid}/{materialUuid} ROLE_ADMIN 平衡或虚拟零视图
    发布 /api/v1/manage/inventory/stocks/{storeUuid}/{materialUuid}/adjust ROLE_ADMIN 初始库存或审计调整
    放置 /api/v1/manage/inventory/stocks/{storeUuid}/{materialUuid}/policy ROLE_ADMIN 设置 allowNegativeStock
    获取 /api/v1/manage/inventory/reservations ROLE_ADMIN 预订审核/搜索
    获取 /api/v1/manage/inventory/reservations/{reservationId} ROLE_ADMIN 预订详情和已解决线路
    获取 /api/v1/manage/inventory/ledger ROLE_ADMIN 账本审计/搜索

    所有突变端点都需要一个原因，拒绝浮点数量，并使用 库存或预订字段的服务方法而不是通用实体更新。 通用 CRUD 仅适用于无害的材料元数据和配方创作； 控制器白名单必须排除所有记帐字段。

    7.1 管理调整请求¶

    {
  "quantityDelta": "50.000000",
  "reason": "initial_receipt",
  "referenceId": "purchase-order-123",
  "allowNegativeStock": false
}

    quantityDelta 已签名。负调整不得驱动现有量低于保留值 数量，除非allowNegativeStock=true；否则它已经失效了 确认预订。对于同一个管理引用，操作是幂等的 当提供参考时。

    9. 持久化和迁移计划¶

    一次清单迁移创建第一阶段表并且仅创建本地外键：

    表 关键约束和指标
    inventory_material 唯一uuid、唯一code、状态索引
    inventory_stock 唯一(store_uuid, material_id)，平衡查找索引，FK 到材质
    inventory_specification_recipe 独特的uuid，独特的specification_uuid
    inventory_recipe_line 独特的(recipe_id, material_id)，配方/材料的FK
    inventory_reservation 唯一的 uuid、唯一的 reservation_id、商店订单的唯一活动/请求密钥
    inventory_reservation_line 独特(reservation_id, material_uuid)，FK预订
    inventory_ledger_entry 操作/参考/材料幂等键，存储/材料/时间索引
    inventory_consumed_event 唯一的 event_id，处理时间索引
    inventory_outbox_message 唯一的 event_id，到期未发布的索引

    无迁移引用 trade_specification、trade_order、store_order 或 store 通过外键。 UUID关系有效性属于事件契约并且 本地快照，而不是数据库连接。

    10. 测试策略¶

    10.1 单元测试¶

    • 库存活动后的物料验证、状态更改和不可变的业务代码。
    • 配方唯一性、生产线数量验证和材料激活检查。
    • 库存可用数量计算和当地负库存政策。
    • 预订状态转换和不可变的线路快照。
    • 账本条目构建和参考幂等性。
    • 库存收件箱/发件箱实体元数据和发布者重试行为。

    10.2 服务和集成测试¶

    • 读取不存在的余额会返回虚拟零视图并且不会保留行。
    • 手动调整以原子方式创建余额和匹配的账本条目。
    • 配方扩展聚合了重复的规格和重复的材料需求。
    • 直接成品回退保留使用规范 UUID 编码的材料。
    • 配方或直接材料缺失会产生SPECIFICATION_NOT_STOCKABLE。
    • 禁用负库存拒绝在没有部分预订的情况下供应不足。
    • 启用负库存会创建或超额保留可审计账本行的余额。
    • 禁用负库存时，并发预订尝试不会超售。
    • 重复的eventId是一个空操作；具有相同输入返回的重复 reservationId 原始结果；冲突的副本会安全失败。
    • 数据库或传输错误回滚收件箱、余额、预订、分类帐和 一起发件箱。
    • 释放是幂等的，并使保留的数量再次可用。

    10.3 交叉捆绑测试¶

    • INVENTORY_ENABLED=false 保持当前商店直接接受并创建不 库存事件或记录。
    • INVENTORY_ENABLED=true 创建一个 Store 请求，在 awaiting_inventory 中等待，并且 仅在匹配库存确认后才接受。
    • 库存拒绝变为商店OUT_OF_STOCK，然后遵循现有贸易 拒绝/取消工作流程。
    • 交易取消会导致商店释放请求和库存释放而无需 改变历史预订线路。
    • 无效、过时、重复和不匹配的关联事件不会改变存储或 贸易订单状态。

    11. 实现顺序¶

    1. 添加此捆绑包的服务配置、路由、消息 DTO 路由和迁移。
    2. 实施材料、库存、配方、存储库和管理 API。
    3. 实施经过审核的手动库存调整和虚拟零读取行为。
    4. 实现预订服务、账本、收件箱、发件箱、发布者和测试。
    5. 在INVENTORY_ENABLED后面添加Store请求/结果行为。
    6. 添加取消驱动的发布和跨捆绑集成测试。 7.仅在相应的之后添加履行驱动的消费和到期调度 商店/贸易业务政策获得批准。

    此命令使库存模块保持可独立测试，同时使商店 集成是一种显式的、功能控制的部署，而不是对每个功能的隐式更改 订单流。
