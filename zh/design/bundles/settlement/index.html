    结算捆绑设计¶

    状态：仅设计，未实施。

    结算是一个通用的分配和结算规划域。它 接受已确认的资金事实，根据不可变的规则评估版本化规则 源上下文，生成可审核的收件人分配，并请求预订 通过主机提供的凭证端口。它有意独立于贸易 订单、付款发票和电子钱包实体。

    1. 目标和范围¶

    1.1 目标¶

    和解决定谁有权获得确认的金额、原因以及金额。 它在登记任何余额之前记录持久计划，执行每个分配 幂等地，并保留撤销该预订所需的确切引用。

    trusted funding source
  -> SettlementFundingConfirmed
  -> immutable source context
  -> versioned rules and recipient resolvers
  -> SettlementPlan + SettlementAllocation[]
  -> voucher booking adapter
  -> recipient accounts

    第一个主机集成将是已付款的付款发票。这只是一项资金 制片人。结算核心不得需要发票、订单、订单项目、 或任何存在的 Wallet 类。

    1.2 范围¶

    • 以稳定的标量引用为代表的通用、可信的资金来源。
    • 不可变的资金、背景、规则、接收者、计算和发布快照。
    • 一笔资金可以多次分配给不透明的接受者。
    • 可组合的资格规则和金额公式。
    • 通过受控插件可扩展的收件人解析。
    • 在固定的 18 位小数内部刻度上进行精确、任意精度的计算。
    • 确定性转换为目标帐户过帐规模，包括最大- 舍入灰尘的剩余分配。
    • T+0（默认）、延迟（T+N）和手动缺席/强制发布策略，所有 在资金离开结算边界之前在结算方安排。
    • 通过钱包实施的结算拥有的端口进行凭证支持的过账。一次 应用信用后，资金完全属于接收方，不再进行结算 与他们互动，除非冲销原始凭证。
    • 撤销原始过账凭证，绝不重新计算当前规则。
    • SQL 发件箱、收件箱重复数据删除、业务幂等性、重试和审计跟踪。
    • 当任何预订的结算金额尚未撤销时，付款退款将被阻止。
    • 管理读取、模拟、批准、重试、发布授权和撤销命令。

    1.3 明确的非目标¶

    初始捆绑包不得：

    • 直接依赖于App\Trade\Entity\Order、OrderItem、App\Payment\Entity\Invoice、 App\Wallet\Entity\Wallet，或者他们的存储库。
    • 存储跨捆绑 Doctrine 关联或外键。
    • 将任何任意对象、HTTP 请求或管理员输入视为证明 资金存在。
    • 执行数据库存储的 PHP、Symfony ExpressionLanguage、容器查找或 任意对象属性路径作为结算规则。
    • 使用 float、本机整数算术、隐式舍入或小数 数据库类型作为财务计算的真实来源。
    • 创建第二个钱包分类账、替代支付网关、税务引擎或 应收账款/应付账款子系统。
    • 通过创建一个账户，迫使余额不足的收款人为逆转提供资金 钱包余额为负。未来应收账款/应付账款功能拥有回收功能。
    • 第一阶段进行外汇兑换。一项计划只有一种单位/货币。
    • 从旧版 night-keeper 实现导入历史数据。

    1.4 重要术语¶

    术语 意义
    资金 由值得信赖的外部生产商提供的确认金额。
    来源 产生融资事实的外部业务聚合。
    背景 可用于和解规则的不可变的白名单事实。
    规则 资格、收件人解析和公式的版本化声明性定义。
    计划 确定资金金额及其计算分配的总额。
    分配 一位收件人的授权金额及其独立的过帐生命周期。
    发布 通过主机凭证边界预订分配。成功后
    信用证，该金额属于接收方，结算不会对其进行进一步管理。
    可用性政策 结算方安排何时过账。 T+0立即发帖；
    T+N/manual 将发布命令推迟到将来的某个时间。它不是钱包 held 状态。
    逆转 冲销确切的原始凭证支持信用。这是唯一的互动
    结算按照已过账的金额进行。
    确定性锁 在发布任何分配后，对付款退款进行源级阻止。
    后备分配 显式分配原本未分配的舍入或规则余数。

    2. 确认的产品决策¶

    以下决定是此设计的一部分，不得通过以下方式隐式更改： 实施细节。

    关注 决定
    初始触发 资助方在资金确认后即可制定计划。付款支付的是第一生产者。
    来源范围 任何受信任的来源类型都可以参与；发票和订单不是特殊的结算实体。
    计划币种 一项计划有一种货币/单位。外汇延期。
    收件人身份 RecipientReference(type, id) 是不透明且可扩展的。
    收件人关系 封闭接收者语法解析文字引用、冻结上下文候选或声明的事实。
    钱包丢失 当策略允许时，钱包适配器会自动配置映射帐户。
    计算精度 内部算术具有固定的 18 位小数位数。
    发帖精度 目标科目定义最终过账规模。现有人民币钱包使用美分（规模 2）。
    四舍五入 分配级别下限，然后是确定性最大余数分布。默认灰尘接收者为平台；规则可能会覆盖它。
    保护 仅当 unallocatedAmount == 0 时计划才能完成。
    后备范围 回退仅处理计算余数。失败的收件人过帐仍保留收件人的失败分配并重试。
    默认可用性 T+0 默认：结算立即过帐，并且收件人可以使用积分。
    延迟可用性 T+N/manual 是结算方发布时间表，而不是钱包可用性。一旦发放，资金完全属于收款人；结算不执行保留/释放。
    发布后退款 首次成功分配过账后，付款退款将被锁定。
    退款解锁 没有自动解锁。授权运营商必须完成所有已发布分配的撤销，然后明确解锁来源退款。
    逆转资金不足 撤销仍悬而未决，退款仍被阻止。未来的 A/R-A/P 模块可能会协调恢复。
    规则治理 发布的规则版本是不可变的；计划存储所使用的确切版本和跟踪。
    执行粒度 分配独立发布。计划可以是partially_posted。
    遗留数据 没有从 night-keeper 迁移。它只是产品参考输入。

    3. 所有权和依赖边界¶

    3.1 所有权矩阵¶

    关注 业主 结算责任
    外部收款/付款证明 付款、银行、提供商、财务流程 仅使用可信的资金事实。
    订单、商品、SKU、商店、员工关系 贸易/商店/主机域 仅通过端口接收规范化上下文。
    规则选择、计划、分配、状态 结算 权威性。
    收件人帐户映射和配置 钱包适配器/账户主机 解决不透明的收件人参考并创建帐户（如果允许）。
    钱包余额、优惠券、交易、可用性 钱包 权威性。应用积分后，钱包拥有可用性（包括任何不相关的 held 使用）。
    退款过渡 付款或来源所有者 询问通用最终性守卫；切勿直接检查结算表。
    未付冲销收款 未来A/R-A/P模块 超出结算范围。

    3.2 核心依赖规则¶

    Settlement 核心命名空间只能导入 Core 基础设施及其自己的类。 它不得导入相邻的域名称空间：

    forbidden from src/Settlement core:
  App\Trade\*
  App\Payment\*
  App\Wallet\*
  App\Store\*
  App\Identity\Entity\User

    主机应用程序可以在拥有的相邻模块中提供适配器，例如：

    src/Payment/Integration/Settlement/PaymentFundingPublisher.php
src/Trade/Integration/Settlement/TradeSettlementContextResolver.php
src/Wallet/Integration/Settlement/WalletSettlementVoucherPort.php
src/Settlement/Integration/Payment/SettlementPaymentRefundGuard.php

    最后一个适配器是集成外壳，而不是结算核心。它实现了一个 支付拥有的扩展合约，调用结算拥有的应用接口。 这可以防止循环实体或存储库依赖。

    3.3 仅稳定引用¶

    每个跨界字段都是标量字符串、UUID、代码或不可变快照。 本地数字主键只能在一个模块内使用。

    价值 示例 禁止更换
    资金来源 payment_invoice:7b4... ManyToOne Invoice
    主题 trade.order.v1:0ae... ManyToOne Order
    收件人 store:3d1... ManyToOne Store
    优惠券收据 不透明 voucherReference ManyToOne Voucher
    事件关联 UUID 另一个模块的整数 ID

    3.4 为什么不重用旧版 Settle 模块¶

    night-keeper 展示了成熟的业务需求：多接收者计划、 优先级规则、固定/比例金额、执行前生成和逆转。 这里采用了这些概念。它的实现故意不被重用：

    • 它使Settle成为OrderItem的OneToOne扩展。
    • 它将接收者身份与用户/员工/商店 ORM 关系联系起来。
    • 它根据服务容器评估存储的表达式。
    • 它假设固定的admin -> store -> beneficiary钱包路线。
    • 它使用浮动算术并重新推导逆转交易对手。
    • 只有布尔结算状态，没有持久消息幂等性。

    解决方案在替换这些实现的同时保留了产品的表现力 具有显式端口、快照、状态机、任意精度的选择，以及 凭证参考。

    5. 资助合同¶

    5.1 资金不是发票¶

    计划从已确认的资金事实开始。它不是从订单开始， 订单项、发票、钱包交易或任意对象。

    实施后符合资格的生产者示例：

    来源类型 授权确认示例
    payment.invoice.v1 付款标记已付款的发票并写入发件箱事件。

    6. 源上下文¶

    6.1 目的¶

    资金证明金额存在。源上下文提供了做出决定所需的事实 应该如何分配。和解永远不会遵循以下教义路径：

    orderItem.order.store.owner

    相反，源模块将必要的事实投射到冻结的白名单中 SettlementContext。

    事实是扁平的、明确命名的，并且由源上下文进行版本控制。他们不是一个 通用属性访问语言。

  "order.storeUuid": "...",
  "order.completedAt": null,
  "order.customerUuid": "...",
  "line.count": 2,

    一份订单仍然是一项资金和一项计划。源适配器还可以提供 冻结项目上下文； order_item 规则对每个项目评估一次并创建不同的 该计划内的分配。必须明确分配依据。一定不能 假设当前的OrderItem::price是权威的，其中订单级促销 没有分配给线路。

    每个项目上下文都有一个不可变的项目 ID、平面 item.* 事实、可选的项目级别 收件人候选者和审核快照。项目事实覆盖订单事实，而 项目被评估。他们无法检查其他物品或实时源实体。

    6.4 上下文解析器规则¶

    • 解析器在查询其自己的模块之前验证其主题类型/版本。
    • 解析器执行一个标量投影查询或等效的有界读取；它 不会将实体或代理泄漏到上下文中。
    • 缺少来源、不受支持的状态、不一致的货币和不明确的商业 基础是明确的领域错误，而不是空洞的事实。
    • 解析器仅提供具有记录的业务目的的事实。
    • 解析器可以提供指定的收件人候选者，但它们是快照，并不 授予钱包访问权限。
    • 例如，源上下文演变需要新的源版本 trade.order.v2；现有规则/计划保留其历史快照。

    7. 规则模型和表达能力¶

    7.1 规则结构¶

    SettlementRuleVersion 是一个不可变的已发布定义。可以对草稿进行编辑； 发布会创建一个新版本，并且不会改变计划使用的已发布版本。

    {
  "appliesTo": ["trade.order.v1"],
  "scope": "order",
  "conflictMode": "stack",
  "eligibility": {
    "all": [
      {"factEquals": ["order.status", "paid"]},
      {"factIn": ["order.storeUuid", ["store-uuid"]]}
    ]
  },
  "recipient": {"resolver": "context_candidate", "key": "store.owner"},
  "formula": {"rateOf": {"basis": "funding.distributable", "bps": 8000}},
  "reasonCode": "store_revenue"
}

    priority、effectiveFrom 和 effectiveTo 是版本元数据而不是 定义字段。管理客户端创建规则草案、创建或更新规则 草稿版本，然后发布该版本。 GET /manage/settlement-rules/configuration 返回接受的操作名称和必填字段。

    POST /manage/settlement-rules
POST /manage/settlement-rule-versions
PUT  /manage/settlement-rule-versions/{versionUuid}
POST /manage/settlement-rule-versions/{versionUuid}/publish

    该定义仍然是用于持久性和 API 传输的 JSON，但它是由 严格、封闭的结算评估员。未知节点、未知事实、畸形金额 字符串和不受支持的货币行为在发布之前会被拒绝。

    7.2 规则选择¶

    规则选择是确定性的：

    1. 解析上下文并从注入的时钟中捕获一个asOf时间。
    2. 按源类型、启用状态、生效时间间隔查询活动规则版本。
    3. 按priority ASC排序，然后是不可变规则UUID ASC。
    4. 根据上下文版本验证每条规则。
    5. 评估其资格谓词。
    6. 对 order 规则评估一次，然后对每个 order_item 规则评估一次 冻结项目上下文；在每个范围/项目内独立应用冲突模式。
    7. 应用计划级保存和舍入。
    8. 仅当每次验证都成功时才创建计划。

    第一阶段支持的冲突模式：

    模式 意义
    stack 规则可以与其他匹配规则一起添加分配。
    exclusive_group 命名组中第一个匹配的规则获胜；该组中的后续规则将被跳过。
    stop 匹配的规则在其提案被接受后结束进一步的规则选择。

    规则范围默认为order。 order_item 需要来自源的项目上下文 适配器。它的分配键会自动指定为特定于项目，即使有多个 项目会解析到同一收件人，因此每个项目都保持独立可审核性。

    每条合格线的代理奖励可以表示为：

    {
  "appliesTo": ["trade.order.v1"],
  "scope": "order_item",
  "eligibility": {
    "all": {
      "children": [
        {"factEquals": ["item.specificationId", 32]},
        {"amountAtLeast": ["item.unitPrice", "3.01"]}
      ]
    }
  },
  "recipient": {
    "resolver": "fact_reference",
    "typeFact": "order.agentRecipientType",
    "idFact": "order.agentRecipientId"
  },
  "formula": {
    "multiplyByQuantity": {
      "value": {"fixedAmount": {"amount": "3.00"}},
      "quantity": "item.quantity"
    }
  },
  "reasonCode": "agent_specification_reward"
}

    对于人民币，上面的item.unitPrice是十进制快照金额； 3.01表示严格 大于 3.00 而当前语法提供包含量比较。 每个生成的分配都会保留源项目 ID 和不可变项目快照。

    7.3 资格原语¶

    规则保持小且可组合。初始原语是：

    原始 意义
    FactEquals 声明的事实和标量文字完全相等。
    FactIn 事实属于已声明的标量列表。
    IntAtLeast / IntAtMost 已声明事实的整数比较。
    AmountAtLeast / AmountAtMost 精确的量子量比较。
    OccurredBefore / OccurredAfter 使用 ISO-8601 事实进行即时比较。
    AllOf 所有子谓词都必须通过。
    AnyOf 至少必须通过一个子谓词。
    Not 恰好否定一个子谓词。

    故意没有 eval，没有通用方法调用，没有对 Symfony 服务的访问， 并且没有可以遍历对象图的表达式。必须进行更复杂的匹配 在到达结算之前投射到源事实中。

    7.4 公式原语¶

    原始 结果
    FixedAmount 字面精确的十进制数。
    FactAmount 声明的量子量事实。
    FundingAmount 该计划的可分配资金金额。
    RateOf 使用基点的子公式的精确分数。
    MultiplyByQuantity 公式和声明的整数的乘积。
    Add / Subtract 对孩子进行精确算术。
    MinOf / MaxOf 确切的最小/最大子代数。

    在计划级别舍入之前，所有公式结果都是精确的非负有理值。 Subtract 和 Remaining 必须拒绝否定结果。规则可能不会默默地改变 负数变为零。

    7.5 收件人解析¶

    接收者关系在冻结上下文上使用封闭配置语法：

    旋转变压器 输入 结果
    literal 配置类型/id 固定平台或指定收件人。
    context_candidate 候选键 由源适配器投影的接收者。
    fact_reference 声明 recipient.* 事实对 规范化的源事实接收者。
    源适配器必须将更多关系投射到接收者候选者中或
    宣告的事实。在计划创建后，他们可能无法读取实时订单/员工/用户实体。

    7.6 高级规则¶

    如果一个稳定的业务关注点不能被表达为原语，它可以实现：

    interface SettlementRuleHandlerInterface
{
    public static function getName(): string;

    public static function getVersion(): int;

    /** @param array<string, mixed> $config */
    public function propose(SettlementContext $context, array $config): array;
}

    该处理程序仅返回 AllocationProposal 值对象。它不得发布优惠券， 更改计划状态、加载跨模块实体、访问 Symfony 容器或执行 网络输入/输出。每个处理程序都需要显式的单元测试、版本化的配置模式，以及 便于审计的解释负载。

    8. 精确资金和溢出安全¶

    8.1 硬性规则：无浮动¶

    结算财务代码不得使用 PHP float、round()、(int) 类型转换 金融价值，或货币字符串的本机算术。 PHP的有符号整数范围是 对于任意 18 位数值来说是不够的，并且乘法可能会在 验证看到结果。

    8.2 所需的库¶

    实现必须添加 brick/math 作为生产依赖项。它提供了不可变的、 任意精度的数字对象，而不使 ext-bcmath 或 ext-gmp 成为 未声明的部署先决条件。

    类型 结算使用
    Brick\Math\BigInteger 规范量子整数、总数、排名和目标发布单位。
    Brick\Math\BigRational 精确的百分比、除法和中间公式结果。
    Brick\Math\BigDecimal 解析/显示并转换为声明的比例。
    Brick\Math\RoundingMode 每次故意丢失精度的转换时都需要。

    8.3 金额表示¶

    ExactAmount 不是 PHP 标量货币整数：

    quantum integer string: "12345678901000000000"
scale:                  18
display decimal:        12.345678901000000000
currency:               CNY

    数据库将量子整数保存为规范的以 10 为基数的字符串。这样就避免了 数据库小数精度限制和 PHP 整数溢出。它没有 + 标志，没有 除了 "0" 之外，前导零，并且没有小数点分隔符。

    final readonly class QuantumAmount
{
    public function __construct(
        public string $quantum,
        public int $scale,
        public string $currency,
    ) {
    }
}

    初始比例固定为18。币种目标钱包发币规模独立 此计算比例：现有人民币钱包的比例为2，积分可能为0，并且 未来的令牌帐户可能是18。

    8.4 公式评估¶

    公式计算尽可能长时间地保持分数精确：

    $basis = BigRational::of($context->distributableAmountQuantum());
$commission = $basis->multipliedBy('1500/10000');

    不会仅仅因为中间运算包含一个公式就将其转换为 18 级 师。非终止结果仍然是有理数。转换仅发生在 该计划的明确分配量子边界和最终目标发布规模。

    每个部门必须有以下结果之一：

    • 精确除法：使用精确结果。
    • 故意分配舍入：使用记录的舍入算法。
    • 要求精确但无法表示的规则：拒绝带有 域错误。

    8.5 转换为钱包过账单位¶

    令C = 18为计算规模，P为目标发布规模。对于人民币钱包， P = 2。转换系数为10^(C - P)。

    walletMinor = allocationQuantum / 10^(18 - postingScale)

    这种转换可能不准确。捆绑包在整个计划中处理它，而不是每行：

    1. 准确评估所有匹配的分配。
    2. 验证确切的分配总额是否小于或等于资金。
    3. 将每个分配按楼层转换为其目标过帐单位，直至为零。 4.保留其精确的小数余数和稳定的分配UUID。
    4. 根据资助金额确定可用目标单位总数。
    5. 通过降序余数分配剩余的整数单位。
    6. 通过不可变分配 UUID 升序打破相等余数。
    7. 如果存在已配置的后备收件人，它将在此之前接收规则剩余部分 最终分配；默认后备是平台接收者。
    8. 保留准确金额、公布金额、舍入增量、排名和政策快照。
    9. 在编写计划之前主张目标单位的保护。

    所选策略是largest_remainder。它是确定性的、可解释的，并且 不铸造也不燃烧一分钱。

    8.6 守恒不变量¶

    按计算规模：

    fundingAmount = allocationAmountTotal + unallocatedAmount

    最终过帐规模：

    fundingPostingAmount = sum(allocation.postingAmount) + unallocatedPostingAmount

    在计划被标记为 posted、reversal_pending 或 reversed 之前，它 必须满足：

    unallocatedAmount = 0
unallocatedPostingAmount = 0

    后备分配是具有真实接收者、规则跟踪和 优惠券。这不是未跟踪的会计调整。

    8.7 护栏¶

    • 比例必须在有界配置范围0..18内；第一阶段将其修复为 18。
    • 量子字符串长度在解析为之前具有实现配置的最大值 避免基于输入的内存滥用。
    • 规则金额、比率值、数量事实和公式深度具有有限模式。
    • 第一阶段的利率值表示为整数基点；任意小数 费率需要专门的审查原语。
    • 所有金额比较都使用 BigInteger/BigRational，而不是词汇字符串。
    • 钱包适配器验证最终发布整数是否符合钱包支持的要求 数据库/PHP 范围。超出范围的分配将成为不可重试的手动审核 失败；它永远不会被截断。

    9. 领域模型¶

    9.1 实体概述¶

    实体 表 目的

    SettlementReversal settlement_reversal 一名操作员授权的逆转操作及审核理由。

    10. State Machines¶

    10.1 Plan State¶

    stateDiagram-v2
    [*] --> planning
    planning --> planned: calculation + conservation pass
    planned --> posting: posting outbox claimed
    posting --> partially_posted: at least one allocation posted
    posting --> posted: every allocation posted
    partially_posted --> posted: remaining allocations posted
    posting --> failed: no allocation posted and non-retryable failure
    partially_posted --> reversal_pending: authorized reversal requested
    posted --> reversal_pending: authorized reversal requested
    reversal_pending --> reversed: all posted allocations reversed
    reversal_pending --> reversal_failed: non-retryable reversal failure
    reversal_failed --> reversal_pending: authorized retry

    The persisted implementation may derive posting, partially_posted, and posted from allocation state, but externally visible state must have these semantics.

    planned does not lock a source refund. The first posted allocation sets refund_locked_at; therefore a partially_posted plan already has finality lock.

    A plan has no Wallet-side hold/release state. Once an allocation is posted, the funds belong to the recipient and the plan only tracks the reversal evidence of those vouchers.

    10.2 Allocation State¶

    stateDiagram-v2
    [*] --> planned
    planned --> posting_requested: immediate policy, or delayed/manual policy becomes due
    posting_requested --> posted: credit voucher applied
    posting_requested --> retryable_failure
    retryable_failure --> posting_requested
    planned --> cancelled: reversal requested before posting
    posted --> reversal_requested
    reversal_requested --> reversed
    reversal_requested --> reversal_pending: insufficient recipient balance
    reversal_pending --> reversal_requested: retry / A-R-A-P recovery

    There is no transition from a posted allocation back to planned, no replacement recipient, and no rewritten amount. There is no release transition because Settlement never holds funds after posting: post() is the moment ownership transfers to the recipient, and reversal of that voucher is the only later operation.

    10.3 Refund Finality State¶

    Settlement owns the evidence but the funding source owns its refund state:

    no posted allocation
  -> refund eligibility is source-defined

first successful allocation posting
  -> Settlement records refund_locked_at
  -> Payment/producer rejects refund

authorized complete Settlement reversal
  -> all posted allocation vouchers reversed
  -> Settlement records refund_unlocked_at
  -> Payment/producer may execute its normal refund process

    There is intentionally no timer that automatically unlocks a source refund. Settlement-side posting scheduling changes when a credit is handed to the recipient, not whether funding finality exists once that credit is handed over.

    11. Wallet Voucher Boundary¶

    One-way handoff. Settlement decides when a confirmed allocation becomes the recipient's money and posts that allocation through the voucher boundary. From the moment the credit voucher is applied, the funds are unconditionally the recipient's; Settlement performs no balancing, no held freeze, no release, and no partial management of that money. The only later operation is reversing the exact original voucher.

    11.1 Settlement-Owned Port¶

    Settlement owns the contract below and never returns a Wallet entity or Voucher entity:

    interface SettlementVoucherPort
{
    /**
     * Credit the recipient's account. On success the amount is unconditionally theirs.
     * @throws SettlementVoucherException on rejection or non-retryable mapping failure
     */
    public function post(ConfirmedAllocation $allocation): VoucherPostingReceipt;

    /** Reverse the exact original posting; insufficient funds is a classified result. */
    public function reverse(PostedAllocation $allocation, ReversalRequest $request): VoucherPostingReceipt;
}

    VoucherPostingReceipt contains Settlement-safe scalars only:

    final readonly class VoucherPostingReceipt
{
    public function __construct(
        public string $externalReference,
        public string $idempotencyKey,
        public \DateTimeImmutable $processedAt,
        public string $status,
    ) {
    }
}

    externalReference is opaque to Settlement. The Wallet implementation may use a Wallet voucher UUID; Settlement cannot parse it or query it.

    11.2 Wallet Adapter Responsibilities¶

    The Wallet adapter:

    1. Maps RecipientReference(type, id) and currency to an account provisioning policy.
    2. Creates the Wallet if it does not exist and the reference type is permitted to own a Wallet for that currency.
    3. Validates Wallet currency, frozen state, posting range, and recipient mapping.
    4. Calls Wallet's voucher-backed credit gate with voucherType = settlement.
    5. Uses allocation UUID as stable voucher source and a deterministic reference id, for example settlement-credit:{allocationUuid}.
    6. Returns an opaque voucher receipt for a successful credit.
    7. Uses the original opaque voucher reference to reverse exactly the original booking.

    The adapter may depend on Wallet services because it belongs at the Wallet integration edge. Settlement core does not.

    11.3 Voucher Semantics¶

    For a successful allocation posting:

    Voucher type:       settlement
Voucher source ID:  allocation UUID
Reference ID:       settlement-credit:{allocation UUID}
Direction:           credit
Fund source:         external (the confirmed funding entered the Wallet boundary)
Created by:          settlement

    Wallet's existing unique referenceId and (voucherType, voucherId) constraints are both required. The adapter MUST verify that a duplicate receipt matches allocation, recipient wallet, amount, currency, direction, and applied status before treating it as success.

    11.4 T+0, T+N, And Manual Posting Scheduling¶

    T+0 is the default: excess ownership is immediate. Delayed and manual policies are Settlement-side scheduling decisions about when to post the credit, not Wallet-side availability controls.

    发布政策 结算行为 收件人所有权
    immediate（T+0，默认） 计划创建后立即运行发布命令。 在信用申请时。
    delayed (T+N) 发布命令安排在posting_available_at；调度程序在该时间/之后运行它。 预定过帐后的信用申请。
    manual 过帐命令将保留在结算中，直到授权操作员批准为止。 批准后进行信贷申请。

    对于延迟策略，调度程序必须等到 posting_available_at 才能发布 发布命令。 posting_available_at 在规划期间计算并冻结。的 规则或资金政策必须说明其业务日历语义：下一个结算日 与严格的持续时间相比。该实现应该使用注入的业务日历 服务而不是默默地将 T+1 解释为 24 小时。

    manual 发布需要授权操作员命令。 manual 分配等待 planned 直到批准设置其 posting_available_at （过去）或发出过帐 直接命令。

    因为过帐是所有权转移，所以安排延迟/手动分配是 仍然受与 T+0 相同的发布幂等性、重试和反转规则的约束。那里 没有 held 金额，没有 release 命令，并且在任何地方都没有单独的 held 余额。

    11.5 钱包最终确定¶

    一旦post()返回分配的成功收据：

    • 存入金额为收款人的无条件余额。
    • 结算不会跟踪该余额的可用性、支出或部分所有权。
    • 结算不执行补偿日记账分录、保留或冻结该款项。
    • 唯一的结算操作是冲销原始凭证，该凭证已被处理 与任何主机存款冲销一样：它会扣除收件人的可用余额。
    • 结算不需要held列、发布状态或发布调度程序。

    这保持了边界的干净：结算控制着结算的时间和正确性 分配和钱包（已经拥有余额，出于其他目的持有，冻结 标志和反转语义）拥有信用之后的一切。

    11.6 反转语义¶

    冲销始终针对原始结算凭证：

    原始状态 钱包效应
    发布 借记收款人的可用余额；写出原始信用凭证的冲销。
    未发布（立即/延迟/手动到期） 取消分配；没有钱包通话。

    如果分配后可用余额不足，钱包 返回分类的资金不足结果。结算记录reversal_pending， 保持资金退款锁定，不进行补偿性调整。未来应收款 模块可以解决债务，然后允许重试，但它不能重写此历史记录。 结算不会产生负余额来强制逆转。

    11.7 需要更改钱包¶

    现有的钱包存款/反向支持凭证来源。唯一需要的钱包端 结算的扩展是 settlement 的凭证提供者/授权路径 优惠券类型：

    • 在钱包内添加结算拥有的凭证提供商/授权路径。
    • 复用Wallet现有的存款+凭证+交易原子性作为信用。
    • 重复使用 Wallet 现有的存款冲销进行冲销；没有 held 集成 结算所需。
    • 保留钱包的交易、凭证、锁、货币、幂等性和对账 不变量。
    • 不要通过通用自助服务 HTTP 端点公开这些操作。

    结算功能交付不需要 Wallet.held 进行任何更改。钱包仍可使用 held 用于与结算无关的完全独立的商业目的；结算必须 不依赖它。

    12. 支付退款锁定集成¶

    12.1 通用支付扩展点¶

    付款应公开通用的、带标签的退款保护合同，而不是导入 结算：

    interface PaymentRefundGuardInterface
{
    public function supports(string $sourceType): bool;

    public function assertRefundAllowed(string $sourceId, int $amount, string $currency): void;
}

    结算集成适配器为其拥有的源类型实现此接口。 在将发票转换为退款工作之前，付款会调用所有适用的防护措施。 适配器仅使用标量源标识来请求 SettlementFinalityService。

    这使得未来的资金消费者能够定义自己的最终性保护，而无需做出任何决定 付款知道任何结算表或实体。

    12.2 退款规则¶

    对于任何已成功发布分配的来源：

    refund requested
  -> guard sees refund_locked_at and no refund_unlocked_at
  -> reject with a stable business error
  -> operator requests full Settlement reversal
  -> every posted allocation reverses the original voucher
  -> operator explicitly unlocks the plan/source
  -> normal Payment refund may proceed

    当计划在第一阶段最终锁定时，不允许部分付款退款。 支持比例部分退款需要未来的分配级别设计 部分冲销、四舍五入剩余所有权和源级退款总额。

    12.3 显式解锁¶

    解锁是一个授权的、可审计的命令。它需要：

    • 计划状态reversed。
    • 发布前的每个分配reversed或cancelled。
    • 两个计划 unallocated 字段均为零。
    • 记录的撤销请求 UUID 和操作员原因。
    • 没有待处理的发件箱命令用于过帐、过帐取消或撤消。

    解锁本身并不退款。只允许源码所有者正常退款 过程开始。

    13. 可靠处理和幂等性¶

    13.1 本地事务边界¶

    计划创建交易：

    Settlement transaction:
  validate inbox event
  + persist consumed event
  + resolve and snapshot context
  + select/evaluate/snapshot rules
  + create plan and allocations
  + assert conservation
  + insert posting outbox commands
  + commit

    本次交易中未调用任何凭证。收件人发帖是外部的 边界，即使在共享一个数据库的模块化整体中，因为它属于钱包 并且必须独立地容忍重试。

    settlement.allocation.post.cancel.v1 分配UUID 在运行之前反转/撤回 delayed/manual 发布命令（发布取消）。
    settlement.allocation.reverse.requested.v1 分配UUID 要求撤销原始凭证。

    没有 release 发件箱消息。发布就是交接；没有第二个 使资金可用的结算行动。

    13.3 发布处理程序¶

    receive allocation-post command
  -> lock/load allocation by UUID
  -> if already posted: verify receipt and acknowledge
  -> if cancelled/reversed: acknowledge as obsolete
  -> if posting_policy is delayed and not yet due: re-defer the command
  -> call SettlementVoucherPort.post(allocation)
  -> transactionally record immutable receipt and posted state
  -> set plan refund_locked_at if this is first successful posting
  -> recompute plan aggregate state

    如果钱包发送成功但处理程序在保留收据之前崩溃，请重试 使用相同的posting_idempotency_key；钱包返回原始凭证收据。

    不可重试 收件人类型未知、货币映射无效、目标金额超出范围 标记分配失败，计划仍不完整/手动审核。
    需要恢复 收款人缺乏可用于撤销的资金 标记reversal_pending；保持退款锁定。
    诚信冲突 有效负载/收据发生变化的重复密钥 停止处理、警报、人工审核。

    执行失败永远不会将其金额路由到后备接收者。后备只是 对于计算出的有效余数，它本身会像每次分配一样发布/重试。

    13.5 并发¶

    • 收件箱唯一密钥序列化重复的传输传递。
    • 计划资金唯一键序列化重复的资金事实。
    • 分配源 UUID 和发布幂等键序列化重复发布。
    • 钱包执行自己的锁和凭证唯一密钥保护。
    • 计划的聚合状态在计划行锁或原子版本控制下重新计算 分配转换后更新。
    • 发件箱索赔租约可防止重复的中继工作，但并不完全依赖于发件箱索赔租约 曾经的行为。
    • 反转命令与发布安全竞争：分配状态被锁定；未发布的 分配被取消（包括尚未执行的 delayed/manual 发布命令 运行），而过帐分配则冲销其记录的收据。
    • delayed 发布命令通过手动批准或发布取消安全运行： posting_idempotency_key 的发布是幂等的，因此在 分配被取消或撤销被确认为已过时。

    14.管理API和授权¶

    14.1 API原理¶

    结算计划、分配、过帐金额和状态转换都是财务性的 记录。通用 CRUD 端点不得允许直接突变或删除它们。 控制器向应用程序服务发出命令。

    14.2 建议的管理命令¶

    端点概念 命令 所需授权
    创建/更新规则草案 规则草稿命令 结算规则管理员。
    发布/撤销规则 规则治理命令 单独的审批者或特权财务角色。
    模拟 针对提供的可信/已清理的固定装置上下文进行纯计算 规则管理员；没有持久性或优惠券调用。
    阅读计划/分配 查询 范围内的财务/审计许可。
    重试分配 重新排队现有分配发布命令 运营角色。
    批准手动发布 授权manual分配的发布命令 结算过帐权限。
    取消待发帖 在运行之前撤回 delayed/manual 发布命令 运营角色。
    请求撤销 创建 SettlementReversal 财务逆转权。
    重试反转 重新排队现有反转命令 财务逆转权。
    解锁源码退款 明确的最终性解锁 冲销证明后的财务当局。

    所有命令请求都需要客户端幂等性密钥，人们可以在其中重试操作。 参与者身份、角色/授权原因、请求 ID、时间戳和已清理的信息 请求元数据包含在审核记录中。

    14.3 读取安全性¶

    分配接收者、资金和审计参考资料都是敏感的。读取 API 不得 重用订单/商店连接进行授权。结算查询授权使用 接收计划/源标量参考和参与者声明的专用策略。安 集成适配器可以通过接口提供特定于源的范围检查；它 不得将源实体泄漏到结算域中。

    15. 可观察性、审计和对账¶

    15.1 所需的审核证据¶

    完成的分配必须回答所有这些问题，而无需加载另一个 模块的可变数据：

    • 分配了哪些确认的资金？
    • 使用了哪些来源/上下文事实，它们的哈希值是什么？
    • 应用了哪个规则版本和收件人解析器版本？
    • 计算出什么精确的理性/公式结果？
    • 它是如何转换为最终过账单位的？每个剩余单位去了哪里？
    • 哪个收件人参考收到了它？
    • 哪个凭证收据预订了它，何时以及使用什么幂等密钥？
    • 哪个发布策略安排了它，以及在什么时间posting_available_at？
    • 是否被冲销、由谁冲销、为何冲销以及使用哪张原始凭证冲销收据？

    15.2 指标¶

    实现应该使用现有的核心指标方法添加模块指标：

    settlement_plans_total{status,currency}
settlement_allocations_total{status,recipient_type,currency}
settlement_outbox_backlog{topic}
settlement_posting_failures_total{class}
settlement_reversal_pending_total{currency}
settlement_pending_posting_total{policy}           # delayed/manual allocations awaiting their posting command
settlement_unallocated_amount_quantum{currency}
settlement_refund_locks_total{source_type}

    金额可以导出为仔细记录的十进制字符串或仅在以下情况下转换： 指标后端支持任意精度。 Prometheus 浮体样本不得 用作财务真相。

    15.3 和解¶

    结算对账将其不可变的分配收据与钱包的进行比较 边界券：

    结算领域 钱包凭证领域
    分配UUID voucher_id 对于类型 settlement
    发布幂等性密钥 reference_id
    过账金额/币种 优惠券金额/货币
    发帖参考 钱包凭证外部身份
    反转参考 原始凭证冲销身份

    任何不匹配都是诚信事件。和解报告了这一情况，但没有默默地报告 通过调整计划或钱包余额来修复资金。

    16. 数据库迁移要求¶

    迁移必须可跨 SQLite 测试、PostgreSQL CI 和 MySQL 部署进行移植。 避免特定于数据库的 JSON 路径逻辑或财务值的数字转换。

    所需索引包括：

    settlement_rule:
  UNIQUE(uuid)
  UNIQUE(code)

settlement_rule_version:
  UNIQUE(uuid)
  UNIQUE(rule_uuid, version)
  INDEX(status, effective_from, effective_to)

settlement_plan:
  UNIQUE(uuid)
  UNIQUE(funding_id)
  UNIQUE(source_type, source_id, funding_kind)
  INDEX(status, created_at)
  INDEX(source_type, source_id)
  INDEX(refund_locked_at, refund_unlocked_at)

settlement_allocation:
  UNIQUE(uuid)
  UNIQUE(plan_uuid, allocation_key)
  UNIQUE(posting_idempotency_key)
  UNIQUE(reversal_idempotency_key)
  INDEX(plan_uuid, status)
  INDEX(status, next_attempt_at)
  INDEX(posting_policy, posting_available_at, status)   # scheduler picks due delayed/manual postings
  INDEX(posting_due_at, status)                         # scheduler/cancel sweeps

settlement_reversal:
  UNIQUE(uuid)
  UNIQUE(idempotency_key)
  INDEX(plan_uuid, status)

settlement_consumed_event:
  UNIQUE(event_id)

settlement_outbox_message:
  UNIQUE(event_id)
  INDEX(published_at, available_at)
  INDEX(claimed_at)

    该模式将金融量子值存储在 VARCHAR 列中，并附有记录 最大长度，不是 BIGINT 或 DECIMAL。应用程序级规范格式验证 是强制性的；仅在可移植的情况下才可以添加可选的数据库检查。

    17. 实施阶段¶

    每个阶段都是可独立审查和测试的。后续阶段不得绕过 与早期阶段相比不变。

    相 范围 所需证据
    P0 添加brick/math；精确数量/舍入基元；单元测试。 不使用浮子；溢出和18级测试。
    P1 结算模式、计划/分配聚合、规则版本、纯模拟。 规则和守恒集成测试。
    P2 上下文解析器/接收者解析器注册表和一个通用夹具适配器。 快照和插件合约测试。
    P3 结算收件箱/发件箱、发布端口、假适配器、分配状态机。 重复、崩溃/重试、部分后期集成测试。
    P4 钱包结算适配器（仅限优惠券提供商路径）、立即 T+0 过账、优惠券收据核对。 真实钱包凭证交易测试。
    P5 付款发件箱生产者和通用退款保护/最终性集成。 付费发布和退款前撤销 E2E 测试。
    P6 结算端T+N及手动过账调度、过账取消、调度器投递。 发布时间表、批准和取消比赛测试。

    贸易环境适配器和非支付资金生产者可以独立交付 P2之后。即使 P5 是第一个生产集成，该核心仍然是通用的。

    18. 测试策略和强制不变量¶

    18.1 单元测试¶

    面积 所需案例

    18.2 集成测试¶

    边界 所需案例
    学说 每个唯一的键、不可变的快照行为、实用的查询索引。
    资金收件箱 首次交付、同事件重试、新事件同资金、改变重播冲突。

    上下文适配器 标量投影、源缺失、禁止源状态、不受后来突变影响的快照。

    18.3 架构测试¶

    自动化架构检查应强制执行：

    • src/Settlement核心不导入贸易、支付、钱包、商店或身份实体 命名空间。
    • 规则实现不使用 Symfony 容器、Doctrine EntityManager 或 网络客户端。
    • 财务结算代码不使用float、round()、bc*、本机货币 强制转换或 number_format() 作为计算输入。
    • 源适配器仅返回标量上下文和RecipientReference值对象。
    • 凭证端口 DTO 不包含钱包实体类型。

    18.4 端到端场景¶

    至少，一次性环境烟雾流量必须证明：

    1. 付款确认一笔资金金额。
    2. 和解创建了一个不可变的、保守的计划，其中包含多个接收者以及任何 配置后备分配。
    3. 尽管重新交付，钱包每次分配只会收到一张优惠券/交易。
    4. T+0 收款人余额立即可用。
    5. 首次分配过帐后，付款退款将被阻止。
    6. 操作员冲销冲销确切的过帐凭证。
    7. 明确的最终性解锁可以实现正常的来源退款。
    8. T+N 分配在预定时间之前不会发布，然后只发布一次； 发布前可以取消，发布后只能通过 原始凭证（没有持有/释放阶段）。

    建筑边界是固定的。以下是部署/产品配置 在启用生产者进行生产之前必须选择：

    决定 初始默认
    初始可信资金生产者 仅限付费发件箱适配器。
    初始源上下文主题 记录的支付/贸易集成主题，而不是直接实体访问。

    • [ ] brick/math 添加并用于所有结算财务计算。

    • [ ] 每个资金生产者以原子方式写入其源突变和发件箱事件。
    • [ ] 每个消耗的事件、计划、分配过帐、过帐取消和冲销都有一个 稳定的数据库支持的幂等性密钥。
    • [ ] 上下文、规则、接收者、计算、舍入和接收证据被冻结。
    • [ ] 每个计划都通过 unallocated = 0 展示了精确的目标单位保护。
    • [ ] 回退余数是正常分配，绝不是隐式调整。
    • [ ] 电子钱包过帐使用凭证支持的信用，而不是直接余额更新。

    • [ ] 新消息、发件箱/收件箱处理、迁移、API 权限、指标和 调度程序命令具有项目测试策略所需的测试。
