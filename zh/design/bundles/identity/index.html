    Identity Module Design¶

    Overview¶

    This document describes the Identity module (src/Identity). It implements:

    • JWT access tokens (RS256) with a 7200s TTL
    • server-stored refresh tokens (opaque, hashed) with 1 year TTL and rotation
    • phone-based OTP login/verification, delivered via Alibaba Cloud SMS
    • identifier-based login: identifier can be email, username or a verified phone
    • password-based user self-registration (POST /api/auth/register)
    • user profile management with password change and profile update
    • admin user CRUD with managed password changes
    • profile management: tiered membership (bronze/silver/gold/platinum/diamond), auto-created 1:1 with User, points delegated to Wallet (currency=POINTS). Also carries nickname/avatar/metadata as user profile data.

    Goals¶

    • Keep existing identifier+password flow intact
    • Add phone+OTP as an additional auth path
    • Add password registration as a self-service onboarding path
    • Add user controllers for profile management (App) and admin CRUD (Manage)
    • Use Redis for OTP storage and rate-limiting
    • Use RS256 for JWT signing and verify with public key
    • Store refresh tokens hashed in MySQL (identity_refresh_token table)

    Environment variables (.env.example)¶

    See .env.example at repository root for all variables. Key ones:

    • JWT_PRIVATE_KEY_PATH, JWT_PUBLIC_KEY_PATH, JWT_PASSPHRASE
    • ACCESS_TOKEN_TTL (7200)
    • REFRESH_TOKEN_TTL (31536000)
    • REFRESH_TOKEN_SECRET
    • OTP_TTL (300)
    • OTP_REDIS_DSN
    • ALIYUN_ACCESS_KEY_ID, ALIYUN_ACCESS_KEY_SECRET
    • ALIYUN_SMS_SIGN_NAME
    • ALIYUN_SMS_TEMPLATE_LOGIN_OTP
    • ALIYUN_SMS_TEMPLATE_VERIFY_PHONE
    • ALIYUN_SMS_DRY_RUN (development safe flag)

    DB Schema (MySQL)¶

    We will add the following table for refresh tokens (migration SQL will be provided):

    CREATE TABLE identity_refresh_token ( id BIGINT NOT NULL AUTO_INCREMENT PRIMARY KEY, user_id INT NOT NULL, refresh_token_hash VARCHAR(128) NOT NULL, jti VARCHAR(64) DEFAULT NULL, created_at DATETIME NOT NULL, expires_at DATETIME NOT NULL, revoked_at DATETIME DEFAULT NULL, replaced_by_token_id BIGINT DEFAULT NULL, ip_address VARCHAR(45) DEFAULT NULL, user_agent TEXT, INDEX (refresh_token_hash), INDEX (user_id), FOREIGN KEY (user_id) REFERENCES users (id) ON DELETE CASCADE );

    Note: users.phone is nullable; a UNIQUE index on phone is used. MySQL allows multiple NULLs, which satisfies "nullable but unique when present" semantics.

    Token flows¶

    Login (identifier + password) - POST /api/auth/login { identifier, password } - identifier may be email, username or a phone (phone allowed only if phone_verified=true) - on success returns { access_token, refresh_token, expires_in }

    Register (password self-registration) - POST /api/auth/register { email, username, password, phone? } - Public endpoint (no auth required) - Validates uniqueness of email, username, and phone - Creates User with hashed password via UserService::register() - Returns JWT tokens directly (same format as login) - Password minimum 6 characters

    OTP Login / Verify - POST /api/auth/otp/request { phone, purpose } - generates OTP, stores hash in Redis, sends SMS via Aliyun - POST /api/auth/otp/verify { phone, otp, purpose } - verifies OTP; if purpose=login issues tokens; if purpose=verify_phone marks phone_verified

    Token Refresh - POST /api/auth/token/refresh { refresh_token } - Server looks up hashed refresh token, validates, rotates (creates new refresh token, revokes old)

    Logout - POST /api/auth/logout { refresh_token } - marks refresh token revoked

    User Profile (App)¶

    Method Path Auth Description
    GET /api/v1/app/users/me ROLE_USER Get current user profile
    PUT /api/v1/app/users/me ROLE_USER Update email, username, phone, optional password
    POST /api/v1/app/users/change-password ROLE_USER Change own password (requires current password)

    User Management (Manage)¶

    Method Path Auth Description
    GET /api/v1/manage/users ROLE_ADMIN List all users
    GET /api/v1/manage/users/{id} ROLE_ADMIN View user detail
    POST /api/v1/manage/users ROLE_ADMIN Create user (with hashed password)
    PUT /api/v1/manage/users/{id} ROLE_ADMIN Update user (email, username, password, phone, roles)
    DELETE /api/v1/manage/users/{id} ROLE_ADMIN Delete user
    POST /api/v1/manage/users/{id}/change-password ROLE_ADMIN Admin change user password (no current pw required)

    跨境用户身份¶

    users.id 保留本地身份数据库密钥。在 Identity 被引用之前 单独部署的模块或服务，User 必须公开唯一的 UUID。其他 模块和集成事件使用 userUuid，而不是本地 users.id，作为持久的 客户或员工参考。

    迁移可能会暂时将 UUID 解析为 Identity 内的本地 ID，但是 Store， 库存、支付集成和未来服务不得保留外键或 对 users.id 的长期引用。

    档案管理（管理）¶

    Profile 是身份配置文件实体：用户的 1:1 扩展，在用户保留时自动创建。 它包含会员级别、个人资料字段（昵称/头像/元数据）和 joinAt。 会员积分存储在钱包中（货币=积分），而不是存储在个人资料中。

    实体 表 目的
    Profile identity_profile 1:1 用户扩展：级别、昵称、头像、元数据、joinedAt

    级别常数：

    public const LEVEL_BRONZE = 'bronze';
public const LEVEL_SILVER = 'silver';
public const LEVEL_GOLD = 'gold';
public const LEVEL_PLATINUM = 'platinum';
public const LEVEL_DIAMOND = 'diamond';

    级别层次结构（对于 findByLevelOrAbove）：

    bronze (0) < silver (1) < gold (2) < platinum (3) < diamond (4)

    个人资料字段：

    领域 类型 描述
    nickname 字符串（255）可为空 显示名称（显示时优先于用户名）
    avatar 字符串（500）可为空 头像网址
    metadata json 可为空 可扩展的首选项（主题、语言等）

    通过 Doctrine Listener 自动创建：

    UserProfileListener (#[AsDoctrineListener(event: Events::postPersist)]) 确保 默认情况下，每个持久用户都有一个配置文件。在新的EntityManager::flush()之后 用户，如果不存在配置文件，则会在LEVEL_BRONZE处自动创建一个。这涵盖 所有用户创建路径：UserService::register()、管理 CRUD、编程创建。

    方法 路径 授权 描述
    获取 /api/v1/manage/profiles 角色管理员 列出所有配置文件
    获取 /api/v1/manage/profiles/{id} 角色管理员 查看个人资料详情
    发布 /api/v1/manage/profiles 角色管理员 创建个人资料（用户、级别、昵称、头像、元数据、joinedAt）
    放置 /api/v1/manage/profiles/{id} 角色管理员 更新个人资料（级别、昵称、头像、元数据、joinedAt）
    删除 /api/v1/manage/profiles/{id} 角色管理员 删除个人资料

    用户实体关系：

    // User has inverse side OneToOne
#[ORM\OneToOne(mappedBy: 'user', targetEntity: Profile::class, cascade: ['persist', 'remove'])]
private ?Profile $profile = null;

public function getProfile(): ?Profile;
public function setProfile(?Profile $profile): self;  // syncs bidirectional

    存储库方法：

    ProfileRepository extends ServiceEntityRepository
  findById(int $id): ?Profile
  findByUser(User $user): ?Profile
  findByUserId(int $userId): ?Profile
  findByLevel(string $level): array              // exact level match
  findByLevelOrAbove(string $minLevel): array    // cumulative (>= this level)

    通过钱包积分：

    个人资料点使用钱包模块。用户的积分存储为：

    Wallet for user_id=X, currency="POINTS"

    个人资料上不存在积分字段。促销条件使用 user.profile.level 进行 基于级别的规则和基于积分的规则的参考钱包。

    个人资料应用程序自助服务（应用程序）¶

    App ProfileController 使用 SingleDetailApiViewMixin (GET) 和 SingleCreateAndUpdateApiViewMixin（放置）。处理属性过滤 通过 mixin 通过 acceptedCreateProperties / acceptedUpdateProperties：

    #[Route('/app/profiles', name: 'app-profiles-')]
#[IsGranted('ROLE_USER')]
class ProfileController extends RestController
{
    use ApiView, SingleDetailApiViewMixin, SingleCreateAndUpdateApiViewMixin;

    protected array $acceptedCreateProperties = ['nickname', 'avatar', 'metadata'];
    protected array $acceptedUpdateProperties = ['nickname', 'avatar', 'metadata'];

    protected function commonFilter(): array
    {
        $user = $this->getUser();
        return $user instanceof User ? ['user' => $user] : ['id' => -1];
    }

    protected function defaultCreateValues(): array
    {
        $user = $this->getUser();
        return ['user' => $user, 'level' => Profile::LEVEL_BRONZE];
    }
}

    用户只能修改nickname、avatar和metadata。级别更改需要通过/manage/profiles进行管理。 SingleCreateAndUpdateApiViewMixin 现在支持 acceptedCreateProperties/acceptedUpdateProperties/ requiredCreateProperties/requiredUpdateProperties — 与 CreateApiViewMixin 相同的合约 UpdateApiViewMixin。

    方法 路径 授权 描述
    获取 /api/v1/app/profiles ROLE_USER 查看自己的个人资料
    放置 /api/v1/app/profiles ROLE_USER 更新自己的个人资料（仅限昵称、头像、元数据）

    档案服务¶

    App\Identity\Service\ProfileService 扩展了 BaseService 并添加了：

    方法 描述
    joinAsMember(User $user) 在 LEVEL_BRONZE 处创建幂等配置文件。如果用户已有个人资料，则返回现有记录

    安全考虑¶

    • 仅使用 HTTPS
    • 将私钥和秘密保留在回购协议之外；使用秘密管理器
    • 使用 REFRESH_TOKEN_SECRET 通过 HMAC-SHA256 哈希刷新令牌
    • OTP是6位数字，以散列形式存储在Redis中，一次性使用，TTL 5分钟
    • 实施速率限制：每个电话、每个 IP 和每个帐户限制
    • 检测刷新令牌重用：如果使用撤销/替换的令牌，则撤销所有用户令牌

    阿里云短信集成¶

    • 将使用阿里云SDK（alibabacloud/client）。提供者从 env 读取密钥。
    • 模板必须在阿里云控制台创建并审核。模板变量：{code}
    • 我们提供 ALIYUN_SMS_DRY_RUN 进行暂存以避免真正发送
