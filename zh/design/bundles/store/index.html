    商店捆绑设计¶

    状态：在模块化整体中实现第 1-3 阶段。 商店、会员资格、 商店订单、贸易/商店发件箱-收件箱、Messenger 消费者和商店接受 已实施。库存保留仍然是一个有意推迟的界限。 Store 捆绑包 (src/Store/) 拥有多商店上下文、商店操作和 店方订单预测。贸易仍然是单一商业订单切入点 以及订单金额、付款、退款和客户订单状态的真实来源。

    1. 目标和范围¶

    1.1 目标¶

    提供一个多存储边界，可以从 Symfony 模块开始，然后再作为 提取为服务而不改变商业订单的所有权。

    Customer -> Trade Order API -> Trade Order + Trade Outbox
                                  |
                                  v
                         Store event consumer
                                  |
                                  v
                         StoreOrder + store decision
                                  |
                                  v
                         Store result event -> Trade consumer

    该捆绑包拥有：

    • 商店身份、生命周期、业务配置和公共商店身份。
    • 商店会员资格和商店本地运营授权。
    • 存储请求上下文解析和验证。
    • 商店接受和履行数据的 StoreOrder 预测/聚合。
    • 商店集成事件的幂等消费和发布。
    • 商店接受或拒绝贸易订单的合同。

    该捆绑包不拥有：

    • 客户订单创建 API。
    • 商业订单金额、折扣、付款、退款或客户取消。
    • 规范的付款发票。
    • 全球产品/SKU主数据。
    • 库存实施。库存预留是定义的集成边界 此处并在稍后的库存包中设计。

    1.2 非目标¶

    第一个存储阶段不得：

    • 通过/stores/{id}/orders创建第二个面向客户的订单。
    • 保留贸易付款、退款或总金额状态的可写副本。
    • 将 Doctrine 外键添加到贸易、支付、身份或未来的库存表中。
    • 让客户端提供的storeId或storeCode成为授权事实。
    • 将trade_order.metadata视为权威商店关系。
    • 需要分布式事务或一次性代理交付。

    1.3 所有权矩阵¶

    关注 业主 商店责任
    订单 UUID、行项目金额、总计、货币 贸易 仅使用不可变快照
    客户付款及退款 贸易+支付 仅对由此产生的业务事件作出反应
    商店身份和会员资格 商店 权威
    商店接受/拒绝 商店 权威
    商店履行运营 商店 权威一次介绍
    商店特定商品资格 商店 验收期间验证
    库存预订 库存，未来 请求和反应；不拥有股票分类帐
    促销计算 推广+贸易 在报价/订购时接收服务器解析的商店代码

    2. 架构原则¶

    2.1 一份商业订单¶

    Trade\Entity\Order 是唯一的客户订单聚合。客户通过创建它 现有的交易订单端点。 StoreOrder 仅作为以下结果创建 trade.order.created.v1 事件。

    Trade Order                         StoreOrder
-----------                         ----------
payment / refund                    store acceptance
commercial workflow                 operational workflow
customer-facing status              store-facing status
commercial amount                   copied amount snapshot for display only
invoice references                  fulfillment and reservation references

    StoreOrder 不得公开创建独立商业订单的 API。

    2.2 显式事件契约¶

    Trade 和 Store 通过版本化、可序列化的集成事件进行通信。他们 不得通过传递 Doctrine 实体、存储库或服务对象进行通信。

    发布者不知道存在哪些消费者。消费者只知道一个事件 架构及其自己的本地服务。

    2.3 本地事务，最终的跨束一致性¶

    每个模块将自己的业务记录和发件箱事件写入一个数据库中 交易。中继至少传递一次事件。消费者提供幂等性。

    local database transaction:
  business mutation + outbox insert

cross-module delivery:
  at least once + inbox deduplication + business unique keys

    任何组件都不能承担一次性消息代理保证。

    2.4 运行时工作者¶

    模块化整体作为 Compose 服务启动异步处理，而不是在 PHP-FPM请求流程：

    服务 命令 责任
    worker messenger:consume async 通过 Messenger 重试处理使用 Trade 和 Store 集成消息
    scheduler 贸易/商店发件箱发布者循环 每 OUTBOX_PUBLISH_INTERVAL 秒中继一次未发布的发件箱行（默认 5）

    调度程序和工作线程使用与 app 相同的应用程序映像和环境。这个 保持发件箱模式在 SQL 中的持久性，同时使整体操作自动化。

    2.4 稳定标量引用¶

    跨界引用是 UUID 和标量快照，而不是 Doctrine 关联。

    示例：

    • StoreOrder.tradeOrderUuid，而不是ManyToOne Trade\Order。
    • Membership.userUuid，而不是ManyToOne Identity\User。
    • 未来库存预留 UUID，而不是库存实体关系。

    This prevents cross-module schema coupling and permits separate databases later.

    3. Existing System Changes Required¶

    This bundle cannot be implemented as a completely isolated source directory because Trade owns the only order entry point. The required changes are intentionally narrow and generic; Trade MUST NOT import Store entities, repositories, or services.

    Area Required target change Reason
    Trade order workflow Add awaiting_store_acceptance, store_accepted, and store_rejected places/transitions Prevent payment before store acceptance
    Trade order creation Persist server-generated store snapshot and a trade.order.created.v1 outbox event Start asynchronous Store processing
    Trade payment entry Permit payment only after store_accepted Avoid payment for unavailable stock/store
    Trade outbox relay Publish versioned integration events Decouple publisher from Store consumer
    Identity User identity Add a unique User UUID before Store persists or publishes user references Prevent Store from depending on users.id
    Root routing/DI Register Store controllers and Store service configuration Compose the new bundle

    The implemented Store-scoped workflow is draft -> awaiting_store_acceptance -> store_accepted -> confirmed -> paid -> fulfilled -> completed. Store rejection follows awaiting_store_acceptance -> store_rejected -> cancelled. Non-Store orders retain the existing Trade workflow.

    The current context transport is X-Store-Code, resolved only against an active Store by StoreContextResolver. A Store-scoped App order returns 202. The Trade-order consumer currently auto-accepts eligible active Stores; Inventory reservation is the future decision boundary.

    3.1 Store Context At The Trade Entry Point¶

    The Trade controller obtains a StoreContext before calculating a quote or creating an order. It MUST use a generic interface or DTO, never a Store entity type.

    final readonly class StoreContext
{
    public function __construct(
        public string $storeUuid,
        public string $storeCode,
        public string $storeName,
        public string $channel,
    ) {}
}

    The Store bundle implements the resolver. Trade consumes only the resolved scalar data. The exact location mechanism may be one of:

    Mechanism Use Trust Rule
    Canonical host/subdomain Store-branded storefront Resolve from trusted request host mapping
    Gateway-injected header API gateway or mini-program gateway Accept only after gateway authentication/signature
    Explicit route selection A customer deliberately selects a store Validate availability server-side before use

    Raw request-body storeId, storeUuid, and storeCode are never authoritative. A client may provide a selection hint only when a Store resolver validates it and returns a concrete StoreContext.

    3.2 Trade Metadata Snapshot¶

    Trade stores a historical display snapshot under a reserved metadata key:

    {
  "_store": {
    "uuid": "store-uuid",
    "code": "shanghai-xuhui",
    "name": "Xuhui Store",
    "channel": "mini_program"
  }
}

    The snapshot is written by trusted server code only. It is useful for audit and order display, but it is not a query, authorization, or integrity boundary. StoreOrder is the Store-side authoritative record, and the integration event carries the same immutable snapshot.

    5. Entity Design¶

    5.1 Store¶

    Table: store

    Field Type Required Description
    id int Yes Internal primary key
    uuid string(36), unique Yes Stable public/cross-service identifier
    code string(50), unique Yes Immutable machine-readable store code
    name string(255) Yes Current display name
    status string(30) Yes active, suspended, closed
    timezone string(64) Yes IANA zone, such as Asia/Shanghai
    contact json nullable No Sanitized contact data
    address json nullable No Structured address/geolocation data
    settings json nullable No Store-local configuration, not secrets
    createdAt datetime_immutable Yes Creation time
    updatedAt datetime_immutable nullable No Last update

    Rules:

    • uuid is the only cross-service store identifier.
    • code is stable after activation because Promotion and external channels may use it.
    • closed stores cannot be selected for new orders.
    • Historical orders use snapshots, so Store deletion is forbidden; closure is a status.

    5.2 Membership¶

    Table: store_membership

    领域 类型 必填 描述
    id 整数 是的 内部主键
    store 多对一商店 是的 本地商店关系
    userUuid 字符串(36) 是的 身份用户 UUID 标量；没有外键
    role 字符串（30） 是的 owner、manager、clerk、fulfillment
    status 字符串（30） 是的 active、suspended、revoked
    createdAt 日期时间不可变 是的 授予时间
    updatedAt datetime_immutable 可为空 没有 最后更新

    限制和规则：

    • 独特的(store_id, user_uuid)。
    • 用于授权查找的索引(user_uuid, status)。
    • 会员角色是一个商店的本地成员角色，不得写入Identity\User.roles。
    • ROLE_ADMIN 仍然是平台范围的覆盖；商店会员资格支持商店范围 仅操作。

    5.3 商店订单¶

    表： store_order

    StoreOrder 是从一个交易订单创建事件创建的商店端聚合。 这不是第二个商业订单。

    领域 类型 必填 描述
    id 整数 是的 内部主键
    uuid 字符串(36)，唯一 是的 商店订单公共标识符
    tradeOrderUuid 字符串(36)，唯一 是的 不可变的交易订单参考
    store 多对一商店 是的 本地商店关系
    storeCodeSnapshot 字符串（50） 是的 放置时的代码
    storeNameSnapshot 字符串（255） 是的 安置时的姓名
    customerUserUuid 字符串(36) 可为空 没有 标量客户身份 UUID 参考
    currency 字符串（10） 是的 复制用于显示/验证
    totalAmount 大整数 是的 不可变的复制商业金额（以美分为单位）
    orderSnapshot json 是的 来自事件的不可变的生产线和交付快照
    operationalStatus 字符串（40） 是的 存储操作状态机
    rejectionCode 字符串（50）可为空 没有 机读拒绝原因
    rejectionReason 文本可为空 没有 消毒操作员/客户原因
    acceptedAt datetime_immutable 可为空 没有 门店受理时间
    rejectedAt datetime_immutable 可为空 没有 店铺拒绝时间
    fulfillmentData json 可为空 没有 取货/送货/分配数据，商店自有
    reservationId 字符串（64）可为空 没有 未来库存预留参考
    createdAt 日期时间不可变 是的 投影创建时间
    updatedAt datetime_immutable 可为空 没有 最后更新

    索引：

    索引 目的
    独特trade_order_uuid 业务幂等性：每个交易订单一个 StoreOrder
    (store_id, operational_status, created_at) 存储工作队列和报告
    (customer_user_uuid, created_at) 客户阅读意见
    (reservation_id) 未来库存调节

    totalAmount、currency 和 orderSnapshot 是 Store 操作的复制事实。 即使存在分歧，贸易仍然具有权威性；不匹配是值得警惕的合同 违规，而不是商店端重新定价的机会。

    5.4 商店运营状态¶

    状态 意义 业主
    pending_validation 收到事件；商店检查资格 商店
    awaiting_inventory 商店经过验证；预订待定 商店/库存集成
    accepted 商店可以履行订单；发出接受事件 商店
    rejected 商店无法履行订单；发出拒绝事件 商店
    fulfillment_pending 商业付款完成；店家可准备工作 商店
    fulfilling 店铺正在积极准备/发货中 商店
    fulfilled 商店报告本地履行完成 商店
    cancelled 交易取消后商店停止运营 商店

    Store 工作流不得使用 paid、refunded 或 completed 作为其自己的状态 名称。这些国家仍然是贸易商业国家。

    5.5 发件箱和收件箱实体¶

    商店发件箱消息¶

    表： store_outbox_message

    领域 类型 描述
    id 大整数 内部序列
    eventId 字符串(36)，唯一 全球唯一的事件标识符
    topic 字符串（120） 例如store.order.accepted.v1
    aggregateType 字符串（80） store_order
    aggregateId 字符串（64） 商店订单 UUID
    payload json 事件信封/有效负载，可安全序列化
    occurredAt 日期时间不可变 商务活动时间
    availableAt 日期时间不可变 重试调度时间
    publishedAt datetime_immutable 可为空 交货确认时间
    attempts 整数 中继尝试计数器
    lastError 文本可为空 已清理的继电器错误

    存储消费事件¶

    表： store_consumed_event

    Field Type Description
    id bigint Internal sequence
    eventId string(36), unique Incoming integration event id
    topic string(120) Original topic
    aggregateId string(64) Source aggregate id
    processedAt datetime_immutable Successful local processing time
    payloadHash string(64) SHA-256 of canonical payload for diagnostics

    Inbox uniqueness prevents replayed broker messages from repeating Store decisions. The business unique key on StoreOrder.tradeOrderUuid remains mandatory defense in depth.

    6. Trade Order State Machine Extension¶

    6.1 Target States¶

    The target Trade workflow replaces the pre-payment path with Store confirmation.

    draft
  -> awaiting_store_acceptance
  -> store_accepted
  -> confirmed
  -> paid
  -> fulfilled
  -> completed
  -> refunded

awaiting_store_acceptance -> store_rejected -> cancelled
awaiting_store_acceptance -> cancelled (timeout or customer cancellation)
store_accepted -> cancelled (before payment)
confirmed -> cancelled (before payment)

    The precise naming may be adjusted with the Trade workflow owner, but these invariants are required:

    1. Trade emits trade.order.created.v1 only after it has an immutable order UUID and Store snapshot.
    2. A payment invoice cannot be created or paid before Store acceptance.
    3. A Store rejection or acceptance timeout makes the commercial order terminally cancelled before payment.
    4. Store acceptance/rejection consumers are idempotent.

    6.2 Payment Gate¶

    The Trade payment service checks order.status is payment-eligible. Payment endpoints MUST return a conflict response while an order is awaiting Store acceptance. This is a business gate, not a UI convention.

    6.3 Order Creation Response¶

    Because Store validation is asynchronous, a successful initial request returns 202:

    {
  "data": {
    "orderUuid": "trade-order-uuid",
    "status": "awaiting_store_acceptance",
    "store": {
      "uuid": "store-uuid",
      "name": "Xuhui Store"
    }
  },
  "code": 202,
  "message": "Order submitted for store acceptance"
}

    The client polls the existing order detail endpoint or consumes its own notification channel. It must not assume that a 202 response means the Store has stock.

    7. Integration Event Contracts¶

    7.1 Envelope¶

    All integration events use this envelope:

    {
  "eventId": "uuid",
  "type": "trade.order.created",
  "version": 1,
  "occurredAt": "2026-07-24T12:00:00+00:00",
  "aggregateType": "trade_order",
  "aggregateId": "trade-order-uuid",
  "correlationId": "trade-order-uuid",
  "causationId": null,
  "payload": {}
}

    Rules:

    • eventId is immutable and globally unique.
    • aggregateId is the aggregate UUID, never an internal database id.
    • correlationId follows the business flow across services; for this flow it begins as the Trade order UUID.
    • causationId is the triggering event id, or null for an initial HTTP command.
    • A breaking payload change creates a new event version/topic; it never mutates v1.
    • Payloads must contain only data safe for the receiving domain. Do not publish secrets, payment credentials, raw provider callbacks, or unnecessary PII.

    7.2 trade.order.created.v1¶

    Publisher: Trade outbox relay after order creation commits.

    Consumer: Store TradeOrderCreatedConsumer.

    {
  "orderUuid": "trade-order-uuid",
  "store": {
    "uuid": "store-uuid",
    "code": "shanghai-xuhui",
    "name": "Xuhui Store",
    "channel": "mini_program"
  },
  "customerUserUuid": "identity-user-uuid",
  "currency": "CNY",
  "totalAmount": 12800,
  "items": [
    {
      "lineId": "trade-order-item-uuid",
      "catalogReference": "SKU-001",
      "quantity": 2,
      "unitPrice": 6400,
      "lineAmount": 12800,
      "snapshot": {}
    }
  ],
  "delivery": {},
  "placedAt": "2026-07-24T12:00:00+00:00"
}

    The event is a historical placement snapshot. Store does not re-read Trade tables to complete the payload.

    7.3 store.order.accepted.v1¶

    Publisher: Store, after local validation and the future inventory reservation contract succeed.

    Consumer: Trade order decision consumer.

    {
  "orderUuid": "trade-order-uuid",
  "storeOrderUuid": "store-order-uuid",
  "storeUuid": "store-uuid",
  "acceptedAt": "2026-07-24T12:01:00+00:00",
  "reservationId": "inventory-reservation-uuid"
}

    Trade applies the store_accept transition only when the event store UUID matches the server-written order snapshot and the order is awaiting Store acceptance. Duplicates are no-ops.

    7.4 store.order.rejected.v1¶

    Publisher: Store, when validation or inventory reservation cannot succeed.

    Consumer: Trade order decision consumer.

    {
  "orderUuid": "trade-order-uuid",
  "storeOrderUuid": "store-order-uuid",
  "storeUuid": "store-uuid",
  "reasonCode": "OUT_OF_STOCK",
  "reason": "One or more items are unavailable.",
  "rejectedAt": "2026-07-24T12:01:00+00:00"
}

    Allowed reasonCode values begin with:

    Code Meaning
    STORE_NOT_FOUND Resolved Store no longer exists; indicates configuration drift
    STORE_UNAVAILABLE Suspended, closed, or not accepting the channel
    ITEM_NOT_AVAILABLE Store cannot sell one or more requested items
    OUT_OF_STOCK Inventory reservation rejected
    DELIVERY_NOT_SUPPORTED Delivery method/address not serviceable
    ACCEPTANCE_TIMEOUT Store decision did not arrive before the Trade deadline
    SYSTEM_ERROR Retry budget exhausted; operator action required

    Trade transitions the unpaid order to cancellation and records a user-safe reason. It does not expose internal exception details.

    7.5 Future Events¶

    The following are reserved, not part of the first Store implementation:

    Event Publisher Purpose
    trade.order.cancelled.v1 Trade Stop Store work and release reservation
    trade.order.paid.v1 Trade Allow Store to begin preparation/fulfillment
    trade.order.refunded.v1 Trade Stop or reverse Store work where allowed
    store.order.fulfilled.v1 Store Tell Trade fulfillment completed, if Trade retains its workflow transition
    inventory.reservation.confirmed.v1 Inventory Confirm Store-requested reservation
    inventory.reservation.rejected.v1 Inventory Reject Store-requested reservation

    8. Consumer And Publisher Design¶

    8.1 Trade Order Created Consumer¶

    TradeOrderCreatedConsumer processes one message as follows:

    receive message
  -> validate envelope and schema version
  -> start Store local transaction
  -> insert StoreConsumedEvent(eventId), or return if already present
  -> find Store by payload.store.uuid
  -> create/find StoreOrder by tradeOrderUuid
  -> validate Store status, channel, local eligibility
  -> request inventory reservation (future boundary)
  -> set StoreOrder accepted or rejected
  -> insert StoreOutboxMessage for result event
  -> commit
  -> acknowledge broker message

    The broker message is acknowledged only after the Store transaction commits. If the process crashes before acknowledgement, the event is delivered again and becomes an inbox/business-idempotent no-op.

    8.2 Outbox Publisher¶

    The outbox publisher is a transport adapter, not business logic:

    poll unpublished outbox messages in created order
  -> lock one batch
  -> publish envelope to transport topic
  -> mark publishedAt on broker acknowledgement
  -> on transient error: increment attempts and retry later
  -> on retry exhaustion: retain record and alert/DLQ

    Initial deployment may use Symfony Messenger with Doctrine transport. The business contract must not depend on that choice. RabbitMQ, Kafka, SQS, or an HTTP event relay can replace the transport without changing StoreOrder business code.

    8.3 Retry Classification¶

    Failure Consumer action
    Duplicate eventId Acknowledge; no mutation
    Duplicate tradeOrderUuid, same snapshot Continue idempotently; ensure result event exists
    Duplicate tradeOrderUuid, different snapshot Do not overwrite; critical alert and DLQ
    Temporary database/broker failure Roll back and retry
    Invalid event schema/version DLQ; do not retry blindly
    Business rejection such as out of stock Commit rejected StoreOrder + rejection outbox event
    Unexpected domain exception Roll back; retry with bounded backoff, then DLQ

    8.4 Ordering And Concurrency¶

    • The Store consumer serializes concurrent decisions by tradeOrderUuid through the unique StoreOrder key and transaction locking where necessary.
    • An event topic should preserve ordering per aggregate key where the transport supports it, but correctness must not rely on global ordering.
    • Store acceptance after a terminal Trade cancellation is harmless: Trade ignores the stale accept event and Store consumes trade.order.cancelled.v1 to release work.
    • All result handlers validate expected source state before applying transitions.

    9. Store APIs¶

    9.1 Public Store Discovery¶

    Method Path Auth Purpose
    GET /api/v1/app/stores Optional/ROLE_USER by channel Discover selectable active stores
    GET /api/v1/app/stores/{uuid} Optional/ROLE_USER by channel Read store details and availability

    These endpoints do not create orders. The storefront uses the selected Store context when calling the existing Trade quote/order APIs.

    9.2 Customer Store Order Read View¶

    Method Path Auth Purpose
    GET /api/v1/app/store-orders/{uuid} ROLE_USER Read Store operational information for own commercial order

    The controller resolves ownership through the customerUserUuid stored in StoreOrder. It must not reveal operational notes, employee IDs, inventory internals, or internal rejection diagnostics.

    The API is a convenience read model; the customer still uses Trade order APIs for payment, cancellation, refunds, and canonical commercial status.

    9.3 Platform Store Administration¶

    Method Path Auth Purpose
    GET/POST/PUT /api/v1/manage/stores ROLE_ADMIN Store CRUD; closure instead of delete
    GET/POST/PUT /api/v1/manage/store-memberships ROLE_ADMIN Assign/revoke Store memberships
    GET /api/v1/manage/store-orders ROLE_ADMIN Cross-store operational reporting
    GET /api/v1/manage/store-orders/{uuid} ROLE_ADMIN Operational detail

    9.4 Store Staff Operations¶

    Store staff must not use generic Trade manage/orders routes, which are platform-wide ROLE_ADMIN endpoints. Store provides scoped operational endpoints:

    Method Path Required membership Purpose
    GET /api/v1/store/manage/orders active member Current store work queue
    GET /api/v1/store/manage/orders/{uuid} active member StoreOrder operational detail
    POST /api/v1/store/manage/orders/{uuid}/accept owner/manager Manual acceptance when policy permits
    POST /api/v1/store/manage/orders/{uuid}/reject owner/manager Reject before payment with reason code
    POST /api/v1/store/manage/orders/{uuid}/fulfill fulfillment/manager Mark Store operation fulfilled

    The first asynchronous acceptance implementation may not expose manual actions until the timeout/escalation policy is ready. All actions check membership against the StoreOrder's local Store relation, not a request-supplied store identifier.

    10. Authorization Model¶

    10.1 Roles¶

    Principal Scope Capabilities
    ROLE_ADMIN Platform All Store administration and reporting
    Store owner One Store Membership, store settings, acceptance, fulfillment
    Store manager One Store Acceptance, rejection, fulfillment, operational views
    Store clerk One Store Read operational queue; limited configured actions
    Store fulfillment One Store Fulfillment-only operational actions
    Customer Own orders Read customer-safe StoreOrder view only

    10.2 Authorization Rules¶

    1. 平台角色存在于身份中并保留其现有含义。
    2. 存储角色仅存在于Membership中。
    3. Store 控制器将经过身份验证的 Identity 用户解析为标量 userUuid 并 查询 在本地存储成员资格。
    4. ROLE_ADMIN 仅在明确的管理路由上绕过成员资格检查。
    5. 商店工作人员无法直接提升贸易订单的商业状态。 6、门店员工行为产生门店事件；贸易仅适用于商业转型 通过它自己的事件消费者和工作流守卫。

    11. 商店背景和促销合同¶

    促销目前在交易的价格计算上下文中使用 storeCode。的 商店捆绑包为该值提供了权威来源：

    request -> StoreContextResolver -> active Store -> StoreContext.storeCode
        -> Trade calculatePrices(..., storeCode, ...)
        -> Promotion storeCode filtering

    规则：

    • 客户不能通过发布storeCode来选择任意促销商店。
    • Trade 将解析器生成的代码传递到定价管道。
    • 商店快照与订单创建事件一起保存，以便商店消费者可以 验证订单的定价是否适用于预期商店。
    • 促销保持独立：它不引用存储表或实体。
    • 全球促销仍以现有的空商店代码约定为代表； 商店选择决不能无意中将一个不知名的商店变成全球定价。

    这种设计使现有的Promotion.storeCode成为路由输入，而不是Store 领域模型或授权机制。

    12. 库存边界¶

    库存被故意排除在第一个商店数据模型之外。商店定义了 它需要的命令/结果边界：

    Store validates order
  -> inventory.reservation.requested.v1
  -> Inventory reserves quantity idempotently
  -> inventory.reservation.confirmed.v1
       or inventory.reservation.rejected.v1
  -> Store accepts/rejects StoreOrder

    未来的请求负载必须包括：

    • reservationId：存储生成的幂等性/引用 UUID。
    • storeUuid。
    • tradeOrderUuid 和 storeOrderUuid。
    • 商品库存键、数量和不可变的关联 ID。
    • 预订到期/截止日期。

    商店拥有请求预订的决定并保留结果reservationId。 库存拥有可用数量、预留分类账、减量/释放和库存 和解。两个模块都不会访问对方的数据库。

    13. 超时和补偿¶

    13.1 接受超时¶

    Trade 在创建订单时记录可配置的接受截止日期。预定的 贸易工作发现订单在截止日期后仍在等待商店接受，并且：

    1. 应用取消转换。
    2. 将trade.order.cancelled.v1写入交易发件箱，原因为ACCEPTANCE_TIMEOUT。
    3. Store消费cancel，将其挂起的操作标记为已取消，并询问future 库存以释放任何预订。

    该作业必须是幂等的：终端或已接受的订单将被忽略。

    13.2 迟到的事件¶

    迟到的活动 所需行为
    交易超时取消后商店接受 贸易忽略它并记录相关性；商店发布取消活动相关工作
    交易取消后商店拒绝 贸易忽视了它；商店保留被拒绝的审核记录
    商店等待库存时取消交易 商店将取消标记为待处理，并在已知后释放预订
    接受前的付款事件 贸易拒绝/标记为不变违约；付款开始必须已被控制

    13.3 无分布式回滚¶

    一旦事件跨越发件箱边界，远程突变就无法回滚。 补偿表示为新的业务事件和本地状态转换，而不是 跨服务数据库事务。

    14. 持久化和迁移计划¶

    14.1 初始存储迁移¶

    存储迁移仅创建存储拥有的表：

    store
store_membership
store_order
store_outbox_message
store_consumed_event

    它可能包括来自 store_membership.store_id 和 store_order.store_id 的外键 到本地 store 表。它不得将外键添加到 users、trade_order、 payment_invoice，或未来的库存表。

    14.2 贸易移民¶

    单独的贸易迁移仅添加所需的通用订单编排数据 新的工作流程，例如现有 JSON 元数据和任何显式存储快照 接受截止日期字段。它不能向 Store 添加外键。

    14.3 数据回填¶

    对于没有商店元数据的现有订单：

    • 将它们视为遗留/全球订单。
    • 除非存在可靠的外部映射，否则不要伪造StoreOrder记录。
    • 现有的付款/退款行为保持不变。
    • 新商店接受工作流程仅适用于新创建的商店范围订单。

    17. 实施阶段¶

    第一阶段：商店基础¶

    1. 创建 Store、Membership、StoreOrder、Outbox 和 Inbox 实体/存储库。 2.添加Store服务接口和服务。 3、实施平台店铺管理和会员管理。

    3. 添加商店发现端点和商店员工授权测试。

    第 3 阶段：存储消费者和决策事件¶

    1. 实现TradeOrderCreatedConsumer，具有收件箱和业务幂等性。

    第 5 阶段：服务提取准备就绪¶

    1. 将事件架构移至版本化合同包或 JSON 架构存储库。
    2. 用代理替换进程内传输，同时保留发件箱/收件箱行为。 3.独立移动Store数据库和消费者。
    3. 在 CI 中运行消费者驱动的契约测试。
    4. 在启用生产提取之前添加重放工具和操作仪表板。

    18. 验收标准¶

    Store 捆绑设计在以下情况下实施：

    标准 要求
    单一订单输入 没有商店端点创建商业订单；贸易仍然是切入点
    商店隔离 商店没有与贸易、支付、身份或库存相关的学说关联/FK
    上下文完整性 商店标识来自服务器解析的 StoreContext，而不是客户端正文字段
    专卖店投影 每个交易订单 UUID 都会幂等地创建一个 StoreOrder
    事件隔离 集成事件有效负载是版本化标量/JSON 合约，而不是 Doctrine 实体
    可靠的出版物 业务突变与本地发件箱写共享一笔交易
    可靠消费 收件箱事件 ID 唯一性和 StoreOrder 业务唯一性可保护重试
    支付门 商店范围内的订单在商店接受之前无法开始付款
    拒绝/超时 Trade 在商店拒绝或接受超时时取消未付款的订单
    授权 店铺会员范围 店铺运营；平台管理员保留显式覆盖
    库存边界 商店有预订合同挂钩，但没有嵌入式库存分类账
    提取准备 存储可以移动到单独的数据库/使用者，无需跨模式连接或事务
