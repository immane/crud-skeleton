    商店捆绑设计¶

    状态：在模块化整体中实现第 1-3 阶段。 商店、会员资格、 商店订单、贸易/商店发件箱-收件箱、Messenger 消费者和商店接受 已实施。库存保留仍然是一个有意推迟的界限。 Store 捆绑包 (src/Store/) 拥有多商店上下文、商店操作和 店方订单预测。贸易仍然是单一商业订单切入点 以及订单金额、付款、退款和客户订单状态的真实来源。

    1. 目标和范围¶

    1.1 目标¶

    提供一个多存储边界，可以从 Symfony 模块开始，然后再作为 提取为服务而不改变商业订单的所有权。

    Customer -> Trade Order API -> Trade Order + Trade Outbox
                                  |
                                  v
                         Store event consumer
                                  |
                                  v
                         StoreOrder + store decision
                                  |
                                  v
                         Store result event -> Trade consumer

    该捆绑包拥有：

    • 商店身份、生命周期、业务配置和公共商店身份。
    • 商店会员资格和商店本地运营授权。
    • 存储请求上下文解析和验证。
    • 商店接受和履行数据的 StoreOrder 预测/聚合。
    • 商店集成事件的幂等消费和发布。
    • 商店接受或拒绝贸易订单的合同。

    该捆绑包不拥有：

    • 客户订单创建 API。
    • 商业订单金额、折扣、付款、退款或客户取消。
    • 规范的付款发票。
    • 全球产品/SKU主数据。
    • 库存实施。库存预留是定义的集成边界 此处并在稍后的库存包中设计。

    1.2 非目标¶

    第一个存储阶段不得：

    • 通过/stores/{id}/orders创建第二个面向客户的订单。
    • 保留贸易付款、退款或总金额状态的可写副本。
    • 将 Doctrine 外键添加到贸易、支付、身份或未来的库存表中。
    • 让客户端提供的storeId或storeCode成为授权事实。
    • 将trade_order.metadata视为权威商店关系。
    • 需要分布式事务或一次性代理交付。

    1.3 所有权矩阵¶

    关注 业主 商店责任
    订单 UUID、行项目金额、总计、货币 贸易 仅使用不可变快照
    客户付款及退款 贸易+支付 仅对由此产生的业务事件作出反应
    商店身份和会员资格 商店 权威
    商店接受/拒绝 商店 权威
    商店履行运营 商店 权威一次介绍
    商店特定商品资格 商店 验收期间验证
    库存预订 库存，未来 请求和反应；不拥有股票分类帐
    促销计算 推广+贸易 在报价/订购时接收服务器解析的商店代码

    2. 架构原则¶

    2.1 一份商业订单¶

    Trade\Entity\Order 是唯一的客户订单聚合。客户通过创建它 现有的交易订单端点。 StoreOrder 仅作为以下结果创建 trade.order.created.v1 事件。

    Trade Order                         StoreOrder
-----------                         ----------
payment / refund                    store acceptance
commercial workflow                 operational workflow
customer-facing status              store-facing status
commercial amount                   copied amount snapshot for display only
invoice references                  fulfillment and reservation references

    StoreOrder 不得公开创建独立商业订单的 API。

    2.2 显式事件契约¶

    Trade 和 Store 通过版本化、可序列化的集成事件进行通信。他们 不得通过传递 Doctrine 实体、存储库或服务对象进行通信。

    发布者不知道存在哪些消费者。消费者只知道一个事件 架构及其自己的本地服务。

    2.3 本地事务，最终的跨束一致性¶

    每个模块将自己的业务记录和发件箱事件写入一个数据库中 交易。中继至少传递一次事件。消费者提供幂等性。

    local database transaction:
  business mutation + outbox insert

cross-module delivery:
  at least once + inbox deduplication + business unique keys

    任何组件都不能承担一次性消息代理保证。

    2.4 运行时工作者¶

    模块化整体作为 Compose 服务启动异步处理，而不是在 PHP-FPM请求流程：

    服务 命令 责任
    worker messenger:consume async 通过 Messenger 重试处理使用 Trade 和 Store 集成消息
    scheduler 贸易/商店发件箱发布者循环 每 OUTBOX_PUBLISH_INTERVAL 秒中继一次未发布的发件箱行（默认 5）

    调度程序和工作线程使用与 app 相同的应用程序映像和环境。这个 保持发件箱模式在 SQL 中的持久性，同时使整体操作自动化。

    2.4 稳定标量引用¶

    跨界引用是 UUID 和标量快照，而不是 Doctrine 关联。

    示例：

    • StoreOrder.tradeOrderUuid，而不是ManyToOne Trade\Order。
    • Membership.userUuid，而不是ManyToOne Identity\User。
    • 未来库存预留 UUID，而不是库存实体关系。

    这可以防止跨模块模式耦合并允许稍后使用单独的数据库。

    3. 需要更改现有系统¶

    该捆绑包无法实现为完全隔离的源目录，因为 Trade拥有唯一的订单入口点。所需的改变有意缩小范围 和通用；贸易不得进口商店实体、存储库或服务。

    面积 所需的目标改变 原因
    贸易订单工作流程 添加 awaiting_store_acceptance、store_accepted 和 store_rejected 位置/转换 防止商店验收前付款
    贸易订单创建 保留服务器生成的存储快照和 trade.order.created.v1 发件箱事件 启动异步存储处理
    贸易支付录入 仅在 store_accepted 之后才允许付款避免为不可用的库存/商店付款
    贸易发件箱中继 发布版本化集成事件 将发布者与商店消费者分离
    身份 用户身份 在存储保留或发布用户引用之前添加唯一的用户 UUID 防止 Store 依赖 users.id
    根路由/DI 注册Store控制器和Store服务配置 编写新包

    实现的商店范围的工作流程是draft -> awaiting_store_acceptance -> store_accepted -> confirmed -> paid -> fulfilled -> completed。商店拒绝如下 awaiting_store_acceptance -> store_rejected -> cancelled。非商店订单保留 现有的贸易工作流程。

    当前上下文传输是 X-Store-Code，仅针对活动 Store 进行解析 由StoreContextResolver。商店范围的应用程序订单返回 202。贸易秩序 消费者目前自动接受符合条件的活跃商店；库存预留是 未来的决策边界。

    3.1 在交易入口点存储上下文¶

    交易控制器在计算报价或创建之前获取 StoreContext 一个订单。它必须使用通用接口或 DTO，而不是 Store 实体类型。

    final readonly class StoreContext
{
    public function __construct(
        public string $storeUuid,
        public string $storeCode,
        public string $storeName,
        public string $channel,
    ) {}
}

    Store 包实现了解析器。贸易仅消耗已解析的标量数据。 确切的定位机制可能是以下之一：

    机制 使用 信任规则
    规范主机/子域 商店品牌店面 从可信请求主机映射解析
    网关注入标头 API网关或小程序网关 仅在网关验证/签名后接受
    明确的路线选择 顾客刻意选择店铺 使用前验证服务器端的可用性

    原始请求正文 storeId、storeUuid 和 storeCode 永远不具有权威性。一个 仅当存储解析器验证并返回时，客户端才可以提供选择提示 具体的StoreContext。

    3.2 交易元数据快照¶

    Trade 在保留的元数据键下存储历史显示快照：

    {
  "_store": {
    "uuid": "store-uuid",
    "code": "shanghai-xuhui",
    "name": "Xuhui Store",
    "channel": "mini_program"
  }
}

    快照仅由受信任的服务器代码写入。对于审计和订单很有用 显示，但它不是查询、授权或完整性边界。 StoreOrder 是 Store端权威记录，集成事件也有同样的记录 不可变的快照。

    5. 实体设计¶

    5.1 商店¶

    表： store

    领域 类型 必填 描述
    id 整数 是的 内部主键
    uuid 字符串(36)，唯一 是的 稳定的公共/跨服务标识符
    code 字符串（50），唯一 是的 不可变的机器可读存储代码
    name 字符串（255） 是的 当前显示名称
    status 字符串（30） 是的 active、suspended、closed
    timezone 字符串（64） 是的 IANA 区域，例如 Asia/Shanghai
    contact json 可为空 没有 已消毒的联系数据
    address json 可为空 没有 结构化地址/地理位置数据
    settings json 可为空 没有 存储本地配置，而不是秘密
    createdAt 日期时间不可变 是的 创作时间
    updatedAt datetime_immutable 可为空 没有 最后更新

    规则：

    • uuid 是唯一的跨服务商店标识符。
    • code 激活后稳定，因为促销和外部渠道可能会使用它。
    • closed新订单无法选择店铺。
    • 历史订单使用快照，禁止删除Store；关闭是一种状态。

    5.2 会员资格¶

    表： store_membership

    Field Type Required Description
    id int Yes Internal primary key
    store ManyToOne Store Yes Local Store relation
    userUuid string(36) Yes Identity User UUID scalar; no foreign key
    role string(30) Yes owner, manager, clerk, fulfillment
    status string(30) Yes active, suspended, revoked
    createdAt datetime_immutable Yes Grant time
    updatedAt datetime_immutable nullable No Last update

    Constraints and rules:

    • Unique (store_id, user_uuid).
    • Index (user_uuid, status) for authorization lookup.
    • A membership role is local to one Store and MUST NOT be written into Identity\User.roles.
    • ROLE_ADMIN remains a platform-wide override; Store membership supports store-scoped operations only.

    5.3 StoreOrder¶

    Table: store_order

    StoreOrder is the Store-side aggregate created from one Trade order-created event. It is not a second commercial order.

    Field Type Required Description
    id int Yes Internal primary key
    uuid string(36), unique Yes Store order public identifier
    tradeOrderUuid string(36), unique Yes Immutable Trade order reference
    store ManyToOne Store Yes Local Store relation
    storeCodeSnapshot string(50) Yes Code at placement time
    storeNameSnapshot string(255) Yes Name at placement time
    customerUserUuid string(36) nullable No Scalar customer Identity UUID reference
    currency string(10) Yes Copied for display/validation
    totalAmount bigint Yes Immutable copied commercial amount in cents
    orderSnapshot json Yes Immutable line and delivery snapshot from event
    operationalStatus string(40) Yes Store operational state machine
    rejectionCode string(50) nullable No Machine-readable rejection reason
    rejectionReason text nullable No Sanitized operator/customer reason
    acceptedAt datetime_immutable nullable No Store acceptance time
    rejectedAt datetime_immutable nullable No Store rejection time
    fulfillmentData json nullable No Pickup/delivery/assignment data, Store-owned
    reservationId string(64) nullable No Future inventory reservation reference
    createdAt datetime_immutable Yes Projection creation time
    updatedAt datetime_immutable nullable No Last update

    Indexes:

    Index Purpose
    Unique trade_order_uuid Business idempotency: one StoreOrder per Trade order
    (store_id, operational_status, created_at) Store work queue and reporting
    (customer_user_uuid, created_at) Customer read views
    (reservation_id) Future inventory reconciliation

    totalAmount, currency, and orderSnapshot are copied facts for Store operations. Trade remains authoritative if they ever differ; a mismatch is an alert-worthy contract violation, not a Store-side repricing opportunity.

    5.4 Store Operational Statuses¶

    Status Meaning Owner
    pending_validation Event received; Store checks eligibility Store
    awaiting_inventory Store validated; reservation pending Store/Inventory integration
    accepted Store can fulfill order; acceptance event emitted Store
    rejected Store cannot fulfill order; rejection event emitted Store
    fulfillment_pending Commercial payment complete; Store may prepare work Store
    fulfilling Store is actively preparing/dispatching Store
    fulfilled Store reports local fulfillment complete Store
    cancelled Store operation stopped after Trade cancellation Store

    The Store workflow MUST NOT use paid, refunded, or completed as its own state names. Those remain Trade commercial states.

    5.5 Outbox And Inbox Entities¶

    StoreOutboxMessage¶

    Table: store_outbox_message

    Field Type Description
    id bigint Internal sequence
    eventId string(36), unique Globally unique event identifier
    topic string(120) e.g. store.order.accepted.v1
    aggregateType string(80) store_order
    aggregateId string(64) StoreOrder UUID
    payload json Event envelope/payload, safe to serialize
    occurredAt datetime_immutable Business event time
    availableAt datetime_immutable Retry scheduling time
    publishedAt datetime_immutable nullable Delivery acknowledgement time

    lastError text nullable Sanitized relay error

    StoreConsumedEvent¶

    Table: store_consumed_event

    领域 类型 描述

    6. 交易订单状态机扩展¶

    6.1 目标国家¶

    目标交易工作流程将预付款路径替换为商店确认。

    draft
  -> awaiting_store_acceptance
  -> store_accepted
  -> confirmed
  -> paid
  -> fulfilled
  -> completed
  -> refunded

awaiting_store_acceptance -> store_rejected -> cancelled
awaiting_store_acceptance -> cancelled (timeout or customer cancellation)
store_accepted -> cancelled (before payment)
confirmed -> cancelled (before payment)

    精确的命名可以与交易工作流程所有者一起调整，但是这些不变量 需要：

    1. Trade 仅在具有不可变订单 UUID 且 存储快照。
    2. 在商店接受之前，无法创建或支付付款发票。
    3. 商店拒绝或接受超时使商业订单终止 付款前取消。 4.存储接受/拒绝消费者是幂等的。

    6.2 支付门¶

    贸易付款服务检查order.status是否符合付款条件。支付端点 当订单等待商店接受时，必须返回冲突响应。这是一个 业务门，而不是 UI 约定。

    6.3 订单创建响应¶

    由于存储验证是异步的，因此成功的初始请求将返回 202：

    {
  "data": {
    "orderUuid": "trade-order-uuid",
    "status": "awaiting_store_acceptance",
    "store": {
      "uuid": "store-uuid",
      "name": "Xuhui Store"
    }
  },
  "code": 202,
  "message": "Order submitted for store acceptance"
}

    客户端轮询现有订单详细信息端点或使用自己的通知 频道。不得假设 202 响应意味着商店有库存。

    7. 集成事件合约¶

    7.1 信封¶

    所有集成事件都使用此信封：

    {
  "eventId": "uuid",
  "type": "trade.order.created",
  "version": 1,
  "occurredAt": "2026-07-24T12:00:00+00:00",
  "aggregateType": "trade_order",
  "aggregateId": "trade-order-uuid",
  "correlationId": "trade-order-uuid",
  "causationId": null,
  "payload": {}
}

    规则：

    • eventId 是不可变的并且全局唯一。
    • aggregateId 是聚合 UUID，而不是内部数据库 ID。
    • correlationId遵循跨服务的业务流程；对于这个流程，它开始于 交易订单 UUID。
    • causationId 是触发事件 ID，或者 null 是初始 HTTP 命令。
    • 重大负载更改会创建新的事件版本/主题；它永远不会改变 v1。
    • 有效负载必须仅包含对接收域安全的数据。不公开秘密， 付款凭据、原始提供商回调或不必要的 PII。

    7.2 trade.order.created.v1¶

    发布者： 订单创建提交后进行交易发件箱中继。

    消费者： 存储TradeOrderCreatedConsumer。

    {
  "orderUuid": "trade-order-uuid",
  "store": {
    "uuid": "store-uuid",
    "code": "shanghai-xuhui",
    "name": "Xuhui Store",
    "channel": "mini_program"
  },
  "customerUserUuid": "identity-user-uuid",
  "currency": "CNY",
  "totalAmount": 12800,
  "items": [
    {
      "lineId": "trade-order-item-uuid",
      "catalogReference": "SKU-001",
      "quantity": 2,
      "unitPrice": 6400,
      "lineAmount": 12800,
      "snapshot": {}
    }
  ],
  "delivery": {},
  "placedAt": "2026-07-24T12:00:00+00:00"
}

    该事件是历史放置快照。商店不会重新读取交易表 完成有效负载。

    7.3 store.order.accepted.v1¶

    发布者： 商店，经过本地验证和未来库存预留 合约成功。

    消费者： 交易订单决策消费者。

    {
  "orderUuid": "trade-order-uuid",
  "storeOrderUuid": "store-order-uuid",
  "storeUuid": "store-uuid",
  "acceptedAt": "2026-07-24T12:01:00+00:00",
  "reservationId": "inventory-reservation-uuid"
}

    仅当事件存储 UUID 与 服务器写入的订单快照，订单正在等待商店接受。重复项 是无操作的。

    7.4 store.order.rejected.v1¶

    发布者： 存储，当验证或库存预留无法成功时。

    消费者： 交易订单决策消费者。

    {
  "orderUuid": "trade-order-uuid",
  "storeOrderUuid": "store-order-uuid",
  "storeUuid": "store-uuid",
  "reasonCode": "OUT_OF_STOCK",
  "reason": "One or more items are unavailable.",
  "rejectedAt": "2026-07-24T12:01:00+00:00"
}

    允许的 reasonCode 值开头为：

    代码 意义
    STORE_NOT_FOUND 已解决的商店不再存在；表明配置漂移
    STORE_UNAVAILABLE 暂停、关闭或不接受频道
    ITEM_NOT_AVAILABLE 商店无法销售一件或多件请求的商品
    OUT_OF_STOCK 库存预订被拒绝
    DELIVERY_NOT_SUPPORTED 送货方式/地址不可用
    ACCEPTANCE_TIMEOUT 商店决定未在交易截止日期之前到达
    SYSTEM_ERROR 重试预算已用完；需要操作员采取行动

    Trade 将未付款订单转为取消，并记录用户安全原因。它 不公开内部异常详细信息。

    7.5 未来事件¶

    以下内容是保留的，不是第一个 Store 实现的一部分：

    活动 出版商 目的
    trade.order.cancelled.v1 贸易 停止商店工作并释放预订
    trade.order.paid.v1 贸易 允许商店开始准备/履行
    trade.order.refunded.v1 贸易 停止或逆转 在允许的情况下存储工作
    store.order.fulfilled.v1 商店 如果 Trade 保留其工作流程转换，则告诉 Trade 履行已完成
    inventory.reservation.confirmed.v1 库存 确认商店要求的预订
    inventory.reservation.rejected.v1 库存 拒绝商店要求的预订

    8. 消费者和发行商设计¶

    8.1 交易订单创建消费者¶

    TradeOrderCreatedConsumer 按如下方式处理一条消息：

    receive message
  -> validate envelope and schema version
  -> start Store local transaction
  -> insert StoreConsumedEvent(eventId), or return if already present
  -> find Store by payload.store.uuid
  -> create/find StoreOrder by tradeOrderUuid
  -> validate Store status, channel, local eligibility
  -> request inventory reservation (future boundary)
  -> set StoreOrder accepted or rejected
  -> insert StoreOutboxMessage for result event
  -> commit
  -> acknowledge broker message

    仅在 Store 事务提交后才会确认代理消息。如果 进程在确认之前崩溃，事件被再次传递并成为 收件箱/业务幂等无操作。

    8.2 发件箱发布者¶

    发件箱发布者是传输适配器，而不是业务逻辑：

    poll unpublished outbox messages in created order
  -> lock one batch
  -> publish envelope to transport topic
  -> mark publishedAt on broker acknowledgement
  -> on transient error: increment attempts and retry later
  -> on retry exhaustion: retain record and alert/DLQ

    初始部署可以使用带有 Doctrine 传输的 Symfony Messenger。业务 合同不得取决于该选择。 RabbitMQ、Kafka、SQS 或 HTTP 事件中继 可以在不改变StoreOrder业务代码的情况下更换运输。

    8.3 重试分类¶

    失败 消费者行动
    重复 eventId 承认;无突变
    重复的 tradeOrderUuid，相同的快照 继续幂等；确保结果事件存在
    重复的 tradeOrderUuid，不同的快照 不要覆盖；严重警报和 DLQ
    临时数据库/代理故障 回滚并重试
    无效的事件架构/版本 DLQ；不要盲目重试
    断货等商家拒收 提交拒绝的 StoreOrder + 拒绝发件箱事件
    意外的域异常 回滚;使用有界退避重试，然后 DLQ

    8.4 排序和并发¶

    • Store 消费者通过 tradeOrderUuid 通过 必要时有唯一的 StoreOrder 密钥和事务锁定。
    • 事件主题应在传输支持的情况下保留每个聚合键的排序 它，但正确性不能依赖于全局排序。
    • 终端后商店接受 贸易取消是无害的：贸易忽略 陈旧的接受事件和 Store 消耗 trade.order.cancelled.v1 来释放工作。
    • 所有结果处理程序在应用转换之前都会验证预期的源状态。

    10. 授权模型¶

    10.1 角色¶

    校长 范围 能力
    ROLE_ADMIN 平台 所有商店管理和报告
    商店 owner 一间店 会员资格、商店设置、接受、履行
    商店 manager 一间店 接受、拒绝、履行、操作观点
    商店 clerk 一间店 读取操作队列；有限的配置操作
    商店 fulfillment 一间店 仅限履行的运营行动
    客户 自有订单 仅读取客户安全的 StoreOrder 视图

    10.2 授权规则¶

    1. 平台角色存在于身份中并保留其现有含义。
    2. 存储角色仅存在于Membership中。
    3. Store 控制器将经过身份验证的 Identity 用户解析为标量 userUuid 并 查询 在本地存储成员资格。
    4. ROLE_ADMIN 仅在明确的管理路由上绕过成员资格检查。
    5. 商店工作人员无法直接提升贸易订单的商业状态。 6、门店员工行为产生门店事件；贸易仅适用于商业转型 通过它自己的事件消费者和工作流守卫。

    11. 商店背景和促销合同¶

    促销目前在交易的价格计算上下文中使用 storeCode。的 商店捆绑包为该值提供了权威来源：

    request -> StoreContextResolver -> active Store -> StoreContext.storeCode
        -> Trade calculatePrices(..., storeCode, ...)
        -> Promotion storeCode filtering

    规则：

    • 客户不能通过发布storeCode来选择任意促销商店。
    • Trade 将解析器生成的代码传递到定价管道。
    • 商店快照与订单创建事件一起保存，以便商店消费者可以 验证订单的定价是否适用于预期商店。
    • 促销保持独立：它不引用存储表或实体。
    • 全球促销仍以现有的空商店代码约定为代表； 商店选择决不能无意中将一个不知名的商店变成全球定价。

    这种设计使现有的Promotion.storeCode成为路由输入，而不是Store 领域模型或授权机制。

    12. 库存边界¶

    库存被故意排除在第一个商店数据模型之外。商店定义了 它需要的命令/结果边界：

    Store validates order
  -> inventory.reservation.requested.v1
  -> Inventory reserves quantity idempotently
  -> inventory.reservation.confirmed.v1
       or inventory.reservation.rejected.v1
  -> Store accepts/rejects StoreOrder

    未来的请求负载必须包括：

    • reservationId：存储生成的幂等性/引用 UUID。
    • storeUuid。
    • tradeOrderUuid 和 storeOrderUuid。
    • 商品库存键、数量和不可变的关联 ID。
    • 预订到期/截止日期。

    商店拥有请求预订的决定并保留结果reservationId。 库存拥有可用数量、预留分类账、减量/释放和库存 和解。两个模块都不会访问对方的数据库。

    13. 超时和补偿¶

    13.1 接受超时¶

    Trade 在创建订单时记录可配置的接受截止日期。预定的 贸易工作发现订单在截止日期后仍在等待商店接受，并且：

    1. 应用取消转换。
    2. 将trade.order.cancelled.v1写入交易发件箱，原因为ACCEPTANCE_TIMEOUT。
    3. Store消费cancel，将其挂起的操作标记为已取消，并询问future 库存以释放任何预订。

    该作业必须是幂等的：终端或已接受的订单将被忽略。

    13.2 迟到的事件¶

    迟到的活动 所需行为
    交易超时取消后商店接受 贸易忽略它并记录相关性；商店发布取消活动相关工作
    交易取消后商店拒绝 贸易忽视了它；商店保留被拒绝的审核记录
    商店等待库存时取消交易 商店将取消标记为待处理，并在已知后释放预订
    接受前的付款事件 贸易拒绝/标记为不变违约；付款开始必须已被控制

    13.3 无分布式回滚¶

    一旦事件跨越发件箱边界，远程突变就无法回滚。 补偿表示为新的业务事件和本地状态转换，而不是 跨服务数据库事务。

    14. 持久化和迁移计划¶

    14.1 初始存储迁移¶

    存储迁移仅创建存储拥有的表：

    store
store_membership
store_order
store_outbox_message
store_consumed_event

    它可能包括来自 store_membership.store_id 和 store_order.store_id 的外键 到本地 store 表。它不得将外键添加到 users、trade_order、 payment_invoice，或未来的库存表。

    14.2 贸易移民¶

    单独的贸易迁移仅添加所需的通用订单编排数据 新的工作流程，例如现有 JSON 元数据和任何显式存储快照 接受截止日期字段。它不能向 Store 添加外键。

    14.3 数据回填¶

    对于没有商店元数据的现有订单：

    • 将它们视为遗留/全球订单。
    • 除非存在可靠的外部映射，否则不要伪造StoreOrder记录。
    • 现有的付款/退款行为保持不变。
    • 新商店接受工作流程仅适用于新创建的商店范围订单。

    15. 故障处理和可观察性¶

    15.1 错误类别¶

    类别 HTTP/事件行为 记录
    无效的商店上下文 交易创建订单前拒绝 带有安全存储提示的警告
    店铺生意拒绝 发布拒绝事件 带有原因代码/相关性的信息
    事件架构违规 DLQ 事件 ID/主题错误
    消费者瞬态故障 重试 尝试计数警告
    快照不匹配 不要改变现有的 StoreOrder 严重警报
    发件箱发布失败 重试/DLQ 聚合/事件 ID 错误

    15.2 必需的结构化日志字段¶

    所有异步路径包括：

    eventId, topic, aggregateId, correlationId, causationId,
tradeOrderUuid, storeOrderUuid, storeUuid, attempt

    日志不得包含客户电话/地址详细信息、付款秘密、原始网关 有效负载或完整项目快照，除非为了安全诊断而明确编辑。

    15.3 运营指标¶

    目标部署至少导出：

    • 发件箱积压计数和最早的未发布年龄。
    • 消费者按主题滞后。
    • 按商店和原因代码的接受/拒绝计数。
    • 从交易订单创建到商店决策的接受延迟。
    • 超时取消计数。
    • 收件箱重复计数。
    • DLQ 计数和最早的消息年龄。

    贸易两次获得商店受理 仅一种合法的工作流程转换
    交易接受超时竞赛 商店接受 恰好一个终端贸易结果；过时的事件被安全地忽略

    16.3 合约测试¶

    事件生产者和消费者需要独立于 Doctrine 存储的合约装置 序列化。测试验证：

    • 必填字段和标量类型。
    • v1 事件兼容性。
    • 未知的可选字段公差。
    • 有效负载中缺少禁止的敏感字段。
    • 用于收件箱诊断的稳定规范有效负载哈希。

    17. 实施阶段¶

    第一阶段：商店基础¶

    1. 创建 Store、Membership、StoreOrder、Outbox 和 Inbox 实体/存储库。 2.添加Store服务接口和服务。 3、实施平台店铺管理和会员管理。
    2. 为所选通道实现 StoreContext 解析。
    3. 添加商店发现端点和商店员工授权测试。

    第 2 阶段：贸易编排合同¶

    1. 添加目标交易工作流程状态/转换和付款门。
    2. 将服务器生成的商店快照添加到新的交易订单中。
    3. 添加通用贸易集成事件发件箱抽象。
    4. 仅在 Trade 事务提交后发布 trade.order.created.v1。
    5. 对于商店范围内的订单创建，返回 202。
    6. 当不存在 Store 上下文时保留旧订单行为，前提是该旧订单行为存在 模式仍然是产品要求。

    第 3 阶段：存储消费者和决策事件¶

    1. 实现TradeOrderCreatedConsumer，具有收件箱和业务幂等性。
    2. 从不可变事件快照创建 StoreOrder。
    3. 实施商店资格检查和接受/拒绝决定。
    4. 将store.order.accepted.v1 / store.order.rejected.v1写入存储发件箱。
    5. 实施应用受保护的工作流程转换的 Trade 消费者。 6.添加超时取消和后期事件处理。

    第 4 阶段：履行和库存整合¶

    1. 定义库存预留事件合同。
    2. Gate Store接受预订确认。 3.添加商店履行操作和相应的贸易事件消费者，其中 商业工作流程转换仍由 Trade 拥有。 4.添加取消/解除补偿。

    第 5 阶段：服务提取准备就绪¶

    1. 将事件架构移至版本化合同包或 JSON 架构存储库。
    2. 用代理替换进程内传输，同时保留发件箱/收件箱行为。 3.独立移动Store数据库和消费者。
    3. 在 CI 中运行消费者驱动的契约测试。
    4. 在启用生产提取之前添加重放工具和操作仪表板。

    18. 验收标准¶

    Store 捆绑设计在以下情况下实施：

    标准 要求
    单一订单输入 没有商店端点创建商业订单；贸易仍然是切入点
    商店隔离 商店没有与贸易、支付、身份或库存相关的学说关联/FK
    上下文完整性 商店标识来自服务器解析的 StoreContext，而不是客户端正文字段
    专卖店投影 每个交易订单 UUID 都会幂等地创建一个 StoreOrder
    事件隔离 集成事件有效负载是版本化标量/JSON 合约，而不是 Doctrine 实体
    可靠的出版物 业务突变与本地发件箱写共享一笔交易
    可靠消费 收件箱事件 ID 唯一性和 StoreOrder 业务唯一性可保护重试
    支付门 商店范围内的订单在商店接受之前无法开始付款
    拒绝/超时 Trade 在商店拒绝或接受超时时取消未付款的订单
    授权 店铺会员范围 店铺运营；平台管理员保留显式覆盖
    库存边界 商店有预订合同挂钩，但没有嵌入式库存分类账
    提取准备 存储可以移动到单独的数据库/使用者，无需跨模式连接或事务
