    商店捆绑设计¶

    状态：在模块化整体中实现第 1-3 阶段。 商店、会员资格、 实现了 StoreOrder、贸易/商店发件箱-收件箱和 Messenger 消费者。 简化交易流程（draft -> pending -> confirmed -> paid -> fulfilled -> completed）； StoreOrder 是从 trade.order.created.v1 创建的投影，并在以下情况下自动接受： INVENTORY_ENABLED=0。库存保留仍然是一个有意推迟的界限。 Store 捆绑包 (src/Store/) 拥有多商店上下文、商店操作、 商店端订单预测，以及产品/规格目录（共享/全局 Product.store = NULL 和 store-private Product.store = Store，表 保留 trade_product/trade_specification）。贸易仍然是单一商业 订单入口点以及订单金额、付款、退款等的真实来源 客户订单状态。请参阅 Store Catalog Model 了解不变量。

    1. 目标和范围¶

    1.1 目标¶

    提供一个多存储边界，可以从 Symfony 模块开始，然后再作为 提取为服务而不改变商业订单的所有权。

    Customer -> Trade Order API -> Trade Order + Trade Outbox
                                  |
                                  v
                         Store event consumer
                                  |
                                  v
                         StoreOrder + store decision
                                  |
                                  v
                         Store result event -> Trade consumer

    该捆绑包拥有：

    • 商店身份、生命周期、业务配置和公共商店身份。
    • 商店会员资格和商店本地运营授权。
    • 存储请求上下文解析和验证。
    • 商店接受和履行数据的 StoreOrder 预测/聚合。
    • 商店集成事件的幂等消费和发布。
    • 商店履行和验证贸易订单所依据的合同（删除接受；仅履行+验证）。
    • 产品和规格目录（共享/全局和商店私有，可为空store）。

    该捆绑包不拥有：

    • 客户订单创建 API。
    • 商业订单金额、折扣、付款、退款或客户取消。
    • 规范的付款发票。
    • 库存实施。库存预留是定义的集成边界 此处并在稍后的库存包中设计。

    1.2 非目标¶

    第一个存储阶段不得：

    • 通过/stores/{id}/orders创建第二个面向客户的订单。
    • 保留贸易付款、退款或总金额状态的可写副本。
    • 将 Doctrine 外键添加到贸易、支付、身份或未来的库存表中。
    • 让客户端提供的storeId或storeCode成为授权事实。
    • 将trade_order.metadata视为权威商店关系。
    • 需要分布式事务或一次性代理交付。

    1.3 所有权矩阵¶

    关注 业主 商店责任
    订单 UUID、行项目金额、总计、货币 贸易 仅使用不可变快照
    客户付款及退款 贸易+支付 仅对由此产生的业务事件作出反应
    商店身份和会员资格 商店 权威
    商店接受（历史，现在自动接受） 商店 仅投影； INVENTORY_ENABLED=0
    商店履行运营 商店 权威一次介绍
    商店特定商品资格 商店 验收期间验证
    库存预订 库存，未来 请求和反应；不拥有股票分类帐
    促销计算 推广+贸易 在报价/订购时接收服务器解析的商店代码

    2. 架构原则¶

    2.1 一份商业订单¶

    Trade\Entity\Order 是唯一的客户订单聚合。客户通过创建它 现有的交易订单端点。 StoreOrder 仅作为以下结果创建 trade.order.created.v1 事件。

    Trade Order                         StoreOrder
-----------                         ----------
payment / refund                    store acceptance
commercial workflow                 operational workflow
customer-facing status              store-facing status
commercial amount                   copied amount snapshot for display only
invoice references                  fulfillment and reservation references

    StoreOrder 不得公开创建独立商业订单的 API。

    2.2 显式事件契约¶

    Trade 和 Store 通过版本化、可序列化的集成事件进行通信。他们 不得通过传递 Doctrine 实体、存储库或服务对象进行通信。

    发布者不知道存在哪些消费者。消费者只知道一个事件 架构及其自己的本地服务。

    2.3 本地事务，最终的跨束一致性¶

    每个模块将自己的业务记录和发件箱事件写入一个数据库中 交易。中继至少传递一次事件。消费者提供幂等性。

    local database transaction:
  business mutation + outbox insert

cross-module delivery:
  at least once + inbox deduplication + business unique keys

    任何组件都不能承担一次性消息代理保证。

    2.4 运行时工作者¶

    模块化整体作为 Compose 服务启动异步处理，而不是在 PHP-FPM请求流程：

    服务 命令 责任
    worker messenger:consume async 通过 Messenger 重试处理使用 Trade 和 Store 集成消息
    scheduler 贸易/商店发件箱发布者循环 每 OUTBOX_PUBLISH_INTERVAL 秒中继一次未发布的发件箱行（默认 5）

    调度程序和工作线程使用与 app 相同的应用程序映像和环境。这个 保持发件箱模式在 SQL 中的持久性，同时使整体操作自动化。

    2.5 稳定标量引用¶

    跨界引用是 UUID 和标量快照，而不是 Doctrine 关联。

    示例：

    • StoreOrder.tradeOrderUuid，而不是ManyToOne Trade\Order。
    • Membership.userUuid，而不是ManyToOne Identity\User。
    • 未来库存预留 UUID，而不是库存实体关系。

    这可以防止跨模块模式耦合并允许稍后使用单独的数据库。

    3. 需要更改现有系统¶

    该捆绑包无法实现为完全隔离的源目录，因为 Trade拥有唯一的订单入口点。所需的改变有意缩小范围 和通用；贸易不得进口商店实体、存储库或服务。

    面积 所需的目标改变 原因
    贸易订单工作流程 简化：draft -> pending -> confirmed -> paid -> fulfilled -> completed（无商店接受状态） 商店是一个投影；商店接受付款时未受限制
    贸易订单创建 保留服务器生成的 Store 快照（_store、_completionMode），并在 StoreContext 存在时始终发出 trade.order.created.v1 启动异步Store投影； TradeOrder 总是进入 pending
    贸易支付录入 无店门；标准贸易付款资格适用 商店不再阻止付款
    交易完成守护 仅在 _completionMode=store_verification 时通过 OrderCompletionGuardListener / OrderVerificationCompletionListener 强制执行 fulfilled -> completed每个订单的不可变验证要求
    贸易发件箱中继 发布版本化集成事件 将发布者与商店消费者分离
    身份 用户身份 在存储保留或发布用户引用之前添加唯一的用户 UUID 防止 Store 依赖 users.id
    根路由/DI 注册Store控制器和Store服务配置 编写新包

    对于商店和非商店订单，实施的贸易工作流程都是 draft -> pending -> confirmed -> paid -> fulfilled -> completed。没有 awaiting_store_acceptance、store_accepted 或 store_rejected 位置。当 StoreContext 存在时，Trade/Service/OrderService::createOrder 始终应用 submit (draft -> pending)，并且始终写入 trade.order.created.v1 发件箱行（请参阅第 6.3 节）。

    当前上下文传输是 X-Store-Code，仅针对活动 Store 进行解析 通过StoreContextResolver。商店范围内的应用程序订单会创建 pending 贸易订单 (HTTP 201)，并且商店消费者会在 INVENTORY_ENABLED=0 时自动接受符合条件的活跃商店；库存预留是未来的决策边界。当 Store 不可用（未找到/不活动）时，消费者抛出 RuntimeException 来触发 Messenger 重试/DLQ。

    3.1 在交易入口点存储上下文¶

    交易控制器在计算报价或创建之前获取 StoreContext 一个订单。它必须使用通用接口或 DTO，而不是 Store 实体类型。

    final readonly class StoreContext
{
    public function __construct(
        public string $storeUuid,
        public string $storeCode,
        public string $storeName,
        public string $channel,
        public bool $requireVerification = false,
    ) {}

    /** @return array{uuid: string, code: string, name: string, channel: string, requireVerification: bool} */
    public function toSnapshot(): array
    {
        return [
            'uuid' => $this->storeUuid,
            'code' => $this->storeCode,
            'name' => $this->storeName,
            'channel' => $this->channel,
            'requireVerification' => $this->requireVerification,
        ];
    }
}

    由 Store/Service/StoreContextResolver 从 StoreSettings::from($store->getSettings())->requireVerification 解决。

    Store 包实现了解析器。贸易仅消耗已解析的标量数据。 确切的定位机制可能是以下之一：

    机制 使用 信任规则
    规范主机/子域 商店品牌店面 从可信请求主机映射解析
    网关注入标头 API网关或小程序网关 仅在网关验证/签名后接受
    明确的路线选择 顾客刻意选择店铺 使用前验证服务器端的可用性

    原始请求正文 storeId、storeUuid 和 storeCode 永远不具有权威性。一个 仅当存储解析器验证并返回时，客户端才可以提供选择提示 具体的StoreContext。

    3.2 交易元数据快照¶

    Trade 在保留的元数据键下存储历史显示快照：

    {
  "_store": {
    "uuid": "store-uuid",
    "code": "shanghai-demo",
    "name": "Demo Store",
    "channel": "mini_program",
    "requireVerification": false
  },
  "_completionMode": "manual",
  "_storeVerificationReceived": true
}
    • _store.requireVerification — 订单创建时 Store.settings.fulfillment.requireVerification 的快照（每个订单不可变）。也在 trade.order.created.v1 store.requireVerification 中携带并保留为 StoreOrder.verificationRequired（参见第 5.3 节）。实时 Store.settings 更改不会影响飞行中的订单。
    • _completionMode — manual（默认）或store_verification。由 Trade/Service/OrderService 快照为 storeContext->requireVerification ? 'store_verification' : 'manual'。由Trade/EventListener/OrderCompletionGuardListener（除非allowCompletionFromStoreVerification否则阻止complete）和Trade/EventListener/OrderVerificationCompletionListener/Trade/MessageHandler/StoreOrderVerifiedHandler强制执行。
    • _storeVerificationReceived — 当 store.order.verified.v1 到达时，由 StoreOrderVerifiedHandler 设置的可选布尔标志。如果交易订单尚未fulfilled，则存储该标志并在fulfill之后自动完成OrderVerificationCompletionListener（乱序处理）。

    快照仅由受信任的服务器代码写入。对于审计和订单很有用 显示，但它不是查询、授权或完整性边界。 StoreOrder是 Store端权威记录，集成事件也有同样的记录 不可变的快照。 TradeOrder.metadata是权威的补全模式源； StoreOrder 存储 Store 端 verificationRequired 快照。

    5. 实体设计¶

    5.1 商店¶

    表： store

    领域 类型 必填 描述
    id 整数 是的 内部主键

    6. Trade Order State Machine Extension¶

    6.1 Target States¶

    Trade order workflow is intentionally simple and does not carry a Store acceptance branch. See config/packages/workflow.yaml and src/Trade/Entity/Order.php.

    draft -> pending -> confirmed -> paid -> fulfilled -> completed
draft -> cancelled
pending -> cancelled
confirmed -> cancelled
paid -> refunded
fulfilled -> completed
fulfilled -> cancelled
    • There are no awaiting_store_acceptance, store_accepted, store_rejected, awaiting_store_verification, store_submit, store_accept, store_reject, request_verification, or store_verify places/transitions.
    • Trade/Service/OrderService::createOrder always applies submit (draft -> pending) when a StoreContext is present, persists _store + _completionMode into metadata (see §3.2), and always writes a trade.order.created.v1 outbox row.
    • Store verification does not introduce workflow states; it gates the existing fulfilled -> completed transition via guards (see below).

    Store verification completion (single optional flow) — fulfillment.requireVerification

    fulfillment.requireVerification metadata._completionMode Trade completion behavior
    false (default) manual fulfilled --complete--> completed directly. No Store verification required.
    true store_verification fulfilled --complete--> completed only when Order::isCompletingFromStoreVerification()=true. Direct complete is blocked by Trade/EventListener/OrderCompletionGuardListener. Verification fact arrives via store.order.verified.v1 → Trade/MessageHandler/StoreOrderVerifiedHandler (sets _storeVerificationReceived=true and calls allowCompletionFromStoreVerification() → workflow->apply(complete)). Out-of-order case: if verified.v1 arrives before fulfilled, the handler stores _storeVerificationReceived and Trade/EventListener/OrderVerificationCompletionListener auto-completes right after fulfill.

    Store side: POST /store/{scopeId}/orders/{uuid}/verify (no verificationCode; UUID is the verification token) checks StoreOrder.isVerificationRequired() (immutable snapshot) and operationalStatus=fulfilled, then transitions fulfilled -> verified and emits store.order.verified.v1 with verifiedBy/verifiedAt.

    Invariants:

    1. Trade always emits trade.order.created.v1 when a StoreContext exists, after it has an immutable order UUID and Store snapshot (including requireVerification).
    2. Payment is not gated on Store state. pending -> confirmed -> paid proceeds normally.
    3. Store projection is eventual; TradeOrderCreatedHandler auto-accepts (pending_validation -> accepted) when INVENTORY_ENABLED=0.
    4. Verification consumers are idempotent (StoreConsumedEvent + workflow.can() checks + store-uuid match).
    5. When _completionMode=store_verification, fulfilled cannot complete without the Store verification flag (OrderCompletionGuardListener + OrderVerificationCompletionListener).

    6.2 Payment Gate¶

    No Store gate exists. The Trade payment service checks standard order.status eligibility (pending, confirmed, etc.). Payment endpoints do not return a conflict for Store-scoped orders awaiting any Store step. This was changed when awaiting_store_acceptance was removed.

    6.3 Order Creation Response¶

    POST /api/v1/app/orders with X-Store-Code always creates a pending order and returns 201 Order created (even for Store-scoped orders). A trade.order.created.v1 outbox row is always written when StoreContext exists:

    {
  "data": {
    "orderUuid": "trade-order-uuid",
    "status": "pending",
    "store": {
      "uuid": "store-uuid",
      "name": "Demo Store"
    }
  },
  "code": 201,
  "message": "Order created"
}

    The Store projection is created asynchronously; the client polls GET /api/v1/app/store-orders/{uuid} or the Trade order detail endpoint. Store availability does not affect the HTTP status; unavailable Store handling is via async retry/DLQ (see §8.1).

    For completion: fulfilled --complete--> completed is direct when fulfillment.requireVerification=false (_completionMode=manual). When true (_completionMode=store_verification), the client/staff must trigger POST /store/{scopeId}/orders/{uuid}/verify and the Trade order auto-completes on store.order.verified.v1 (see §7.5 and §8.1).

    7. Integration Event Contracts¶

    7.1 Envelope¶

    All integration events use this envelope:

    {
  "eventId": "uuid",
  "type": "trade.order.created",
  "version": 1,
  "occurredAt": "2026-07-24T12:00:00+00:00",
  "aggregateType": "trade_order",
  "aggregateId": "trade-order-uuid",
  "correlationId": "trade-order-uuid",
  "causationId": null,
  "payload": {}
}

    Rules:

    • eventId is immutable and globally unique.
    • aggregateId is the aggregate UUID, never an internal database id.
    • correlationId follows the business flow across services; for this flow it begins as the Trade order UUID.
    • causationId is the triggering event id, or null for an initial HTTP command.
    • A breaking payload change creates a new event version/topic; it never mutates v1.
    • Payloads must contain only data safe for the receiving domain. Do not publish secrets, payment credentials, raw provider callbacks, or unnecessary PII.

    7.2 trade.order.created.v1¶

    7.4 store.order.rejected.v1 — Removed¶

    Removed in the simplified coupling. The Store no longer emits store.order.rejected.v1. Rejection reasons below are retained only as a future inventory-rejection vocabulary; Trade does not consume a Store rejection event and does not transition to cancelled from a Store event.

    Previously allowed reasonCode values:

    Code Meaning
    STORE_NOT_FOUND Resolved Store no longer exists; indicates configuration drift
    STORE_UNAVAILABLE Suspended, closed, or not accepting the channel
    ITEM_NOT_AVAILABLE Store cannot sell one or more requested items
    OUT_OF_STOCK Inventory reservation rejected
    DELIVERY_NOT_SUPPORTED Delivery method/address not serviceable
    ACCEPTANCE_TIMEOUT Store decision did not arrive before the Trade deadline

    7.5 Implemented Verification Event¶

    store.order.verified.v1 (Store → Trade) is implemented when the order's snapshotted verificationRequired=true (i.e. Store.settings.fulfillment.requireVerification=true at order creation time, metadata._completionMode=store_verification).

    {
  "orderUuid": "trade-order-uuid",
  "storeOrderUuid": "store-order-uuid",
  "storeUuid": "store-uuid",
  "verifiedBy": "staff-user-uuid",
  "verifiedAt": "2026-09-03T08:00:00+00:00"
}
    • No verificationCode. Verification uses the order UUID as the verification token: POST /store/{scopeId}/orders/{uuid}/verify takes no body (empty JSON {} accepted). The controller resolves the StoreOrder by UUID and verifies membership scope.
    • Preconditions in Store/Service/StoreOrderService::verify(): isVerificationRequired()=true and operationalStatus=fulfilled; otherwise LogicException. On success transitions fulfilled -> verified (StoreOrder::verify() sets verifiedAt/verifiedBy) and records store.order.verified.v1 via store_outbox_message (Store/Service/StoreOutboxService).
    • Consumer: Trade/MessageHandler/StoreOrderVerifiedHandler (async StoreOrderVerifiedMessage). Checks order.metadata._store.uuid === payload.storeUuid and metadata._completionMode === 'store_verification'. Inside a transaction sets metadata._storeVerificationReceived=true, calls Order::allowCompletionFromStoreVerification(), then workflow->can(complete) → workflow->apply(complete) if fulfilled; otherwise the flag remains and Trade/EventListener/OrderVerificationCompletionListener completes after fulfill (out-of-order handling). Idempotent via workflow.can() and repeated flag writes.
    • Audit fields on store_order are verifiedAt/verifiedBy only (see §5.3); verificationCode column was removed.

    8. Consumer And Publisher Design¶

    8.1 Trade Order Created Consumer¶

    Store/MessageHandler/TradeOrderCreatedHandler (TradeOrderCreatedMessage) processes one message as follows:

    receive message (trade.order.created.v1)
  -> validate envelope and schema version (eventId + payload)
  -> start Store local transaction
  -> insert StoreConsumedEvent(eventId), or return if already present (inbox dedup)
  -> find Store by payload.store.uuid; if not found or not active, throw RuntimeException
     (triggers Messenger retry; not a business rejection)
  -> create/find StoreOrder by tradeOrderUuid via StoreOrderService::createFromTradeOrderSnapshot
     (includes verificationRequired snapshot from payload.store.requireVerification;
      idempotent on duplicate tradeOrderUuid with same snapshot; LogicException on mismatch)
  -> if StoreTradeOrderCancellation exists for this tradeOrderUuid -> StoreOrder.cancel()
  -> if StoreOrder.operationalStatus != pending_validation -> return (already handled)
  -> if !INVENTORY_ENABLED -> StoreOrderService::accept() (pending_validation -> accepted, no outbox)
  -> else -> StoreOrder.awaitInventory(reservationId) + StoreOutboxService.record('inventory.reservation.requested.v1')
  -> commit
  -> acknowledge broker message

    No store.order.accepted.v1 / rejected.v1 is emitted. The unavailable-Store path throws RuntimeException('Store is not available.') so the broker retries rather than committing a rejected projection.

    The broker message is acknowledged only after the Store transaction commits. If the process crashes before acknowledgement, the event is delivered again and becomes an inbox/business-idempotent no-op.

    8.2 Outbox Publisher¶

    The outbox publisher is a transport adapter, not business logic:

    poll unpublished outbox messages in created order
  -> lock one batch
  -> publish envelope to transport topic
  -> mark publishedAt on broker acknowledgement
  -> on transient error: increment attempts and retry later
  -> on retry exhaustion: retain record and alert/DLQ

    Initial deployment may use Symfony Messenger with Doctrine transport. The business contract must not depend on that choice. RabbitMQ, Kafka, SQS, or an HTTP event relay can replace the transport without changing StoreOrder business code.

    8.3 Retry Classification¶

    Failure Consumer action
    Duplicate eventId Acknowledge; no mutation (inbox hit)
    Duplicate tradeOrderUuid, same snapshot Continue idempotently; return existing StoreOrder
    Duplicate tradeOrderUuid, different snapshot Do not overwrite; throw LogicException → critical alert and DLQ
    Temporary database/broker failure Roll back and retry
    Invalid event schema/version DLQ; do not retry blindly (InvalidArgumentException)
    Store not found / not active Throw RuntimeException('Store is not available.') → retry with backoff (Messenger retry), then DLQ
    Inventory rejection (future) Commit rejected StoreOrder; inventory DLQ handling to be defined
    Unexpected domain exception Roll back; retry with bounded backoff, then DLQ

    8.4 Ordering And Concurrency¶

    • Store 消费者通过 tradeOrderUuid 通过 必要时有唯一的 StoreOrder 密钥和事务锁定。
    • 事件主题应在传输支持的情况下保留每个聚合键的排序 它，但正确性不能依赖于全局排序。
    • 交易后的商店验证fulfilled是唯一的跨捆绑结果事件； store.order.verified.v1 通过 _storeVerificationReceived + workflow.can(complete) 实现幂等。
    • 交易取消由 Store/MessageHandler/TradeOrderCancelledHandler (StoreTradeOrderCancellation + StoreOrder.cancel()) 消耗，确保忽略后期验证。
    • 所有结果处理程序在应用转换之前都会验证预期的源状态。

    获取 /api/v1/store/manage/orders/{uuid} 活跃会员 StoreOrder操作详情
    发布 /api/v1/store/manage/orders/{uuid}/fulfill 履行/经理/所有者 (store:order:fulfill) 标记存储操作 fulfilled（本地转换；已完成 -> 已完成）。如果 _storeVerificationReceived 已经为 true，则触发 OrderVerificationCompletionListener 自动完成。
    发布 /api/v1/store/{scopeId}/orders/{uuid}/verify 履行/经理/所有者 (store:order:verify) 完成后存储验证 — 需要 StoreOrder.isVerificationRequired()=true（快照，非实时设置）和 operationalStatus=fulfilled；主体为空（{}）；使用订单 UUID 作为验证令牌。转换 fulfilled -> verified 并发出 store.order.verified.v1 和 verifiedAt/verifiedBy（无 verificationCode）。 Staff userUuid 取自经过身份验证的 Identity 用户。

    POST .../accept 和 POST .../reject 已被删除。商店验收是自动的；拒绝被推迟到未来的库存。

    所有操作都会根据 StoreOrder 的本地 Store 关系检查成员资格，而不是请求提供的商店标识符。 fulfill/verify 是幂等守卫：如果不是 fulfilled 或不是 verificationRequired，verify 会失败并返回 LogicException。

    10. 授权模型¶

    10.1 角色¶

    校长 范围 能力
    ROLE_ADMIN 平台 所有商店管理和报告
    商店 owner 一间店 会员、商店设置、履行、验证
    商店 manager 一间店 履行、验证、操作视图
    商店 clerk 一间店 读取操作队列；有限的配置操作
    商店 fulfillment 一间店 仅限履行的运营行动
    客户 自有订单 仅读取客户安全的 StoreOrder 视图

    10.2 授权规则¶

    1. 平台角色存在于身份中并保留其现有含义。
    2. 存储角色仅存在于Membership中。
    3. Store 控制器将经过身份验证的 Identity 用户解析为标量 userUuid 并 查询 在本地存储成员资格。
    4. ROLE_ADMIN 仅在明确的管理路由上绕过成员资格检查。
    5. 商店工作人员无法直接提升贸易订单的商业状态。
    6. 商店员工操作（fulfill、verify）产生商店事件；贸易仅通过 StoreOrderVerifiedHandler + OrderCompletionGuardListener/OrderVerificationCompletionListener 和工作流程防护应用商业 complete。

    11. 商店背景和促销合同¶

    促销目前在交易的价格计算上下文中使用 storeCode。的 商店捆绑包为该值提供了权威来源：

    request -> StoreContextResolver -> active Store -> StoreContext.storeCode
        -> Trade calculatePrices(..., storeCode, ...)
        -> Promotion storeCode filtering

    规则：

    • 客户不能通过发布storeCode来选择任意促销商店。
    • Trade 将解析器生成的代码传递到定价管道。
    • 商店快照与订单创建事件一起保存，以便商店消费者可以 验证订单的定价是否适用于预期商店。
    • 促销保持独立：它不引用存储表或实体。
    • 全球促销仍以现有的空商店代码约定为代表； 商店选择决不能无意中将一个不知名的商店变成全球定价。

    这种设计使现有的Promotion.storeCode成为路由输入，而不是Store 领域模型或授权机制。

    12. 库存边界¶

    库存被故意排除在第一个商店数据模型之外。商店定义了 它需要的命令/结果边界：

    Store validates order (TradeOrderCreatedHandler)
  -> if INVENTORY_ENABLED=0: auto-accept (pending_validation -> accepted), no inventory event
  -> if INVENTORY_ENABLED=1:
       inventory.reservation.requested.v1
       -> Inventory reserves quantity idempotently
       -> inventory.reservation.confirmed.v1  -> StoreOrder.accept()
            or inventory.reservation.rejected.v1 -> StoreOrder.reject()

    未来的请求负载必须包括：

    • reservationId：存储生成的幂等性/引用 UUID。
    • storeUuid。
    • tradeOrderUuid和storeOrderUuid。
    • 商品库存键、数量和不可变的关联 ID。
    • 预订到期/截止日期。

    商店拥有请求预订的决定权并保留结果reservationId。 库存拥有可用数量、预留分类账、减量/释放和库存 和解。两个模块都不会访问对方的数据库。

    13. 超时和补偿¶

    13.1 接受超时¶

    Trade 在创建订单时记录可配置的接受截止日期。预定的 贸易工作发现订单在截止日期后仍在等待商店接受，并且：

    1. 应用取消转换。
    2. 将trade.order.cancelled.v1写入交易发件箱，原因为ACCEPTANCE_TIMEOUT。
    3. Store消费cancel，将其挂起的操作标记为已取消，并询问future 库存以释放任何预订。

    该作业必须是幂等的：终端或已接受的订单将被忽略。

    13.2 迟到的事件¶

    迟到的活动 所需行为
    交易超时取消后商店接受 贸易忽略它并记录相关性；商店发布取消活动相关工作
    交易取消后商店拒绝 贸易忽视了它；商店保留被拒绝的审核记录
    商店等待库存时取消交易 商店将取消标记为待处理，并在已知后释放预订
    接受前的付款事件 贸易拒绝/标记为不变违约；付款开始必须已被控制

    13.3 无分布式回滚¶

    一旦事件跨越发件箱边界，远程突变就无法回滚。 补偿表示为新的业务事件和本地状态转换，而不是 跨服务数据库事务。

    14. 持久化和迁移计划¶

    14.1 初始存储迁移¶

    存储迁移仅创建存储拥有的表：

    store
store_membership
store_order
store_outbox_message
store_consumed_event

    它可能包括来自 store_membership.store_id 和 store_order.store_id 的外键 到本地 store 表。它不得将外键添加到 users、trade_order、 payment_invoice，或未来的库存表。

    14.2 贸易移民¶

    单独的贸易迁移仅添加所需的通用订单编排数据 新的工作流程，例如现有 trade_order.metadata JSON 中的存储快照 (_store)、_completionMode 和 _storeVerificationReceived。不添加接受截止日期字段或 Store FK。

    14.3 数据回填¶

    对于没有商店元数据的现有订单：

    • 将它们视为遗留/全球订单。
    • 除非存在可靠的外部映射，否则不要伪造StoreOrder记录。
    • 现有的付款/退款行为保持不变。
    • 简化的预测（自动接受）和验证门 (_completionMode) 仅适用于此更改后新创建的商店范围订单。

    15. 故障处理和可观察性¶

    15.1 错误类别¶

    类别 HTTP/事件行为 记录
    无效的商店上下文 交易创建订单前拒绝 带有安全存储提示的警告
    商店不可用（未找到/未激活） 消费者抛出 RuntimeException('Store is not available.') → 重试/DLQ storeUuid/tradeOrderUuid/尝试警告
    事件架构违规 DLQ 事件 ID/主题错误
    消费者瞬态故障 重试 尝试计数警告
    快照不匹配（tradeOrderUuid 与 storeCode/verificationRequired/amount 冲突） 不要改变现有的 StoreOrder；抛出 LogicException → 严重警报 严重警报
    验证前提条件失败（!verificationRequired 或 status != fulfilled） 来自 StoreOrderService::verify 的 HTTP 409/422 storeOrderUuid/verificationRequired/status 警告
    发件箱发布失败 重试/DLQ 聚合/事件 ID 错误

    15.2 必需的结构化日志字段¶

    所有异步路径包括：

    eventId, topic, aggregateId, correlationId, causationId,
tradeOrderUuid, storeOrderUuid, storeUuid, attempt

    日志不得包含客户电话/地址详细信息、付款秘密、原始网关 有效负载或完整项目快照，除非为了安全诊断而明确编辑。

    15.3 运营指标¶

    目标部署至少导出：

    • 发件箱积压计数和最早的未发布年龄。
    • 消费者按主题滞后。
    • 按商店划分的 StoreOrder 创建计数（自动接受与等待库存）。
    • 按商店划分的验证计数（verified 状态）。
    • 履行到完成的延迟（手动与存储验证）。
    • 收件箱重复计数。
    • DLQ 计数和最早的消息年龄。

    17. 实施阶段¶

    第一阶段：商店基础¶

    1. 创建 Store、Membership、StoreOrder、Outbox 和 Inbox 实体/存储库。 2.添加Store服务接口和服务。 3、实施平台店铺管理和会员管理。
    2. 为所选通道实现 StoreContext 解析。
    3. 添加商店发现端点和商店员工授权测试。

    第 2 阶段：贸易编排合同¶

    1. 将交易工作流程简化为 draft -> pending -> confirmed -> paid -> fulfilled -> completed（删除接受状态）。
    2. 将服务器生成的商店快照（_store + _completionMode + _storeVerificationReceived）添加到新的交易订单中。
    3. 添加通用贸易集成事件发件箱抽象。
    4. Trade 事务提交后，当 StoreContext 存在时，始终发布 trade.order.created.v1； draft -> pending 通过 submit。
    5. 对于商店范围内的订单创建，返回 201 (pending)（无 202）。
    6. 当不存在 Store 上下文时保留旧订单行为，前提是该旧订单行为存在 模式仍然是产品要求。

    第 3 阶段：存储消费者和决策事件¶

    1. 实现Store/MessageHandler/TradeOrderCreatedHandler，具有收件箱和业务幂等性。
    2. 从不可变事件快照（包括verificationRequired）创建StoreOrder。 3、INVENTORY_ENABLED=0时自动接受（pending_validation -> accepted）；否则请求库存预留 (awaiting_inventory)。
    3. 通过 RuntimeException 重试不可用的 Store（无拒绝事件）。
    4. 实现StoreOrderService::fulfill / verify和store.order.verified.v1发件箱。
    5. 实现Trade/MessageHandler/StoreOrderVerifiedHandler + OrderCompletionGuardListener / OrderVerificationCompletionListener（包括乱序处理）。

    第 4 阶段：履行和库存整合¶

    1. 定义库存预留事件合同。
    2. Gate Store接受预订确认。 3.添加商店履行操作和相应的贸易事件消费者，其中 商业工作流程转换仍由 Trade 拥有。 4.添加取消/解除补偿。

    第 5 阶段：服务提取准备就绪¶

    1. 将事件架构移至版本化合同包或 JSON 架构存储库。
    2. 用代理替换进程内传输，同时保留发件箱/收件箱行为。 3.独立移动Store数据库和消费者。
    3. 在 CI 中运行消费者驱动的契约测试。
    4. 在启用生产提取之前添加重放工具和操作仪表板。

    18. 验收标准¶

    Store 捆绑设计在以下情况下实施：

    标准 要求
    单一订单输入 没有商店端点创建商业订单；贸易仍然是切入点
    商店隔离 商店没有与贸易、支付、身份或库存相关的学说关联/FK
    上下文完整性 商店标识来自服务器解析的 StoreContext，而不是客户端正文字段
    专卖店投影 每个交易订单 UUID 都会幂等地创建一个 StoreOrder
    事件隔离 集成事件有效负载是版本化标量/JSON 合约，而不是 Doctrine 实体
    可靠的出版物 业务突变与本地发件箱写共享一笔交易
    可靠消费 收件箱事件 ID 唯一性和 StoreOrder 业务唯一性可保护重试
    支付门 无店门；贸易支付资格是标准的（无 awaiting_store_acceptance 块）
    拒绝/超时 无存储拒绝事件/接受超时；不可用的存储通过 DLQ 重试，未取消
    验证门 当fulfillment.requireVerification=true、fulfilled -> completed需要store.order.verified.v1时（不可变的每订单快照，verificationRequired + _completionMode）
    授权 商店会员范围fulfill/verify；平台管理员保留显式覆盖
    库存边界 商店有预订合同挂钩，但没有嵌入式库存分类账
    提取准备 存储可以移动到单独的数据库/使用者，无需跨模式连接或事务
