    贸易捆绑设计¶

    交易包 (src/Trade/) 拥有订单、订单项目、价格计算和 基于 Symfony Workflow 的订单状态机。产品和规格归 Store（src/Store/Entity/Product.php、src/Store/Entity/Specification.php、 保留表 trade_product/trade_specification) 并可空 store (NULL = 共享/全局）；参见Store Catalog Model。 Trade 仍然是 商业订单权限并通过标量快照引用商店目录 StoreContext。

    1. 概述¶

    Trade提供完整的订单管理系统：

    • 商店目录集成与 Store 产品和规格（类似 SKU 的变体，Product.store 对于共享/全局可为空）
    • 订单 具有状态机生命周期（草稿 -> 已完成）
    • 订单商品带有价格快照以确保历史准确性
    • 价格计算管道：具有优先级排序的可插入计算器（在 BasePriceCalculator 中强制执行商店可见性）
    • 软删除：产品和规格使用 isDeleted 标志（商店实体）
    • UUID v4：订单和商品的外部标识符
    • 商店集成：商店范围的订单写入本地发件箱事件并等待商店接受

    1.1 目录所有权¶

    产品和规格是 Store 实体（Product.store 可为空）。目录读取、报价和订单需要 StoreContext (X-Store-Code → Store)； BasePriceCalculator 仅接受已解析商店的共享 (store IS NULL) 或商店拥有的规范。请参阅Store Catalog Model。

    1.2 实体¶

    实体 表 目的
    Store\Product trade_product 可销售产品，包含名称、描述、状态、可为空 store
    Store\Specification trade_specification 产品变体（名称、美分价格、状态）
    Order trade_order 带有状态机、总计、货币的采购订单
    OrderItem trade_order_item 包含 specificationUuid（标量）、specificationTitle、快照、数量、单价的订单项
    TradeOutboxMessage trade_outbox_message 交易整合事件接力记录

    1.2 商店范围订单（可选，默认关闭）¶

    POST /api/v1/app/orders 仍然是唯一的客户订单入口点。值得信赖的 X-Store-Code 由 Store 捆绑解析为 Trade-owned 标量 StoreContext；贸易永远不会导入商店实体。订单始终收到 _store 元数据快照，但是否进入Store工作流程由 Store.settings（参见store.md §5.1.1，默认情况下都是false）：

    • order.requireAcceptance=false（默认）：订单保持draft（就像普通订单一样）， POST /api/v1/app/orders 返回 201 Order created，不返回 trade.order.created.v1。
    • order.requireAcceptance=true：命令输入awaiting_store_acceptance，写入 trade.order.created.v1 在同一事务中并返回 202 Order submitted for store acceptance。

    app:trade:outbox:publish 在发出时通过 Messenger 调度事件。商店消耗它 幂等地写入其 StoreOrder 和结果 Outbox 事件 (store.order.accepted/rejected/verified)， 和贸易消费者适用 store.order.accepted.v1 / store.order.rejected.v1 / store.order.verified.v1（后者在fulfillment.requireVerification=true时驱动fulfilled --request_verification--> awaiting_store_verification --store_verify--> completed）。守卫阻塞在Store/EventListener/StoreOrderWorkflowGuardListener中； Trade/EventListener/OrderWorkflowListener 是 completed 的状态驱动，并且不会硬编码存储转换名称。状态栏是 VARCHAR(40) 支持这些工作流状态。

    3. 实体关系¶

    Store\Product (status: active/inactive, isDeleted: bool, metadata: JSON, store: ?Store)
  |
  +-- 1:N -> Store\Specification (cascade: persist)

Store\Specification (name, price: int cents, status, sort, isDeleted)
  |  inherits Product.store visibility
  +-- (no FK) -> Trade\OrderItem via scalar specificationUuid + snapshots

Order (uuid, totalAmount: int cents, currency: CNY, status: state machine, notes, metadata _store)
  |
  +-- M:1 -> User
  +-- 1:N -> OrderItem (cascade: persist)

OrderItem (uuid, quantity, unitPrice: cents, price: cents, cost, profit, specificationUuid, specificationTitle, specSnapshot/productSnapshot: JSON)
  |
  +-- M:1 -> Order
  +-- (scalar) specificationUuid (indexed, no FK)

    4. 实体设计细节¶

    4.1 产品¶

    • UUID v4 供外部参考
    • status：active或inactive
    • isDeleted：软删除标志
    • metadata：JSON可扩展字段

    4.2 规格¶

    • 属于产品
    • price 以分为单位（整数，在 API 边界与小数之间转换）
    • status：活动/非活动
    • sort：手动排序
    • isDeleted：软删除标志

    4.3 顺序¶

    • UUID v4
    • totalAmount 以分为单位
    • currency：默认CNY
    • status：状态机标记字段（草稿/待定/已确认/已付款/已完成/已完成/已取消/已退款）
    • cancelledAt、completedAt：由OrderWorkflowListener设置
    • items：级联持久化

    4.4 订单项目¶

    • UUID v4
    • unitPrice：订购时规格价格的快照（美分）
    • price：unitPrice * quantity，在#[ORM\PrePersist]中自动计算
    • cost、profit：用于保证金跟踪
    • specSnapshot、productSnapshot：创建历史记录时捕获的 JSON 快照

    5. 价格计算管道¶

    5.1 合同¶

    interface PriceCalculatorInterface
{
    public function calculate(PriceCalculationContext $context): void;
    public static function getPriority(): int;
}

    5.2 计算器链（优先顺序）¶

    优先 计算器 模块 责任
    -100 -100 BasePriceCalculator 贸易 解析规范实体、验证活动/未删除、提取单价、捕获快照
    50 50 QuantityCalculator 贸易 计算每个项目的 price = unitPrice * quantity
    55 TotalAggregator 贸易 在促销评估之前建立小计
    60 PromotionCalculator 促销 DSL 评估 → 匹配 → 应用（最多 20 次迭代、应用 ID 跟踪、独占/锁定项目/最佳价格冲突模式）

    外部模块（例如，Promotion、未来的Coupon）通过实现PriceCalculatorInterface并使用#[AutoconfigureTag('trade.price_calculator')]进行标记来挂钩到管道中。贸易对这些模块的认知度为零。

    5.3 管道执行¶

    OrderService::calculatePrices($items, $currency)
  -> Collect all PriceCalculatorInterface implementations (auto-tagged)
  -> Sort by getPriority() ascending
  -> Execute each in sequence on PriceCalculationContext
  -> Return PriceCalculationResult (items, totalAmount, currency)

    5.4 管道执行¶

    OrderService::calculatePrices($items, $currency, $storeCode = null, $meta = [])
  -> Create PriceCalculationContext with items, currency, user, storeCode, meta
  -> Collect all PriceCalculatorInterface implementations (auto-tagged)
  -> Sort by getPriority() ascending
  -> Execute each in sequence on PriceCalculationContext
     (BasePriceCalculator → QuantityCalculator → TotalAggregator → PromotionCalculator)
  -> Return PriceCalculationResult (items, totalAmount, currency, meta)

    5.5 个 DTO¶

    class PriceCalculationContext
{
    public array $inputItems;     // Raw input from request
    public array $items;          // Mutated by calculators
    public int $totalAmount;      // Final total in cents
    public string $currency;      // e.g., 'CNY'
    public array $meta = [];      // Bidirectional opaque channel for calculators
    public ?object $user = null;  // Current user (for member-level conditions)
    public ?string $storeCode = null; // Multi-store routing
}

class PriceCalculationResult
{
    public int $totalAmount;
    public string $currency;
    public array $items;          // Calculated order items
    public array $meta;           // From context.meta (carries promotion/coupon results)
}

    5.6 meta 渠道合约¶

    meta 是 Trade 从不检查的不透明数组。计算器从中读取作为输入 并将其写入作为输出。合同是：

    方向 示例 设置者
    客户端→计算器 {coupon: {code: "ABC123"}} 请求正文 → calculatePrices($items, $currency, $storeCode, $meta)
    计算器 → 客户端 {promotion: {inner: [...], outer: {...}}} PromotionCalculator 写入 context.meta['promotion']
    任意键均可共存 {promotion: {...}, coupon: {...}, existing: "..."} 多种计算器

    保证： - Trade 永远不会读取或改变 meta 内容 - 它会保持不变。 - PriceCalculationResult::fromContext() 将 context.meta 逐字复制到结果中。 - 新模块（例如优惠券）遵循相同的模式：实现PriceCalculatorInterface， 从context.meta['coupon']读取，写入context.meta['coupon']。

    5.7 注册¶

    计算器通过 config/services.yaml 自动发现和标记：

    services:
  App\Trade\Service\Pricing\:
    resource: '../src/Trade/Service/Pricing/'
    tags: ['trade.price_calculator']

    可以通过实现该接口来添加新的计算器——无需更改其他代码。

    6. 订单状态机¶

    6.1 配置¶

    文件：config/packages/workflow.yaml - 两个可选的存储流（默认情况下均为false，请参阅store.md §5.1.1）。

    framework:
  workflows:
    order:
      type: state_machine
      marking_store: { type: method, property: status }
      places:
        - draft
        - pending
        - awaiting_store_acceptance
        - store_accepted
        - store_rejected
        - confirmed
        - paid
        - fulfilled
        - awaiting_store_verification
        - completed
        - cancelled
        - refunded
      transitions:
        submit:   draft -> pending
        store_submit: draft -> awaiting_store_acceptance # guard: order.requireAcceptance && hasStore
        store_accept: awaiting_store_acceptance -> store_accepted
        store_reject: awaiting_store_acceptance -> store_rejected
        confirm:  [pending, store_accepted] -> confirmed
        pay:      confirmed -> paid
        fulfill:  paid -> fulfilled
        request_verification: fulfilled -> awaiting_store_verification # guard: fulfillment.requireVerification && hasStore
        store_verify: awaiting_store_verification -> completed           # Staff verify
        complete: fulfilled -> completed                                 # guard blocks when requireVerification
        cancel:   [draft, pending, awaiting_store_acceptance, store_accepted, store_rejected, confirmed, fulfilled, awaiting_store_verification] -> cancelled
        refund:   completed -> refunded

    守卫住在Store/EventListener/StoreOrderWorkflowGuardListener（通过StoreRepository读取Store.settings）。普通订单（_store 不存在）在工作流程层仍然是允许的。

    6.2 有效转换（非商店快乐路径 + 商店分支）¶

    来自 至 过渡名称 当
    草稿 待定 submit 总是 / requireAcceptance=false + hasStore
    草稿 等待商店接受 store_submit requireAcceptance=true + hasStore
    等待商店接受 商店接受 store_accept 通过 store.order.accepted.v1
    等待商店接受 商店被拒绝 store_reject 通过 store.order.rejected.v1
    待定/ store_accepted 确认 confirm
    确认 付费 pay
    付费 履行 fulfill
    履行 等待商店验证 request_verification requireVerification=true + hasStore
    等待商店验证 已完成 store_verify store.order.verified.v1 {verificationCode, verifiedBy}
    履行 已完成 complete requireVerification=false 或没有商店
    草稿/待定/.../已完成/awaiting_store_verification 取消 cancel
    已完成 已退款 refund

    6.3 工作流监听器¶

    class OrderWorkflowListener
{
    // On cancel/paying/fulfill/refund -> set timestamps per transition
    // On *landed in* completed (complete via Trade OR store_verify via Store) -> set completedAt + dispatch OrderCompletedEvent (status-driven, no Store transition name)
}

    7. 订单创建流程¶

    POST /api/v1/manage/orders
  Body: {items: [{specification: {id: N}, quantity: N}, ...], currency: "CNY", notes: "...", meta: {coupon: {...}}}
  |
  v
OrderService::calculatePrices($items, $currency, $storeCode, $meta)
  -> Create PriceCalculationContext(items, currency)
  -> Set context.user, context.storeCode, context.meta = $meta
   -> Price Calculation Pipeline (Base → Quantity → TotalAggregator [subtotal] → Promotion)
   -> Returns PriceCalculationResult (items, totalAmount, currency, meta)
  |
  v
OrderService::createOrder($calculatedItems, $user, $totalAmount, $currency, $notes)
  -> Within transaction:
     -> Create Order entity
     -> For each calculated item: create OrderItem
        -> Snapshot spec + product data
        -> Auto-calculate price = unitPrice * quantity (PrePersist)
     -> Persist + flush
  -> Returns Order entity

    7.1 报价流程（订单预览）¶

    POST /api/v1/app/orders/quote
  Body: {items: [{specificationId: N, quantity: N}, ...], meta: {coupon: {code: "ABC"}}}
  |
  v
OrderService::calculatePrices($items, $currency, $storeCode, $meta)
  -> Returns PriceCalculationResult (items, totalAmount, currency, meta)
  -> No Order is persisted — pure pricing preview

Response:
{
  data: {
    items: [{specificationId: 1, unitPrice: 10000, price: 10000, ...}],
    totalAmount: 8000,
    currency: "CNY",
    meta: {
      promotion: { inner: [{promotionId: 1, promotionName: "满减", ...}] }
    }
  }
}

    获取 /api/v1/app/specifications/by-product/{id} 按产品划分的规格
    获取 /api/v1/app/specifications/{id} 规格详细信息
    获取 /api/v1/app/orders 列出当前用户的订单
    获取 /api/v1/app/orders/{id} 订单详情
    发布 /api/v1/app/orders 创建订单
    发布 /api/v1/app/orders/quote 无需创建订单即可计算价格
    获取 /api/v1/app/orders/{id}/items 查看订单项目
    发布 /api/v1/app/orders/{id}/cancel 取消自己的订单

    9. 订单控制器约束¶

    9.1 更新约束¶

    订单只能在draft状态下更新。应拒绝尝试更新非草稿订单。

    9.2 删除约束¶

    订单只能在draft状态下删除。其他州要求首先取消。

    9.3 工作流程操作¶

    • todo：列出至少有一个已启用转换的所有订单
    • transitions：返回特定订单的可用转换
    • do/{transition}：在事务中执行指定的转换，可以选择接受数据以在转换之前更新实体

    9.4 付款（支付）¶

    • POST /manage/orders/{id}/pay 与 {systemWalletId, paymentMethod}
    • 验证订单处于confirmed状态
    • 从用户钱包中扣除，通过TransferService将积分存入系统钱包
    • 设置paidAt、paymentMethod，应用pay转换

    9.5 履行¶

    • POST /manage/orders/{id}/fulfill 与 {trackingNumber, shippingAddress}
    • 验证订单处于paid状态
    • 设置fulfilledAt、trackingNumber、shippingAddress
    • 应用fulfill过渡

    9.6 退款¶

    • POST /manage/orders/{id}/refund 与 {systemWalletId, reason}
    • 验证订单处于completed状态
    • 通过TransferService从系统钱包转回用户钱包
    • 设置refundedAt、refundReason，应用refund转换

    9.7 用户取消¶

    • POST /app/orders/{id}/cancel -- 经过身份验证的用户取消自己的订单
    • 仅当状态为 draft、pending 或 confirmed 时允许
    • 将状态设置为cancelled（不通过工作流程，直接更新）

    9.8 查看项目¶

    • GET /manage/orders/{id}/items -- 管理视图
    • GET /app/orders/{id}/items -- 用户视图（所有权已验证）

    10. 资金处理合同¶

    方面 规则
    存储 bigint 数据库中的（分）
    PHP 类型 int 金额
    API输入 十进制字符串/数字
    API输出 十进制字符串/数字
    写入时转换 * 100（通过@transform表达或服务）
    读取时转换 / 100
