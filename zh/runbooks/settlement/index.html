    结算操作手册¶

    本 Runbook 是配置、发布和操作 结算捆绑。它补充了设计文件 与混凝土， 分步程序和工作示例。

    1. 一分钟概念¶

    • 资金是结算时确认的、可信的金额（例如订单付款） 必须分配。
    • 计划是将一笔资金分为分配给受助者。
    • 规则是谁得到什么的版本化、声明性定义。
    • 规则一旦发布就不可更改；计划存储所使用的确切版本和跟踪。
    • 货币精确（18 进制量子，brick/math）；没有漂浮物。
    • 分配通过SettlementVoucherPort边界发布到钱包， 通过结算发件箱异步进行。

    2. 规则生命周期¶

    create rule draft → create draft version → update draft version → publish version
    步骤 端点
    创建规则草案 POST /api/v1/manage/settlement-rules (code, name)
    创建草稿版本 POST /api/v1/manage/settlement-rule-versions
    更新草稿版本 PUT /api/v1/manage/settlement-rule-versions/{id}
    发布版本 POST /api/v1/manage/settlement-rule-versions/{uuid}/publish
    阅读接受的架构 GET /api/v1/manage/settlement-rules/configuration

    发布的版本是不可变的。要更改规则，请使用新的规则创建新版本 有效间隔并发布。现有计划保留其历史快照。

    3. 规则定义结构¶

    {
  "appliesTo": ["trade.order.v1"],
  "scope": "order",
  "conflictMode": "stack",
  "eligibility": { "all": [ { "factEquals": ["order.status", "paid"] } ] },
  "recipient": { "resolver": "context_candidate", "key": "store.owner" },
  "formula": { "rateOf": { "basis": "funding.distributable", "bps": 8000 } },
  "reasonCode": "store_revenue"
}

    priority、effectiveFrom 和 effectiveTo 是 版本元数据，而不是定义 字段。它们是根据版本创建/更新请求提供的。

    3.1 必需与可选¶

    领域 必填 笔记
    appliesTo 是的 来源类型，例如trade.order.v1
    recipient 是的 literal、context_candidate 或 fact_reference
    formula 是的 金额表达式
    scope 没有 order（默认）或order_item
    eligibility 没有 谓词树
    conflictMode 没有 stack（默认）、exclusive_group、stop
    group 没有 conflictMode=exclusive_group
    allocationKey 没有 覆盖自动生成的密钥
    reasonCode 没有 审核标签（默认rule）

    4. 收件人解析¶

    旋转变压器 输入 结果
    literal type、id 固定收件人
    context_candidate key 源适配器投射的接收者
    fact_reference typeFact、idFact 已声明事实的接收者

    生产接收者是{"type":"wallet","id":"<wallet-id>"}。钱包适配器 将这些解析为真实的电子钱包帐户。

    { "resolver": "literal", "type": "wallet", "id": "platform-wallet-id" }

    { "resolver": "context_candidate", "key": "store.owner" }

    { "resolver": "fact_reference", "typeFact": "order.agentRecipientType", "idFact": "order.agentRecipientId" }

    5. 资格原语¶

    原始 示例
    factEquals ["order.status", "paid"]
    factIn ["order.storeType", ["direct", "franchise"]]
    intAtLeast / intAtMost ["order.itemCount", 3]
    amountAtLeast / amountAtMost ["order.total", "100.00"]
    occurredBefore / occurredAfter ["order.paidAt", "2026-12-31T23:59:59+00:00"]
    all / any / not 复合谓词

    所有事实都必须由源适配器投射到冻结资金快照中。 未知的事实在计划创建时被拒绝。

    6. 公式原语¶

    原始 结果
    fundingAmount 该计划的可分配资金金额
    fixedAmount 字面精确小数
    factAmount 申报金额事实
    rateOf 以基点为单位的儿童配方分数
    multiplyByQuantity 公式×整数数量
    add / subtract 精确算术
    minOf / maxOf 精确的最小值/最大值

    bps 必须在 0..10000 范围内 (8000 = 80%)。金额永远不会是负数；负数 结果拒绝计划创建。

    7. 逐步：订单级别百分比拆分¶

    目标：给店主每笔付款订单的 80%。

    7.1 创建规则草案¶

    POST /api/v1/manage/settlement-rules

    { "code": "store-revenue", "name": "Store revenue 80%" }

    7.2 创建草稿版本¶

    POST /api/v1/manage/settlement-rule-versions

    {
  "ruleUuid": "<rule-uuid>",
  "definition": {
    "appliesTo": ["trade.order.v1"],
    "scope": "order",
    "conflictMode": "stack",
    "eligibility": { "all": [ { "factEquals": ["order.status", "paid"] } ] },
    "recipient": { "resolver": "context_candidate", "key": "store.owner" },
    "formula": { "rateOf": { "basis": "funding.distributable", "bps": 8000 } },
    "reasonCode": "store_revenue"
  },
  "priority": 100,
  "effectiveFrom": "2026-08-19T00:00:00+00:00",
  "effectiveTo": null
}

    7.3 发布¶

    POST /api/v1/manage/settlement-rule-versions/{versionUuid}/publish

    该版本现在是不可变的并且从 effectiveFrom 开始处于活动状态。

    8. 一步一步：每件特工奖励¶

    目标：对于每一个规格为32且单价高于3.00的订单行， 支付订单代理3.00 × quantity。

    8.1 创建规则草案¶

    POST /api/v1/manage/settlement-rules

    { "code": "agent-spec-32", "name": "Agent reward spec 32" }

    8.2 创建草稿版本¶

    POST /api/v1/manage/settlement-rule-versions

    {
  "ruleUuid": "<rule-uuid>",
  "definition": {
    "appliesTo": ["trade.order.v1"],
    "scope": "order_item",
    "eligibility": {
      "all": {
        "children": [
          { "factEquals": ["item.specificationId", 32] },
          { "amountAtLeast": ["item.unitPrice", "3.01"] }
        ]
      }
    },
    "recipient": {
      "resolver": "fact_reference",
      "typeFact": "order.agentRecipientType",
      "idFact": "order.agentRecipientId"
    },
    "formula": {
      "multiplyByQuantity": {
        "value": { "fixedAmount": { "amount": "3.00" } },
        "quantity": "item.quantity"
      }
    },
    "reasonCode": "agent_specification_reward"
  },
  "priority": 100,
  "effectiveFrom": "2026-08-19T00:00:00+00:00",
  "effectiveTo": null
}

    8.3 注释¶

    • item.unitPrice是十进制快照金额； 3.01 表示严格大于 3.00 因为语法提供了包容性比较。
    • 每个合格行都会使用源项目 ID 和快照生成自己的分配 坚持审核。
    • 源适配器必须项目 item.specificationId、item.unitPrice、 item.quantity，以及订单级代理接收者事实。

    9. 冲突模式¶

    模式 意义
    stack 规则将分配与其他匹配规则一起添加（默认）
    exclusive_group 命名 group 中第一个匹配的规则获胜；该组中的后续规则将被跳过
    stop 匹配的规则在其建议被接受后结束进一步的规则选择

    10. 发布和操作¶

    分配通过结算发件箱异步发布到电子钱包。

    命令 目的
    app:settlement:outbox:publish 将发布命令中继到钱包
    app:settlement:allocations:requeue-due 重新排队可重试的发帖失败

    这些都安排在compose.yaml中。要手动过帐单个分配：

    POST /api/v1/manage/settlement-plans/{planUuid}/allocations/{allocationUuid}/post

    要撤消已发布的分配：

    POST /api/v1/manage/settlement-plans/{planUuid}/allocations/{allocationUuid}/reverse

    11. 审计与对账¶

    端点 目的
    GET /api/v1/manage/settlement-plans 列出计划
    GET /api/v1/manage/settlement-plans/{id} 计划细节与分配
    GET /api/v1/manage/settlement-allocations 分配清单
    GET /api/v1/manage/settlement-rules 列表规则
    GET /api/v1/manage/settlement-rule-versions 列出规则版本
    GET /api/v1/manage/settlement-outbox-messages 列出发件箱消息
    GET /api/v1/manage/settlement-consumed-events 列出消耗的资金事件

    守恒不变量（必须在计划为 posted 之前保持）：

    fundingAmount = allocationAmountTotal + unallocatedAmount
fundingPostingAmount = sum(allocation.postingAmount) + unallocatedPostingAmount
unallocatedAmount = 0
unallocatedPostingAmount = 0

    12. 故障排除¶

    症状 可能的原因 修复
    计划创建被拒绝 未知事实、负金额或分配总额超过资金 查看资格/公式和快照事实
    规则不适用 appliesTo 不匹配、尚未生效或未发布 检查源类型、effectiveFrom、发布状态
    分配卡在 posting_requested 发件箱继电器未运行 运行 app:settlement:outbox:publish
    retryable_failure 中的分配暂时性钱包错误 运行 app:settlement:allocations:requeue-due
    收件人被拒绝 不是 wallet 类型/id 配置 {"type":"wallet","id":"<wallet-id>"}
    保护失败 四舍五入或规则余数未吸收 确保存在后备收件人（默认平台）

    13. 上线前的检查清单¶

    • [ ] 规则版本通过配置模式进行解析和验证。
    • [ ] appliesTo 匹配资金来源类型。
    • [ ] effectiveFrom已设置，并且effectiveTo不与已发布的版本重叠。
    • [ ] 收件人解析为真实的钱包 ID。
    • [ ] 资格和公式引用的每个 config/fact 均由源适配器预测。
    • [ ] 已安排发件箱中继和重新排队命令。
    • [ ] 存在后备接收者，因此保留舍入余数。
    • [ ] 审核端点返回预期的计划、分配和跟踪。
